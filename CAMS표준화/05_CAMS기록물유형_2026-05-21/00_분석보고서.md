# CAMS 기록물 유형 분석 보고서 (2026-05-21)

> 배경: 재선이사님 코멘트(2026-05-21) — "CAMS 기록물 유형 약 15종, 정확히 몇 종이고 각 유형별 메타데이터·구조 파악 필요. 기본구조 하나 vs N개 결정 후에야 RAMP 매핑·통합 가능."
> 입력: `01_원본자료/CAMS_SCHEMA_원본.xlsx` (773 테이블, 12,818 컬럼) + `CAMS_RAMP_통합/ramp기관스키마정보.xlsx` (365 테이블, 5,740 컬럼)
> 데이터 접근 불가 → 스키마 구조 + 코멘트 기반 분석. 코드값은 RG_DOCUMENT.ARCAVETYPE / DOCTYPE 컬럼 코멘트에서 추출.

---

## 1. 핵심 결론

### 1-1. CAMS 기록물 유형 = 7~8 종 (ARCAVETYPE 기준)

`RG_DOCUMENT.ARCAVETYPE` (VARCHAR2(2)) 컬럼이 진짜 유형 분기 코드:

| 코드 | 유형 |
|---|---|
| 01 | 일반문서 |
| 02 | 시청각 |
| 03 | (미사용) |
| 04 | 총독부 |
| 05 | 정부간행물 |
| 06 | 해외기록물 |
| 07 | 역사기록물 |
| 08 | 행정박물 |

추가 분기: `DOCTYPE` (RG001, 6종 — 형태) + `ORGTYPE` (RG008) + `DUTY_BASIS_TYPE` (건상세유형)

→ ARCAVETYPE 7종 × DOCTYPE 6종 의 **조합으로 "약 15종"** 이라고 사용자가 인지하는 것으로 추정. 실제 등록 유형 마스터는 **8종 (07 포함)** 또는 7종.

### 1-2. CAMS 구조 = 1상속 패턴

**확정**: RG_DOCUMENT/RG_DETAIL 이 모든 기록물의 마스터. 유형별 추가 메타는 **BSID/DSID를 키로 공유하는 부속 테이블**.

| 유형 | 부속 테이블 | 키 공유 | 특화 메타 컬럼 수 |
|---|---|---|---|
| 일반문서 (메인) | RG_DOCUMENT + RG_DETAIL | (마스터) | 251 |
| 정부간행물 | RG_GOVTINFO (+ _CR 목차) | ✅ BSID PK | 46 |
| 총독부 | RG_OLD_GOVTINFO (+ _CR) | ✅ BSID PK | 1 (목차만) |
| 행정박물 | RG_ADMIN_ADDINFO | ✅ BSID PK | 14 |
| 시청각 | SV_ARCHIVE_ADDITION_ITEM + SV_ADDITION_LANGUAGE | ✅ BSID 또는 BSID+DSID | 15 |
| 해외기록물 | RG_POSS_MEDIAINFO | ❌ MEDIA_SEQ_NO 자체키 | 9 |
| **구술기록** | RG_ORAL_* (5개) | ❌ REG_SEQ_NO 자체키 | 26 |

**핵심 발견**:
- **공통 컬럼은 RG_DOCUMENT/RG_DETAIL 의 251개에 거의 다 들어있음** — 유형별 부속은 진짜 "추가" 메타만 보유
- **총독부는 RG_DOCUMENT 거의 그대로 사용** (특화 1개) — 분류체계만 별도(CM_OLDGOV_*)
- **구술기록·해외기록만 진짜 별도 시스템** (BSID 안 거침)

→ **사용자 가설("RG_DOCUMENT/DETAIL = 모든 기록물 마스터, 유형별 메타는 BSID 공유 부속") 데이터로 입증**. 단 구술·해외 예외.

### 1-3. RAMP 구조 = 코드 분기 (단일 테이블)

**RAMP는 CAMS와 다른 철학**:
- `tb_rdfolder`/`tb_rdrecord` 의 **단일 마스터 + 풍부한 유형 코드 컬럼**
  - tb_rdfolder: `fls_type_se_cd`, `fls_dtl_type_cd`, `new_pbrc_se_cd` 등 22개 분기 컬럼
  - tb_rdrecord: `pbrc_dtl_type_cd`, `adr_type`(시청각), `spcl_pbrc_type`(특수), `cpyr_type`(저작권) 등 19개
- 유형별 별도 메타 테이블은 **일부만** 존재:
  - 정부간행물 = `tb_gvrnprdl` (★ rctr_id+pblc_id 자체키 — fls_id와 별도 관계)
  - 행정박물 = `tb_adarchivalobj` (★ rctr_id+adaf_id 자체키) + 부속 6개
- 총독부·구술·해외기록 = **대응 없음** (tb_rdrecord 코드 분기로만)

→ **CAMS 1상속 vs RAMP 코드 분기** — 통합 DB 채택 구조 결정 필요

## 2. 통합 DB 설계 결정사항

### 2-1. "기본구조 하나 vs N개" — 결정 필요

| 옵션 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **A. CAMS 방식 채택** (1상속) | 마스터 1개 + 유형별 부속 N개 | 메타 보존 충실, 정규화 | 조회 시 JOIN 많음, 관리 테이블 수↑ |
| **B. RAMP 방식 채택** (코드 분기) | 마스터에 NULL 가능 컬럼 다수 | 단일 테이블, 단순 | NULL 컬럼 많음, 유형별 강제 제약 어려움 |
| **C. 하이브리드** | 공통 메타 = 마스터 / 큰 차이 유형(정부간행물·구술 등) = 부속 | 균형 | 결정 기준 복잡 |

→ **추천: C 하이브리드** — 구술·해외 같은 별도 시스템은 부속 유지, 그 외는 코드 분기

### 2-2. 키 통합 방향

| CAMS 키 | RAMP 키 | 매핑 |
|---|---|---|
| BSID | fls_id | ✅ 사용자 확정 (1:1) |
| DSID | ritm_id | ✅ 사용자 확정 (1:1) |
| RG_ORAL_*.REG_SEQ_NO | (없음) | **신규 부여 — 통합 시 fls_id 발급** |
| RG_POSS_MEDIAINFO.MEDIA_SEQ_NO | (없음) | **별도 매체 영역으로** |
| RG_GOVTINFO.BSID | tb_gvrnprdl.pblc_id | ⚠ **이중 키 — 통합 시 BSID 표준화** |
| RG_ADMIN_ADDINFO.BSID | tb_adarchivalobj.adaf_id | ⚠ 동일 |

### 2-3. 마이그레이션 영향

- **구술·해외기록** = CAMS에서 BSID 없는 별도 시스템 → 통합 시 BSID 신규 발급 필요
- **정부간행물·행정박물** = CAMS BSID 와 RAMP 자체키(pblc_id, adaf_id) 이중 운영 중. 통합 시 BSID 표준으로 일원화
