# 68. 데이터 품질 진단 — 운영 DB 부하 대응 방안 (초안)

작성일: 2026-04-28
상태: **초안 — 사용자 검토 대기**
관련 문서: 67 (데이터 품질 진단 설계)

---

## 0. 배경 / 문제 정의

67번 설계의 **업무 규칙 진단(RULE)** 과 **값 프로파일링(VALUE)** 은 운영 DB 에 SELECT 를 날려 검증하는 구조다. 다음 케이스에서 **운영 DB 부하**가 우려된다:

- 정규식(REGEX) / EXPRESSION 룰 — 인덱스 없이 풀스캔
- REFERENCE 룰의 NOT IN — 카디널리티 큰 참조 테이블에서 느림
- 컬럼 50개 × 룰 100개 = 진단 1회당 100~500 SQL
- 운영 시간대 즉시 실행 시 OLTP 트랜잭션과 경합

본 문서는 위 부하를 통제하기 위한 **5가지 카테고리 × N개 기법** 을 정리하고 1차 출시 권장 조합을 제시한다.

---

## 1. 부하의 위치 자체를 바꾸기 — **솔루션 범위 밖 (참고용)**

> dataQ 는 **여러 환경에 배포되는 범용 솔루션**이다. 다음 세 가지는 환경 측의 인프라 자산이지 솔루션이 강제·구축할 수 없다. 환경에서 이미 제공하는 경우에 한해 **옵션 형태로 활용**할 수 있도록 연결 포인트만 남긴다.

| 방향 | 솔루션의 책임 | 환경에서 제공 시 활용 방법 |
|---|---|---|
| **운영 DB 의 Read Replica** | dataQ 가 replica 를 만들지 않음 | 환경에 있으면 데이터소스 등록 시 **RO_DSN** 컬럼에 별도 접속정보 입력 → 진단 SQL 만 RO 로 라우팅 (Phase 2 옵션) |
| **자체 PostgreSQL 추출 후 검증** | 솔루션이 ETL 책임지지 않음 | 환경에서 별도 ETL 로 추출본 적재 시 그 DB 를 일반 데이터소스로 등록하면 그만 — 별도 처리 없음 |
| **Spark / Trino / Snowflake 등 분석 인프라** | 솔루션 감당 불가 | 환경 정책상 검증을 별도 엔진에서 돌리는 거면 dataQ 는 룰 정의/결과 import 만 받는 형태로 후순위 검토 |

→ **핵심**: 본 문서의 1차 출시 권장 조합은 위 세 가지 **없이도 동작하는 가드** 만 사용한다. §2~§5 가 실제 적용 범위.

## 2. 부하의 양 줄이기 (1차 출시 적용)

| 기법                                                                | 효과                                    | 적용 범위 / 주의                                                                                                              |
| ----------------------------------------------------------------- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **샘플링 — 사용자 선택 옵션** (1만건 / 1% / 10% / 100%)                       | 부하 1/100 ~ 1/10                       | UI 에서 진단 실행 시 사용자가 직접 선택. 기본값은 보수적(1만건)으로, 풀스캔은 명시적 동의. 희소한 위반(예: 0.01%)은 샘플링으로 미검출될 수 있음을 사용자에게 안내                     |
| **증분 검증 — 사용자 선택 옵션** (UPDT_DT 이후 행만)                             | 최초 1회 후 부하↓, 정기 야간 진단의 누적 비용 대폭 감소    | 룰 정의 시 INCREMENTAL_COL 등록 = "증분 가능 여부" 만 명시. 진단 **실행 시점에 사용자가 [증분] / [풀스캔] 토글로 선택**. INCREMENTAL_COL 미정의 룰은 [증분] 옵션 비활성 |
| **도메인 그룹 단위 묶음 검증** (NEW)                                         | 같은 도메인의 N개 컬럼을 1 SQL 의 OR/UNION 으로 합산 | 표준사전의 도메인이 정의된 컬럼만 적용. 예: "이메일" 도메인을 갖는 컬럼 12개에 동일 정규식 룰 → 12 SQL 이 아니라 1~3 SQL. 비즈니스 룰(특정 컬럼 1건의 조건)에는 부적용             |
| **REFERENCE 룰 SQL 최적화** (NOT IN → NOT EXISTS / LEFT JOIN IS NULL) | 큰 ref 테이블에서 5~10×                     | SQL 빌더 복잡도↑                                                                                                             |
| **컬럼 단위 통합 SQL — 값 프로파일링 한정**                                     | 한 테이블 N 컬럼을 1 SELECT 의 다중 집계로 합산      | **VALUE 진단에만 적용**. RULE 진단(특히 비즈니스 룰)은 룰별 SQL 분리가 정설 (조건이 컬럼/룰마다 달라 통합 불가)                                              |

> ❌ **제외 — 저비용 룰 우선 실행**: 어차피 고비용 룰(REGEX/EXPRESSION)을 결국 처리해야 하므로 진단 전체 시간 단축 효과가 미미. 진행률 UX 측면에서는 의미 있지만 부하 감소 기법으로는 부적합 → 본 문서 범위에서 제외.

### 2.1 증분 검증 운영 정책 (보강)

- **사용자 옵션**: 진단 실행 모달의 [검증 범위] 라디오
  - ⦿ 증분 (직전 검증 이후 변경된 행만) — INCREMENTAL_COL 정의된 룰에 한해 선택 가능
  - ○ 풀스캔 — 모든 룰 적용. 운영 부하 동의 체크 필요
- **트리거 컬럼**: TB_QUAL_RULE 에 `INCREMENTAL_COL` 컬럼 (예: UPDT_DT, REG_DT). NULL 이면 [증분] 옵션 비활성
- **마지막 검증 시점**: TB_QUAL_DIAG_HISTORY 의 직전 DONE 의 END_DT 를 기준점으로 사용
- **WHERE 절**: 증분 선택 시 룰 SQL 에 `AND <INCREMENTAL_COL> > :lastDiagDt` 자동 부착
- **기준점 보정**: 시계 차이 대비 5분 lookback 추가 (`> :lastDiagDt - INTERVAL '5 min'`)
- **첫 실행 분기**: 직전 DONE 이력이 없으면 증분 선택했어도 강제 풀스캔 (사용자에게 안내 메시지)
- **룰 변경 후 첫 실행**: 룰 SQL 변경 후 첫 실행 시 사용자에게 "다음 1회는 풀스캔 권장" 경고 노출 (자동 강제는 안 함, 사용자 선택 존중)
- **혼합 실행**: 진단 1회에 증분 가능 룰 + 불가능 룰이 섞여있으면, 사용자가 [증분] 선택 시 가능 룰만 증분, 불가능 룰은 풀스캔 자동 적용 (또는 스킵 — 사용자가 모달에서 선택)
- **신뢰도 표기**: 결과 화면에 "증분 검증 (UPDT_DT > 2026-04-27 22:00 기준 12,453 행 검증)" 명시

### 2.2 도메인 그룹 묶음 — 적용 가능 범위

| 적용 가능                                       | 적용 불가                 |
| ------------------------------------------- | --------------------- |
| 같은 도메인 N개 컬럼 + 같은 룰 (REGEX/RANGE/LENGTH 등)  | 컬럼별로 룰 파라미터가 다른 경우    |
| 도메인 표준에 정의된 정규식 룰 (예: "이메일", "전화번호")        | 비즈니스 룰 (특정 컬럼의 특정 조건) |
| 통계적 검증 (NULL률, 길이 분포) — VALUE 진단에서 자연스럽게 합산 | 다중 컬럼 비교 룰 (COMPARE)  |

> 묶음 검증은 **룰 등록 UX** 차원에서 우선 의미 — 도메인 1번 골라 룰 1개 등록 → 해당 도메인 모든 컬럼에 자동 적용. 실행 시 SQL 합병은 후속 최적화.

### 2.3 샘플링 SQL 예시 (DBMS 별)

| DBMS | 1% 샘플 | N건 샘플 |
|---|---|---|
| PostgreSQL | `TABLESAMPLE BERNOULLI(1)` | `ORDER BY random() LIMIT 10000` (느림) 또는 `TABLESAMPLE SYSTEM(0.1)` |
| Oracle | `SAMPLE(1)` 절 | `WHERE ROWNUM <= 10000` (랜덤성↓) |
| MariaDB/MySQL | 미지원 → `WHERE RAND() < 0.01` (풀스캔, 효과↓) | `ORDER BY RAND() LIMIT 10000` |
| MSSQL | `TABLESAMPLE (1 PERCENT)` | `TABLESAMPLE (10000 ROWS)` |

→ **권고**: PostgreSQL/Oracle/MSSQL 은 샘플링 권장, MariaDB 는 샘플링이 사실상 풀스캔이므로 차라리 풀스캔 + 야간 강제.

## 3. 시간 / 동시성 분산 (1차 출시 적용)

| 가드 | 메커니즘 | 65번 스케줄러 연계 |
|---|---|---|
| **저부하 시간대 강제** | 룰 진단의 즉시실행은 샘플링만 허용. 풀스캔은 야간(22~06시) 스케줄 등록 강제 | DSScheduleManage 에서 시간대 검증 |
| **동시 실행 1개** | DM_ID + DIAG_TYPE='RULE' 하나만 RUNNING (65번 SKIP 정책 재사용) | countRunningByModelAndType 그대로 |
| **룰 단위 SQL 직렬화** | 룰 100개라도 1개씩 순차, DB 동시 connection 1개 | BusinessRuleService 내부 for-loop |
| **SQL 타임아웃** | 룰 1건당 30초, 전체 30분, 초과시 ERROR 마감 | `setQueryTimeout()` + Future cancel |
| **운영 DB 별 동시 진단 1개** | 한 데이터소스에 STANDARD/STRUCT/RULE/VALUE 합쳐서 1건만 | 전역 SKIP 정책 (확장) |

> 마지막 항목은 65번의 현재 SKIP 정책(`DM_ID + DIAG_TYPE`)을 `DS_ID` 기준으로 확장. 동일 DB 를 여러 모델이 공유하는 경우 모델 단위 SKIP 만으로는 부하 가드 부족.

## 7. 의사결정 항목 (사용자 검토)

> §1 의 인프라 항목(Replica/추출/Spark)은 솔루션 범위 밖이라 의사결정 안건에서 제외. 환경에서 제공받는 케이스는 RO_DSN 컬럼만 추가하는 후속 옵션으로 충분.

| # | 안건 | 추천 | 결정 |
|---|---|---|---|
| 1 | **풀스캔 즉시실행 허용 여부** — 동의 체크 + 부하경고 후 허용 vs 스케줄로만 강제 | 동의 체크 후 허용 | |
| 2 | **샘플링 기본값** — 1만건 vs 1% vs 10% | 1만건 (테이블 크기 무관 일관) | |
| 3 | **증분 검증 1차 도입 여부** — Phase 1 부터 vs Phase 2 | Phase 1 (룰 SQL 빌더에 WHERE 1줄만 추가) | |
| 4 | **증분 검증 트리거 컬럼 등록 방식** — 룰 등록 시 사용자 직접 입력 vs 모델 메타에서 자동 추정 | 사용자 입력 + (가능하면) 자동 후보 제시 | |

## 8. 미정 / 리스크

- **EXPLAIN PLAN 자체 부하** — Oracle 의 `EXPLAIN PLAN FOR` 는 SELECT 자체를 안 돌리지만, PostgreSQL 의 `EXPLAIN ANALYZE` 는 실제 실행. dry-run 시 `EXPLAIN` (ANALYZE 없이) 만 사용
- **샘플링과 위반률 통계 신뢰도** — 1만건 샘플로 위반률 0.5% 검출 시 신뢰구간 ±0.14% (95% conf). UI 에 "표본 N=10000, ±0.14% 오차" 표시 검토
- **Read Replica 의 lag** — 검증 시점 데이터가 운영보다 N분 늦을 수 있음. 사용자에게 "검증시각 ≠ 운영현재" 명시
- **DBMS 별 함수 차이** — REGEX 함수 (REGEXP_LIKE / REGEXP / `~`) , 샘플링 절, EXPLAIN 출력 형식 모두 다름. SqlDialect 패턴 (DDL Generator) 확장
- **사용자 룰 오류로 인한 운영 부하 책임** — "동의 체크" 가 법적 책임 분배에 충분한가는 검토 필요
