# 97. 결함 조치 기록 · 패턴 카탈로그

**용도 2가지**
1. **조치 기록** — 발견한 결함의 증상·원인·조치·검증을 남긴다
2. **패턴 카탈로그** — 같은 유형을 **다시 찾을 수 있게** 탐색 명령과 예방책을 남긴다

> 새 결함을 만나면 먼저 §2 패턴 목록에서 유사 패턴을 찾아라. 대부분 이미 겪은 유형이다.
> 새 유형이면 §2 에 패턴을 추가하고 **탐색 명령을 반드시 같이 적어라.** 그게 이 문서의 값이다.

**갱신 규칙**: 결함 1건 = §3 에 1행 + 상세 1절. 새 패턴이면 §2 에도 1절.

## 2. 패턴 카탈로그

### P1. 스키마·계약 변경 잔재 — 사라진 대상을 계속 참조

**정의**: 컬럼·테이블·statement 가 제거·개명됐는데 참조하는 쪽이 안 따라간 경우. 런타임에만 터진다.

**사례**
- 결함① — `terms.selectTermsInfo` 호출, 실제 정의는 `selectTermsInfoByNm` 뿐
- 결함④ — `impact.xml` 이 `a.DM_CLCT_ID` 참조, CLCT 폐기 때 컬럼 제거됨

**왜 안 잡혔나**: 컴파일이 안 잡는다(MyBatis 는 문자열). 화면이 그 버튼을 안 누르면 UI 테스트도 안 잡는다.

**탐색 명령**
```bash
# (1) Java 가 부르는 statement ↔ XML 정의 대조
grep -ohE '<(select|insert|update|delete)[ \t][^>]*id="[^"]+"' q-common/src/main/resources/mapper/stnd/*.xml \
  | grep -oE 'id="[^"]+"' | sed 's/id="//;s/"//' | sort -u > /tmp/defined.txt
NS=$(grep -m1 -ohE 'namespace="[^"]+"' q-common/src/main/resources/mapper/stnd/*.xml | sed 's/namespace="//;s/"//' | paste -sd'|')
grep -rhoE "\"($NS)\.[a-zA-Z0-9_]+\"" --include="*.java" q-center/src q-executor/src | tr -d '"' | sed 's/.*\.//' | sort -u > /tmp/called.txt
comm -23 /tmp/called.txt /tmp/defined.txt   # 호출하는데 정의 없음

# (2) 매퍼가 참조하는 컬럼 ↔ 실제 스키마 대조 (INSERT 절 기준이 가장 정확)
#     94번 §3-4 의 방식. UPDATE SET 파싱은 #{x,jdbcType=} 오인으로 신뢰 불가

# (3) 매퍼 참조 테이블 ↔ DDL  (대소문자 무시 필수)
grep -ohiE '\btb_[a-z0-9_]+' q-common/src/main/resources/mapper/stnd/*.xml | tr 'A-Z' 'a-z' | sort -u
```

**예방**: 컬럼·테이블 제거 시 `grep -ri '<제거대상>' q-common/src/main/resources/mapper/` 를 **반드시** 돌린다. CLAUDE.md 의 DDL self-check 절차가 이걸 위한 것.

### P2. 영향 행 수 미검사 — 0건 처리인데 성공 응답

**정의**: `UPDATE`/`DELETE` 가 0행을 처리해도 반환값을 안 보고 200 을 돌려주는 경우. **조용히 실패**한다.

**사례**
- 결함② — `updateAttr`/`updateObj`/`deleteAttr`. PK 에 `OBJ_OWNER` 가 들어가는데 클라이언트가 안 보내면 0건인데 200

**왜 위험한가**: 사용자는 저장됐다고 믿는다. 다음 조회에서 옛 값이 보여도 캐시 문제로 오해한다.

**탐색 명령**
```bash
# 반환값을 버리는 update/delete 호출
grep -rnE '^\s*(sqlSessionTemplate|session)\.(update|delete)\(' --include="*.java" q-center/src q-executor/src \
  | grep -vE '^\S+:[0-9]+:\s*(int|long|Integer)\s' 
```

**판정**: 반환값을 안 받는 게 전부 결함은 아니다. **키가 복합 PK 이고 클라이언트 입력에 의존**하면 결함이다.

**대조 사례 (올바른 구현)**: `DiagTargetController` 는 `int cnt = ...update(...)` 후 `res.put("success", cnt > 0)` 로 정직하게 돌려준다. 같은 프로젝트 안에 좋은 예가 있으니 그 패턴을 따를 것.

**예방**: 복합 PK 대상 UPDATE/DELETE 는 **영향 행 수 검사 + 대상 식별자를 담은 메시지** 를 기본으로 한다.

### P3. 다중 완료 경로 중 일부만 후속 처리

**정의**: 같은 작업을 끝내는 경로가 여러 개인데, 후속 상태 갱신은 일부 경로에만 있는 경우.

**사례**
- 결함③ — 스케줄 로그를 마감하는 경로가 3곳. `markFinish` 만 `LAST_EXEC_*` 를 갱신하고 ERROR 마감 2곳은 안 함 → 실패한 스케줄은 "마지막 실행" 이 영원히 빈칸

**탐색 명령**
```bash
# 같은 매퍼를 부르는 지점이 여러 개인지 → 각 지점의 후속 처리가 같은지 비교
grep -rn '"diagSchedule.updateLogFinish"' --include="*.java" q-center/src q-executor/src
grep -rn '"diagSchedule.updateScheduleLastExec"' --include="*.java" q-center/src q-executor/src
# 호출 지점 수가 다르면 의심
```

일반화:
```bash
# 매퍼 statement 별 Java 호출 지점 수 — 1보다 크면 경로 분기 존재
grep -rhoE '"[a-zA-Z]+\.[a-zA-Z0-9_]+"' --include="*.java" q-center/src q-executor/src \
  | sort | uniq -c | sort -rn | awk '$1>1'
```

**예방**: 종료 처리는 **한 메서드로 모은다**. 분기별로 복사하지 않는다.

### P4. DB 제약과 애플리케이션 의도 불일치

**정의**: 코드는 "일부만 지우고 나머지는 남긴다" 를 의도하는데, FK 제약이 그걸 허용하지 않아 **트랜잭션 전체가 실패**하는 경우.

**사례**
- 결함⑤ (DEF-01) — `approve.xml:251` 이 `APRV_YN='N'` 으로 "미승인 용어만 삭제, 승인 용어는 보존" 을 의도. 그러나 `tb_terms_words_fk_2` 에 `ON DELETE` 절이 없어(NO ACTION), 승인 용어가 참조 중이면 단어 삭제가 FK 위반 → **롤백**. 의도가 성립하지 않을 뿐 아니라 raw `PSQLException` 이 사용자에게 노출됨

**탐색 명령**
```bash
# ON DELETE 절이 없는 FK 목록 (NO ACTION = 참조 있으면 삭제 차단)
docker exec -i dataq-db psql -U admin -d postgres -c "\pset pager off" -c \
"SELECT conrelid::regclass AS child, conname, pg_get_constraintdef(oid) AS def
   FROM pg_constraint WHERE contype='f' AND connamespace='quality'::regnamespace
    AND pg_get_constraintdef(oid) NOT LIKE '%ON DELETE%' ORDER BY 1;"

# 그 다음: 그 부모 테이블을 DELETE 하는 매퍼를 찾아 가드 유무 확인
grep -rn "DELETE FROM TB_WORD\|DELETE FROM TB_TERMS\|DELETE FROM TB_DOMAIN" q-common/src/main/resources/mapper/
```

**예방**: 부모 행을 지우는 코드는 **FK 정의를 먼저 확인**하고, 차단되는 조건이면 **친화 메시지로 선제 차단**한다. `deleteWords` 의 참조 가드가 이 프로젝트의 표준 패턴.

### P5. 복합 키 일부 누락 — cascade/동기화가 엉뚱한 행까지 건드림

**정의**: PK 가 `(A, B, C)` 인데 WHERE 에 `(A, C)` 만 써서, 다른 `B` 값의 행까지 영향받는 경우.

**사례 (전부 `OBJ_OWNER` 누락)**
- `cascadeRejectAttrsInObj` — `DM_ID + OBJ_NM` 만 → 동명이 테이블이 다른 스키마에 있으면 그쪽 컬럼까지 반려
- `clearFkParentRefByAttr` — 동일
- `syncDataModelObjAttrCnt` — 동일 → 컬럼 수가 엉뚱하게 계산됨

**탐색 명령**
```bash
# OBJ_NM 을 쓰면서 OBJ_OWNER 를 안 쓰는 매퍼 구문 (데이터모델 영역 복합 PK)
grep -n "OBJ_NM" q-common/src/main/resources/mapper/stnd/*.xml \
  | grep -v "OBJ_OWNER" | grep -iE "where|and"
```

**판정 기준**: `TB_DATA_MODEL_OBJ` / `TB_DATA_MODEL_ATTR` 의 PK 는 `OBJ_OWNER` 를 포함한다. 조회/갱신 WHERE 에 없으면 의심.

**예방**: 복합 PK 테이블은 **PK 전체를 WHERE 에 쓴다**. `COALESCE(OBJ_OWNER,'')` 형태로 NULL 처리까지 통일.

### P6. 상태 전이 가드 부재 — 임의 상태로 점프 가능

**정의**: 상태 머신인데 UPDATE WHERE 에 **현재 상태 조건이 없어서** 어떤 상태에서든 어떤 상태로든 갈 수 있는 경우.

**사례**
- DEF-09 — `dmChangeHistory.xml` 의 `updateAprvStatus` WHERE 가 `CHANGE_SEQ` 뿐 → `APPROVED` → `REJECTED`, `REJECTED` → `APPROVED` 임의 전이 가능
- DEF-14 (관찰) — `approve.xml:236` 의 `DELETE FROM TB_WORD` 에 `APRV_YN` 조건 없음 → 승인된 항목도 반려 API 로 삭제 가능

**탐색 명령**
```bash
# 상태 컬럼을 SET 하는데 WHERE 에 그 컬럼이 없는 UPDATE
grep -n -A8 "SET.*APRV_STATUS\|SET.*APRV_YN\|SET.*STATUS" q-common/src/main/resources/mapper/stnd/*.xml \
  | grep -B6 "WHERE" | grep -L "APRV_STATUS =\|APRV_YN ="
```

**예방**: 상태 전이 UPDATE 는 `WHERE ... AND 현재상태 IN (허용집합)` 을 넣고, **영향 행 수 0 이면 거부**한다 (P2 와 결합).

### P7. 선언과 구현 불일치 — 주석·문서가 하겠다는 걸 코드가 안 함

**정의**: javadoc·설계서·컬럼 코멘트가 기술한 동작이 실제로는 없는 경우. 읽는 사람이 있다고 믿는다.

**사례**
- DEF-02 — `deleteObjs` javadoc "하위 컬럼·인덱스·제약조건 cascade 삭제" 인데 코드는 컬럼만 지움
- `TB_CHANGE_HISTORY.CHANGE_SOURCE` 컬럼 코멘트는 `ADMIN_DIRECT/USER_REQUEST/…` 를 기대하나 세팅 코드 0건 → 항상 NULL
- `datamodel.xml` 의 `<sql id="visibilityFilter">` — 정의만 있고 `<include refid>` 0건
- 88번 설계서의 `RENAME_OBJ`·`ADD_INDEX`·`MODIFY_ATTR_META` CHANGE_TYPE — 코드에 없음

**탐색 명령**
```bash
# (1) 정의만 되고 include 안 되는 sql 조각
for id in $(grep -ohE '<sql id="[^"]+"' q-common/src/main/resources/mapper/stnd/*.xml | sed 's/<sql id="//;s/"//'); do
  n=$(grep -c "refid=\"$id\"" q-common/src/main/resources/mapper/stnd/*.xml | awk -F: '{s+=$2} END{print s}')
  [ "$n" = "0" ] && echo "UNUSED sql fragment: $id"
done

# (2) 항상 NULL 인 컬럼 (코멘트는 값을 기대하는데)
docker exec -i dataq-db psql -U admin -d postgres -t -A -c \
"SELECT 'change_source', count(*) FILTER (WHERE change_source IS NOT NULL), count(*) FROM quality.tb_change_history;"

# (3) 문서에만 있는 엔드포인트/타입 — 94번 §3-4 역방향 대조 방식
```

**예방**: 주석이 cascade 를 약속하면 **그 cascade 를 검증하는 케이스를 같이 만든다** (96번 DM-040~043).

**탐색 명령**

```bash
# 데이터모델 쪽
grep -c "COALESCE(APRV_STATUS" q-common/src/main/resources/mapper/stnd/datamodel.xml
```

### P9. 부분 적용 — 정책이 일부 경로에만 걸림

**정의**: 승인·이력 같은 횡단 정책이 API 마다 제각각 적용된 경우. 우회로가 생긴다.

**사례 (88번 거버넌스)**
- `saveAttrs` ADD 만 완전 적용. **UPDATE 는 이력만 DRAFT, 모델 row 는 즉시 반영** (DEF-04)
- `saveAttrs` DELETE 는 **물리 삭제 즉시** → 반려해도 복구 불가 (DEF-05)
- `addAttr`/`deleteAttr`/`createPk`/`deletePk`/`createFk`/`deleteFk` — 거버넌스·이력 **둘 다 없음**
- `uploadAttrs`/`uploadTables`/import 계열 — 없음
- 수집은 `APRV_STATUS` 를 `APPROVED` 로 덮어씀

**탐색 명령**
```bash
# 정책 적용 지점을 세고, 해당 도메인의 변경 API 총수와 비교
```

### P11. 트랜잭션 경계 부재 — 다건 변경이 부분 반영됨

**정의**: 논리적으로 하나인 작업을 여러 문장으로 나눠 실행하는데, **문장 단위 자동 커밋**이라 중간 실패 시 앞부분만 커밋되는 경우. 롤백이 없다.

**사례 (2026-08-23 확인)**
- `DataModelController.updateObj` — 테이블 rename cascade **5개**(`:1474-1478`)와 OWNER 변경 cascade **4개**(`:1488-1491`)가 전부 `sqlSessionTemplate`
  - 3번째에서 실패하면 1·2번은 커밋된 채로 남음
  - 결과: 컬럼은 새 이름, 인덱스는 옛 이름 → **영구 불일치**. 재실행해도 WHERE 가 옛 이름을 못 찾아 복구 불가

**분포**: `sqlSessionFactory.openSession()` 19곳 vs `sqlSessionTemplate.(update|insert|delete)` 121곳. 어디가 트랜잭션인지 전수 파악 안 됨.

**왜 통합테스트로 못 잡나**: 중간 실패를 인위적으로 만들어야 한다(제약 위반·연결 끊김). **정적 조사가 맞는 방법.**

**탐색 명령**
```bash
# 한 메서드 안에서 sqlSessionTemplate 변경 문장이 2회 이상 → 트랜잭션 후보
awk '/^\t(public|private|protected) /{m=$0; c=0}
     /sqlSessionTemplate\.(update|insert|delete)\(/{c++; if(c==2) print FILENAME": "NR": "m}' \
  q-center/src/main/java/qualitycenter/controller/*.java

# cascade/rename 계열이 트랜잭션 밖인지
grep -n 'sqlSessionTemplate.update("datamodel.\(cascade\|rename\)' \
  q-center/src/main/java/qualitycenter/controller/DataModelController.java
```

**판정 기준**: 한 요청에서 **2개 이상의 테이블을 바꾸는데** `openSession` 이 아니면 결함.

**예방**: 다건 변경은 `sqlSessionFactory.openSession()` + `commit()`/`rollback()`. `deleteObjs`(`:1583-1645`)가 이 프로젝트의 올바른 예 — 단일 세션, 1건 실패 시 전체 롤백.

2. 패턴이 있으면 **그 패턴의 탐색 명령을 돌려 같은 유형이 더 있는지 확인** (1건 고치고 끝내지 말 것)
3. 패턴이 없으면 §2 에 추가 — **탐색 명령을 반드시 같이 적는다**
4. §3 대장에 1행 추가
5. 수정했으면 §4 에 상세 + **교훈** 1줄
6. 96번에 회귀 케이스 추가 (`★` 표시)

### 발견 경로별 권장 순서

| 순서 | 방법 | 잡히는 유형 |
|---|---|---|
| 1 | 정적 대조 (호출↔정의, 컬럼↔스키마) | P1 |
| 2 | API 일괄 실호출 (읽기 전용) | P1, P8 |
| 3 | 소스 상태전이·cascade 추적 | P5, P6, P7, P9 |
| 4 | 통합 시나리오 실측 | P2, P3, P4 |
| 5 | UI 테스트 | 화면 회귀 |

**UI 테스트가 마지막인 이유**: 비용이 가장 크고 잡히는 범위가 가장 좁다. 46개 전건 통과 상태에서 결함 ④·⑤ 가 살아 있었다.
