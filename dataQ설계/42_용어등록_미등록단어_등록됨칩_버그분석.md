# 용어 등록 모달 - 미등록 단어가 "등록됨"으로 표시되는 버그 분석

**작성일:** 2026-04-19
**대상:** 데이터 표준 사전 > 용어 > 등록 모달 (용어 수정 모달도 동일 증상)
**수정 여부:** 분석만, 코드 수정 X

---

## 1. 증상

용어 등록 모달의 **Step 2 "단어 목록 선택"** 단계에서,
입력한 용어명이 형태소 분석기로 쪼개져 각 형태소(토큰) 별로 표준사전의 단어 후보가 나열된다.

- **기대 동작**: 사전에 해당 형태소와 매칭되는 단어가 있으면 `등록됨` 칩(초록색) + 선택 가능한 단어 테이블 표시, 없으면 `미등록` 칩(빨강색) + 인라인 단어 등록 폼 표시.
- **실제 동작**: 사전에 존재하지 않는 형태소임에도 항상 `등록됨` 칩이 표시되고, 테이블에는 해당 형태소가 단어인 것처럼 하나의 행이 나타난다. 그 행을 체크하면 용어 구성 단어로 선택된다.

결과적으로 **사용자는 "사전에 등록된 단어만 조합한다"라는 UI의 약속을 위반한 채 용어를 생성하게 된다.**

---

## 2. 재현 시나리오

1. 데이터 표준 사전 > 용어 > **등록** 클릭
2. Step 1 용어명 입력: 표준사전에 절대 존재하지 않을 문자열 (예: `꺆쓘잇짢`)
3. **다음** → Step 2로 진입
4. 각 형태소마다 초록색 `등록됨` 칩이 붙음
5. 테이블에 해당 형태소가 `wordNm`만 채워진 행으로 하나씩 표시됨
6. 체크박스 선택 → Step 3로 진행 가능 → 용어 등록까지 진행됨

---

## 3. 원인 분석

### 3-1. 백엔드 — `getTermsTokenListByNm`가 미등록 토큰에도 가짜 단어 VO를 채워서 리턴

[q-center/src/main/java/qualitycenter/controller/DataStandardController.java:573-629](q-center/src/main/java/qualitycenter/controller/DataStandardController.java#L573-L629)

```java
// pos.equals("NN") 인 경우 (명사)
wordVoLst = sqlSessionTemplate.selectList("word.selectWordByNm", token);
if (wordVoLst.size() > 0) {
    // 사전에 있음 — 진짜 단어
    for (StdWordVo wordVo : wordVoLst) {
        wordVo.setPartOfSpeech("NN");
    }
} else {
    // 사전에 없음 — 그런데도 placeholder StdWordVo를 생성해서 리스트에 추가
    StdWordVo wordVo = new StdWordVo();
    wordVo.setWordNm(token);
    wordVo.setPartOfSpeech("NN");
    wordVoLst.add(wordVo);     // <-- 이 한 줄이 핵심 원인
}
```

명사가 아닌 경우(조사/어미 등)도 동일하게 가짜 VO를 생성해서 `wordLst`에 넣는다.

```java
} else { // 품사가 NN 이 아닌 경우
    StdWordVo wordVo = new StdWordVo();
    wordVo.setWordNm(token);
    wordVo.setPartOfSpeech(pos);
    wordVoLst.add(wordVo);
}
```

그리고 최종적으로 모두 `WordDataVo.wordLst`에 담아 리턴:

```java
WordDataVo wordData = new WordDataVo();
wordData.setWordNm(token);
for (StdWordVo wordVo : wordVoLst) {
    wordData.getWordLst().add(wordVo);
}
wordDatas.add(wordData);
```

**결과:** 어떤 토큰이든 `wordLst.length >= 1`이 보장된다. 미등록이라는 정보는 응답 페이로드에서 완전히 소실된다. 유일하게 남는 힌트는 "가짜 VO의 `id` 필드가 null"이라는 점뿐.

### 3-2. 프론트엔드 — `wordLst.length > 0`만 보고 "등록됨" 판정

[q-center/vue/front/src/components/DSTerm.vue:243-247](q-center/vue/front/src/components/DSTerm.vue#L243-L247)

```html
<v-row v-for="(item, index) in addTerm_wordListArr" :key="index">
  <h3>{{ item.wordNm }}
    <v-chip v-if="item.wordLst && item.wordLst.length > 0" color="green">등록됨</v-chip>
    <v-chip v-else color="red">미등록</v-chip>
  </h3>
```

Step 2 표시 분기 기준이 **`wordLst.length > 0`**뿐. 백엔드가 placeholder로 `length >= 1`을 보장하므로 `v-else` 분기(미등록/인라인 등록 폼)는 사실상 도달 불가능한 dead code가 된다.

[q-center/vue/front/src/components/DSTerm.vue:2164-2175](q-center/vue/front/src/components/DSTerm.vue#L2164-L2175)

```javascript
for (let i = 0; i < res.data.length; i++) {
  if (res.data[i].wordLst && res.data[i].wordLst.length > 0) {
    res.data[i].wordLst[0].index = i;
  } else {
    // 이 분기는 백엔드가 항상 length >= 1을 보장하므로 실행되지 않음
    res.data[i].wordLst = [];
    res.data[i].inlineWordNm = res.data[i].wordNm || '';
    res.data[i].inlineWordEngAbrvNm = '';
    res.data[i].inlineWordEngNm = '';
    res.data[i].inlineSaving = false;
  }
}
```

즉 프론트는 **"사전에 존재하는 단어냐"를 판단하는 로직이 완전히 구현되어 있다** — 단지 백엔드가 그 판단의 근거(빈 `wordLst`)를 제공하지 않을 뿐이다. 두 계층의 계약이 어긋나 있다.

### 3-3. 자료구조로 보는 대비

| 케이스 | 백엔드 응답 | 프론트 기대 | 프론트 실제 |
|---|---|---|---|
| 사전에 있는 단어 | `wordLst=[{id:'W001', wordNm:'개시', ...}]` | 등록됨 | 등록됨 ✅ |
| 사전에 없는 단어 (현재) | `wordLst=[{id:null, wordNm:'꺆쓘', pos:'NN'}]` | 미등록 | 등록됨 ❌ |
| 사전에 없는 단어 (정상이어야 할 모습) | `wordLst=[]` 또는 `wordLst=null` | 미등록 | 미등록 ✅ |

## 4. 파급 영향

### 4-1. DB 일관성 — `TB_TERMS_WORDS.WORD_ID` 가 null로 저장될 가능성

용어 등록 시 프론트는 선택된 단어로 payload를 만든다.

[q-center/vue/front/src/components/DSTerm.vue:1964-1979](q-center/vue/front/src/components/DSTerm.vue#L1964-L1979)

```javascript
createWordList.push({
  termsId: null,
  wordId: sortedArr[i].id,       // 가짜 VO는 id가 null
  wordNm: sortedArr[i].wordNm,
  wordEngAbrvNm: sortedArr[i].wordEngAbrvNm,  // 가짜는 undefined
  domainClsfNm: sortedArr[i].domainClsfNm,    // 가짜는 undefined
  wordOrd: i,
})
```

백엔드는 이 리스트를 그대로 `TB_TERMS_WORDS`에 INSERT.

[q-common/src/main/resources/mapper/stnd/terms.xml:297-312](q-common/src/main/resources/mapper/stnd/terms.xml#L297-L312)

```xml
<insert id="insertTermsWords" ...>
  INSERT INTO TB_TERMS_WORDS (TERMS_ID, WORD_ID, WORD_NM, WORD_ORD)
  VALUES (#{item.termsId}, #{item.wordId}, #{item.wordNm}, #{item.wordOrd})
</insert>
```

→ 가짜 단어가 포함되면 `WORD_ID = NULL`인 레코드가 삽입된다. `WORD_ID`가 FK + NOT NULL이라면 제약 오류로 롤백, NULL 허용이라면 조용히 저장되어 **"존재하지 않는 단어로 구성된 용어"**가 만들어진다. 이후 용어 승인 시점에 "구성 단어 미승인 체크"를 하더라도 id가 null이면 매칭 자체가 불가능해 그 검증을 우회한다.

### 4-2. 형식단어(마지막 단어) 검증 우회

[q-center/src/main/java/qualitycenter/controller/DataStandardController.java:476-482](q-center/src/main/java/qualitycenter/controller/DataStandardController.java#L476-L482)

```java
StdTermsVo.Word lastWord = wordList.get(wordList.size() - 1);
if (lastWord.getWordId() != null) {    // wordId null이면 검증 SKIP
    List<StdWordVo> lastWordInfo = session.selectList("word.selectWordInfoById", lastWord.getWordId());
    if (!lastWordInfo.isEmpty() && !"Y".equals(lastWordInfo.get(0).getWordClsfYn())) {
        throw new Exception("용어의 마지막 단어는 형식단어여야 합니다...");
    }
}
```

마지막 단어가 가짜(=사전 미등록)면 `wordId == null` → **if 블록 진입 자체를 못해서** "마지막 단어는 형식단어여야 한다" 규칙이 통째로 우회된다.

### 4-3. 용어 영문약어명(`termsEngAbrvNm`) 생성 오류

[q-center/vue/front/src/components/DSTerm.vue:2014](q-center/vue/front/src/components/DSTerm.vue#L2014)

```javascript
_createEngAbrvNm += sortedArr[i].wordEngAbrvNm + '_';
```

가짜 단어의 `wordEngAbrvNm`은 undefined. 결과 문자열은 `undefined_OPEN_DT_` 같은 오염된 값이 되어 Step 3의 영문약어명 필드에 그대로 바인딩된다.

### 4-4. 인라인 단어 등록 기능 Dead Code

`v-else` 분기에 붙어있는 인라인 등록 폼(단어 한글명/영문약어/영문명 + "단어 등록" 버튼)은 현 구현으로는 **절대 화면에 나타나지 않는다**. "미등록 단어는 그 자리에서 등록할 수 있게 한다"는 UX 의도가 버그 때문에 완전히 죽어있다.

## 5. 수정 방향 제안 (코드 수정은 하지 않음)

### 옵션 A — 백엔드가 미등록 토큰은 빈 `wordLst`로 리턴 (권장)

`getTermsTokenListByNm`의 `if (wordVoLst.size() > 0) { ... } else { ... }` 구조에서, **else 블록의 placeholder VO 추가를 제거**한다. 비명사 토큰(조사/어미)도 동일 처리.

- 장점: 프론트의 `v-if="item.wordLst.length > 0"` 로직이 원래 의도대로 동작. 인라인 단어 등록 폼도 자동 활성화. 변경 범위 최소.
- 영향 범위: 동일 API를 쓰는 다른 곳이 있는지 확인 필요 ([q-center/vue/front/src/components/DSCode.vue](q-center/vue/front/src/components/DSCode.vue)에서도 호출). 빈 배열을 받을 때 해당 컴포넌트가 깨지지 않는지 검증 필요.

### 옵션 B — 응답에 `registered` 플래그 추가

`WordDataVo`에 `private boolean registered;` 필드를 추가하고, 프론트는 `item.registered`로 칩을 판정하도록 바꾼다.

- 장점: 기존 `wordLst`에 placeholder를 남기는 로직을 유지하고 싶을 때 호환성 확보.
- 단점: VO 2개(`WordDataVo` + `StdWordVo`) 모두 손봐야 하고, "placeholder가 대체 왜 필요한가"라는 근본 질문은 해결되지 않음.

### 옵션 C — 프론트에서 "진짜 단어"만 필터

응답을 받을 때 `wordLst.filter(w => w.id)`로 가짜 VO를 걸러낸 뒤 바인딩.

- 장점: 백엔드 미수정.
- 단점: 계약 불일치를 프론트가 감추는 형태. 같은 API를 쓰는 다른 화면에서 같은 필터를 잊으면 재발. 근본 수정이 아님.

**추천:** **옵션 A** — 백엔드 `getTermsTokenListByNm` 수정. 이 함수의 placeholder 추가는 어떤 기능적 이점도 없고 오히려 4개의 잠재 버그(4-1~4-4)를 만드는 원인이다.

### 수정 시 같이 점검할 것

1. `TB_TERMS_WORDS.WORD_ID` 의 NOT NULL / FK 제약 상태 확인 — 현재 NULL 데이터가 이미 쌓여 있는지 조회 필요.
2. 단일 단어가 용어로 쓰이는 경로(`wordVoLst.size() == 1` 조기 리턴, [DataStandardController.java:582-591](q-center/src/main/java/qualitycenter/controller/DataStandardController.java#L582-L591))는 이번 버그와 무관하므로 건드리지 말 것.
3. 용어 수정 모달(`updateTerm_wordListArr`)도 동일 API를 쓰므로 등록 수정 시 1회 테스트로 커버.
4. [DSCode.vue](q-center/vue/front/src/components/DSCode.vue)의 `getTermsTokenListByNm` 호출부가 빈 `wordLst`에 어떻게 반응하는지 회귀 테스트.

## 6. 요약

- **버그 원인**: 백엔드 `getTermsTokenListByNm`이 사전에 없는 형태소에도 `{wordNm만 채워진 placeholder StdWordVo}`를 넣어 리턴 → 프론트는 `wordLst.length > 0`만으로 "등록됨" 판정 → 미등록 단어가 등록됨처럼 표시.
- **실질 리스크**: (1) `TB_TERMS_WORDS.WORD_ID = NULL` 저장, (2) 형식단어 검증 우회, (3) 용어 영문약어명 오염, (4) 인라인 단어 등록 폼 dead code.
- **수정 권장**: 백엔드 `else` 블록에서 placeholder VO 추가를 제거 (옵션 A).
