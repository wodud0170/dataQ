| 할 일 | 내용 |
|---|---|
| `SqlDialect` 확장 | 문장 메서드 `createTable`(DdlGenerator 가 씀)·`dropTable`·`renameTable`·`changeOwner`·`addColumn`·`dropColumn`·`modifyColumn`·`renameColumn`·`commentOnTable/Column`(소유자·이름을 따로 받음)·`qualify`. 끝의 `;` 는 붙이지 않고 조각에서 문장 사이에만 쓴다 |
| dialect 5종 | Oracle, Tibero(Oracle 상속), PostgreSQL, MariaDB(주석은 열 정의 안 `COMMENT`, 이름 변경은 `CHANGE COLUMN`), SQL Server(`sp_rename`, 주석은 `sp_addextendedproperty`). DBMS 값은 데이터소스 `DBMS_TP`(드라이버 유형) 그대로. 규칙이 없는 DBMS(Cubrid·Altibase·Goldilocks)는 조각 대신 `-- {DBMS} 용 DDL 규칙이 없습니다` → [DB 반영] SKIPPED |
| 조각 생성 | `generateDdlSnippet` 이 모델(DM_ID) → 데이터소스 DBMS 로 dialect 를 고른다. 데이터소스 없는 모델(논리 모델)은 PostgreSQL 문법으로 남기되 DBMS 칸은 비운다. 변경 이력에 `DDL_DBMS_TP` 컬럼을 새로 두고 조각의 DBMS 를 적는다. 컬럼 변경은 이름 바뀌면 RENAME, 타입·길이·소수점 바뀌면 MODIFY 두 문장. 테이블 변경은 이름 바뀌면 RENAME, 소유자 바뀌면 소유자 이동(Oracle·Tibero 는 DDL 없음 → 주석 조각) |
| 신규 테이블 | 조각은 지금처럼 표시(`(...)`)로 남기고, [DB 반영] 때 그 테이블의 현재 승인된 컬럼·PK·UK·FK·주석으로 `CREATE TABLE` 을 만들어 실행(`DdlGenerator` 공개 메서드, 소유자 접두어). 실행한 문장으로 이력의 조각을 바꾸고, 같은 테이블의 그 뒤 변경 중 아직 반영하지 않은 승인 건(컬럼 추가·변경·삭제, PK·FK)은 "테이블 생성(#번호)에 포함" SUCCESS 로 기록 |
| 실행 | 실행 대상은 **모델의 데이터소스로 고정**. 화면의 데이터소스 입력을 없애고 모델의 데이터소스·DBMS 를 보여 준다. 모델에 데이터소스가 없거나, 조각의 DBMS 와 데이터소스 DBMS 가 다르면 그 건은 실패로 남기고 실행하지 않는다. 조각을 문장 단위로 나눠(작은따옴표 안 `;` 무시) 하나씩 실행 |
| 타입 매핑 표 | `TB_DATA_TYPE_MAP`(DATA_TYPE, DBMS_TP, PHYS_DATA_TYPE, DFLT_DATA_LEN, 생성·수정 4칸). 물리 타입은 틀 문자열: `{len}`·`{dec}` 자리표시, `[...]` 는 안의 값이 모두 있을 때만 남는 선택 구간 (예: `NUMBER[({len}[,{dec}])]`, `VARCHAR2({len} CHAR)` + 기본 길이 255). 행이 없으면 지금처럼 이름(길이,소수) 그대로. 지금 dialect 의 13종 규칙과 빠진 5종(DATETIME·FLOAT·DOUBLE·TIME·BOOLEAN)·N 계열·정수 계열을 5개 DBMS 에 시드. dialect 의 `columnType` 은 이 표만 읽는다(10초 캐시) |
| PK 이름 규칙 | 새 설정 테이블 `TB_SYS_CONF`(CONF_KEY, CONF_VAL, CONF_DESC, 수정 2칸)에 `DDL_PK_NM_TMPL` = `PK_{TABLE}`(지금 규칙). `createPk` 기본 이름·`DdlGenerator`·컬럼 화면의 PK 이름 안내문이 이 값을 쓴다 |
| 관리 화면 | 관리 > **DDL 규칙** (`MMDdlRule.vue`): PK 이름 규칙, 데이터 타입 매핑 목록(DBMS 별 필터)·추가·수정·삭제·미리보기. 권한 DS_ADMIN(데이터 소스 관리 — DBMS 별 규칙이라 같은 담당) |
| 시험 | Oracle 19c(1522)에 시험 스키마, 개발 DB(PostgreSQL)에 시험 스키마를 만들어 데이터소스 2개·물리 모델 2개 등록. 테이블 추가·삭제, 컬럼 추가·삭제·타입 변경·이름 변경 6종을 API 로 만들고 [DB 반영] → SUCCESS 와 실제 DB 구조를 확인. 시험 객체는 끝에서 지움 |

**DDL**: `TB_DATA_TYPE_MAP`, `TB_SYS_CONF` 새 테이블, `TB_DATA_MODEL_CHANGE_HISTORY.DDL_DBMS_TP` 컬럼, 시드. 덤프 2종·변경이력·sync 스크립트.

### 4.7 WP4 수집 DBMS 확대 — 설계 (PC1 범위)

104 §2 WP4, §3.3("Cubrid 보강은 기존 시험 컨테이너로. Tibero 는 시험 DB 가 없어 쿼리만 작성하고 검증은 보류. SQL Server·MariaDB 는 시험용 Docker 이미지를 받는 것을 허락받은 뒤").

**PC1 사정**
- Cubrid 시험 컨테이너(`cubrid-test`)는 PC2 에만 있다. PC1 에서 Cubrid 인덱스·제약조건 쿼리를 만들면 실행해 볼 곳이 없고, 이미지를 받는 것은 허락 대상 → **보류 §2-6**.
- SQL Server·MariaDB 는 이미지 허락 대기(보류 §2-5).
- 따라서 PC1 에서 하는 일은 **Tibero 4종**뿐이다.

**Tibero 쿼리 4종** (`dm-collect.xml` 의 `TiberoGetObjs`·`TiberoGetAttrs`·`TiberoGetIndexes`·`TiberoGetConstraints`)
- Tibero 는 Oracle 호환 딕셔너리(ALL_TABLES·ALL_TAB_COLUMNS·ALL_TAB_COMMENTS·ALL_COL_COMMENTS·ALL_OBJECTS·ALL_INDEXES·ALL_IND_COLUMNS·ALL_CONSTRAINTS·ALL_CONS_COLUMNS)와 `(+)` 외부 조인을 지원하므로 Oracle 쿼리에서 출발한다.
- 다른 점: 시스템 테이블스페이스 이름 — Oracle 은 SYSTEM·SYSAUX, Tibero 는 SYSTEM·SYSSUB. 두 이름을 모두 빼도록 `NOT IN ('SYSTEM','SYSAUX','SYSSUB')`.
- 스키마 목록 SQL 은 이미 Oracle·Tibero 공용(`datamodel.xml selectSchemaListSql`).
- 검증: Tibero 시험 DB 가 없으므로 **Oracle 19c 에서 같은 쿼리를 돌려** 문법과 결과(Oracle 쿼리와 같은 행)를 확인한다. 실제 Tibero 검증은 보류(104 §3.3 그대로).

**완료 기준(104)** — Tibero·SQL Server 모델에서 4종 수집이 끝나고 구조 진단이 실행된다 → PC1 에서는 달성 불가(시험 DB 없음). Tibero 쿼리 작성·Oracle 대조까지를 PC1 결과로 남긴다.

**요청 유형(REQ_TP)**: WORD, TERMS, CODE, DOMAIN(표준사전), DM_CHANGE(데이터 모델 변경 신청). 엔진은 유형을 가리지 않는다(51번) — 다른 대상은 유형만 더하면 된다.

**결재자 정하기** (문서를 만들 때 모든 단계의 결재자를 정해 둔다 — 나중에 역할·부서가 바뀌어도 진행 중 문서는 그대로)
- USER: 지정 사용자. ROLE: 그 역할을 받은 사용자 전원(WP2 역할). ADMIN: 관리자 전원(구현 중 추가 — 사용자 목록에 최고 관리자가 나오지 않아 "→ 관리자" 단계를 USER 로 만들 수 없음). ORG_HEAD: 요청자 부서의 부서장, 요청자 본인이 부서장이면 상위 부서장(위로 올라가며 요청자가 아닌 첫 부서장).
- 결재자를 하나도 못 찾으면(부서 없음·부서장 없음·역할에 사용자 없음) 그 단계는 관리자(ADM_YN) 전원에게 간다 — 결재가 막히지 않게. (보류 §2-8: 이 규칙 확인)
- 요청자 자신은 결재자에서 뺀다(자기 결재 방지). 빼고 나서 비면 위 규칙대로 관리자.
- 합의(AGREE_YN): Y = 그 단계 결재자 전원이 승인해야 다음 단계, N = 한 명이 승인하면 다음 단계.
- "요청자 직접 지정"(104 표의 네 번째 방식)은 등록 화면 7곳(단어·용어·코드·도메인·일괄 표준화·엑셀·모델 신청)에 결재자 선택을 넣어야 해 이번에 하지 않는다 → 보류 §2-7.

**엔진** (`q-common` `AprvService` — q-center·q-executor 공용)
- `open(reqTp, targetId, targetNm, reqUserId, …)` — 그 유형의 결재선이 켜져 있으면 문서·단계를 만들고 1단계 결재자에게 APRV_REQ 알림. 결재선이 없으면 아무것도 안 한다(지금처럼).
- `act(docId, userId, approve, comment)` — 현재 단계 결재자(또는 관리자 대결)만. 반려: 어느 단계든 문서 REJECTED, 요청자에게 APRV_REJECT. 승인: 단계 완료(합의 규칙)면 다음 단계로 넘기고 다음 결재자에게 APRV_REQ, 요청자에게 APRV_STEP. 마지막 단계면 문서 APPROVED, 요청자에게 APRV_DONE, 호출자에게 "최종" 을 돌려줘 **기존 승인 처리를 그대로 부르게** 한다.
- 대상이 없어진 문서(진행 중 항목이 다른 경로로 지워짐)는 목록을 읽을 때 CANCELED 로 닫는다.

**연결**
- 표준사전: 위 요청 생성 지점 7곳에서 APRV_YN='N' 으로 넣은 뒤 `open`. `putStdAprvStat` 은 항목마다 진행 중 문서가 있으면 `act` → 최종 승인일 때만 기존 승인 처리, 반려면 기존 반려 처리(물리 삭제). 문서가 없는 항목은 지금처럼 STD_APPROVE. STD_APPROVE 가 없어도 그 문서의 현재 결재자면 처리할 수 있다.
- 데이터 모델: `submit` 때 SUBMISSION_ID 로 `open`. `approve`·`reject` 는 이력 건이 속한 신청에 진행 중 문서가 있으면 `act` → 최종 승인·반려 때 **그 신청의 SUBMITTED 건 전체**에 기존 처리(결재 문서가 있으면 일부만 골라 처리하지 않는다). `submissions` 는 DM_APPROVE 가 없어도 내가 현재 결재자인 신청을 보여 준다.
- 기존 두 승인 화면은 진행 중 문서가 있는 건에 "결재 n/m 단계 — 현재 결재자" 를 보인다.

**새 화면**
- 마이페이지 > **결재함** (`DSAprvBox.vue`, 로그인 사용자 모두): [내 차례]·[내가 올린 결재]·[처리한 결재] 목록 → 상세(결재 진행 단계, 대상 내용 — 표준사전 항목 필드 / 데이터 모델 변경 건 목록) → [승인]·[반려(사유 필수)]. 표준사전 항목은 [수정 후 승인] — 결재자가 설명·영문명 등을 고친 뒤 승인, 변경 이력에 "결재자 수정" 으로 남김(104 "결재자 수정 후 승인").
- 관리 > **결재선** (`MMAprvLine.vue`, USER_ADMIN): 요청 유형 5개마다 사용 여부·단계(이름·결재자 방식·대상·합의) 편집.

- 헤더 **알림**: 종 아이콘 + 읽지 않은 수 배지, 누르면 최근 알림 목록(누르면 읽음 처리 후 결재함 열기), [모두 읽음]. WebSocket 으로 실시간 갱신(`/user/exchange/amq.direct/message.user` 구독), 화면 진입 때와 1분마다 개수 다시 읽기(q-executor 에서 만든 알림 대비).

**권한**: 결재선·조직 관리 = USER_ADMIN(사용자·권한 관리와 같은 담당 — 새 권한 코드를 만들지 않음). 결재 처리 = 문서의 현재 결재자(관리자는 대결 가능).

**완료 기준(104)**: "팀장 → 관리자" 2단계 결재선(1단계 ORG_HEAD, 2단계 ROLE 또는 USER)으로 단어 등록 → 1단계 승인 → 2단계 반려 → 재요청(다시 등록) → 최종 승인까지, 단계마다 결재자에게 알림. 결재선이 없는 유형은 지금과 같게.

### 4.15 WP7 표준 입력 통제·영향도 — 설계 (구현 전)

104 §2 WP7(8·23·24·25·26·27). 순서: 8 유사어 → 24 자동완성 → 23 매핑 확대 → 25 준수 강제 → 26 영향도 → 27 미사용 표준. 완료 기준: "표준 준수 필수" 모델에서 비표준 컬럼 저장 거부, 자동완성으로 고른 컬럼은 저장 직후 표준 진단 이슈 0건.

**지금 코드에서 확인한 것**
- 유사어 경고(`checkSynonymWord`)는 단어 등록에서 실제로 나오지 않는다 — 앞의 중복 검사(`word.selectWordInfoByNm`)가 이음동의어까지 같은 이름으로 보고 "이미 승인된 단어명입니다." 로 막는다. 한글컬럼 일괄 표준화의 단어 등록은 같은 경우 기존 단어를 돌려준다.
- 용어 등록 자동 분석은 유사어 토큰을 표준 단어로 조용히 바꾼다(MATCHED, `selected` = 표준 단어). 화면에 바뀌었다는 표시가 없다.
- 컬럼 한글명 → 용어 매핑(DM-035)은 한글명이 용어 **이음동의어**와 같을 때 한글명을 표준 용어명으로 바꾸지 않아, 저장 뒤 표준 검사(한글명 = 용어명)에서 떨어진다.
- 컬럼과 용어는 `ATTR_NM = TERMS_ENG_ABRV_NM` 로만 이어진다(TERMS_ID 열 없음). 사전을 따지는 연결은 개인정보 컬럼 쿼리(`privCol.xml`)가 쓰는 방식(모델 사전 = 용어 사전).
- 단어 영향도의 연관 컬럼은 `ATTR_NM ILIKE '%약어%'` 부분 일치·사전 무관. 도메인 영향도는 용어만. 용어·코드 영향도와 역방향은 없다. 미사용 표준 조회는 없다.
- 컬럼 저장(`saveAttrs`)은 표준 검사가 실패하면 표준 여부만 N/N 으로 낮추고 저장한다. 엄격 거부는 화면 없는 `addAttr` 뿐.

**WP7-8 유사어 → 권장단어**

**WP7-25 표준 준수 강제** — `TB_DATA_MODEL.STND_REQ_YN`(기본 N). 데이터 모델 관리 등록·수정 창에 스위치 "표준 준수 필수". 켜진 모델은 컬럼 추가·수정(한글명·영문명·타입·길이가 바뀔 때) 저장에서 표준 검사가 실패하면 그 테이블 저장을 거부("표준 준수 필수 모델 — 비표준 컬럼: …"). 예외: 화면이 거부 메시지와 함께 [표준 예외로 신청] 을 띄우고, 사유를 넣어 다시 보내면 그 컬럼 변경을 결재 대상(변경 이력 DRAFT·1단계)으로 저장한다 — 데이터 모델 변경 승인(5.2)과 결재선(DM_CHANGE)을 그대로 쓴다. 모델 엑셀 업로드 등록(DM-022)도 같은 검사. 수집(실 DB 반영)은 막지 않는다. 시스템 단위는 시스템 화면에서 "하위 모델 모두 표준 준수 필수로" 일괄 설정 API.

**WP7-26 영향도 확대** — 새 API `GET /api/std/impact/term?termsId=`(연관 컬럼: 사용 중 모델 중 모델 사전 = 용어 사전, 컬럼명 = 영문약어명 / 한글명만 같은 컬럼은 따로), `GET /api/std/impact/code?termsId=`(코드 그룹을 쓰는 용어 → 그 용어 컬럼, 이 코드를 상위·하위로 쓰는 코드), 도메인 영향도에 연관 컬럼(그 도메인 용어들의 컬럼) 추가, 단어 영향도 연관 컬럼은 '_' 로 나눈 토큰이 약어와 같은 컬럼만·사전 기준으로 바꿈, 역방향 `GET /api/dm/impact/column?dmId=&objOwner=&objNm=&attrNm=`(용어·구성 단어·도메인·코드). 화면: 용어·코드 상세 [영향도 분석], 도메인 영향도 창에 컬럼, 컬럼 화면 행 메뉴 [영향도].

**WP7-27 미사용 표준** — 새 화면 표준 사전 > 미사용 표준(`DSUnusedStd`): 유형(단어 — 어떤 용어에도 없음 / 용어 — 어떤 사용 중 모델 컬럼에도 없음 / 도메인 — 어떤 용어도 안 씀 / 코드 — 어떤 용어도 그 코드 그룹을 안 씀은 해당 없음이라 '컬럼에 안 쓰이는 코드'), 승인만·사전, 엑셀 내려받기, 이름 클릭 → 그 화면 검색. 삭제는 각 화면에서.
