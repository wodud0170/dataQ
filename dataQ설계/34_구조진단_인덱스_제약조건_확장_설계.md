## 1. 현재 상태

### 1.1 구조 진단이 감지하는 것

| 대상 | 감지 항목 | 비교 속성 |
|------|----------|----------|
| 테이블 | ADDED / DELETED | 존재 여부 |
| 컬럼 | ADDED / MODIFIED / DELETED | dataType, dataLen, nullableYn |

### 1.2 감지하지 못하는 것 (수집/비교 미구현)

DBMS 카탈로그에는 모든 정보가 존재하나, 현재 코드에서 수집·비교하지 않아 감지 불가.

| 대상 | 카탈로그 소스 (Oracle 기준) | 감지 가능한 변경 (구현 시) |
|------|------------------------|----------------------|
| 인덱스 | ALL_INDEXES, ALL_IND_COLUMNS | 추가/삭제, 구성 컬럼·순서·방향 변경, 유니크↔일반 변경 |
| PK | ALL_CONSTRAINTS (P), ALL_CONS_COLUMNS | 구성 컬럼 추가/삭제, 복합키 순서 변경 |
| FK | ALL_CONSTRAINTS (R), ALL_CONS_COLUMNS | 추가/삭제, 참조 테이블/컬럼 변경, CASCADE 규칙 변경 |
| UK/CHECK | ALL_CONSTRAINTS (U/C), ALL_CONS_COLUMNS | 추가/삭제, 구성 컬럼 변경 |

## 2. 확장 목표

수집된 인덱스/제약조건 스냅샷과 현재 DBMS의 인덱스/제약조건을 비교하여 변경사항을 감지한다.

```
현재:  수집 컬럼 ←→ 현재 DB 컬럼     → 컬럼 변경 감지
확장:  수집 인덱스 ←→ 현재 DB 인덱스   → 인덱스 변경 감지
      수집 제약조건 ←→ 현재 DB 제약조건 → 제약조건 변경 감지
```

### 3.2 별도 테이블 분리 (3개 테이블)

기존 TB_STRUCT_DIAG_DETAIL은 컬럼 변경 전용으로 유지하고, 인덱스/제약조건은 별도 테이블로 분리한다.

#### TB_STRUCT_DIAG_INDEX_DETAIL (인덱스 변경 상세)

```sql
CREATE TABLE TB_STRUCT_DIAG_INDEX_DETAIL (
    DIAG_ID             VARCHAR(40)     NOT NULL,
    SEQ                 INTEGER         NOT NULL,
    OWNER               VARCHAR(100),
    TABLE_NM            VARCHAR(200),
    INDEX_NM            VARCHAR(200),
    CHANGE_TYPE         VARCHAR(20),        -- ADDED / MODIFIED / DELETED
    PREV_INDEX_TYPE     VARCHAR(50),
    CURR_INDEX_TYPE     VARCHAR(50),
    PREV_UNIQUENESS     VARCHAR(10),
    CURR_UNIQUENESS     VARCHAR(10),
    PREV_COLUMNS        VARCHAR(1000),      -- DEPT_CD(1,ASC),HIRE_DT(2,DESC)
    CURR_COLUMNS        VARCHAR(1000),
    CONSTRAINT PK_TB_STRUCT_DIAG_INDEX_DETAIL PRIMARY KEY (DIAG_ID, SEQ)
);

COMMENT ON TABLE TB_STRUCT_DIAG_INDEX_DETAIL IS '구조 진단 상세 - 인덱스 변경';
COMMENT ON COLUMN TB_STRUCT_DIAG_INDEX_DETAIL.PREV_COLUMNS IS '구성 컬럼 (컬럼명(순서,방향) 쉼표 구분)';
```

#### TB_STRUCT_DIAG_CONSTRAINT_DETAIL (제약조건 변경 상세)

```sql
CREATE TABLE TB_STRUCT_DIAG_CONSTRAINT_DETAIL (
    DIAG_ID             VARCHAR(40)     NOT NULL,
    SEQ                 INTEGER         NOT NULL,
    OWNER               VARCHAR(100),
    TABLE_NM            VARCHAR(200),
    CONSTRAINT_NM       VARCHAR(200),
    CHANGE_TYPE         VARCHAR(20),        -- ADDED / MODIFIED / DELETED
    PREV_CONSTRAINT_TYPE VARCHAR(10),       -- P / R / U / C
    CURR_CONSTRAINT_TYPE VARCHAR(10),
    PREV_COLUMNS        VARCHAR(1000),      -- DEPT_CD(1),EMP_ID(2)
    CURR_COLUMNS        VARCHAR(1000),
    PREV_REF_TABLE      VARCHAR(200),
    CURR_REF_TABLE      VARCHAR(200),
    PREV_REF_COLUMNS    VARCHAR(1000),
    CURR_REF_COLUMNS    VARCHAR(1000),
    PREV_DELETE_RULE    VARCHAR(20),
    CURR_DELETE_RULE    VARCHAR(20),
    PREV_STATUS         VARCHAR(10),        -- ENABLED / DISABLED
    CURR_STATUS         VARCHAR(10),
    CONSTRAINT PK_TB_STRUCT_DIAG_CONSTRAINT_DETAIL PRIMARY KEY (DIAG_ID, SEQ)
);

COMMENT ON TABLE TB_STRUCT_DIAG_CONSTRAINT_DETAIL IS '구조 진단 상세 - 제약조건 변경';
COMMENT ON COLUMN TB_STRUCT_DIAG_CONSTRAINT_DETAIL.PREV_CONSTRAINT_TYPE IS 'P(PK), R(FK), U(UK), C(CHECK)';
```

### 3.3 왜 별도 테이블인가

| 기준 | 별도 테이블 (3개) | 기존 테이블 확장 (1개) |
|------|-----------------|-------------------|
| NULL 컬럼 | **없음** — 각 테이블이 자기 역할 컬럼만 보유 | 카테고리별 미사용 컬럼 대량 NULL |
| 유지보수 | **독립 확장** — 인덱스에 속성 추가해도 제약조건 테이블 무관 | ALTER 시 모든 카테고리 영향 |
| 의미 명확성 | 테이블명만 봐도 용도 파악 | CHANGE_CATEGORY로 구분해야 의미 파악 |
| 조회 | 카테고리별 API 분리 → 프론트 탭별 바인딩 | WHERE 필터 필요 |
| SEQ 관리 | 각 테이블 독립 SEQ | 혼합 SEQ (의미 불명확) |

→ **각 테이블이 자기 역할의 컬럼만 갖는 깔끔한 구조 선택**

## 5. Diff 로직 확장 (StructDiagService)

### 5.1 현재 run() 흐름

```
1. prevAttrs 로드 (수집 스냅샷)
2. currAttrs 읽기 (실제 DBMS)
3. toAttrMap() → owner|tableNm|columnNm 키
4. diff (ADDED/MODIFIED/DELETED)
5. 결과 저장
```

### 5.2 확장 후 run() 흐름

```
1. prevAttrs 로드
2. currAttrs 읽기
3. 컬럼 diff (기존)
4. prevIndexes 로드 (TB_DATA_MODEL_INDEX)          ← 추가
5. currIndexes 읽기 (DBMS 인덱스 쿼리)              ← 추가
6. 인덱스 diff                                      ← 추가
7. prevConstraints 로드 (TB_DATA_MODEL_CONSTRAINT)  ← 추가
8. currConstraints 읽기 (DBMS 제약조건 쿼리)         ← 추가
9. 제약조건 diff                                     ← 추가
10. 결과 저장 (COLUMN + INDEX + CONSTRAINT 통합)
```

### 5.3 인덱스 Diff 상세

#### 키 구성
```
owner|tableNm|indexNm
```
인덱스명이 유니크하므로 이 키로 매칭.

#### 비교 대상 속성
| 속성 | 변경 의미 |
|------|----------|
| indexType | 인덱스 유형 변경 (NORMAL → BITMAP 등) |
| uniqueness | 유니크 여부 변경 |
| columns | 구성 컬럼/순서/방향 변경 |

#### columns 문자열 생성
```java
// TB_DATA_MODEL_INDEX에서 같은 인덱스의 행들을 columnPos 순으로 정렬 후 연결
// "DEPT_CD(1,ASC),HIRE_DT(2,DESC)"
private String buildIndexColumnsStr(List<Map<String, Object>> indexRows) {
    indexRows.sort((a, b) -> ((Integer)a.get("columnPos")).compareTo((Integer)b.get("columnPos")));
    StringBuilder sb = new StringBuilder();
    for (Map<String, Object> row : indexRows) {
        if (sb.length() > 0) sb.append(",");
        sb.append(row.get("columnNm"))
          .append("(").append(row.get("columnPos"))
          .append(",").append(row.get("sortOrder") != null ? row.get("sortOrder") : "ASC")
          .append(")");
    }
    return sb.toString();
}
```

#### diff 로직
```java
// 인덱스를 owner|tableNm|indexNm 키로 그룹핑
Map<String, IndexInfo> prevIndexMap = toIndexMap(prevIndexes);
Map<String, IndexInfo> currIndexMap = toIndexMap(currIndexes);

// ADDED: currMap에만 있는 것
// DELETED: prevMap에만 있는 것
// MODIFIED: 둘 다 있지만 indexType/uniqueness/columnsStr 다른 것
```

### 5.4 제약조건 Diff 상세

#### 키 구성
```
owner|tableNm|constraintNm
```

#### 비교 대상 속성
| 속성 | 변경 의미 |
|------|----------|
| constraintType | 유형 변경 (거의 없지만 대비) |
| columns | 구성 컬럼/순서 변경 |
| refTable + refColumns | FK 참조 대상 변경 |
| deleteRule | FK 삭제 규칙 변경 |
| status | ENABLED ↔ DISABLED 변경 |

#### columns / refColumns 문자열 생성
```java
// "DEPT_CD(1),EMP_ID(2)"
private String buildConstraintColumnsStr(List<Map<String, Object>> rows) {
    rows.sort((a, b) -> ((Integer)a.get("columnPos")).compareTo((Integer)b.get("columnPos")));
    StringBuilder sb = new StringBuilder();
    for (Map<String, Object> row : rows) {
        if (sb.length() > 0) sb.append(",");
        sb.append(row.get("columnNm")).append("(").append(row.get("columnPos")).append(")");
    }
    return sb.toString();
}
```

```
현재:  [추가: 테이블 0, 컬럼 2] [변경: 컬럼 2] [삭제: 테이블 0, 컬럼 1]
확장:  [추가: 테이블 0, 컬럼 2, 인덱스 1] [변경: 컬럼 2, 제약조건 1] [삭제: 컬럼 1]
```

### 10.3 변경사항 영역: 탭 분리

별도 테이블이므로 프론트도 탭으로 분리하여 각 카테고리 전용 헤더/데이터를 사용한다.

```
[컬럼 변경 (5)] [인덱스 변경 (1)] [제약조건 변경 (1)]
```

각 탭 내부에 기존과 동일한 변경유형 필터:
```
[전체] [추가] [변경] [삭제]    [엑셀 다운로드]
```

### 10.4 탭별 테이블 헤더

**컬럼 변경 탭** (기존과 동일):

| 오너 | 테이블명 | 컬럼명 | 변경유형 | 이전 타입/길이 | 현재 타입/길이 |
|------|---------|--------|---------|-------------|-------------|

**인덱스 변경 탭**:

| 오너 | 테이블명 | 인덱스명 | 변경유형 | 이전 타입 | 현재 타입 | 이전 유니크 | 현재 유니크 | 이전 구성컬럼 | 현재 구성컬럼 |
|------|---------|---------|---------|----------|----------|-----------|-----------|------------|------------|

**제약조건 변경 탭**:

| 오너 | 테이블명 | 제약조건명 | 변경유형 | 이전 유형 | 현재 유형 | 이전 구성컬럼 | 현재 구성컬럼 | 이전 참조 | 현재 참조 |
|------|---------|----------|---------|----------|----------|------------|------------|----------|----------|

→ 각 탭이 자기 테이블의 데이터만 표시하므로 헤더가 명확하고 NULL 컬럼 없음

### 10.5 API 확장

| Method | URL | 현재 | 확장 |
|--------|-----|------|------|
| GET | `/api/std/structDiag/result/{diagId}` | `{ history, details }` | `{ history, details, indexDetails, constraintDetails }` |

하나의 API에서 3개 테이블을 각각 조회하여 반환. 프론트에서 탭별로 바인딩.

### 10.6 엑셀 다운로드

각 탭에서 해당 카테고리 데이터만 다운로드. 파일명 예시:
- `구조진단결과_컬럼_20260413.csv`
- `구조진단결과_인덱스_20260413.csv`
- `구조진단결과_제약조건_20260413.csv`

## 12. 하위호환성

| 항목 | 처리 |
|------|------|
| 기존 DETAIL 데이터 | TB_STRUCT_DIAG_DETAIL 변경 없음 → 기존 데이터 그대로 유지 |
| 신규 테이블 (INDEX/CONSTRAINT DETAIL) | 기존 진단에는 데이터 없음 → 프론트 탭에 "데이터 없음" 표시 |
| 수집 이력에 인덱스/제약조건 없는 경우 | 인덱스/제약조건 diff 스킵 (수집 데이터 없으면 해당 카테고리 비교 안 함) |
| HISTORY 통계 신규 컬럼 | DEFAULT 0 → 기존 이력 조회 시 0으로 표시 (정상) |

수집 이력에 인덱스/제약조건이 없을 때의 처리 방침:

```java
// 인덱스 수집 데이터가 없으면 인덱스 diff 자체를 스킵
List<Map<String, Object>> prevIndexes = sqlSessionTemplate.selectList(
    "structdiag.selectIndexListByClctId", targetClctId);
if (prevIndexes != null && !prevIndexes.isEmpty()) {
    // 인덱스 diff 실행
} else {
    log.info(">> 인덱스 수집 데이터 없음 - 인덱스 diff 스킵");
}
```

→ 기존 수집건(인덱스 미수집)으로 구조 진단 해도 기존 동작에 영향 없음
