# 95. 통합테스트 계획서 (2026-08-23)

## 0. 왜 지금 이 문서인가

2026-08-22~23 전수 점검에서 나온 사실이 이 계획의 근거다.

| 사실 | 함의 |
|---|---|
| 셀레니움 46개가 **전부 통과**하는 상태에서도, 단어 영향도 분석(`/api/std/impact/word`)은 **항상 500** 이었다 | 화면 단위 테스트는 화면이 안 부르는 경로를 못 본다 |
| 결함 4건 중 **3건이 "조용히 실패"** 유형 (0건 갱신인데 200 / LAST_EXEC 미갱신 / 이력 currValue null) | 단건 성공 여부만 보면 안 잡힌다. **후속 상태를 봐야** 잡힌다 |
| 용어 변경이력 18건 중 16건(89%)이 값이 빈 채로 3개월간 누적 | 아무도 "승인 후 이력이 제대로 남았는지" 를 확인하지 않았다 |
| 기능 321건 중 셀레니움 API 커버 117건(36%), 미커버 83건 | 커버리지 자체가 낮다 |
| 기존 테스트 문서 5종이 **전부 화면·기능 단위** (인증 / 대시보드 / 단어 관리 / …) | 업무 흐름을 관통하는 검증이 설계된 적이 없다 |

**결론**: 기능 단위 검증(현행)은 유지하되, 그 위에 **업무 시나리오를 관통하는 통합테스트 계층**을 새로 얹는다.

## 1. 현행 테스트의 성격과 한계

### 1-1. 현행 46개가 실제로 검증하는 것

```
test_word_approval_flow.py   →  단어 등록 → 승인 → 삭제        (표준사전 안에서 닫힘)
test_53_grid_add_save.py     →  컬럼 그리드 추가 → 저장         (데이터모델 안에서 닫힘)
test_qual_rule_result.py     →  룰 진단 결과 API 13종 응답 검증  (API 형태 검증)
test_phase4_schedule_coverage →  스케줄 6경로                   (스케줄 안에서 닫힘)
```

각 파일이 **한 영역 안에서 시작하고 끝난다.** 영역을 넘는 인과는 검증하지 않는다.

### 1-2. 그래서 못 잡는 것 — 실제 사례 4건

| 놓친 결함 | 왜 못 잡았나 |
|---|---|
| 단어 영향도 분석 500 | 단어 화면 테스트가 [영향도 분석] 버튼을 안 누른다 |
| `updateAttr` 0건인데 200 | 응답 200만 보고 **DB 실제 값을 안 본다** |
| 스케줄 ERROR 시 LAST_EXEC 미갱신 | 로그 마감만 보고 **스케줄 행의 후속 상태를 안 본다** |
| 용어 승인 이력 currValue null | 승인 성공만 보고 **이력 테이블을 안 본다** |

공통점: **"요청이 성공했는가" 는 봤지만 "그 결과 시스템 상태가 올바르게 변했는가" 는 안 봤다.**

### 1-3. 통합테스트가 추가로 검증해야 하는 것

1. **영역 간 인과** — 표준사전 변경이 데이터모델·진단 결과에 반영되는가
2. **상태 전이 정합성** — 승인 상태 머신이 규정대로 도는가, 중간 상태가 새지 않는가
3. **cascade 정확성** — 함께 지워져야 할 것만 지워지고, 남아야 할 것은 남는가
4. **부작용 부재** — 의도하지 않은 데이터가 바뀌지 않았는가 (회귀)
5. **누적 지표** — 준수율·건수 같은 집계가 변경 후 올바르게 재계산되는가

## 2. 테스트 계층 정의

| 계층 | 대상 | 판정 | 현황 | 도구 |
|---|---|---|---|---|
| **L1 기능 단위** | 화면 1개 / API 1개 | 응답·렌더 정상 | 46개 존재, 전부 통과 | selenium + requests |
| **L2 API 계약** | 엔드포인트 응답 형태·상태코드 | 200 + 스키마 | 읽기전용 84건 1회 실시 | `probe.py` (정식화 필요) |
| **L3 통합 시나리오** | 업무 흐름 (여러 영역 관통) | **최종 상태 + 부작용 부재** | **없음 → 본 문서에서 신설** | selenium + requests + psql 단언 |
| **L4 데이터 정합성** | 전역 불변식 | 고아·중복·불일치 0 | 임시 SQL 로 1회 실시 | psql 단언 세트 |

**L3 가 이 문서의 주제.** L2·L4 는 L3 의 보조 장치로 함께 정식화한다.

## 3. 통합테스트 설계 원칙

### 원칙 1 — 시나리오는 "역할 × 목적" 으로 시작한다

화면 이름이 아니라 **누가 무엇을 이루려 하는가** 로 시작한다.

```
✗ "단어 화면에서 등록 버튼을 누른다"
✓ "일반 사용자가 신규 컬럼에 쓸 표준 용어를 만들어 승인까지 받는다"
```

### 원칙 2 — 판정은 3중으로 한다

| 층 | 확인 대상 | 예 |
|---|---|---|
| **UI** | 화면에 보이는가 | 목록에 행이 뜬다 |
| **API** | 응답이 맞는가 | `resultCode=200`, 목록 건수 증가 |
| **DB** | **상태가 맞는가** | `aprv_yn='Y'`, 이력 행 존재, `curr_value` not null |

**DB 단언이 없는 통합테스트 케이스는 반려한다.** 결함 4건 중 3건이 DB 단언만 있었으면 잡혔다.

### 원칙 3 — 부작용 부재를 명시적으로 확인한다

각 시나리오는 "바뀌어야 할 것" 뿐 아니라 **"바뀌면 안 되는 것"** 을 단언한다.

```sql
-- 단어 A 반려 시: 미승인 용어만 지워지고 승인된 용어는 남아야 함
SELECT count(*) FROM tb_terms WHERE terms_nm='승인된용어';  -- 기대 1 (0 이면 과도 삭제 결함)
```

### 원칙 4 — 시나리오는 자립한다

- 실행 전 **필요한 데이터를 스스로 만든다** (하드코딩된 기존 데이터 의존 금지)
- 실행 후 **자기가 만든 것만 정리한다**
- 실행 순서에 의존하지 않는다

> **근거**: 2026-08-22 에 하드코딩 fixture 3건(`CAMS` 모델 / `단어등록TEST` 단어 / `TB_MEMEBER` 테이블)이 전부 썩어서 테스트가 깨졌다. `arr[0]` 이 특정 모델일 거라는 가정도 2개 테스트를 깼다.

### 원칙 5 — 실패 시 어디서 끊겼는지 즉시 알 수 있어야 한다

각 단계에 ID(`S1-3`)를 부여하고, 실패 시 **그 시점의 DB 상태를 덤프**한다.

## 4. 통합 시나리오 목록 (L3)

업무 흐름 기준 **10개 시나리오**. 각각이 여러 영역을 관통한다.

| ID | 시나리오 | 관통 영역 | 핵심 검증 |
|---|---|---|---|
| **IT-01** | 신규 시스템 온보딩 — 데이터소스 등록부터 준수율 확인까지 | 데이터소스 → 모델 → 수집 → 표준진단 → 대시보드 | 준수율 집계가 수집·진단 결과와 일치 |
| **IT-02** | 표준화 개선 루프 — 진단 이슈를 표준 등록으로 해소 | 진단결과 → 표준화도구 → 단어·용어 등록 → 승인 → 재진단 | **재진단 후 준수율이 실제로 오르는가** |
| **IT-03** | 승인 워크플로우 정주행 | 일반사용자 등록 → 승인대기 → 관리자 승인 → 이력 | 이력의 `curr_value` 가 채워지는가 (결함 ① 회귀) |
| **IT-04** | 승인 워크플로우 반려·cascade | 단어 반려 → 미승인 용어 cascade 삭제 → 재등록 | 승인된 용어는 **안 지워지는가** (과도 삭제 부재) |
| **IT-05** | 용어 승인 가드 | 미승인 단어로 만든 용어 승인 시도 | 거부되는가 + 단어 승인 후에는 통과하는가 |
| **IT-06** | 모델 변경 거버넌스 정주행 | 일반사용자 컬럼 추가(DRAFT) → 신청 → 승인 → DDL → 변경이력 | 각 단계의 **가시성 규칙** (타인 DRAFT 미노출) |
| **IT-07** | 모델 변경 반려 cascade | 테이블 반려 → 하위 컬럼 cascade | 인덱스·제약은 cascade 되는가 (미구현으로 알려짐 — 명시적 확인) |
| **IT-08** | 구조 변경 감지 | 수집 → 운영DB ALTER → 구조진단 → 변경 감지 | ADDED/MODIFIED/DELETED 분류 정확도 |
| **IT-09** | 스케줄 자동화 end-to-end | BOTH 스케줄 → 자동 트리거 → 병행 실행 → 마감 → LAST_EXEC | 실패 경로에서도 LAST_EXEC 반영 (결함 ③ 회귀) |
| **IT-10** | 진단 제외 관리 영향 | 테이블 OFF → 진단 모수 축소 → 컬럼 OFF cascade → ON 복귀 | 모수가 정확히 줄고 정확히 복원되는가 |

### 4-1. 시나리오 선정 근거

- **IT-01 / IT-02** — 제품의 핵심 가치 흐름. "표준을 세워 데이터 품질을 올린다" 가 여기서만 관통 검증된다
- **IT-03 / IT-04 / IT-05** — 승인은 cascade·가드가 얽혀 있고, 실제 결함(①)이 나온 영역
- **IT-06 / IT-07** — 88번 거버넌스. **승인 우회 경로 6종**이 알려져 있어 명시적 확인 필요
- **IT-08** — 외부 DB 상태 변화를 감지하는 유일한 기능
- **IT-09** — 결함 ③ 이 나온 영역. 자동 트리거는 시간 의존이라 단위로는 검증 어려움
- **IT-10** — 진단 모수에 영향을 주므로 IT-01/02 의 전제를 흔들 수 있음

### 4-2. 커버리지 목표

| | 현재 | IT-01~10 적용 후 (목표) |
|---|---|---|
| 기능 321건 중 시나리오로 관통되는 비율 | 0% | 40% 이상 |
| 영역 간 인과 검증 | 없음 | 10개 흐름 |
| DB 단언 보유 케이스 | 일부 | **전부** |

## 6. 테스트 데이터 정책

### 6-1. 명명 규칙

모든 통합테스트 데이터는 접두사로 식별 가능해야 한다.

| 대상 | 접두사 | 예 |
|---|---|---|
| 단어 | `IT단어_` | `IT단어_0823_01` |
| 용어 | `IT용어_` | `IT용어_0823_01` |
| 도메인 | `IT도메인_` | `IT도메인_0823_01` |
| 데이터모델 | `IT_MODEL_` | `IT_MODEL_0823_143022` |
| 테이블 | `IT_TBL_` | `IT_TBL_ORDER` |
| 스케줄 | `IT_SCH_` | `IT_SCH_0823_143022` |

### 6-2. 단어 영문명 제약 (반드시 지킬 것)

```
영문약어: ^[A-Z][A-Z0-9]*$      (대문자 시작, 대문자+숫자만)
영문명:   ^[A-Za-z][A-Za-z0-9]*$ (영문 시작, 영문+숫자만 — 공백·언더바 불허)
```
> 86번 #42 "단어는 원자(atomic)" 결정. 2026-08-22 에 테스트 4개가 `"SELENIUM TEST 158"` 처럼 공백을 넣어 전부 실패했다.

### 6-3. 용어명 구성 제약

- 마지막 단어는 **형식단어**(`WORD_CLSF_YN='Y'`) 여야 한다
- 유니크 접미사를 **뒤에 붙이면 안 된다** — 형태소 분석의 마지막 토큰이 접미사가 되어 전제가 깨진다
  ```
  ✗ 셀유형코드_761  →  [셀, 유형, 코드, _, 761]  마지막 = 761
  ✓ 셀유형코드      →  [셀, 유형, 코드]          마지막 = 코드(CD)
  ```

### 6-4. cleanup

각 시나리오는 `finally` 에서 자기 데이터만 삭제한다. 삭제 순서는 FK 역순:

```sql
DELETE FROM tb_terms_words        WHERE terms_nm  LIKE 'IT용어_%';
DELETE FROM tb_aprv_stats         WHERE req_item_nm LIKE 'IT%';
DELETE FROM tb_change_history     WHERE target_nm LIKE 'IT%';
DELETE FROM tb_terms              WHERE terms_nm  LIKE 'IT용어_%';
DELETE FROM tb_word               WHERE word_nm   LIKE 'IT단어_%';
DELETE FROM tb_domain             WHERE domain_nm LIKE 'IT도메인_%';
DELETE FROM tb_data_model_attr    WHERE obj_nm    LIKE 'IT_TBL_%';
DELETE FROM tb_data_model_obj     WHERE obj_nm    LIKE 'IT_TBL_%';
DELETE FROM tb_diag_schedule_log  WHERE schedule_nm_snapshot LIKE 'IT_SCH_%';
DELETE FROM tb_diag_schedule      WHERE schedule_nm LIKE 'IT_SCH_%';
```

## 7. UI 조작 시 주의 (2026-08-22 에 실제로 겪은 함정)

통합테스트는 UI 를 많이 타므로, 아래는 **케이스 작성 시 필수 준수**.

| 함정 | 잘못된 방법 | 올바른 방법 |
|---|---|---|
| Vuetify input 이 안 비워짐 | `inp.clear()` 후 `send_keys()` → 잔여 텍스트에 이어붙음 | `clear()` + `Ctrl+A` + `send_keys()` 후 `get_attribute("value")` 로 **실제 입력값 검증** |
| 이미 선택된 체크박스를 클릭 | 무조건 클릭 → **선택이 해제됨** | 상태를 먼저 읽고 미선택 행만 클릭 |
| Vuetify 체크박스 클릭이 안 먹음 | `ActionChains.click()` (ripple 오버레이에 먹힘) | 내부 `<i>` 를 `driver.execute_script("arguments[0].click();", el)` |
| 하드코딩 모델명 | `"CAMS"` (USE_YN='N' 되면 사라짐) | 조건으로 조회 (`clctDt` 있는 모델) |
| `arr[0]` 가정 | "첫 모델이면 수집 이력 있겠지" | 필요 속성으로 필터 (`clctDt`, `dataModelDsId`) |

> **분석 결과가 이미 선택돼 있다는 점** 이 특히 중요하다. `DSTerm._applyAnalyzedWords` 는 MATCHED 단어를 `newSelectedList[i] = [item]` 로 **미리 선택 상태**로 넣는다.

## 8. 실행·판정 기준

### 8-1. 단계 판정

각 단계는 `PASS` / `FAIL` / `BLOCKED` 로 판정한다.

- `BLOCKED` — 선행 단계 실패로 실행 불가. **FAIL 과 구분해서 집계**한다 (한 곳이 깨져 10개가 FAIL 로 보이는 착시 방지)

### 8-2. 시나리오 판정

- 모든 단계 PASS → 시나리오 PASS
- 1개라도 FAIL → 시나리오 FAIL, **후속 단계는 BLOCKED**
- 부작용 단언 실패는 **FAIL 로 처리** (경고 아님)

### 8-3. 리포트 형식

```
[IT-02] 표준화 개선 루프                                    FAIL (7 PASS / 1 FAIL / 3 BLOCKED)
  S1  진단 실행 + 이슈 확인                                  PASS  (이슈 컬럼 12건)
  S2  표준화 도구로 미등록 용어 분석                          PASS  (AUTO 8 / PARTIAL 4)
  ...
  S8  재진단 후 준수율 상승 확인                              FAIL  기대 >72.5%, 실제 72.5% (변화 없음)
        DB: tb_diag_job(최신) total=120 issue_col=33
        DB: 직전 진단 total=120 issue_col=33
  S9  대시보드 준수율 반영                                    BLOCKED
```

1. **케이스 명세 확정** (96번) — 단계·단언까지 문서로 먼저

4. **회귀 편입** — `run_all.py` 와 별도로 `run_integration.py` 신설
