# 논리모델 → 물리모델 프로세스 분석

**작성일:** 2026-04-17  
**목적:** 메타관리 솔루션에서 논리/물리 모델 변환이 어떤 의미인지 정확히 파악하고, DataQ의 기능 방향 결정

---

## 1. 현장에서 존재하는 4가지 프로세스

### 시나리오 A: ERwin 단독 (메타관리 도구 = 사후 수집만)

```
모델러가 ERwin에서 논리모델 설계
    ↓
ERwin 내에서 논리→물리 변환 (ERwin 자체 Glossary 사용)
    ↓
ERwin에서 DDL 생성 → DBA가 DBMS에 배포
    ↓
메타관리 도구에서 DBMS 역수집 → 카탈로그 등록
```

- 메타관리 도구는 "이미 만들어진 것을 수집"하는 역할만
- 표준 검증 없음. 모델러 개인의 규칙에 의존
- 소규모 프로젝트, 메타관리 도구가 없던 시절의 방식

### 시나리오 B: 메타관리 도구 중심 (ERwin 불필요)

```
메타관리 도구에서 표준사전 확정 (단어/용어/도메인)
    ↓
메타관리 도구 내에서 논리모델(엔터티/속성) 직접 설계
    ↓
표준사전 기반으로 물리명 + 데이터타입 자동 생성
  - "사용자등록일자" → 표준단어 분리 → USR_REG_DT
  - 도메인 "일자" → Oracle: DATE, PG: DATE
    ↓
DDL 자동 생성 → 결재 → DBMS 배포
```

- **SMETA가 지향하는 시나리오**
- ERwin 없이 메타관리 도구 안에서 모델링까지 수행
- 중소규모 프로젝트, ERwin 라이선스가 없는 조직에서 사용

### 시나리오 C: 혼합형 (공공 SI에서 가장 흔함)

```
1. 메타관리 도구에서 표준사전 확정
    ↓
2. 모델러가 ERwin/DA#에서 논리모델 설계 (표준사전 참조)
    ↓
3. ERwin에서 논리→물리 변환
    ↓
4. ERwin XML을 메타관리 도구에 임포트
    ↓
5. 메타관리 도구에서 "표준 준수 검증"
   - 물리명이 표준용어 영문약어와 일치하는가?
   - 데이터타입이 표준 도메인과 일치하는가?
   - 불일치 건 목록 → 수정 요청
    ↓
6. 검증 통과 → 결재 → DDL 생성 → DBMS 배포
```

- **공공기관 대형 SI에서 가장 일반적인 패턴**
- 모델링은 ERwin/DA#, 표준 검증과 거버넌스는 메타관리 도구
- DA(데이터 아키텍트)와 표준관리자의 역할 분리

### 시나리오 D: 역공학 (기존 시스템 표준화)

```
운영 DBMS에서 카탈로그 수집 (물리모델)
    ↓
표준 진단 → 이슈 목록 도출
    ↓
미등록 단어/용어 일괄 등록
    ↓
점진적 표준화
```

- 레거시 시스템을 표준화할 때 사용
- 신규 개발이 아닌 운영 중인 시스템 대상

## 2. 핵심 질문: "ERwin에서 이미 변환하는데 메타관리 도구에서 또 하는 이유"

**답: "변환"이 아니라 "검증"이 핵심이다.**

| 관점 | ERwin의 변환 | 메타관리 도구의 변환 |
|------|------------|------------------|
| 규칙 주체 | 모델러 개인 (ERwin Glossary) | 전사 표준 (표준사전) |
| 관리 범위 | 모델러/팀 단위 | 조직 전체 |
| 결재 | 없음 | 있음 |
| 이력 추적 | ERwin 파일 버전 관리 수준 | 변경 건별 이력 + 영향도 |
| 표준 검증 | 불가 | 자동 검증 |

메타관리 도구가 논리→물리 변환을 제공하는 **진짜 이유**:
1. "이 물리모델이 우리 표준에 맞는가?" **검증**
2. ERwin에는 **결재 기능이 없다** → 모델 변경을 결재에 태우려면 메타관리 도구 안에 모델이 있어야 함
3. **이력 관리와 영향도 분석** → 모델 정보가 통합 저장소에 있어야 가능
4. **표준 변경 시 영향받는 모델 파악** → 단어/도메인 변경 → 어떤 엔터티/컬럼이 영향받는지

## 3. "표준 기반 물리 변환"의 구체적 의미

### 3.1 논리명(한글) → 물리명(영문) 변환

```
입력: 논리 속성명 = "사용자등록일자"

Step 1: 표준단어 분리
  "사용자" + "등록" + "일자"

Step 2: 각 단어의 영문약어 조회 (표준사전)
  사용자 → USR
  등록   → REG
  일자   → DT

Step 3: 조합 (언더스코어 연결)
  물리명 = USR_REG_DT

Step 4: 검증
  - 표준용어 "사용자등록일자"의 물리명과 일치하는가?
  - 일치하면 PASS, 불일치면 이슈
```

### 3.2 논리 데이터타입 → 물리 데이터타입 변환

```
입력: 표준 도메인 = "일자도메인"

Step 1: 도메인의 논리 데이터타입 조회
  일자도메인 → 논리타입: DATE

Step 2: 대상 DBMS별 물리 데이터타입 매핑
  Oracle     → DATE
  PostgreSQL → DATE
  MySQL      → DATE
  MSSQL      → DATETIME

또는 VARCHAR 기반 일자도메인인 경우:
  논리타입: VARCHAR(8)
  Oracle     → VARCHAR2(8)
  PostgreSQL → VARCHAR(8)
```

### 3.3 이를 위해 필요한 것

- **표준사전** (단어/용어/도메인) — DataQ에 이미 있음
- **논리-물리 데이터타입 매핑 테이블** — SMETA에는 "데이터타입 관리" 기능으로 존재. DataQ에는 없음
- **DBMS별 매핑 규칙** — Oracle, PG, MySQL 등 DBMS마다 타입이 다르므로 매핑 필요

## 4. ERwin XML의 논리/물리 구분

ERwin XML은 `Model_Type` 요소로 모델 유형을 구분:

| Model_Type | 의미 | XML 내용 |
|-----------|------|---------|
| 1 | Logical Only | Entity/Attribute에 논리명만 존재 |
| 2 | Physical Only | Entity/Attribute에 물리명만 존재 |
| 3 | Logical/Physical | 논리명 + 물리명 모두 존재 |

**Logical/Physical 통합 모델 (가장 흔함)의 경우:**
```xml
<Entity>
  <Name>사용자</Name>              <!-- 논리 엔터티명 -->
  <Physical_Name>TB_USER</Physical_Name>  <!-- 물리 테이블명 -->
  <Attribute>
    <Name>사용자이름</Name>          <!-- 논리 속성명 -->
    <Physical_Name>USR_NM</Physical_Name>  <!-- 물리 컬럼명 -->
    <Datatype>VARCHAR2</Datatype>
    <Length>100</Length>
  </Attribute>
</Entity>
```

DataQ의 `ErwinXmlParser.java`는 이미 이 구조를 파싱하고 있다:
- `Name` → `objNmKr` / `attrNmKr` (논리명)
- `Physical_Name` → `objNm` / `attrNm` (물리명)

## 5. 역할별 업무 분담 (현장 기준)

| 역할 | 논리모델 설계 | 물리모델 변환 | 표준사전 관리 | 표준 검증 | DBMS 배포 |
|------|:----------:|:----------:|:----------:|:-------:|:--------:|
| DA(데이터 아키텍트) | ERwin/DA# | ERwin/DA# | 메타관리 도구 | 메타관리 도구 | DBA에 의뢰 |
| 모델러 | ERwin/DA# | ERwin/DA# | - | - | - |
| DBA | - | 검토 | - | - | DDL 실행 |
| 표준관리자 | - | - | 메타관리 도구 | 메타관리 도구 | - |
| 개발자 | - | - | 용어 신청 | - | - |

## 6. DataQ 현재 상태와 GAP

### 시나리오별 DataQ 지원 현황

| 시나리오 | DataQ 지원 | 상세 |
|---------|:---------:|------|
| A (ERwin 단독) | O | DBMS 역수집으로 카탈로그 등록 가능 |
| B (메타관리 중심) | **X** | 논리모델 직접 설계, 표준기반 자동변환, DDL 생성 모두 없음 |
| C (혼합형) | **△** | ERwin 임포트(있으나 미완성) + 표준진단(있음). 논리/물리 구분 저장 미흡 |
| D (역공학) | **O** | 수집 → 표준진단 → 일괄등록 연계까지 잘 지원 |

### 기능별 GAP 상세

| 기능 | DataQ | SMETA | 비고 |
|------|:-----:|:-----:|------|
| 표준사전 (단어/용어/도메인) | O | O | |
| 승인 워크플로우 | O | O | |
| DBMS 카탈로그 수집 | O | O | |
| ERwin XML 임포트 | △ | O | DataQ: 구현했으나 미완성, 메뉴 숨김 상태 |
| 논리모델 직접 설계 (엔터티 등록) | **X** | **O** | SMETA 고유 |
| 표준 기반 물리명 자동 생성 | **X** | **O** | SMETA 고유 |
| 논리-물리 데이터타입 매핑 테이블 | **X** | **O** | SMETA 고유 |
| DDL 자동 생성 | △ | **O** | DataQ: 코멘트 스크립트만 |

## 7. DataQ 구현 방향 제안

### 목표

**시나리오 B(메타관리 중심) + 시나리오 C(혼합형)를 모두 지원하는 올인원 솔루션**

경쟁사(SMETA)가 제공하는 기능을 못하면 입찰에서 탈락한다. "우리는 시나리오 D만 잘합니다"로는 시장에서 팔리지 않는다.

### 추가 구현 필요 기능 (우선순위)

#### Phase A: ERwin 연동 재설계 (시나리오 C 완성)

| # | 기능 | 설명 | 난이도 |
|---|------|------|:------:|
| 1 | ERwin 임포트 재설계 | 논리명/물리명 구분 저장, Model_Type 처리 | 중 |
| 2 | 임포트 후 표준 검증 연계 | 임포트된 모델에 대해 즉시 표준 진단 실행 | 중 |
| 3 | GAP 분석 연계 | 임포트된 모델 vs 실제 DBMS 비교 | 중 |

#### Phase B: 논리모델 관리 (시나리오 B 기반)

| # | 기능 | 설명 | 난이도 |
|---|------|------|:------:|
| 4 | 논리-물리 데이터타입 매핑 테이블 | DBMS별 논리타입 → 물리타입 매핑 관리 화면 | 중 |
| 5 | 논리모델 직접 설계 (엔터티/속성 등록) | 메타관리 도구 내에서 논리모델 직접 작성 | 고 |
| 6 | 표준 기반 물리명 자동 생성 | 논리 속성명 → 표준단어 분리 → 영문약어 조합 → 물리명 | 중 |
| 7 | 표준 기반 물리 데이터타입 자동 결정 | 도메인 → DBMS별 물리타입 자동 매핑 | 중 |

#### Phase C: DDL/배포 (시나리오 B 완성)

| # | 기능 | 설명 | 난이도 |
|---|------|------|:------:|
| 8 | DDL 자동 생성 | 물리모델 기반 CREATE TABLE/INDEX DDL 생성 | 중 |
| 9 | DDL 결재 연동 | DDL 생성 → 결재 요청 → 승인 후 실행 가능 | 중 |
| 10 | DBMS 배포 (옵션) | 승인된 DDL을 대상 DBMS에 직접 실행 | 고 |

### 이미 DataQ에 있는 강점 (활용 가능)

| 기존 기능 | 활용 방향 |
|----------|---------|
| 자동 표준화 추천 (형태소 분리) | 논리명 → 물리명 자동 변환의 핵심 엔진으로 재활용 |
| 표준 진단 | ERwin 임포트 후 검증, 논리모델 설계 시 실시간 검증에 활용 |
| 영향도 분석 | 표준 변경 시 논리/물리 모델 영향 범위 파악에 활용 |
| 승인 프로세스 | 엔터티 등록/변경/삭제 결재에 그대로 활용 |

### 참고: DataQ의 자동 표준화 추천이 "표준 기반 물리명 자동 생성"의 핵심이 될 수 있음

```
현재: 사용자가 용어 등록 시 → 한글명 입력 → 형태소 분리 → 표준단어 매칭 → 영문약어 조합
    → 이것이 "용어의 물리명(영문약어)"이 됨

확장: 논리모델 설계 시 → 속성 논리명 입력 → 동일한 분리/매칭 엔진 → 물리 컬럼명 자동 생성
    → 이것이 "컬럼의 물리명"이 됨

즉, 이미 가진 자동 표준화 추천 엔진을 논리→물리 변환에 그대로 쓸 수 있다.
경쟁사에 없는 "자동 추천" 기능이 여기서 차별점이 된다.
```
