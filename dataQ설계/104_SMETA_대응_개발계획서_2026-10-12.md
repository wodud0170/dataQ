### WP1. 결재선·조직·알림 — 1단계, 34인일

대상: **50·51·56·57·71번**

**현황**
- 결재가 두 갈래다. 표준사전은 `TB_APRV_STATS`(상태 0~3, 관리자 한 명이 승인, `APR-R01`), 데이터 모델은 `TB_DATA_MODEL_CHANGE_HISTORY`(DRAFT → SUBMITTED → APPROVED/REJECTED, `GOV-B04`).
- 조직이 없다. `TB_USER` 에 부서 컬럼이 없다.
- 알림은 전체 방송(`/topic/onMessage`)이나 브라우저 창 세션 단위로만 보낸다. 로그인 사용자에게 보내는 경로가 없다. 알림 패널은 숨겨져 있다(`COM-029`).

**설계 원칙**
- 두 승인 흐름의 상태값은 그대로 두고 **그 위에 결재 문서를 얹는다.** 마지막 단계가 승인될 때 지금의 승인 처리를 그대로 부른다. 기존 데이터 이관이 필요 없다.
- 결재선을 설정하지 않은 요청 유형은 지금처럼 관리자 1단계로 동작한다.

| 할 일 | 내용 | 인일 |

| 표준사전 연결 | 요청 때 결재 문서 생성. `MMApproval.vue` 의 승인을 "내 차례인 단계"의 승인으로 | 4 |

| 알림 | STOMP 사용자 대상 전송(`/user/queue/…`), 헤더 배지와 알림 목록. 결재 요청·승인·반려 때 보낸다 | 4 |

### WP3. DBMS 별 DDL·DB 반영 정상화 — 1단계, 18인일

대상: **46·47·9·44번**. 이 묶음이 끝나야 103번의 48번(DB 직접 반영) 우위가 실제로 성립한다.

**현황**
- 모델 전체 DDL 은 `SqlDialect` 구현 2종(Oracle·PostgreSQL)으로 만든다(`DM-012`).
- 변경분 DDL 조각은 dialect 를 쓰지 않는 한 가지 문법이다(`GOV-B11`). §0.1 의 1·2번 때문에 신규 테이블은 반영이 안 되고, Oracle 에서는 컬럼 추가·변경이 실패한다.
- 논리 타입 18종을 물리 타입으로 바꾸는 규칙은 dialect 코드 안에 고정돼 있다.

| 할 일 | 내용 | 인일 |
|---|---|---:|
| `SqlDialect` 확장 | `addColumn`·`dropColumn`·`modifyColumn`·`createTable` 추가 | 3 |
| 조각 생성 | 모델 데이터소스의 DBMS 로 dialect 를 골라 조각 생성. 신규 테이블은 `DdlGenerator.appendCreateTable` 재사용 | 3 |
| dialect 추가 | Tibero(Oracle 상속), MariaDB, SQL Server | 4 |

### WP4. 수집 DBMS 확대 — 1단계, 15인일

**현황**
