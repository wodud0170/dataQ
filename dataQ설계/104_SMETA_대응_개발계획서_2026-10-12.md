**현황**

- 알림은 전체 방송(`/topic/onMessage`)이나 브라우저 창 세션 단위로만 보낸다. 로그인 사용자에게 보내는 코드와 그걸 구독하는 화면이 없다. 사용자명 기준 목적지 해석기(`UsernameUserDestinationResolver`, `…message.user` → `/exchange/amq.direct/message.user-user{사용자명}`)는 등록돼 있고, 브로커 접두어는 `/topic`·`/exchange` 뿐이다(`/queue` 는 주석, `WebSocketConfiguration.java:74-105`). 알림 패널은 숨겨져 있다(`COM-029`).

- 두 승인 흐름의 상태값은 그대로 두고 **그 위에 결재 문서를 얹는다.** 마지막 단계가 승인될 때 지금의 승인 처리를 그대로 부른다. 기존 데이터 이관이 필요 없다.
- 결재선을 설정하지 않은 요청 유형은 지금처럼 관리자 1단계로 동작한다.

- PC2 시험 DB 는 Docker 컨테이너다(`oracle-19c` localhost:11521, Cubrid 는 `cub11` 34000 — `cubrid-test` 라는 이름은 없음). PC2 의 옛 compose 배포 `q-center`·`q-executor` 컨테이너는 무한 재시작하던 것을 10-14 에 멈추고 재시작을 꺼 뒀다. PC2 에는 `dataq-db` 컨테이너가 없어 셀레니움의 `docker exec dataq-db` 호출을 네이티브 psql 로 바꿔야 한다.
- 서버는 저장소의 `target` jar 로 띄운다. `build.bat` 는 PC2 에서 옛 `ndata-quality-master` jar 를 띄우므로 쓰지 않는다.
- 셀레니움은 Edge 155 용 드라이버가 필요하다.
- 102번 생성 도구는 `dataQ설계/도구/102_기능명세서/` 에 있다.

## 5. 개발 규칙 (모든 묶음 공통)

- DDL 을 바꾸면 그 자리에서 `DDL_full_schema.sql`·`docker/dataq-db/initdb/01_schema.sql`·`DDL_변경이력.md` 를 갱신한다(CLAUDE.md).
- 새 필드는 VO → resultMap → SELECT → 화면 순으로 모두 반영한다(CLAUDE.md 체크리스트).
- 새 표준 테이블에는 `DICT_ID` 를 넣고, 조회는 사전 범위로 한다(98번).
- 묶음마다 `run_all.py` 에 시나리오를 추가하고 헤드리스로 전체 회귀를 돌린다.
- 묶음이 끝나면 102번 기능명세서의 해당 장을 갱신한다.
