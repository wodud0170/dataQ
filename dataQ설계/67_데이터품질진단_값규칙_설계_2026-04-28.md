# 67. 데이터 품질 진단 (값 진단 + 업무 규칙) 설계 (초안)

작성일: 2026-04-28
상태: **초안 — 사용자 검토 대기**
관련 문서: 65 (진단 스케줄러), 66 (기능 명세)

---

## 0. 검토용 한 줄 요약

기존 dataQ 의 진단은 **모델 메타(컬럼명/도메인/타입)가 표준에 맞는지** 만 본다. 새로 만들 두 종류는 **실제 들어가 있는 값** 을 본다.
- **값 진단(Value Profiling)** — 자동 통계: NULL률·중복률·길이·범위·패턴 분포 (룰 정의 필요 없음)
- **업무 규칙 진단(Business Rule)** — 사용자가 정의한 룰 검사: 예 "급여 > 0", "주민번호 정규식", "회원ID 가 회원 테이블에 존재"

두 가지는 같은 "실행/스케줄/결과조회" 골격을 공유하지만, **룰을 사람이 등록하느냐 안 하느냐**가 핵심 차이.

## 1. 용어 정의

| 용어                  | 뜻                                                          |
| ------------------- | ---------------------------------------------------------- |
| **표준 진단**           | (기존) 모델 메타가 표준사전(단어/용어/도메인)에 맞는지                           |
| **구조 변경 진단**        | (기존) 두 시점 수집 결과의 구조 차이                                     |
| **값 진단 (VALUE)**    | (신규) 컬럼별 실제 값의 통계 프로파일링 — NULL률/유일값 수/길이 분포/min·max/이상치 후보 |
| **업무 규칙 진단 (RULE)** | (신규) 사용자가 정의한 검증식을 데이터에 돌려 위반 행을 집계                        |
| **룰(Rule)**         | 한 컬럼 또는 한 행 단위 검증식 1건. 다중 컬럼 룰도 포함                         |
| **룰 카탈로그**          | 자주 쓰는 룰 템플릿 (주민번호/이메일/전화번호 정규식 등)                          |
| **위반(Violation)**   | 룰을 만족하지 못한 행                                               |
| **샘플 위반 행**         | 위반 행을 전부 저장하면 폭발하므로 PK + 핵심 컬럼만 N개 (기본 100) 저장             |
| **심각도(Severity)**   | ERROR(차단) / WARN(경고) / INFO(참고). 점수 가중치에 사용                |

## 2. 메뉴 구조 — **메뉴 이름 안 (3가지 옵션 중 택1)**

기존 NdNav 의 대그룹은 다음과 같다:
```
1. 대시보드
2. 데이터 표준 사전 (단어/용어/도메인/표준코드)
3. 데이터 모델
4. 표준 진단
5. 구조 변경 진단
6. 자동 표준화 지원 (컬럼 표준화)
7. 커뮤니티
8. 관리 (관리자만)
9. 진단 스케줄
10. 마이페이지
```

이번에 추가될 항목을 어디에 배치할지 옵션 3가지:

### Option C — 룰 관리만 별도, 진단은 기존 그룹에 분산

```

[NEW 7.] 업무 규칙 진단          ← 단독 메뉴 (그룹 없음)
```

**단점**: 일반 사용자도 룰 등록 가능하게 할 거면 안 맞음.

## 3. 값 진단 (Value Profiling)

### 3.1 무엇을 뽑나

테이블 1개 / 컬럼 N개에 대해 다음 지표를 한 번에 계산:

| 지표                         | 모든 컬럼 | 숫자형만 | 문자형만 | 날짜형만 |
| -------------------------- | ----- | ---- | ---- | ---- |
| 총 행수 (TOTAL_CNT)           | ✓     |      |      |      |
| NULL 건수/비율                 | ✓     |      |      |      |
| 유일값 수 (DISTINCT_CNT)       | ✓     |      |      |      |
| 중복 비율 (1 - distinct/total) | ✓     |      |      |      |
| 빈 문자열 건수                   |       |      | ✓    |      |
| 공백 패딩 건수                   |       |      | ✓    |      |
| 최소/최대 길이                   |       |      | ✓    |      |
| 최소/최대 값                    |       | ✓    |      | ✓    |
| 평균/표준편차                    |       | ✓    |      |      |
| 최빈값 Top-5                  | ✓     |      |      |      |
| 음수 건수                      |       | ✓    |      |      |
| 미래일자 건수                    |       |      |      | ✓    |
| 패턴 추정 (정규식 후보)             |       |      | ✓    |      |

### 3.2 처리 흐름

```
[사용자] 모델 + 테이블 + 대상 컬럼 선택 → "프로파일링 시작"
   ↓
[q-center] TB_QUAL_DIAG_HISTORY READY 행 INSERT (DIAG_TYPE='VALUE')
   ↓
[q-executor] ValueProfileService 비동기 시작
   ├ 데이터소스 접속 (DataSourceUtils — 표준/구조 진단과 동일)
   ├ 컬럼 단위로 SQL 생성 (DBMS 별 SqlDialect — DDL Generator 코드 재사용)
   ├ 한 컬럼 = 1 SELECT (집계 SQL: COUNT, NULL, DISTINCT, MIN, MAX, ...)
   ├ 결과를 TB_QUAL_PROFILE_RESULT 에 적재 (UPSERT, DM_ID + OBJ_NM + ATTR_NM)
   └ 종료 시 TB_QUAL_DIAG_HISTORY STATUS='DONE'
   ↓
[사용자] 값 진단 결과 화면에서 조회
```

### 3.3 성능 고려 (68번 문서 §2~§5 1차 권장 조합 적용)

- 한 번의 프로파일링 = (컬럼 수 × 1) ~ (컬럼 수 × 2) SQL.
- 컬럼 50개 × 2 = 100 SQL. 운영DB 부하 우려 → 다음 가드:
  - **샘플링 — 사용자 선택 옵션**: UI 에서 100% / 10% / 1% / 1만건 선택. 기본값 1만건. 풀스캔(100%)은 "운영 부하 동의" 체크 + dry-run EXPLAIN 결과 노출 후 허용. PostgreSQL `TABLESAMPLE`, Oracle `SAMPLE`, MariaDB 는 풀스캔+야간 강제
  - **컬럼 단위 통합 SQL**: 한 테이블 N 컬럼을 1 SELECT 의 다중 집계로 합산 (값 프로파일링 한정. RULE 진단은 룰별 분리)
  - **타임아웃**: SQL 당 30초, 전체 컬럼 합산 30분
  - **동시 실행 1개**: DM_ID + DIAG_TYPE='VALUE' 1건만 RUNNING. **+ DS_ID 기준 SKIP 추가** (한 DB 동시 진단 1건)
- 결과는 항상 직전 1회분만 보존 (UPSERT) — 추세 분석 미지원 (Phase 2 후보)

### 3.4 화면 — 값 프로파일링 (실행)

```
┌─ 값 프로파일링 ─────────────────────────────────────────────┐
│ [모델] CAMS ▾    [테이블] TB_MEMBER ▾    [컬럼] 전체 ▾      │
│ [샘플링] 1만건 ▾  [타임아웃] 30분                            │
│                                            [프로파일링 시작]│
├─────────────────────────────────────────────────────────┤
│ 직전 실행: 2026-04-28 10:30 (DONE)  대상 컬럼 47개          │
│ 그리드 (직전 결과 요약):                                     │
│ ┌─컬럼─┬─타입─┬─NULL%─┬─유일값─┬─중복%─┬─이슈─┐            │
│ │MBR_ID│VARCH │  0.0% │ 12,453 │  0.0%│ -    │            │
│ │AGE   │NUMBER│  3.2% │     85 │ 99.3%│⚠음수3│            │
│ └──────┴──────┴───────┴────────┴──────┴──────┘            │
│ 행 클릭 → 컬럼 상세 (분포 히스토그램, Top-5, 패턴)            │
└──────────────────────────────────────────────────────────┘
```

### 3.5 화면 — 값 진단 결과

- 검색: 모델 / 테이블 / 컬럼명 / 진단 일자
- 그리드: 모델, 테이블, 컬럼, 마지막 진단 일시, NULL%, 유일값, 이슈 카운트
- 행 클릭 → drawer 상세 (3.4 컬럼 상세와 동일 컴포넌트 재사용)

## 4. 업무 규칙 진단 (Business Rule)

### 4.1 룰 카테고리 (RULE_TYPE)

| 코드           | 이름      | 파라미터                  | 예시                            |
| ------------ | ------- | --------------------- | ----------------------------- |
| `NOT_NULL`   | NULL 금지 | 없음                    | "회원ID 는 NULL 금지"              |
| `RANGE`      | 숫자 범위   | min, max              | "급여는 0 이상 1억 이하"              |
| `LENGTH`     | 길이 범위   | minLen, maxLen        | "주민번호는 정확히 13자"               |
| `REGEX`      | 정규식 일치  | pattern               | "이메일 = `^[\\w.-]+@[\\w.-]+$`" |
| `ENUM`       | 허용값 목록  | values[]              | "성별 IN ('M','F','U')"         |
| `UNIQUE`     | 컬럼 유일성  | 없음                    | "사업자번호 중복 없음"                 |
| `REFERENCE`  | 외래키 정합성 | refTable, refCol      | "주문.회원ID 가 회원.ID 에 존재"        |
| `COMPARE`    | 컬럼 간 비교 | leftCol, op, rightCol | "종료일 >= 시작일"                  |
| `EXPRESSION` | SQL 표현식 | sqlExpr               | 자유 표현식 (관리자만 등록 가능)           |

> Phase 1: 위 9개 중 SQL_EXPRESSION 제외한 8개 우선 구현. EXPRESSION 은 SQL Injection 우려라 별도 검증 단계.

### 4.2 룰 정의 데이터 모델

```sql
CREATE TABLE TB_QUAL_RULE (
  RULE_ID         VARCHAR(40)  PRIMARY KEY,
  DM_ID           VARCHAR(40)  NOT NULL,                  -- 데이터모델
  OBJ_NM          VARCHAR(100),                           -- 테이블 (DOMAIN_ID 기반 룰이면 NULL)
  ATTR_NM         VARCHAR(100),                           -- 컬럼 (NULL 이면 ROW/TABLE 단위 또는 도메인 묶음)
  DOMAIN_ID       VARCHAR(40),                            -- 도메인 묶음 적용 시 (NEW)
  RULE_NM         VARCHAR(200) NOT NULL,
  RULE_TYPE       VARCHAR(20)  NOT NULL,
  RULE_PARAMS     TEXT,                                   -- JSON 직렬화
  SEVERITY        VARCHAR(10)  NOT NULL DEFAULT 'WARN',   -- ERROR / WARN / INFO
  USE_YN          CHAR(1)      NOT NULL DEFAULT 'Y',
  -- 부하 가드 (68번 §2)
  INCREMENTAL_COL VARCHAR(100),                           -- 증분 검증 트리거 컬럼 (NULL 이면 풀스캔만)
  EST_COST        VARCHAR(10),                            -- LOW/MID/HIGH (UI 비용 라벨, 자동 추정)
  DESCR           TEXT,
  CRET_USER_ID    VARCHAR(40),
  CRET_DT         TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  UPDT_USER_ID    VARCHAR(40),
  UPDT_DT         TIMESTAMP
);
```

> **DOMAIN_ID 룰** (68번 §2.2): 도메인 단위로 룰을 등록하면 q-executor 가 해당 모델의 같은 도메인을 갖는 모든 컬럼에 동일 룰을 자동 전개. 1차는 등록 UX 만 (실행 시 컬럼 단위 전개), SQL 합병은 Phase 2.

### 4.3 룰 진단 실행 흐름 (68번 1차 권장 조합 적용)

진단 실행 모달:
```
┌─ 업무 규칙 진단 시작 ─────────────────────────────┐
│ 모델: CAMS    대상 룰: 47개 (증분 가능 23 / 풀스캔만 24)│
│                                                       │
│ [샘플링] ⦿ 1만건  ○ 1%  ○ 10%  ○ 100%(풀스캔)        │
│ [검증 범위] ⦿ 증분 (직전 검증 이후 변경분)           │
│              ○ 풀스캔 (모든 행 재검증)                │
│   └ 증분 선택 시: 풀스캔 전용 룰 24개는 풀스캔 자동 적용│
│ [Dry-run] [EXPLAIN PLAN 미리보기]                    │
│                                                       │
│ ☐ 운영 부하 동의 (풀스캔 또는 즉시실행 시 필수)       │
│                              [취소] [진단 시작]        │
└─────────────────────────────────────────────────┘
```

```
사용자 [업무 규칙 진단 시작] (모델 단위)
   ├ 옵션 1: 샘플링 (100%/10%/1%/1만건)
   ├ 옵션 2: 검증 범위 (증분 / 풀스캔)
   │   - 증분: INCREMENTAL_COL 있는 룰만 증분, 없는 룰은 풀스캔 자동
   │   - 첫 실행 또는 룰 변경 후 첫 실행은 풀스캔 권장 안내
   ├ Dry-run EXPLAIN 노출
   └ 풀스캔/즉시실행 시 "운영 부하 동의" 체크 필수
   ↓
q-center: TB_QUAL_DIAG_HISTORY INSERT (DIAG_TYPE='RULE')
   ↓
q-executor: BusinessRuleService (직렬, connection 1개)
   ├ TB_QUAL_RULE WHERE DM_ID=? AND USE_YN='Y' 조회
   ├ DOMAIN_ID 룰은 모델의 같은 도메인 컬럼에 자동 전개
   ├ 룰 1개당 1 SQL 생성 (RuleSqlBuilder — RULE_TYPE 별 dispatch)
   │    예: NOT_NULL  → SELECT COUNT(*) FROM T WHERE col IS NULL
   │        RANGE     → ... WHERE col < min OR col > max
   │        REGEX     → ... WHERE NOT REGEXP_LIKE(col, pattern)
   │        REFERENCE → NOT EXISTS / LEFT JOIN IS NULL (NOT IN 회피)
   │    + 샘플링 절 부착 (TABLESAMPLE / SAMPLE / 풀스캔)
   │    + 증분 절 부착 (AND incCol > :lastDiagDt)
   │    + setQueryTimeout(30s)
   ├ 위반률 90% 초과시 그 룰 자동 중단 (룰 정의 오류 의심) + 결과 INFO 마킹
   ├ 위반 건수 + (옵션) 샘플 위반 행 PK 100개 fetch
   ├ TB_QUAL_RULE_RESULT INSERT (RULE_ID, VIOLATION_CNT, TOTAL_CNT)
   ├ TB_QUAL_VIOLATION_SAMPLE INSERT (룰별 샘플 행)
   └ 종료 → TB_QUAL_DIAG_HISTORY STATUS='DONE'
   ↓
[전체 30분 누적시 강제 종료 / DS_ID SKIP / DM_ID+RULE SKIP]
```

## 5. 데이터 모델 (DDL 신규)

CLCT 폐기 패턴 준수: **DM_ID 기반, 자연키 + UPSERT, soft-delete (USE_YN)**.

```sql
-- 5.1 룰 정의 (4.2 와 동일)
CREATE TABLE TB_QUAL_RULE (...);

-- 5.2 진단 실행 이력 (값/룰 공용)
CREATE TABLE TB_QUAL_DIAG_HISTORY (
  DIAG_ID         VARCHAR(40)  PRIMARY KEY,
  DM_ID           VARCHAR(40)  NOT NULL,
  DIAG_TYPE       VARCHAR(10)  NOT NULL,         -- 'VALUE' / 'RULE'
  DIAG_DT         TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  END_DT          TIMESTAMP,
  STATUS          VARCHAR(20)  NOT NULL DEFAULT 'READY',  -- READY/RUNNING/DONE/ERROR
  TARGET_OBJ_LIST TEXT,                          -- JSON [{objNm, attrNms[]}, ...]
  SAMPLE_RATE     INT          DEFAULT 100,      -- VALUE 만 사용 (1/10/100)
  TOTAL_RULES     INT          DEFAULT 0,        -- RULE 만
  TOTAL_COLS      INT          DEFAULT 0,        -- VALUE 만
  TOTAL_VIOLATIONS INT         DEFAULT 0,
  EXEC_USER_ID    VARCHAR(40),
  ERROR_MSG       TEXT
);

-- 5.3 값 프로파일링 결과 (컬럼별 직전 1회분 UPSERT)
CREATE TABLE TB_QUAL_PROFILE_RESULT (
  DM_ID           VARCHAR(40)  NOT NULL,
  OBJ_NM          VARCHAR(100) NOT NULL,
  ATTR_NM         VARCHAR(100) NOT NULL,
  DIAG_ID         VARCHAR(40)  NOT NULL,
  TOTAL_CNT       BIGINT,
  NULL_CNT        BIGINT,
  DISTINCT_CNT    BIGINT,
  EMPTY_CNT       BIGINT,                        -- 문자형 빈 문자열
  MIN_VAL         VARCHAR(200),                  -- 문자열로 저장 (포맷팅 후)
  MAX_VAL         VARCHAR(200),
  AVG_VAL         NUMERIC(20,4),                 -- 숫자형
  STD_VAL         NUMERIC(20,4),
  MIN_LEN         INT,
  MAX_LEN         INT,
  TOP_VALUES      TEXT,                          -- JSON [{v, cnt}, ...] Top-5
  UPDATED_DT      TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (DM_ID, OBJ_NM, ATTR_NM)           -- UPSERT 자연키
);

-- 5.4 룰 진단 결과 (DIAG_ID + RULE_ID 단위)
CREATE TABLE TB_QUAL_RULE_RESULT (
  DIAG_ID         VARCHAR(40)  NOT NULL,
  RULE_ID         VARCHAR(40)  NOT NULL,
  TOTAL_CNT       BIGINT,
  VIOLATION_CNT   BIGINT,
  VIOLATION_RATE  NUMERIC(7,4),                  -- 0.0000 ~ 100.0000
  SAMPLE_CNT      INT,                           -- 저장된 샘플 행 수
  ERROR_MSG       TEXT,                          -- 룰 SQL 실행 실패 시
  PRIMARY KEY (DIAG_ID, RULE_ID)
);

-- 5.5 위반 샘플 (PK 컬럼만 N개)
CREATE TABLE TB_QUAL_VIOLATION_SAMPLE (
  DIAG_ID         VARCHAR(40)  NOT NULL,
  RULE_ID         VARCHAR(40)  NOT NULL,
  SEQ             INT          NOT NULL,         -- 1..N (기본 100)
  PK_VALUES       TEXT,                          -- JSON {col1: v1, col2: v2}
  VIOLATING_VAL   VARCHAR(500),                  -- 위반한 값 (NULL/잘못된 값)
  PRIMARY KEY (DIAG_ID, RULE_ID, SEQ)
);

-- 5.6 룰 카탈로그 (템플릿)
CREATE TABLE TB_QUAL_RULE_CATALOG (
  CATALOG_ID      VARCHAR(40)  PRIMARY KEY,
  CATALOG_NM      VARCHAR(200) NOT NULL,         -- "주민등록번호 형식"
  RULE_TYPE       VARCHAR(20),
  RULE_PARAMS     TEXT,                          -- 미리 채워진 JSON
  CATEGORY        VARCHAR(50),                   -- "개인정보" / "금융" / ...
  DESCR           TEXT,
  USE_YN          CHAR(1)      DEFAULT 'Y'
);
```

## 7. 진단 스케줄러 통합 (65번 연계)

`TB_DIAG_SCHEDULE.DIAG_TYPE` 값 확장:
- 기존: `STANDARD` / `STRUCT` / `BOTH`
- 신규: `VALUE` / `RULE` / `ALL` (= STANDARD+STRUCT+VALUE+RULE 전부)

`ScheduledDiagLauncher.launch()` 분기 추가:
```java
if (type.contains("VALUE")) { startValueProfile(...); }
if (type.contains("RULE"))  { startRuleDiag(...); }
```

진단 스케줄 등록 화면 (DSScheduleManage) 의 diagType 셀렉트에 옵션 추가:
- 표준 진단 (STANDARD)
- 구조 변경 진단 (STRUCT)
- 표준+구조 (BOTH)
- **값 진단 (VALUE)** ← 신규
- **업무 규칙 진단 (RULE)** ← 신규
- **전체 (ALL)** ← 신규

> SKIP 정책은 `(DM_ID + DIAG_TYPE)` 조합 그대로 적용. ALL 케이스는 분해 후 각 sub-type 별 SKIP 검사.

## 11. 미정/리스크

- **DBMS 별 SQL 차이**: PostgreSQL `REGEXP_MATCHES` vs Oracle `REGEXP_LIKE` vs MariaDB `REGEXP`. SqlDialect (DDL Generator) 패턴 그대로 확장.
- **운영DB 부하**: 68번 문서 §2~§5 의 1차 권장 조합 적용 (샘플링 사용자 옵션 + 증분 검증 + 도메인 묶음 + DS_ID SKIP + 위반 폭주 자동 중단).
- **NULL 안전 비교**: `col != 'X'` 가 NULL 행을 위반으로 잡을지 — 룰 정의 시 "NULL 은 미검사" 옵션 필요.
- **REFERENCE 룰 성능**: NOT IN 은 100만 건에서 느림. NOT EXISTS 또는 LEFT JOIN ... IS NULL 로 대체 (68번 §2 적용).
- **룰 변경 이력**: 룰 수정 시 직전 결과 무효화? — 일단 미반영, 결과 행에 RULE 스냅샷 컬럼 추가 검토. 증분 검증 시 룰 SQL 변경 후 1회는 풀스캔 권장.
- **사용자가 룰을 잘못 만들면 false positive 폭증**: WARN 심각도 기본값 + dry-run EXPLAIN + 위반률 90% 자동 중단 (68번 §5).
- **DOMAIN_ID 룰의 컬럼 타입 불일치**: 같은 도메인이라도 컬럼 타입이 다르면(예: 일부 NUMBER, 일부 VARCHAR) 룰 적용 시 캐스팅 필요. 룰 등록 시 호환성 검사 필요.
