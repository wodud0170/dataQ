## 1. 개요

### 1.1 목적
표준화 진단과 구조 변경 진단을 수동 실행이 아닌 **자동 주기 실행**할 수 있도록 스케줄러를 제공한다. 운영 환경에서 매일/매주 정기적으로 진단을 수행하여 데이터 품질 변화를 지속 모니터링한다.

### 1.2 메뉴 구조

```
진단 스케줄러              ← 신규 대메뉴
  ├─ 스케줄 관리            (스케줄 등록/수정/삭제/활성화)
  └─ 실행 이력              (자동 실행 이력 조회)
```

### 1.3 현재 진단 실행 방식

| 진단 유형 | 현재 실행 방식 | 트리거 |
|----------|-------------|--------|
| 표준화 진단 | DiagController.startDiag() → q-executor DiagService (Thread) | 사용자 수동 클릭 |
| 구조 변경 진단 | StructDiagController.execute() → q-executor StructDiagService (Thread) | 사용자 수동 클릭 |

→ 두 진단 모두 q-center → q-executor WebClient 호출 → 백그라운드 Thread 실행 패턴. 스케줄러도 동일 패턴으로 호출하면 기존 코드 재활용 가능.

## 2. DB 설계

### 2.1 TB_DIAG_SCHEDULE (진단 스케줄)

```sql
CREATE TABLE TB_DIAG_SCHEDULE (
    SCHEDULE_ID         VARCHAR(40)     NOT NULL,
    SCHEDULE_NM         VARCHAR(200)    NOT NULL,
    DIAG_TYPE           VARCHAR(20)     NOT NULL,       -- STANDARD / STRUCT / BOTH
    DATA_MODEL_ID       VARCHAR(40)     NOT NULL,
    CRON_EXPR           VARCHAR(100),                   -- cron 표현식 (고급)
    SCHEDULE_TYPE       VARCHAR(20)     DEFAULT 'SIMPLE', -- SIMPLE / CRON
    REPEAT_CYCLE        VARCHAR(20),                    -- DAILY / WEEKLY / MONTHLY
    REPEAT_TIME         VARCHAR(5),                     -- HH:mm (실행 시각)
    REPEAT_DAY_OF_WEEK  INTEGER,                        -- 1(월)~7(일), WEEKLY일 때
    REPEAT_DAY_OF_MONTH INTEGER,                        -- 1~28, MONTHLY일 때
    USE_YN              CHAR(1)         DEFAULT 'Y',
    LAST_EXEC_DT        TIMESTAMP,
    LAST_EXEC_STATUS    VARCHAR(20),                    -- DONE / ERROR
    CRET_USER_ID        VARCHAR(40),
    CRET_DT             TIMESTAMP       DEFAULT CURRENT_TIMESTAMP,
    UPDT_USER_ID        VARCHAR(40),
    UPDT_DT             TIMESTAMP,
    CONSTRAINT PK_TB_DIAG_SCHEDULE PRIMARY KEY (SCHEDULE_ID)
);

COMMENT ON TABLE TB_DIAG_SCHEDULE IS '진단 스케줄';
COMMENT ON COLUMN TB_DIAG_SCHEDULE.DIAG_TYPE IS 'STANDARD(표준화), STRUCT(구조변경), BOTH(둘 다)';
COMMENT ON COLUMN TB_DIAG_SCHEDULE.SCHEDULE_TYPE IS 'SIMPLE(간편설정), CRON(고급 cron)';
```

### 2.2 TB_DIAG_SCHEDULE_LOG (실행 이력)

```sql
CREATE TABLE TB_DIAG_SCHEDULE_LOG (
    LOG_ID              VARCHAR(40)     NOT NULL,
    SCHEDULE_ID         VARCHAR(40)     NOT NULL,
    EXEC_DT             TIMESTAMP       DEFAULT CURRENT_TIMESTAMP,
    EXEC_STATUS         VARCHAR(20),    -- RUNNING / DONE / ERROR
    DIAG_TYPE           VARCHAR(20),    -- 실행된 진단 유형
    DIAG_JOB_ID         VARCHAR(40),    -- 표준화 진단 Job ID (해당 시)
    STRUCT_DIAG_ID      VARCHAR(40),    -- 구조 진단 ID (해당 시)
    ERROR_MSG           VARCHAR(1000),
    EXEC_DURATION       INTEGER,        -- 실행 소요시간 (초)
    CONSTRAINT PK_TB_DIAG_SCHEDULE_LOG PRIMARY KEY (LOG_ID)
);

COMMENT ON TABLE TB_DIAG_SCHEDULE_LOG IS '진단 스케줄 실행 이력';
```

## 3. 스케줄러 실행 흐름

```
q-executor (@Scheduled, 매 1분)
    │
    ├─ 1. TB_DIAG_SCHEDULE 조회 (USE_YN='Y')
    ├─ 2. 각 스케줄의 실행 시간 도래 여부 판정
    │     ├─ SIMPLE: REPEAT_CYCLE + REPEAT_TIME + REPEAT_DAY 기반
    │     └─ CRON: Spring CronExpression 평가
    ├─ 3. 실행 대상 스케줄 → 진단 실행
    │     ├─ DIAG_TYPE = STANDARD → 최신 수집건으로 표준화 진단
    │     ├─ DIAG_TYPE = STRUCT → 최신 수집건으로 구조 변경 진단
    │     └─ DIAG_TYPE = BOTH → 표준화 먼저 → 구조 변경 순차 실행
    ├─ 4. TB_DIAG_SCHEDULE_LOG에 실행 이력 저장
    └─ 5. TB_DIAG_SCHEDULE.LAST_EXEC_DT/STATUS 업데이트
```

### 3.1 실행 시간 판정 (SIMPLE 모드)

```java
// DAILY: 매일 REPEAT_TIME에 실행
// WEEKLY: 매주 REPEAT_DAY_OF_WEEK의 REPEAT_TIME에 실행
// MONTHLY: 매월 REPEAT_DAY_OF_MONTH의 REPEAT_TIME에 실행

// 판정: 현재 시각이 REPEAT_TIME의 ±1분 이내 && LAST_EXEC_DT가 오늘이 아님
boolean shouldRun = isTimeMatched(schedule) && !isAlreadyRunToday(schedule);
```

### 3.2 기존 진단 서비스 재활용

```java
// 표준화 진단: 기존 DiagController.startDiag()와 동일 로직
String clctId = getLatestClctId(dataModelId);
DiagService diagService = new DiagService(jobId, clctId, ...);
startService(diagService);

// 구조 변경 진단: 기존 StructDiagController 로직
StructDiagService structDiagService = new StructDiagService(diagId, dataModelId, ...);
startService(structDiagService);
```
