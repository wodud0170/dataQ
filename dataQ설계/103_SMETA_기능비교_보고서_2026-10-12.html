NavidM Meta 대 SMETA

판매 중인 비투엔 SMETA 를 시장 기준선으로 놓고, 개발 중인 우리 제품이 무엇을 따라잡고 무엇을 완성해야 하는지 83개 항목으로 정리했습니다. 우리 쪽은 102번 기능명세서(코드에 있는 기능, 실사용 검증 전), SMETA 쪽은 비투엔이 2025년 4월에 낸 사용자 교육자료가 근거입니다.

한눈에

  1. 두 제품은 출발점이 다릅니다.SMETA 는 표준과 테이블을 메타에 등록하고 결재로 통제하며, 메타와 실제 DB 의 차이를 점검합니다. 우리는 DB 에서 수집한 모델을 표준사전으로 진단하고 고치는 흐름으로 만들고 있습니다. 기능 폭은 SMETA 가 넓습니다.
  2. 표준사전의 뼈대는 SMETA 기준선만큼 코드에 있습니다.단어·용어·도메인·금칙어·엑셀 일괄등록은 있고, 여러 벌의 사전은 구조만 있고 여러 경로가 기본 사전에 고정돼 있습니다. 비어 있는 곳은 코드 유형(계층·파생·통합), 도메인 그룹 다단계, 공통표준 골라 넣기, 개인정보·암호화 표시입니다.
  3. 따라잡기 중 공공 사업에서 먼저 걸릴 것은 네 가지입니다.다단계 결재선, 역할별 권한, 범정부 데이터 플랫폼 연계, Tibero 수집. 넷 다 공공기관 사업에서 요구가 잦은 항목입니다.
  4. 코드에 있지만 완성되지 않은 것이 일곱 가지입니다.DB 직접 반영(신규 테이블은 건너뛰고 Oracle 에서 실패), DBMS 를 가리지 않는 변경 DDL, 고른 사전이 반영되지 않는 여러 경로, 엑셀 일괄등록에서만 읽는 사전별 표준화 관례, 메뉴에 연결되지 않은 시스템 계층 화면, 화면 없는 주제영역, 결재 화면에 없는 변경 전후 비교.
  5. 차별 후보 7개는 검증할 가설입니다.한글 컬럼명 일괄 표준화, 진단 결과에서 만드는 조치 스크립트, 변경 등급별 결재 등. 대부분 SMETA 교육자료에 나오지 않았다는 것이지 SMETA 에 없다는 확인이 아니고, 우리 쪽도 실사용 검증 전입니다. 데모와 실제 기관 데이터로 확인하기 전에는 영업 자료에 쓰지 않습니다.

    같은 이름의 기능이 다른 일을 합니다

    기능표만 맞대면 비슷해 보이는 항목도 일하는 순서가 달라 실제 쓰임이 다릅니다. 이 차이를 먼저 잡아야 아래 분류가 읽힙니다.

    SMETA설계를 등록하고 결재로 통제한다

    1. 표준사전과 테이블을 화면·엑셀·모델링 도구로 메타에 등록 요청
    2. 다단계 결재선을 거쳐 승인
    3. 승인된 메타로 DBMS 별 DDL 을 만들어 DB 담당자에게 넘김
    4. 담당자가 직접 DB 에 실행하고 반영 완료를 표시
    5. 배치 통계로 메타·모델·실제 DB 카탈로그의 차이(GAP)를 점검하고, 결과를 엑셀로 받아 다시 등록

    제품 구성도(p.8)에는 값 진단을 맡는 품질 제품 SDQ 와 통합 대시보드·통합 검색을 맡는 포털 제품 SPORTAL 이 SMETA 와 연동하는 별도 제품으로 그려져 있습니다. 메타와 DB 카탈로그의 차이 점검은 SMETA 자체 기능입니다(p.63, 80).

    NavidM Meta수집한 모델을 표준으로 진단·정비한다 (개발 중)

    1. 운영 DB 에 접속해 테이블·컬럼·인덱스·제약조건을 수집 (엑셀·모델링 도구 파일로도 들여옴)
    2. 저장된 모델의 컬럼마다 표준사전 기준으로 표준 진단
    3. 진단 결과에서 조치 스크립트와 용어 등록, 한글 컬럼명 일괄 표준화
    4. 테이블·컬럼의 추가·삭제와 이름·타입·길이 변경만 결재, 한글명·설명 등은 즉시 반영 (PK·FK 와 엑셀·모델링 도구 반입은 아직 결재 밖)
    5. 승인 후 [DB 반영] 으로 대상 DB 에 실행(신규 테이블·Oracle 은 미완성), 구조 변경 진단으로 저장된 모델과 지금 DB 비교

    표준 진단·구조 진단·대시보드를 한 제품 안에 둡니다. 데이터 품질(값) 진단은 DQ 제품으로 분리했습니다. 모두 코드에 있는 기능 기준이며 고객 환경에서 검증하지 않았습니다.

    예: 표준 준수율은 양쪽 다 있습니다. SMETA 화면 설명은 메타시스템의 테이블·컬럼을 대상으로 적고(p.82), 화면 범례는 DBMS 컬럼을 대상으로 적고 있어(p.80) 실제 대상은 데모로 확인해야 합니다. 우리는 저장된 모델의 컬럼을 진단합니다(DG-B04). 그 모델은 대개 수집으로 채우지만 엑셀·모델링 도구로 들어온 컬럼도 함께 진단합니다. 설계 단계의 입력 통제는 SMETA 쪽 기능이 더 많습니다(24·25번).

    검증할 가설과 완성할 것

    우리 코드에만 보이는 기능은 차별점이 아니라 검증할 가설로 둡니다. 코드에 있어도 동작이 덜 된 것은 새 기능보다 먼저 완성해야 합니다.

    가설 — 한글 컬럼명 일괄 표준화

    한글 컬럼명 목록을 단어로 나누고, 없는 단어는 영문약어를 제안하고, 도메인을 추천해 일괄 등록하는 기능이 코드에 있습니다. 다만 일괄 등록은 단어가 모두 있고 도메인이 정해진 행만 되고, 새 단어는 행마다 한 개씩 등록하며, 도메인 추천은 마지막 단어에 분류가 있을 때만 나옵니다. SMETA 교육자료에는 용어 한 건씩 분할만 나옵니다. 실제 기관 컬럼 목록으로 분할 정확도와 손이 가는 정도를 재 봐야 수작업을 줄이는지 말할 수 있습니다.

    20·21·22번 · TR-001–029

    가설 — 진단 결과에서 조치 스크립트

    표준 진단 이슈 행마다 컬럼 변경·코멘트 스크립트를 만들고, 없는 용어를 그 자리에서 등록합니다. SMETA 교육자료에서는 준수 진단 결과가 상세 조회로 끝나고, 조치는 GAP 결과를 엑셀로 받아 다시 등록하는 방식입니다(p.57). 만든 스크립트가 실제 DBMS 에서 오류 없이 도는지 먼저 확인해야 하고, 결과 화면에서 등록한 용어·단어는 기본 사전으로 들어가 모델이 다른 사전을 쓰면 재진단에 반영되지 않습니다(10번).

    60번 · DG-018–027

    가설 — 변경 등급별 결재, 컬럼 단위 진단 제외

    테이블·컬럼의 추가·삭제와 이름·타입·길이 변경만 결재에 올리고 한글명·설명·NULL·기본값은 바로 반영합니다. PK·FK 생성·삭제와 엑셀·모델링 도구 반입은 아직 결재를 거치지 않아 먼저 막아야 합니다(104번 WP0). 진단 제외는 테이블·컬럼 단위로, 진단 유형별로 켜고 끕니다. 공공기관이 즉시 반영을 받아들이는지, 컬럼 단위 제외가 실제로 필요한지 확인해야 합니다.

    45·52번 · GOV-B03 · GOV-018–028

    완성할 것 — 여러 사전과 사전별 관례

    사전 세트와 모델별 사전 지정은 있지만, 엑셀 일괄등록 7종과 진단 결과의 용어·단어 등록, 이름 조회 여러 곳이 기본 사전에 고정돼 있습니다. 사전마다 저장하는 "용어 끝은 형식단어" 강제 여부도 엑셀 용어 일괄등록에서만 읽고, 화면 등록·일괄 표준화·진단 결과 등록은 항상 강제합니다. SMETA 는 이 옵션이 시스템 전체에 하나입니다(p.14). 모든 경로가 고른 사전과 사전 속성을 따르게 한 뒤에야 공통표준과 기관 표준을 한 인스턴스에 올리는 시험을 할 수 있습니다.

    10·12번 · STD-084·085·090 · DG-022·023

    완성할 것 — DB 직접 반영

    승인 뒤 [DB 반영] 으로 대상 DB 에 실행하는 기능이 있지만, 신규 테이블의 DDL 조각은 컬럼 정의 없이 CREATE TABLE … (...) 라서 실행 단계에서 건너뜁니다. 컬럼 추가·변경 조각은 PostgreSQL 문법이라 Oracle 등에서 실패합니다. 47·48번을 함께 고쳐야 동작합니다.

    47·48번 · GOV-B11 · GOV-B12

    완성할 것 — 만들다 만 화면

    시스템 트리 화면은 메뉴에 연결되지 않았고, 주제영역은 서버 API 만 있고 화면이 없습니다. 결재 화면에는 변경 전후 값이 없습니다. 데이터 모델 승인 화면은 유형·대상·상태만 보여 주고, 전후 값은 사후 조회 화면에 JSON 원문으로만 있습니다.
