# 표준 진단 실행 로직 분석 및 개선안

## 1. 현재 실행 흐름

```
[프론트 - DSDataDiag.vue]
  사용자 "진단 시작" 클릭
    ↓
  POST /api/diag/startDiag
    ↓
[q-center - DiagController]
  1) TB_DIAG_JOB INSERT (STATUS='READY')
  2) q-executor에 비동기 HTTP 요청
    ↓
[q-executor - DiagController]
  Thread.start() → DiagService.run()
    ↓
[DiagService - 별도 스레드]
  STATUS → 'RUNNING' (START_DT 기록)
  컬럼별 진단 루프 (50건마다 flush)
  STATUS → 'DONE' (END_DT 기록)
    ↓
[프론트 - 3초 간격 폴링]
  GET /api/diag/getDiagJobById → DB 조회
  DONE/ERROR 수신 시 폴링 중지
```

## 2. "대기(READY)" 상태는 왜 발생하는가?

### 정상적인 경우
- Job INSERT 직후 ~ executor 스레드가 `updateStatus("RUNNING")` 호출까지의 **1~3초 갭**
- 이 사이에 프론트가 폴링하면 READY로 보임
- 정상 흐름이면 금방 RUNNING으로 전환됨

### 비정상적인 경우 (READY에 걸려있음)
| 원인 | 상세 |
|---|---|
| **q-executor 연결 실패** | q-center → q-executor HTTP 요청이 타임아웃/실패. Job은 DB에 INSERT 됐으나 executor가 실행을 시작하지 못함 → **READY 상태로 영구 대기** |
| **executor 과부하** | Thread.start() 호출 됐으나 CPU/메모리 부족으로 스레드 스케줄링 지연 |
| **executor 미기동** | q-executor 서버가 내려가 있는 상태에서 진단 시작 시도 |
| **DB 접속 실패** | executor 스레드가 시작됐으나 `updateStatus("RUNNING")` DB 업데이트에서 예외 발생 → status가 READY인 채로 스레드 종료 |

### 현재 코드의 문제
```java
// q-center DiagController.startDiag()
sqlSessionTemplate.insert("diag.insertDiagJob", jobVo);  // ① DB에 READY로 INSERT
// ... 
return webClientHandler.postData(params)  // ② executor에 요청
  .map(res -> { ... });
```
- ①은 성공했는데 ②가 실패하면 → READY 상태 좀비 Job 생성
- 에러 핸들링에서 Job 상태를 ERROR로 업데이트하는 로직 없음

## 3. 중복 클릭 문제

### 현재 방어 로직
```javascript
// DSDataDiag.vue
<v-btn :disabled="!selectedClctId || isRunning" @click="startDiag">

// isRunning computed
isRunning() {
  return this.currentJob && this.currentJob.status === 'RUNNING';
}
```

### 왜 뚫리는가?

```
T=0ms    사용자 클릭 → startDiag() 호출
T=50ms   API 응답 대기 중 (아직 isRunning = false)
T=100ms  사용자 또 클릭 → startDiag() 또 호출  ← 여기서 중복!
T=200ms  첫 번째 API 응답 → Job1 생성 (READY)
T=300ms  두 번째 API 응답 → Job2 생성 (READY)
T=1초    Job1 → RUNNING, Job2 → RUNNING (병렬 실행)
```

- `isRunning`은 **RUNNING 상태만 체크** → READY는 통과
- API 응답 오기 전에는 `currentJob`이 갱신 안 됨
- **결과: 동일 수집건에 대해 여러 진단 Job이 병렬 실행**

## 4. 개선안

### 4-1. 프론트 중복 클릭 방지 (필수)

```javascript
// 현재
<v-btn :disabled="!selectedClctId || isRunning" @click="startDiag">

// 개선: API 호출 중 상태 추가
data: { starting: false },

startDiag() {
  if (this.starting) return;
  this.starting = true;
  axios.post(...).then(res => {
    // 성공 처리
  }).catch(err => {
    // 에러 처리
  }).finally(() => {
    this.starting = false;
  });
}

<v-btn :disabled="!selectedClctId || isRunning || starting" @click="startDiag">
```
- `starting` 플래그: API 응답 올 때까지 버튼 비활성화
- `isRunning`: RUNNING 상태 동안 비활성화
- 이중 방어

### 4-2. 백엔드 중복 방지 (권장)

```java
// DiagController.startDiag() 시작 부분에 추가
// 해당 수집건에 READY/RUNNING 상태 Job이 있으면 거부
int activeCount = sqlSessionTemplate.selectOne(
    "diag.selectActiveDiagJobCount", clctId);
if (activeCount > 0) {
    result.setResultInfo(RestResult.CODE_409);
    result.setMessage("이미 진행 중인 진단이 있습니다.");
    return Mono.just(result);
}
```

### 4-3. READY 좀비 방지 (권장)

```java
// executor 호출 실패 시 Job 상태를 ERROR로 변경
return webClientHandler.postData(params)
  .map(res -> { ... })
  .onErrorResume(e -> {
      jobVo.setStatus("ERROR");
      sqlSessionTemplate.update("diag.updateDiagJobStatus", jobVo);
      result.setResultInfo(RestResult.CODE_500);
      return Mono.just(result);
  });
```

### 4-4. 우선순위

| 순위 | 개선 항목 | 난이도 | 효과 |
|---|---|---|---|
| 1 | 프론트 `starting` 플래그 | 낮음 | 중복 클릭 즉시 해결 |
| 2 | executor 호출 실패 시 ERROR 처리 | 낮음 | READY 좀비 방지 |
| 3 | 백엔드 중복 Job 체크 | 중간 | 근본적 방어 |

## 5. 결론

- **대기(READY) 상태**: q-executor 연결 실패 또는 스레드 시작 지연 시 발생. 현재 에러 핸들링 부재로 좀비 Job 가능
- **중복 클릭**: 프론트에서 API 호출~응답 사이 0.1~1초간 무방비. `starting` 플래그 하나로 해결 가능
- 가장 시급한 건 **프론트 중복 클릭 방지 (4-1)** — 코드 5줄이면 됨
