# dataQ 연구일지 개요

dataQ에 자동 표준화 기능을 붙이고, 기존 진단·구조 진단을 함께 다듬으며 거친 설계·구현·수정을 시점 단위로 정리한 문서 묶음이다. 최종 설계서가 아니라 각 시점에서 무엇을 알고 있었고, 무엇이 문제였고, 어떻게 판단했는지를 일지 형태로 남겼다. 중간에 되돌아간 구간도 나중에 다듬지 않고 당시 상태 그대로 두었다. 각 문서는 독립적으로 읽히도록 썼다.

## 문서 목록

- **dataQ 자동 표준화: 진단 결과가 멈추는 지점** (2026-03-24)
  진단 화면이 이슈를 보여주기만 하고 해결 흐름이 끊긴다는 문제 인식. 자동 표준화라는 방향이 왜 필요했는지, 그리고 "용어 등록의 체인 의존성"이라는 구조적 장벽.

- **dataQ 자동 표준화 추천 시스템 첫 설계** (2026-03-27)
  개발자가 한글 컬럼명 엑셀을 던지면 시스템이 단어/도메인까지 자동 추천하는 4단계 파이프라인 설계. 기존 용어 완전매칭 → OKT 형태소 → 단어 매칭 → 영문약어 조합 → 도메인 추천의 뼈대를 잡은 지점.

- **dataQ 자동 표준화 첫 구현과 버그들** (2026-03-30)
  첫 구현 후 테스트 22건을 돌리면서 드러난 상태 판정 버그, TB_WORD_DICT 시드 부족, 영문약어 조합의 경계 조건, 그리고 selectCoveringTokens가 OKT 결과에 과도하게 의존한다는 문제 제기.

- **dataQ 자동 표준화 단어 분리 알고리즘 전환 (greedy → DP)** (2026-03-30 ~ 2026-04-02)
  greedy longest-match로 출발했다가 반례(`테슬라코일제목`)를 만나 DP 기반 전역 최적 분리로 전환한 과정. 분량이 가장 많고, 가장 큰 방향 전환이 일어난 구간.

- **dataQ 전체 기획 및 개발 방향** (2026-04-11)
  2026-03-11 최초 커밋부터 현재까지의 개발 이력을 기획 관점으로 되짚은 문서. 각 기능 축이 걸어온 길, Phase 구분, 앞으로의 방향.

- **dataQ 표준 진단 실행 로직: READY 상태와 중복 클릭**
  표준화 진단의 "READY 상태에 멈추는 Job"과 "중복 클릭으로 Job이 두 개 생기는" 문제가 같은 뿌리에서 나왔다는 걸 추적한 기록. 상태 머신 설계 관점의 반성.
