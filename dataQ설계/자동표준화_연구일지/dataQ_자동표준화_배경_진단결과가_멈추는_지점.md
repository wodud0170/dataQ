# dataQ 자동 표준화: 진단 결과가 멈추는 지점

시점: 2026-03-24 전후

## 문제 인식

dataQ는 원래 "데이터 표준화 진단"을 돌려서 용어 미존재·한글명 불일치·타입 불일치·길이 불일치 같은 이슈를 긁어내는 도구로 출발했다. 진단 자체는 돌아갔지만, 진단 결과를 본 다음이 문제였다. 이슈 목록을 확인한 사용자가 실제로 이슈를 해결하려면 이런 경로를 거쳐야 했다.

- 용어가 없다는 이슈 → 표준사전의 용어 등록 화면으로 가서 수동 등록
- 한글명이 어긋난다는 이슈 → DB의 COMMENT를 직접 고치거나 용어를 고침
- 타입·길이가 어긋난다는 이슈 → 도메인을 고치거나 DB의 테이블을 ALTER

어느 경로든 화면 이동이 일어나고, 수동 작업이 붙고, 이슈가 수백 건이면 사실상 포기하게 된다. 진단은 돌아가는데 해결은 안 된다 — 이 단절을 해소하는 것이 이 시점 이후 작업의 출발점이었다.

## 구조적 장벽: 용어 등록의 체인 의존성

진단 결과 화면에 "용어 등록" 버튼 하나를 붙이면 끝날 것 같았는데, 그렇지 않았다. 표준사전 구조가 이렇게 되어 있었다.

```
용어(TB_TERMS) ── 참조 ──> 단어(TB_WORD) ── 참조 ──> 도메인분류
용어(TB_TERMS) ── 참조 ──> 도메인(TB_DOMAIN)
```

용어 하나를 등록하려면 그 용어를 구성하는 단어들이 TB_WORD에 먼저 있어야 하고, 단어에는 도메인분류가 붙어 있어야 한다. 용어에는 도메인(타입+길이)도 필요하다. 진단 결과에서 "이 컬럼은 용어 미존재"라는 이슈를 본 사용자가 바로 등록하려고 해도, 중간에 단어가 없으면 단어 등록 화면으로 빠져야 하고, 도메인이 없으면 도메인 등록 화면으로 또 빠져야 한다. 최악의 경우 화면 이동이 네 번 일어나고 원래 보던 진단 결과 탭으로 돌아와야 한다. 이건 UI 문제가 아니라 데이터 모델의 의존성 구조에서 오는 구조적 장벽이었다.

## 어떤 방향으로 풀 것인가

세 가지 방향을 놓고 고민했다.

1. 등록 체인 자체를 바꾼다 — 용어를 단어/도메인 없이 먼저 만들 수 있게 허용한다. 이건 표준사전의 무결성을 포기하는 거라서 기각했다. 표준사전은 일관성이 생명이다.

2. 이슈를 DB 쪽에서 해결하게 돕는다 — 진단 결과에서 "이 컬럼은 COMMENT가 어긋난다"가 보이면 그 컬럼들을 한 번에 묶어서 `COMMENT ON COLUMN ...` 스크립트를 생성해 내려주는 식. 이건 즉시 효과가 크고 구현도 가볍다. 화면 이동이 없다.

3. 등록 체인을 자동화한다 — 화면 이동을 없애는 게 아니라, 한 모달 안에서 단어 등록과 용어 등록을 연쇄로 처리한다. 여기서 결정적인 관찰은 "컬럼 영문명 `BASS_DT`는 이미 단어 약어 `BASS` + `DT`의 조합"이라는 점이었다. 언더스코어만 잘라도 필요한 단어 목록이 자동으로 나온다. 그러면 "미등록 단어를 먼저 한 번에 등록 → 그 위에서 용어 등록"이라는 흐름이 가능해진다.

결국 세 방향을 다 가기로 했다. 가장 빨리 효과가 나는 건 2번(스크립트 생성)이고, 근본은 3번(등록 체인 자동화)이다. 1번은 버린다.

## 이 시점의 초점

자동 표준화라는 단어를 쓸 때 내가 처음에 떠올린 건 좁은 의미였다 — "진단 이슈 하나를 해결하는 데 필요한 클릭 수를 줄이는 것". 이 단계에서는 아직 "개발자가 한글 컬럼명을 던지면 시스템이 영문 표준을 자동 생성한다"는 지점까지 가지 않았다. 그건 다음 단계(02)에서 한 번 더 스케일이 커진다.

그래도 이 시점에 결정된 몇 가지는 이후로도 그대로 이어진다.

- 화면 이동은 없앤다. 한 모달 안에서 연쇄 등록이 끝나야 한다.
- 영문 컬럼명을 언더스코어로 잘라 단어 후보를 뽑는 것이 1차 신호다.
- 한글 컬럼명에서 단어를 분리하는 문제가 별도로 존재한다 — 이건 1차 구현에서는 "기등록 단어 한글명으로 순서대로 자르기"라는 순진한 방법을 쓰기로 했고, 나중에 이것이 단어 분리 알고리즘 연구(04)로 이어진다.
- DB 쪽 수정은 스크립트 생성까지만 한다. dataQ는 외부 DB의 메타데이터를 읽는 위치에 있고, 쓰기 권한을 요구하지 않는다. 안전선은 여기.

## 이 시점에서 미뤄둔 것들

- 이슈 무시/예외 목록: 일부 컬럼은 의도적으로 표준과 다르다(레거시, 외부 연동). 이걸 언제까지 "이슈"로 남길 건지 규칙이 필요하지만, 신규 테이블(TB_DIAG_EXCEPTION)이 들어가야 해서 뒤로 미뤘다.
- 표준사전 측 수정 경로: 이슈를 "DB를 표준에 맞춘다"가 아니라 "표준을 현재 DB에 맞춘다"로 해결하는 경로. 용어·도메인 수정 모달을 진단 결과에서 바로 여는 형태인데, 이것도 연동이 복잡해서 미뤘다.
- 재진단 원클릭: COMMENT 수정 후 빠르게 확인하는 용도. 재수집이 필요한 경우와 그렇지 않은 경우를 안내해야 해서 UI 메시지가 조심스럽다.

## 다음 일지로 넘어가는 지점

여기까지는 "진단 → 해결" 사이를 이어붙이는 얘기였다. 그런데 이 작업을 하면서 한 가지 깨달음이 왔다. 진단 결과에서 이슈를 하나씩 해결하게 돕는 것도 의미가 있지만, 애초에 **개발자가 테이블을 만들기 전에** 한글 컬럼명을 넣으면 시스템이 표준 용어·영문약어·도메인까지 자동으로 뽑아주면 훨씬 낫다는 것. 이슈가 생긴 다음에 고치는 게 아니라 이슈가 생기기 전에 예방하는 쪽. 그 방향이 다음 일지(02)에서 구체화된다.
