## 0. 핵심 요약 (한 페이지)

### 상태 머신
```
[DRAFT]  ──저장──→  [DRAFT]  ──신청──→  [SUBMITTED]  ──승인──→  [APPROVED]
                                            │
                                            ├─반려──→  [REJECTED] (종속 자식 cascade REJECTED)
```
- **DRAFT**: 사용자가 저장은 했지만 아직 관리자에게 신청 안 함. 본인만 보임.
- **SUBMITTED**: 사용자가 [신청] 눌러서 관리자 승인 대기. 본인 + 관리자만 보임.
- **APPROVED**: 승인됨. 전체 사용자 노출.
- **REJECTED**: 반려됨. 본인 + 관리자만 보임 (사유 포함).

### 3단계 사용자 흐름
1. **변경** — 그리드 인라인 편집 (메모리)
2. **저장** — DB 에 DRAFT 로 저장. 본인 화면에선 보임 (노란색)
3. **신청** — DRAFT 들을 묶음으로 관리자에게 일괄 제출 → SUBMITTED. 신청 모달에서 항목 선택 / 롤백 가능

### 관리자 승인 화면
- 신청 묶음 (submission) 단위로 표시
- 묶음 안의 각 항목 체크박스 — 개별 승인/반려, 또는 일괄
- 컬럼 반려 시 그 컬럼에 종속된 PENDING PK/FK 자동 cascade 반려 (확인 모달)
- 승인 직후 DB ALTER 자동 출력 → [복사] / [DB 반영] / [모델 승인만, 나중에]

### Tier (변경 분류)
- **Tier 1**: schema 영향 변경 → 사용자는 DRAFT/SUBMITTED 거침. 관리자는 즉시 APPROVED
- **Tier 1.5**: 컬럼 순서 → 사용자 UI 자체 차단. 관리자만 위/아래 화살표로 즉시 반영
- **Tier 2**: 한글명/설명 등 메타 → 모두 즉시 + 이력만

### 핵심 정책
- 사용자는 승인 없이 schema 변경 못함
- 모든 외부 노출 = APPROVED 만
- DB DDL 반영 = APPROVED 만, 관리자만 실행
- 중복 체크: DRAFT/SUBMITTED 끼리는 배제, 승인 시점에 재검증
- 반려 cascade: 부모 반려 시 종속 자식 자동 REJECTED

### 테이블 메타 확장 (§15)
- **TABLESPACE_NM** (물리) — DDL `TABLESPACE xxx` 절 자동
- **BIZ_AREA** 업무영역 (논리, 연한 그린 헤더) + **SUBJ_AREA** 주제영역 (물리, 연한 인디고 헤더)
- 동기: 업무영역별 ERD 자동 출력 (차후) — 본 설계는 분류 인프라까지

## 1. 배경 / 문제

현재 DataQ 는 **데이터 모델 변경이 즉시 반영**되는 구조:
- 사용자가 컬럼 추가 → 즉시 다른 사용자에게 노출
- 영문명 변경 → 즉시 INDEX / CONSTRAINT cascade
- 잘못된 변경의 회복 비용 큼

운영 환경에서 요구되는 거버넌스:
1. **변경 승인** — 관리자만 schema 영향 변경 승인
2. **변경 이력** — 누가 언제 무엇을 어떻게 바꿨는지 추적
3. **DB 직접 반영** — 모델 변경을 DBA 손 거치지 않고 DataQ 가 ALTER 실행 (관리자 only)

세 항목은 권한·가시성·실행 매커니즘 공유 — 따로 가면 충돌·중복 다발.
**한 사이클로 묶어 진행**한다.

## 2. 변경 분류 (Tier) — 가장 중요한 결정

모든 변경에 승인 걸면 생산성 마비. 변경의 위험도 / DDL 영향에 따라 3-tier 로 분리.

### Tier 1 — 강제 승인 (사용자 → PENDING → 관리자 승인 / 관리자 본인은 즉시 APPROVED)

DBMS 에 ALTER 가 실제 발생하거나, 진단 / 다른 사용자에게 영향 큰 변경:

- **테이블**: 추가, 삭제, 영문명(OBJ_NM) 변경, **OBJ_OWNER 변경** (실제 ALTER ... SET SCHEMA)
- **컬럼**: 추가, 삭제, 영문명(ATTR_NM) 변경, 데이터 타입 변경, 길이/소수점 변경, NULLABLE 변경, **DEFAULT_VAL 변경**
- **FK 논리 매핑** (FK_PARENT_OBJ_NM/ATTR_NM)
- **PK / FK**: 추가, 삭제
- **인덱스**: 추가, 삭제
- **제약조건**: 추가, 삭제, 수정

→ 사용자 변경 시 `APRV_STATUS='PENDING'`. 본인만 보임 + 노란 시각 표시. 관리자 승인 후 'APPROVED' 로 전 사용자 노출.
→ **관리자 본인이 변경 시 즉시 'APPROVED'** — PENDING 단계 거치지 않음.

### Tier 1.5 — 사용자 UI 자체 차단 + 관리자만 즉시 반영 (신설, 2026-05-14)

사용자 권한으로는 행위 자체를 막아야 하는 변경. 즉, 사용자에겐 UI 가 안 보이거나 비활성.

- **컬럼 순서 (ATTR_ORD)** — DBMS 영향 없음. 모델 표시 일관성에 영향이라 관리자만 다룸. 사용자에겐 ↑↓ 화살표 자체가 안 보임.

→ 관리자가 즉시 반영. 사용자에겐 UI 노출 자체 차단. 이력 INSERT (Tier 1.5 표기).

#### 위/아래 화살표 UX (관리자만)
- 각 컬럼 row 의 액션 영역에 ↑ / ↓ 아이콘 (관리자만 노출, 사용자에겐 비표시)
- ↑ 클릭 → 위 행과 attrOrder 스왑 + 이력 INSERT + 즉시 반영
- ↓ 동일
- 첫 행 ↑ disabled / 마지막 행 ↓ disabled
- "현재 출력 순서로 컬럼 순서 지정" 버튼도 관리자 only

#### 왜 OBJ_OWNER / DEFAULT_VAL 은 Tier 1.5 가 아닌가? (2026-05-14 결정)
- 사용자도 변경 신청 가능해야 함 (단, 승인 필요)
- 실제 ALTER 가 발생하니 schema 영향 변경 → Tier 1 (사용자 → PENDING → 관리자 승인) 으로 분류

#### 컬럼 순서 변경 — 위/아래 화살표 UX
- 각 컬럼 행에 ↑ / ↓ 아이콘 표시 (관리자만 보임)
- ↑ 누르면 위 행과 attrOrder 스왑 (`swapAttrOrd(currentSeq, currentSeq-1)`)
- ↓ 누르면 아래 행과 스왑
- 첫 행 ↑ 비활성, 마지막 행 ↓ 비활성
- 변경 즉시 반영 (PENDING 없음) + 이력 INSERT
- 기존 "현재 출력 순서로 컬럼 순서 지정" 버튼도 관리자 only 로 제한

### Tier 2 — 자유 편집 + 이력 기록 (즉시 반영, 모든 사용자)

DBMS 영향 없고 메타데이터 성격 강한 변경:

- **테이블 한글명** (OBJ_NM_KR)
- **테이블 설명** (OBJ_DESC)
- **컬럼 한글명** (ATTR_NM_KR) — 검색·진단에 영향이지만 표준 플래그 자동 재계산이라 안전
- **컬럼 설명 / 코멘트** (ATTR_COMMENT)
- **표준 플래그** (TERMS_STND_YN, DOMAIN_STND_YN) — 자동 계산

→ 즉시 반영. `TB_DATA_MODEL_CHANGE_HISTORY` 에 이력만 기록.

### Tier 3 — 세션 / UI 상태 (이력 없음)

- 그리드 필터 / 정렬 / 페이지 위치
- 즐겨찾기 / 최근 본 모델
- 사용자 화면 설정

→ 로컬 스토리지 또는 사용자 환경 테이블. 거버넌스 대상 외.

### 🔸 결정된 경계 케이스 (2026-05-14 — 사용자 정책 확정)

| 변경 | 분류 | 사용자 | 관리자 |
|---|---|---|---|
| OBJ_OWNER 변경 | **Tier 1** | 가능 (PENDING) | 즉시 APPROVED |
| 컬럼 DEFAULT_VAL | **Tier 1** | 가능 (PENDING) | 즉시 APPROVED |
| 컬럼 한글명 | Tier 2 | 즉시 + 이력 | 즉시 + 이력 |
| FK_PARENT_OBJ_NM/ATTR_NM | **Tier 1** | 가능 (PENDING) | 즉시 APPROVED |
| **컬럼 순서 (ATTR_ORD)** | **Tier 1.5** | **UI 차단** | 즉시 (위/아래 화살표) |

핵심 원칙: **사용자는 승인 없이 할 수 있는 변경이 없다** (Tier 2 메타데이터만 자유).
**관리자는 모든 변경을 즉시 반영 + 승인 받을 일 없음.**

## 4. 스키마 변경

### 4.1 5개 모델 테이블에 거버넌스 컬럼 추가

대상 테이블:
- `TB_DATA_MODEL`
- `TB_DATA_MODEL_OBJ`
- `TB_DATA_MODEL_ATTR`
- `TB_DATA_MODEL_INDEX`
- `TB_DATA_MODEL_CONSTRAINT`

각 테이블에 공통 추가:
```sql
APRV_STATUS         VARCHAR(20) DEFAULT 'APPROVED'   -- PENDING / APPROVED / REJECTED
REQUESTER_USER_ID   VARCHAR(50)
REQ_DT              VARCHAR(14)
APRV_USER_ID        VARCHAR(50)
APRV_DT             VARCHAR(14)
APRV_COMMENT        VARCHAR(500)
```

**기존 row 마이그레이션**: 일괄 `APRV_STATUS='APPROVED'`, `APRV_USER_ID='system'`, `APRV_DT=now()` — 시스템 도입 이전 데이터 호환.

### 4.2 변경 이력 테이블 (신규)

```sql
CREATE TABLE TB_DATA_MODEL_CHANGE_HISTORY (
  CHANGE_SEQ           BIGSERIAL PRIMARY KEY,
  DM_ID                VARCHAR(40)  NOT NULL,
  CHANGE_DT            VARCHAR(14)  NOT NULL,
  CHANGE_USER_ID       VARCHAR(50)  NOT NULL,
  CHANGE_TYPE          VARCHAR(30)  NOT NULL,   -- ADD_OBJ, DEL_OBJ, RENAME_OBJ, ADD_ATTR, DEL_ATTR, MODIFY_ATTR_TYPE, ADD_INDEX, ...
  CHANGE_TIER          VARCHAR(10)  NOT NULL,   -- TIER1 / TIER2
  OBJ_OWNER            VARCHAR(100),
  OBJ_NM               VARCHAR(200),
  ATTR_NM              VARCHAR(200),
  CONSTRAINT_NM        VARCHAR(200),
  INDEX_NM             VARCHAR(200),
  BEFORE_JSON          TEXT,         -- 변경 전 스냅샷
  AFTER_JSON           TEXT,         -- 변경 후 스냅샷
  DDL_SNIPPET          TEXT,         -- 재실행용 ALTER 문 (Tier 1 만)
  APRV_STATUS          VARCHAR(20),  -- TB_DATA_MODEL_* 의 APRV_STATUS 와 동기화
  APRV_USER_ID         VARCHAR(50),
  APRV_DT              VARCHAR(14),
  APRV_COMMENT         VARCHAR(500),
  DDL_EXEC_DT          VARCHAR(14),  -- 실제 DB ALTER 실행 시각 (NULL = 미실행)
  DDL_EXEC_USER_ID     VARCHAR(50),
  DDL_EXEC_RESULT      VARCHAR(20),  -- SUCCESS / FAILED / SKIPPED / NO_PRIVILEGE
  DDL_EXEC_MESSAGE     VARCHAR(2000)
);
CREATE INDEX ON TB_DATA_MODEL_CHANGE_HISTORY (DM_ID, CHANGE_DT DESC);
CREATE INDEX ON TB_DATA_MODEL_CHANGE_HISTORY (CHANGE_USER_ID);
CREATE INDEX ON TB_DATA_MODEL_CHANGE_HISTORY (APRV_STATUS);
```

### 4.3 DDL 실행 이력 (선택, 별도 OR 위 테이블에 통합)

위 테이블의 `DDL_EXEC_*` 컬럼으로 통합 권장 — 별도 테이블 만들면 JOIN 부담.

## 5. 가시성 필터 (가장 위험한 부분)

### 5.1 매퍼 일괄 패치
모든 SELECT 매퍼에 다음 WHERE 추가:
```sql
AND (APRV_STATUS = 'APPROVED' OR REQUESTER_USER_ID = #{currentUserId})
```

관리자는 우회:
```sql
<if test="!isAdmin">
  AND (APRV_STATUS = 'APPROVED' OR REQUESTER_USER_ID = #{currentUserId})
</if>
```

### 5.2 영향 매퍼 카운트 (대략)
- `datamodel.xml` — 50+ 매퍼
- `diagTarget.xml`, `structdiag.xml` — 10+ 매퍼
- `diag.xml` (표준 진단) — 5+ 매퍼

### 5.3 진단 / 통계 제외
- 표준 진단 / 구조 변경 진단 / 대시보드 카운트 → **APPROVED 만**
- `WHERE APRV_STATUS = 'APPROVED'` 강제 (사용자 본인 PENDING 도 제외)

### 5.4 회귀 위험
누락 시 사고: 다른 사용자의 PENDING row 가 노출됨. 회귀 테스트 필수.

### 6.1 Tier 1 변경 흐름 (예: saveAttrs 의 ADD 모드)

```java
boolean immediate = sessionService.isAdmin() && body.get("forceImmediate") != null;
String aprvStatus = immediate ? "APPROVED" : "PENDING";

vo.setAprvStatus(aprvStatus);

if (immediate) {
    vo.setAprvUserId(currentUserId);

session.insert("insertDataModelAttr", vo);

insertChangeHistory(session, "ADD_ATTR", "TIER1", vo, ddlSnippet);
```

```java
session.update("updateDataModelAttrMeta", vo);  // 즉시 반영
```

## 7. UI 정책

### 7.1 시각 표시 통일안

| 상태 | 색상 | 의미 |
|---|---|---|
| APPROVED | 흰색 / 기본 | 정상 |
| 본인 PENDING | 노란색 (FFF8E1) | 본인이 신청한 미승인 |
| REJECTED | 빨간색 (FFEBEE) | 반려 |
| dirty (편집 중, 미저장) | 회색 옅음 (F5F5F5) | 입력 중 |

dirty 와 PENDING 은 다른 색이어야 사용자 혼란 방지.

### 7.2 변경 후 안내
- Tier 1 변경 저장 직후 swal:
  > "변경 요청이 접수되었습니다. 관리자 승인 후 반영됩니다.
  > [내 변경 요청 현황 보기]"

### 7.3 컬럼 순서 변경 UX (관리자만)
- 각 컬럼 row 의 액션 영역에 ↑ / ↓ 아이콘 (관리자만 노출, 일반 사용자에겐 비표시)
- ↑ 클릭 → 위 행과 attrOrder 스왑 + 이력 INSERT + 즉시 반영
- ↓ 클릭 → 아래 행과 스왑 동일
- 비활성 조건:
  - 첫 행 (attr_ord 가 최소) → ↑ disabled
  - 마지막 행 (attr_ord 가 최대) → ↓ disabled
  - 페이지 전환 시점에는 같은 페이지 안에서만 스왑 (또는 전체 정렬 기준으로 스왑)
- 신규 endpoint `POST /api/dm/swapAttrOrd` — `{dataModelId, objOwner, objNm, attrNm, direction: 'UP' | 'DOWN'}`
- 기존 "현재 출력 순서로 컬럼 순서 지정" 버튼도 관리자 only 로 disabled

### 7.4 신규 화면 / 탭

#### A. 사용자 — "내 변경 요청 현황"
- 본인 PENDING / REJECTED row 목록
- 상태별 필터 / 모델별 필터
- 반려 사유 표시

## 8. DB 직접 반영 (87-18)

### 8.1 흐름
1. 관리자가 변경 이력 (또는 진단 결과) 에서 [DB 반영] 클릭
2. dry-run 미리보기 — 실행될 ALTER 문 표시
3. 사용자 confirm → 실행
4. dsId 로 DBHandler 획득 → DBMS dialect 분기 (Oracle / PG / MySQL)
5. ALTER 실행 → 권한 에러 / 문법 에러 / 성공 분기
6. 결과를 `DDL_EXEC_*` 컬럼에 기록

### 8.2 권한 에러 메시지 변환
DBMS 별 에러 코드 / 메시지 매핑:
| DBMS | 권한 에러 코드 | 메시지 변환 |
|---|---|---|
| Oracle | ORA-01031 (insufficient privileges) | "권한 없음 — DBA 에 ALTER 권한 요청 필요" |
| PostgreSQL | 42501 (insufficient_privilege) | "권한 없음 — owner / DBA 에 권한 요청" |
| MySQL | 1142 (ER_TABLEACCESS_DENIED_ERROR) | "권한 없음 — GRANT ALTER 필요" |
| MSSQL | 262 | "권한 없음" |

### 8.3 idempotency / 재시도
- 같은 이력의 DDL 을 두 번 실행 못 하도록 가드 (DDL_EXEC_DT IS NULL 인 것만 실행 가능)
- 실패 시 명시적 [재실행] 으로 재시도 (DDL_EXEC_RESULT='FAILED' 인 것 한정)

### 8.4 트랜잭션
- 가능한 DBMS (PG / MSSQL) — 다중 ALTER 한 트랜잭션
- 불가능한 DBMS (Oracle / MySQL — DDL 자동 commit) — 건별 try/catch + 결과 누적

## 12. 중복 체크 정책 (2026-05-14 정정)

### 12.1 정책 단순화 결정
당초 안: PENDING 끼리 중복 허용 + 승인 시점 재검증.
**최종 안 (PK 재설계 회피)**: 기존 PK `(dm_id, obj_owner, obj_nm)` 그대로 두고, 어떤 상태든 같은 이름 row 는 하나만 존재. 먼저 등록한 사람이 우선.

### 12.2 흐름
#### 변경 신청 시점 (사용자)
1. 새 컬럼 `EMAIL` 신청 → 같은 모델 안 같은 이름의 row (어떤 상태든) 존재 검사
2. 존재 시 안내:
   > "이미 같은 이름이 등록 중입니다.
   > 데이터 모델 변경 승인 메뉴에서 확인하세요."
3. 사용자는 본인의 DRAFT 면 그 위에 편집 / 본인의 SUBMITTED 면 신청 회수 후 재편집 / 타인의 것은 대기

#### 승인 시점 (관리자)
1. PENDING `EMAIL` 승인 → APPROVED 로 status 전환만 (이름 변경 X, row 그대로)
2. 재검증 불필요 (애초에 중복 불가)

### 12.3 PK 충돌 회피 방식
- 같은 모델 안 (dm_id, obj_owner, obj_nm) PK 는 어떤 상태든 unique
- 사용자 A 가 EMAIL 신청 후 SUBMITTED 면 다른 누구도 같은 이름 신청 불가
- 사용자 A 가 신청 회수 (DRAFT 삭제) 후 사용자 B 가 신청 가능

### 12.4 효과
- DB 단 unique 강제 (기존 PK 그대로) — partial unique index 불필요
- "이미 등록 중" 안내가 명확
- 관리자 화면에서 중복 정리 액션 (반려) 으로 다른 사용자 차례 열어줄 수 있음
- 트랜잭션 격리 — PK INSERT 충돌은 DB 가 자동 처리, application 은 SQLException 잡아서 안내 메시지 변환

### 12.5 차후 검토 (V2)
- 만약 PENDING 끼리 중복 허용이 절실하면 (사용자 동시성 충돌 빈번 시) PK 재설계 검토:
  - 옵션 A: aprv_status 를 PK 의 일부로 — 기존 FK·매퍼 영향 큼
  - 옵션 B: PENDING 전용 shadow 테이블 — 코드 분기 증가
  - V1 결과 보고 결정

## 13. 반려 cascade 정책 (2026-05-14 정정)

### 13.1 원칙 — PENDING 끼리 참조는 허용, 반려 시 cascade 정리
- 사용자가 같은 묶음 안에서 "컬럼 추가 + 그 컬럼으로 PK 생성" 같은 종속 변경을 한 번에 신청 가능
- 단, 부모가 반려되면 종속 자식도 자동 cascade 정리

### 13.2 cascade 케이스

| 부모 반려 | 자식 cascade 동작 |
|---|---|
| 컬럼 추가 반려 | 그 컬럼을 사용하는 PENDING PK / FK / INDEX / CONSTRAINT 자동 REJECTED |
| 테이블 추가 반려 | 그 테이블에 속한 PENDING 컬럼 전부 REJECTED + 종속 PK/FK 등 cascade |
| 참조 부모 컬럼 반려 (FK 의 대상 컬럼) | FK 자체 REJECTED — 참조가 불가능해진 상태 |

### 13.3 cascade 알림
- 관리자가 컬럼 반려 시점에 **종속 PENDING 자식 목록을 모달로 보여줌**
- "이 컬럼을 반려하면 아래 PK / FK / INDEX 신청도 함께 반려됩니다. 진행?"
- 확인 시 일괄 REJECTED + 이력 기록

### 13.4 APPROVED 후의 DB 반영
- APPROVED 가 된 컬럼 / PK / FK 등은 DB ALTER 실행 시 함께 묶임
- DDL 반영에는 APPROVED row 만 포함 (PENDING / REJECTED 절대 제외)
- 이건 가시성 필터 (§5) 가 이미 보장

### 13.5 사용자 간 격리
- 사용자 A 의 PENDING 컬럼은 사용자 B 의 PENDING PK 가 참조할 수 없음 (서로 안 보이므로)
- 자신의 PENDING 끼리만 종속 참조 허용

## 14. 묶음 신청 흐름 (DRAFT → SUBMITTED → APPROVED, 2026-05-14)

### 14.1 상태 정의
| 상태 | 의미 | 가시성 |
|---|---|---|
| DRAFT | 저장됨, 신청 전 | 본인만 |
| SUBMITTED | 신청됨, 관리자 대기 | 본인 + 관리자 |
| APPROVED | 승인됨 | 전 사용자 |
| REJECTED | 반려됨 | 본인 + 관리자 |

### 14.2 사용자 흐름

#### 1단계 — 변경 (메모리)
- 그리드 인라인 편집, newRows / dirty 등 기존 동작 그대로
- 아직 DB 저장 안 됨, 새로고침하면 사라짐

#### 2단계 — 저장 ([저장] 버튼)
- 변경 내역이 DB 에 `APRV_STATUS='DRAFT'` 로 저장
- 다른 사용자에겐 안 보임
- 본인 화면에선 **노란 배경 (DRAFT)** 으로 표시
- 다른 작업 (다른 모델 보기, 로그아웃 등) 해도 보존됨

#### 3단계 — 신청 ([신청] 버튼)
- 사용자 본인의 DRAFT 들이 모달로 펼쳐짐 — "내 신청 대기 변경 목록"
- 모달 안에서 항목 선택:
  - [신청할 항목 체크] 다중 선택
  - [개별 롤백] — 그 변경만 취소 (DB 에서 DRAFT row 삭제 / cascade)
  - [개별 편집] — 그 변경 다시 편집 (그리드로 이동)
- [선택 신청] 버튼 → 선택된 DRAFT 들이 일괄 `APRV_STATUS='SUBMITTED'` 로 전환
- 한 묶음 = `SUBMISSION_ID` 로 그룹화 (관리자가 묶음 단위로 검토)

### 14.3 신청 모달 UI 예시
```
┌────────────────────────────────────────────────┐
│ 내 변경 신청 — 저장됨 8건                       │
├────────────────────────────────────────────────┤
│ ☑ TB_MEMBER에 컬럼 추가 — PHONE_2 (VARCHAR 20) │
│ ☑ TB_MEMBER에 컬럼 추가 — ADDR_2  (VARCHAR 100)│
│ ☑ PK 생성 — TB_MEMBER.MBR_NO                    │
│ ☐ TB_ORDER 한글명 변경 — 주문 → 주문서          │
│ ☑ TB_ORDER.ORD_DT 타입 변경 — VARCHAR → DATE   │
│ ... 외 3건                                      │
│                                                │
│ [선택 신청 (4건)]    [선택 롤백]    [닫기]      │
└────────────────────────────────────────────────┘
```

### 14.4 관리자 흐름

#### 승인 화면
- 신청 묶음 (submission) 별로 펼침
- 묶음 헤더: 신청자 / 신청 시각 / 모델 / 항목 수
- 항목별 체크박스 + 변경 전/후 diff
- 액션:
  - [선택 승인] — 체크한 항목만 APPROVED
  - [선택 반려] — 체크한 항목만 REJECTED + 사유 입력
  - [묶음 일괄 승인] / [묶음 일괄 반려]
- 항목 일부만 승인하고 나머지는 반려 가능 (부분 처리)

#### 부분 처리 시 cascade
- 컬럼 추가 반려 + 그 컬럼으로 만든 PK 신청은 자동 cascade 반려
- 관리자가 컬럼만 반려해도 시스템이 자동으로 종속 자식 정리

### 14.5 DRAFT 의 가시성 / 편집
- 사용자 본인 컬럼 화면에선 DRAFT row 가 노란 배경으로 표시
- DRAFT 위에 추가 편집 가능 (영문명 / 타입 등 다시 수정)
- 편집 결과는 그 DRAFT 를 in-place update
- DRAFT 를 신청 전에 통째로 롤백하면 DB row 삭제 + 종속 DRAFT 도 cascade 삭제

### 14.6 스키마 영향
- `TB_DATA_MODEL_*` 의 `APRV_STATUS` enum 에 `DRAFT` 추가 → 'DRAFT' / 'SUBMITTED' / 'APPROVED' / 'REJECTED'
- 신청 묶음 식별용 `SUBMISSION_ID` (UUID) 컬럼 추가 — DRAFT 일 땐 NULL, 신청 시점에 일괄 부여
- 이력 테이블에도 SUBMISSION_ID 전파

### 14.7 효과 / 장점
- **응집성** — 사용자가 여러 변경을 한 작업 단위로 묶어 신청
- **자율성** — 신청 전엔 자유롭게 편집 / 롤백 / 일부만 선택 신청
- **관리자 효율** — 묶음 단위로 검토. 컨텍스트 (왜 이 변경이 한꺼번에 들어왔는지) 이해 쉬움
- **부분 승인 가능** — 묶음의 일부만 통과시키고 나머지는 반려 가능

### 14.8 비용 / 복잡도
- 상태 4단계 (DRAFT/SUBMITTED/APPROVED/REJECTED) — 단순 2단계 (PENDING/APPROVED) 보다 분기 늘어남
- 신청 모달 UI 신규
- DRAFT 위에 편집 / 롤백 / cascade 정리 — 추가 endpoint 들
- 관리자 화면 — 묶음 / 항목 2단계 표시

## 15. 테이블 메타데이터 확장 — 테이블스페이스 + 업무/주제 영역 (2026-05-14)

### 15.1 추가 요구
- **TABLESPACE_NM** — 테이블이 생성될 DBMS 의 테이블스페이스. 선택값 (NULL 허용). DDL 출력 시 `TABLESPACE xxx` 절 포함. **물리 분류**.
- **업무영역 (BIZ_AREA)** — 테이블을 **논리** 업무 단위로 묶는 분류. 예: 회원관리 / 주문 / 결제 / 상품. 사용자 관점의 그룹.
- **주제영역 (SUBJ_AREA)** — 테이블을 **물리** 단위로 묶는 분류. DBMS 의 스토리지 / 백업 / 파티션 정책 등 물리 운영 관점.

### 15.1.1 동기 (왜 두 영역이 필요한가)
사용자 의도: **업무영역별로 ERD 자동 출력** (출력 전용, 편집 X).
- 회원관리 업무영역 선택 → 그 영역에 속한 테이블만 모아 ERD 다이어그램 생성
- 주제영역 (물리) 도 같은 패턴 — 운영 관점의 그룹별 ERD 조회 가능
- ERD 는 별도 차후 과제 — 본 설계는 분류 인프라까지만

### 15.2 논리/물리 영역 — 헤더 색 구분 (UI 정책)
기존 컬럼 그리드 헤더 컬러 정책 (`hdr-logical` 연한 그린 / `hdr-physical` 연한 인디고) 을 본 두 분류에도 적용:

| 분류 | 헤더 색 | 클래스 |
|---|---|---|
| **업무영역** (BIZ_AREA) | 연한 그린 (#E8F5E9) | `hdr-logical` |
| **주제영역** (SUBJ_AREA) | 연한 인디고 (#E3F2FD) | `hdr-physical` |
| **테이블스페이스** (TABLESPACE_NM) | 연한 인디고 (#E3F2FD) | `hdr-physical` |

테이블 목록 / 등록 모달 / 컬럼 그리드 모두 동일 색 정책 일관 적용.

### 15.5 Tier 분류 (15.x 신규 항목)
| 변경 | Tier | 사유 |
|---|---|---|
| 테이블의 TABLESPACE_NM 변경 | **Tier 1** | DBMS 의 ALTER TABLE ... MOVE TABLESPACE 발생 |
| 테이블의 SUBJ_AREA_ID 변경 (물리 분류) | **Tier 1** | 물리 운영 정책 영향 |
| 테이블의 BIZ_AREA_ID 변경 (논리 분류) | Tier 2 | 단순 분류 메타, DBMS 영향 없음 |
| 업무영역 자체 생성/수정/삭제 | Tier 1 (관리자만) | 분류 체계는 운영 정책 |
| 주제영역 자체 생성/수정/삭제 | Tier 1 (관리자만) | 물리 분류 체계 |

### 15.5 DDL 출력 시 TABLESPACE 반영
```sql
CREATE TABLE TB_MEMBER (
  MBR_NO VARCHAR(20) NOT NULL,
  ...
) TABLESPACE TS_MEMBER;    -- 추가됨 (NULL 이면 절 생략)
```

DBMS dialect 별:
- Oracle: `TABLESPACE xxx` (그대로)
- PostgreSQL: `TABLESPACE xxx` (지원)
- MySQL: `TABLESPACE xxx` (InnoDB 한정, 다른 엔진은 생략)
- SQL Server: `ON [filegroup]` (다른 키워드)
- 미지원 DBMS 면 절 생략 + 다운로드 시 경고

### 15.6 업무영역 조회 화면
- `데이터 모델 > 업무영역` 신규 메뉴 (관리자만 편집 가능, 사용자는 조회만)

- 테이블 화면에 "업무영역" 컬럼 필터 추가
- 업무영역 신규 등록 / 수정 / 삭제 — 관리자 only (#87-19 의 Tier 1 관리자 즉시 적용)
