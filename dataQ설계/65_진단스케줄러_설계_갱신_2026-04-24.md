## 2. 확정해서 가는 사항

### 2-1. 스코프 (이번 설계 범위)

**포함**:
- 표준화 진단 스케줄링 (STANDARD)
- 구조 변경 진단 스케줄링 (STRUCT)
- 둘 다 (BOTH — 표준화 선행 → 구조변경 순차)
- SIMPLE 주기(매일/매주/매월) + CRON 표현식 선택지
- 즉시 실행(RunNow) — 테스트용
- 실행 이력 조회
- 활성/비활성 토글

**제외 (스코프 아웃 확정)**:
- **수집 (Collection) — 스케줄 대상 아님.** 수집은 별도 경로 유지. 스케줄러는 진단만 수행
- 이메일/Slack 알림
- 스케줄 간 의존성 (A 끝나면 B)
- missed job catch-up
- 스케줄 시각화 캘린더 뷰
- 여러 데이터모델 묶음 실행

### 2-2. 스케줄러 위치

**q-executor 에서 주기 평가(@Scheduled) + 자체 내부에서 진단 로직 호출** (36번 원안 유지 / 2026-04-24 사용자 확정).

이유:
- q-executor 가 프로젝트의 **배치/백그라운드 실행 담당**. 수집/진단/표준변환 등 장시간 작업은 이 쪽에서 실행됨. 스케줄러도 같은 성격이라 q-executor 가 맞음
- 진단 서비스(`DiagService`, `StructDiagService`) 의 **실체가 q-executor 내부**. 스케줄러가 같은 모듈에 있으면 HTTP 왕복 없이 직접 호출 가능
- 기존 수동 실행 경로(`q-center DiagController` → WebClient → `q-executor /startDiag`) 는 관리자 UI 전용. 스케줄 자동 실행은 그 경로를 우회해 q-executor 내부 호출로 단순화
- q-center 에는 @Scheduled 로 UI/WebSocket heartbeat 정도만 남겨둠. 도메인 배치는 q-executor

**인프라 준비**:
- q-executor 의 `QualityExecutorApplication` 클래스에 **`@EnableScheduling` 을 추가**해야 함 (현재 q-center 에만 있음)

**원자성 이슈**: 현재는 q-executor 단일 인스턴스. 멀티 노드 운영 시 DB-based lock 또는 리더 선출 필요 — 이번 설계는 단일 노드 전제.

## 3. DB 스키마 (36번 기본 + 보강)

### 3-1. TB_DIAG_SCHEDULE — 스케줄 정의

```sql
CREATE TABLE TB_DIAG_SCHEDULE (
    SCHEDULE_ID         VARCHAR(40)  NOT NULL,
    SCHEDULE_NM         VARCHAR(200) NOT NULL,
    DIAG_TYPE           VARCHAR(20)  NOT NULL,    -- STANDARD | STRUCT | BOTH
    DATA_MODEL_ID       VARCHAR(40)  NOT NULL,    -- 대상 모델 (필수)

    SCHEDULE_TYPE       VARCHAR(20)  DEFAULT 'SIMPLE',  -- SIMPLE | CRON
    REPEAT_CYCLE        VARCHAR(20),                   -- DAILY | WEEKLY | MONTHLY
    REPEAT_TIME         VARCHAR(5),                    -- "HH:mm"
    REPEAT_DAY_OF_WEEK  INTEGER,                       -- 1(월)~7(일)
    REPEAT_DAY_OF_MONTH INTEGER,                       -- 1~28
    CRON_EXPR           VARCHAR(100),                  -- SCHEDULE_TYPE='CRON' 시

    USE_YN              CHAR(1)      DEFAULT 'Y',      -- 활성화
    LAST_EXEC_DT        TIMESTAMP,
    LAST_EXEC_STATUS    VARCHAR(20),                   -- DONE | ERROR | SKIPPED
    LAST_EXEC_LOG_ID    VARCHAR(40),                   -- 최근 실행 LOG 링크 (빠른 조회)

    CRET_USER_ID        VARCHAR(40),
    CRET_DT             TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    UPDT_USER_ID        VARCHAR(40),
    UPDT_DT             TIMESTAMP,
    CONSTRAINT PK_TB_DIAG_SCHEDULE PRIMARY KEY (SCHEDULE_ID)
);

CREATE INDEX IX_DIAG_SCHEDULE_ACTIVE
    ON TB_DIAG_SCHEDULE (USE_YN, DATA_MODEL_ID);
```

### 3-2. TB_DIAG_SCHEDULE_LOG — 실행 이력

```sql
CREATE TABLE TB_DIAG_SCHEDULE_LOG (
    LOG_ID          VARCHAR(40)  NOT NULL,
    SCHEDULE_ID     VARCHAR(40)  NOT NULL,
    EXEC_DT         TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,  -- 트리거 시각
    EXEC_END_DT     TIMESTAMP,                               -- 완료 시각
    EXEC_STATUS     VARCHAR(20),   -- RUNNING | DONE | ERROR | SKIPPED
    TRIGGER_TYPE    VARCHAR(20),   -- AUTO | MANUAL (runNow)
    DIAG_TYPE       VARCHAR(20),   -- 실행된 진단 유형 (BOTH 인 경우 2건 기록)
    DIAG_JOB_ID     VARCHAR(40),   -- STANDARD 일 때 TB_DIAG_JOB 참조
    STRUCT_DIAG_ID  VARCHAR(40),   -- STRUCT 일 때 TB_STRUCT_DIAG_HISTORY 참조
    SCHEDULE_NM_SNAPSHOT VARCHAR(200),  -- 실행 당시 스케줄명 스냅샷 (원 스케줄 삭제돼도 이력에서 조회 가능)
    ERROR_MSG       VARCHAR(2000),   -- 실패 원인 상세 (사용자에게 표시됨, 재시도 없으므로 로그 품질이 중요)
    EXEC_DURATION_SEC INTEGER,
    CONSTRAINT PK_TB_DIAG_SCHEDULE_LOG PRIMARY KEY (LOG_ID)
);

CREATE INDEX IX_DIAG_SCHEDULE_LOG_SCHEDULE
    ON TB_DIAG_SCHEDULE_LOG (SCHEDULE_ID, EXEC_DT DESC);
```

## 4. 스케줄 평가 엔진

### 4-1. 트리거

```java
// q-executor: DiagSchedulerRunner (신규)
//   위치: q-executor/src/main/java/qualityexecutor/service/std/
//   전제: QualityExecutorApplication 에 @EnableScheduling 추가
@Component
@RequiredArgsConstructor
public class DiagSchedulerRunner {

    // 매 1분마다 평가 — SIMPLE 스케줄의 "분" 단위 정밀도 맞춤
    @Scheduled(fixedRate = 60_000L, initialDelay = 30_000L)
    public void evaluateAndRun() {
        List<DiagScheduleVo> active =
            sqlSessionTemplate.selectList("diagSchedule.selectActiveSchedules");
        LocalDateTime now = LocalDateTime.now();
        for (DiagScheduleVo s : active) {
            if (shouldTrigger(s, now)) {
                launch(s, "AUTO");
            }
        }
    }
    ...
}
```

### 4-2. 트리거 판정 — SIMPLE

```
DAILY   : now.time == REPEAT_TIME ± 1분 && 오늘 아직 실행 안 됨
WEEKLY  : now.dayOfWeek == REPEAT_DAY_OF_WEEK && DAILY 조건
MONTHLY : now.dayOfMonth == REPEAT_DAY_OF_MONTH && DAILY 조건
```

"오늘 아직 실행 안 됨" 은 `LAST_EXEC_DT` 기준. `TB_DIAG_SCHEDULE_LOG` 의 최신 AUTO 실행을 직접 조회해도 되지만 성능 위해 스케줄 테이블 캐시 사용.

### 4-3. 트리거 판정 — CRON

Spring `CronExpression.parse(cronExpr).next(lastExecOrEpoch).isBefore(now)` 로 평가. 매 분 호출 기준.

### 4-4. SKIP 정책 — 침범 없이 다음 주기로 양보

트리거 시점에 아래 조건이면 **이번 주기 실행을 포기하고 SKIPPED 이력 1건만 남긴 뒤 다음 평가 주기에 재평가**:
- 동일 dataModelId 의 같은 DIAG_TYPE 에 `TB_DIAG_JOB.status IN ('READY','RUNNING')` job 존재 (기존 `DiagController.startDiag` 의 중복 체크와 동일)
- 구조변경 진단에 `TB_STRUCT_DIAG_HISTORY` 진행 중 레코드 존재 (대응 쿼리 신설)

병행 실행/대기 큐는 만들지 않음 — 단순히 **"이번엔 건너뛴다 → 다음 주기에 다시 판정"** 방식. 결과적으로 충돌 없이 순차 진행되고, 스케줄 간 시간이 충분히 벌려 있으면 실제로는 거의 스킵되지 않음.

## 5. 실행 플로우 상세

```
[트리거 도래]
  ↓
[RUNNING 이력 먼저 INSERT]  ← LOG_ID 확보
  ↓
[DIAG_TYPE 분기]
  ├─ STANDARD
  │    DiagService 직접 기동 (dataModelId 만 넘김)
  │    → TB_DIAG_JOB 에 jobId 생성 + 백그라운드 실행
  │    진단은 현재 데이터 모델 (TB_DATA_MODEL_OBJ/ATTR, USE_YN='Y') 대상
  │
  ├─ STRUCT
  │    StructDiagService 직접 기동
  │    → TB_STRUCT_DIAG_HISTORY 에 diagId 생성
  │
  └─ BOTH
       STANDARD 실행 (완료 대기) → STRUCT 실행
  ↓
[실행 완료 이벤트 수신 — 아래 "비동기 고려" 참조]
  ↓
[성공] → LOG.EXEC_STATUS='DONE', EXEC_END_DT/DURATION 갱신
[실패] → LOG.EXEC_STATUS='ERROR', ERROR_MSG 상세 기록
         재시도 없음 — 다음 정규 주기에 다시 시도됨 (사용자가 원하면 runNow 로 즉시 재실행 가능)
  ↓
[TB_DIAG_SCHEDULE.LAST_EXEC_DT/STATUS/LOG_ID 갱신]
```

**스케줄러가 q-executor 내부에 있으므로 진단 서비스를 직접(In-JVM) 호출**하고, `DiagController.startDiag` 의 HTTP 왕복은 없음. 수동 실행 경로(q-center → q-executor WebClient) 와 진단 로직 자체는 동일 — 둘 다 `DiagService.run()` 같은 공용 진입점을 호출하는 구조로 리팩토링.

**비동기 고려**: 진단 자체가 비동기 백그라운드 실행이라, 스케줄러가 "완료 대기" 하면 `evaluateAndRun` 의 @Scheduled 쓰레드를 묶어두게 됨. 대안 2가지:
- **A**: 스케줄러는 "시작 트리거" 만 보내고 LOG.EXEC_STATUS='RUNNING' 상태로 둠. 진단 완료 시 `DiagService` / `StructDiagService` 가 완료 직후 TB_DIAG_SCHEDULE_LOG 를 직접 갱신 (scheduleLogId 를 파라미터로 전달받아 보관).
- **B**: 스케줄러가 job/diag ID 를 가진 채 짧은 폴링 루프 (ex. 5초 간격 * 최대 1시간) 로 완료 대기. 타임아웃 시 ERROR.

**권장**: **A**. q-executor 내부에서 진단 서비스와 스케줄러가 같은 JVM 에 있으므로, 진단 서비스 완료 훅에 직접 LOG 업데이트를 끼워넣는 게 가장 단순. 타임아웃 감시는 별도 @Scheduled(fixedRate=5m) 로 오래된 RUNNING 레코드 EXPIRED 처리.

**실패 로그 품질 규칙** (재시도 없는 대신 이쪽을 강화):
- `ERROR_MSG` 에 예외 클래스명 + 핵심 원인 한 줄 + 스택 최상단 3~5줄 저장 (전체 스택은 서버 로그에만)
- 실패 유형 분류 코드를 앞부분에 prefix: `[CONFIG]`, `[DB]`, `[TIMEOUT]`, `[DATA_NOT_FOUND]`, `[UNKNOWN]`
- 화면에서는 **칩(빨강) + 요약 한 줄 + 클릭 시 drawer 에 전체** 구조

### 6-2. VO

`DiagScheduleVo`, `DiagScheduleLogVo` — 신규. `q-common/src/main/java/com/ndata/quality/model/std/` 에 배치.

## 7. UI

36번 §5 기본 유지. 보강:

### 7-1. 스케줄 관리 화면 추가 컬럼

기존 `스케줄명 / 진단유형 / 데이터모델 / 주기 / 상태 / 최종실행` 에 추가:

- **최근 실행 결과 요약** — DONE/ERROR 칩 + 소요시간

### 7-1-1. 기본 액션 — 활성/비활성 토글 중심

행마다 노출되는 1차 액션은 `[활성/비활성] 스위치` + `[즉시 실행]` + `[편집]`.

- "더 이상 실행 안 한다" 는 **비활성** 으로 충분. 삭제는 진짜 지워야 할 때만 사용
- 목록에는 상단 필터: `전체 / 활성만 / 비활성만`

### 7-2. 등록/수정 모달 보강

36번 기본 필드 + 추가:
- **Cron 미리보기** — 입력 즉시 `/cronPreview` 로 다음 5회 표시

*(수집 선행 옵션 / 실패 재시도 옵션은 모두 스코프 아웃 — 1절 H/D, 2절 참조. 모달에 해당 필드 없음.)*

### 7-3. 실행 이력 화면 보강

36번 기본 + 추가:
- **트리거 유형** 컬럼 (AUTO | MANUAL)

- **상세 드로어** — DIAG_JOB_ID / STRUCT_DIAG_ID 클릭 시 실제 진단 결과 화면으로 딥링크

## 8. 권한 / 네비게이션

## 9. 관측성

- **로그**: `@Slf4j` + `DiagSchedulerRunner` 클래스 태그. 매 평가 사이클 INFO 1줄(평가 대상 N건, 트리거 M건, 스킵 K건).
- **메트릭**: 1차 구현 제외. 차후 Prometheus 연계 시 `diag_schedule_trigger_total{status}` 카운터 고려.
- **웹 대시보드 위젯**: 선택 구현 — 홈 대시보드에 "최근 24시간 자동 진단 현황" 카드 (총 M건 중 성공 N건, 실패 K건).

## 11. 착수 전 사용자 확정 필요 항목

### 11-1. 2026-04-24 세션에서 확정된 사항

1. ✅ **스케줄러 위치**: **q-executor** 유지 (배치 담당 모듈). 36번 원안 방향 유지.

4. ✅ **동시 실행 방지**: 이번 주기 스킵 + 다음 주기에 재평가 (대기 큐 없음).
5. ✅ **실패 재시도**: **구현 안 함**. 대신 실패 로그 품질 강화 (prefix 코드, 요약 칩, 전체 drawer).
6. ✅ **권한**: 관리자만 생성/수정/삭제/runNow. 조회/이력은 일반 사용자도 가능.

### 11-2. 기본값으로 진행 (이견 없으면 이 값으로 고정)

7. **[기본]** 평가 주기: **1분** (SIMPLE 스케줄의 "분" 해상도).
8. **[기본]** missed job catch-up: **없음**. 서버 다운 시 놓친 실행은 복구 안 함.
9. **[기본]** 알림(이메일/Slack): **이번 범위 밖**. 이력 조회만.
10. ✅ **삭제 방식**: **물리 삭제** (중요 데이터 아님). 평상시 UX 에서 삭제 버튼은 보조 메뉴(`⋮`) 안쪽. 기본 관리는 **활성/비활성 토글**로. 이력(LOG) 보존은 `SCHEDULE_NM_SNAPSHOT` 으로 해결.
