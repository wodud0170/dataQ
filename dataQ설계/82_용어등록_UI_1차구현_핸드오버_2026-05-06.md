## 2. 1차 구현 후 발견된 문제 (미해결)

### 핵심 문제 — 자동 분석이 "사용자 의도된 토큰 분리" 를 못 함

**증상**: 사용자가 `가로세로일시` 입력 시 모달에 의미없는 분리가 동시 표시.
- "일시" → DT (의도)
- "일" → DAY (부분문자열, 의도 아님)
- "시" → CITY (부분문자열, 의도 아님)

→ 사용자가 무엇을 골라야 하는지 헷갈림. 자동 합성된 영문약어가 마지막 클릭 단어 (예: 시=CITY) 기준이라 잘못된 결과.

**원인**: 1차 구현이 DSTerm 의 기존 `getTermsTokenListByNm` 그대로 사용. 이 API 는 **모든 가능한 부분문자열의 매칭**을 반환 (`가로세로일시` → 27개 분류). 매칭된 분류만 v-if 로 필터해도 의미 없는 부분문자열 매칭이 다수 남음.

**셀레니움 검증의 한계**: 통과한 6개 케이스는 매칭 분류가 1~2개로 적은 단순 입력 (`셀명_xxx`, `셀유형코드_xxx`) 이라 자동 클릭으로 통과. **다중 매칭/미매칭 혼합 케이스는 검증 못 함**.

## 3. 다음 단계 (사용자 합의 — 옵션 A)

### 작업 내용

[DSTermRecommend.vue:580](../q-center/vue/front/src/components/DSTermRecommend.vue#L580) 의 `analyzeTermsBatch` API 호출을 DSTerm 자동 분석으로 도입.

`analyzeTermsBatch` 의 응답 구조:
```json
[{
  "termsNm": "가로세로일시",
  "status": "PARTIAL",  // AUTO / PARTIAL / FAILED / REGISTERED
  "words": [
    { "wordNm": "가로", "status": "NEW" },
    { "wordNm": "세로", "status": "NEW" },
    { "wordNm": "일시", "status": "MATCHED", "wordEngAbrvNm": "DT", "wordEngNm": "Date and Time" }
  ],
  "recommendedDomainNm": "일시",
  "recommendedDataType": "DATE", ...
}]
```

→ 단어 1개당 분류 1개 (앞에서부터 가장 긴 매칭 우선 + 미매칭은 NEW). 부분문자열 잡음 없음.

### 구현 계획

1. [DSTerm.vue](../q-center/vue/front/src/components/DSTerm.vue) 의 `runAutoAnalyze()` 의 `getTermsTokenListByNm` 호출을 `analyzeTermsBatch` 로 교체.
2. 응답 매핑:
   - `words[]` → `addTerm_wordListArr` (각 word 가 분류 1개)
   - `status === 'MATCHED'` → `wordLst = [{ wordEngAbrvNm, wordEngNm, ... }]` (자동 선택 가능)
   - `status === 'NEW'` → `wordLst = []` → 인라인 등록 폼 표시
   - `status === 'UNRECOGNIZED'` → 인식 실패 안내
3. **자동 선택 가능** — 응답이 정확한 분리라 MATCHED 단어를 자동 체크해도 swal 노이즈 없음. 사용자 클릭 1번 줄임.
4. `recommendedDomainNm` 도메인 자동 채움 (사용자 검토만).
5. 마지막 단어 ABRV='CD' 검출은 정확한 분리 결과 기준으로 자동 동작.

### 셀레니움 시나리오 보강

- `가로세로일시` — NEW + MATCHED 혼합. 분리 결과 [가로(NEW), 세로(NEW), 일시(MATCHED)] 검증.
- `회원전화번호` — 모두 MATCHED 일 가능성. 자동 등록까지 가는 풀 흐름.
- `XYZ테스트` — 영문 + 한글 혼합 / FAILED 상태 검증.
- 인라인 등록 후 자동 매칭 갱신 흐름 (NEW → MATCHED 전환).
