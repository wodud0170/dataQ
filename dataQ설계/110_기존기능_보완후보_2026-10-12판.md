### 3.12 확인 사항

- 부분 처리: 승인 화면은 묶음의 항목을 상태와 무관하게 보이고 "전체 선택"이 처리 끝난 항목까지 고른다(dmChangeHistory.xml:103-107, MMDataModelApproval.vue:109-111). approve·reject 는 트랜잭션 없이 건별로 반영하므로 중간 건의 "이미 처리된 항목입니다" 예외 전까지 처리된 건은 그대로 남는다(DataModelApprovalController.java:130-132,154-156,184-187).
- 타입·길이만 바꾼 MODIFY_ATTR 반려: restoreAttrFromBefore 가 값을 되돌리며 APRV_STATUS='APPROVED' 로 둔 직후, syncAttrAprvStatus 가 같은 키(영문명 불변)로 REJECTED 를 덮어쓴다(DataModelApprovalController.java:207-209 → 254-255, datamodel.xml:1111, dmChangeHistory.xml:266-275). REJECTED 행은 목록(APPROVED·본인 요청만)과 진단(APPROVED 만)에서 빠지므로, 원래 승인돼 있던 컬럼이 사라진다(DataModelController.java:417-420, datamodel.xml:373).
- 이름·소유자 변경 반려 원복이 본체 행만 되돌린다: updateObj 는 ATTR·INDEX·CONSTRAINT·참조 FK·FK_PARENT 까지 새 이름·소유자로 바꾸는데(DataModelController.java:1498-1517), restoreObjFromBefore 는 TB_DATA_MODEL_OBJ 의 OBJ_NM·OBJ_OWNER 만 복원한다(datamodel.xml:1118-1126). 컬럼 영문명도 saveAttrs 가 INDEX·CONSTRAINT·FK 참조 이름을 바꾸지만(DataModelController.java:2343-2352) restoreAttrFromBefore 는 ATTR 행만 복원한다(datamodel.xml:1102-1116).
- 대기 삭제 반려 복구가 APRV_STATUS 를 무조건 'APPROVED' 로 둔다(datamodel.xml:1141-1149,1167-1185). 예: 추가 신청 중(DRAFT)인 컬럼이 있는 테이블을 삭제 신청 → 삭제 반려 시 그 컬럼(또는 DRAFT 테이블)이 승인 없이 APPROVED 가 되고 ADD 이력은 대기로 남는다.
- 전파로 반려된 이력은 원복을 거치지 않는다: cascadeRejectHistoryByAttr·cascadeRejectHistoryInObj 는 변경 유형을 가리지 않고 이력 상태만 REJECTED 로 바꾼다(dmChangeHistory.xml:211-242). 그 이력이 MODIFY_ATTR·DEL_ATTR 이면 값 복원·USE_YN 복구가 실행되지 않는다(복원은 직접 반려 대상에만 — DataModelApprovalController.java:207-231).
- DRAFT 롤백은 이력 행만 지운다(dmChangeHistory.xml:159-164, 컨트롤러 주석 "V2 검토" — DataModelApprovalController.java:81). ADD_* 로 생긴 DRAFT 행, DEL_* 로 USE_YN='N' 된 행은 이력 없이 남아 다시 신청·승인할 수 없고, MODIFY_* 값은 승인 없이 그대로 확정된다.
- 재수집이 대기 변경을 덮는다: q-executor 수집이 aprvStatus 없이 insertDataModelAttr 를 호출하면 같은 키 행이 APRV_STATUS='APPROVED'·USE_YN='Y' 로 갱신된다(DataModelService.java:233, datamodel.xml:771,778-799; 테이블은 USE_YN='Y' — datamodel.xml:846-850). DRAFT 행은 승인 없이 APPROVED, 대기 삭제는 되살아나며 이력은 대기 상태로 남는다.
- 승인 전 수정 값이 모든 사용자에게 보인다: MODIFY_ATTR·MODIFY_OBJ(TIER1)는 값을 즉시 바꾸고 행 APRV_STATUS 는 그대로 둔다(DataModelController.java:1523-1552,2403-2456). 대기 삭제(USE_YN='N')는 신청자를 포함해 전원에게서 즉시 사라진다. 신청 모달 안내 "승인 전까지는 본인에게만 보입니다."(DMSubmitModal.vue:13-14)는 추가(ADD_*)에만 맞는다.
- DEL_ATTR 승인(물리 삭제) 후 OBJ_ATTR_CNT 를 다시 세지 않는다(DataModelApprovalController.java:213-226). 대기 삭제 시점의 집계는 USE_YN 을 보지 않으므로(datamodel.xml:1574-1581) 삭제된 컬럼이 컬럼 수에 남는다.
- DB 반영: 서버는 APRV_STATUS·기실행 여부를 확인하지 않고 받은 change_seq 의 DDL 을 실행한다(DataModelApprovalController.java:404-439). 대상 데이터소스는 ID 를 손으로 입력하며 모델의 데이터소스와 대조하지 않는다(MMDataModelChangeHistory.vue:167-178). SKIPPED·FAILED·NO_PRIVILEGE 도 DDL_EXEC_DT 가 채워져 [DB 반영] 버튼이 사라진다(MMDataModelChangeHistory.vue:45). ADD_OBJ 이력은 조각에 '(...)' 가 있어 항상 SKIPPED 다(ChangeHistoryService.java:100,106).

- DB 반영 확인창이 DDL_SNIPPET(객체명 포함)을 HTML 이스케이프 없이 SweetAlert `html` 에 넣는다(MMDataModelChangeHistory.vue:169).

- 구조 진단 OFF 집합이 소유자를 구분하지 않는다: selectStructDiagOffSet 은 테이블명만 돌려주고 StructDiagService 는 테이블명(·컬럼명)으로만 비교한다(datamodel.xml:401-414, StructDiagService.java:106-113,152). 다중 소유자 모델에서 한 소유자의 테이블을 끄면 다른 소유자의 같은 이름 테이블도 실제 DB 쪽 목록에서 빠지고, 모델 쪽(소유자 구분)에는 남는다.
- 내 변경 신청 화면 SUBMITTED·REJECTED 구역은 사용자로 거르지 않는다(MMMyDataModelChanges.vue:114-119, `myUser` 변수 미사용 :116). 관리자에게는 전체 사용자 항목이 보이고, history 가 최근 500건 제한이라(dmChangeHistory.xml:78-79) 오래된 본인 항목이 빠질 수 있다. "신청 시각" 열은 CHANGE_DT(변경 저장 시각)이며 신청 시각 컬럼은 테이블에 없다(DDL_full_schema.sql:440-464).

**권한이 빠진 쓰기 API**

**상태 고착·오류 전달**
- 구조 진단 실행은 executor 호출 실패 처리가 없다(`center StructDiagController.java:114-123`) — READY 이력이 남고 그 모델은 이후 409 로 막힌다. 표준 진단은 통신 예외만 ERROR 로 바꾼다(`center DiagController.java:136-145`). WebClientHandler.postData 는 HTTP 상태를 보지 않고 본문을 Response 로 읽으므로(lib/common jar 바이트코드: exchangeToMono → bodyToMono) executor 가 resultCode 500 을 돌려주면 Job·이력이 READY 로 남는다.
- TB_DIAG_JOB·TB_STRUCT_DIAG_HISTORY 의 READY/RUNNING 을 정리하는 로직이 없다. executor 재기동 등으로 실행 스레드가 사라지면 그 모델은 수동 실행이 계속 409 다. 타임아웃(`diagSchedule.xml:221-230`)은 스케줄 LOG 만 마감한다.
- 스케줄 즉시 실행은 executor 응답의 resultCode 를 보지 않는다(`DiagScheduleController.java:203-208`). executor 쪽 실패에도 화면은 '실행 요청 전송' 을 띄우고, 스케줄을 못 찾은 경우 RUNNING LOG 는 연결 ID 가 없어 완료 감지에서 건너뛰다가 60분 뒤 타임아웃으로 마감된다.
- 타임아웃 마감은 스케줄 LAST_EXEC_* 를 갱신하지 않는다. 60분을 넘겨 도는 진단은 나중에 DONE 이 돼도 LOG 가 ERROR 로 남는다(완료 감지는 RUNNING LOG 만 읽는다 `DiagSchedulerRunner.java:172`).

**스케줄 동작**
- CRON 스케줄은 LAST_EXEC_DT 가 완료 때만 갱신되므로(`DiagSchedulerRunner.java:250-254`) 실행이 1분을 넘기면 매 분 평가에서 `cron.next(이전 LAST_EXEC_DT) ≤ 현재` 가 계속 참이 되어 SKIPPED LOG 가 분마다 쌓인다(`:82-93`, `:60-64`, `:148-165`).
- 예약 STANDARD 진단은 TB_DATA_MODEL_CLCT 이력을 요구한다(`ScheduledDiagLauncher.java:108-112`). 화면 실행은 clctId 없이 돈다(`DSDataDiag.vue:206-209`). 수집 이력이 없는 모델은 예약 표준 진단만 [DATA_NOT_FOUND] 로 실패한다.
- 스케줄 등록 검증(`DiagScheduleController.java:301-335`)은 STRUCT·BOTH 대상 모델의 데이터소스 유무를 보지 않는다 — 논리 모델로 등록되고 실행할 때마다 [CONFIG] 오류가 난다. 일자(1~28)·요일(1~7) 범위도 거르지 않고, 시각 정규식은 24~29시를 통과시킨다(`:322`, `DSScheduleManage.vue:284`).
- 중복 실행 방지 범위가 좁다. 자동 평가만 스케줄 LOG(같은 모델·같은 DIAG_TYPE·RUNNING)를 본다(`diagSchedule.xml:142-149`). 즉시 실행과 예약 기동은 TB_DIAG_JOB·TB_STRUCT_DIAG_HISTORY 의 진행 중 건을 확인하지 않아 화면 실행과 겹칠 수 있고, BOTH 는 STANDARD·STRUCT 와 서로 겹침을 보지 않는다(`DiagSchedulerRunner.java:142-143` 주석 "1차 구현").
- 예약 자동 실행의 실행자는 늘 'SCHEDULER' 다 — 평가용 조회(`diagSchedule.xml:82-89`)가 CRET_USER_ID 를 읽지 않는다(`ScheduledDiagLauncher.java:120`, `:151`). 즉시 실행은 스케줄 등록자가 기록되고 누른 사람은 기록되지 않는다.

**표준 진단 결과 화면**
- 준수율이 두 곳에서 다르다. 진단 결과 화면은 조회 시점 모델의 USE_YN='Y' 컬럼 전체(진단 제외·미승인·진단 뒤 추가 컬럼 포함, 이들은 OK 로 집계)를 분모로 정수 반올림한다(`DSDataDiagResult.vue:846-852`, `diag.xml:283-284`). 데이터 모델 목록은 Job 의 TOTAL_CNT(실제 진단 컬럼 수)를 분모로 소수 1자리다(`datamodel.xml:113-115`).
- 컬럼 상세 조회는 TB_TERMS·TB_DOMAIN 을 사전 조건 없이 조인한다(`diag.xml:267-282`). 표준 한글명·타입·길이·매칭 용어가 Job 사전이 아닌 다른 사전 값일 수 있고, 사전마다 값이 다르면 한 컬럼이 여러 행으로 나와 전체 컬럼 수가 부푼다(영문약어·도메인명 유일성은 사전 단위 — `DDL_full_schema.sql:2431`, `:2466`).
