# 41. 반려 물리삭제 — 승인 프로세스 개선

## 1. 개요

### 변경 목적
반려 시 엔티티를 물리 삭제하고, 반려 이력은 TB_APRV_STATS에만 보존한다.
기존 APRV_YN(Y/N), 유니크 인덱스는 변경하지 않는다.
TB_APRV_STATS에 REQ_ITEM_NM 컬럼을 추가하여 이력만으로 항목명을 확인할 수 있게 한다.

### 현재 vs 변경

| 항목 | 현재 | 변경 후 |
|------|------|---------|
| 승인 | APRV_YN='Y' 업데이트 | 동일 (변경 없음) |
| 반려 | APRV_YN='N' 유지 (레코드 잔존) | **엔티티 DELETE** + TB_APRV_STATS에 반려 이력 기록 |
| 반려 후 재등록 | 유니크 제약으로 불가능 | 레코드 삭제되어 같은 이름 재등록 가능 |
| 반려 이력 확인 | 엔티티 + TB_APRV_STATS 조인 | TB_APRV_STATS 단독 조회 |

### 생명주기
```
일반 사용자 등록 → APRV_YN='N' (승인대기)
  → 관리자 승인 → APRV_YN='Y'
  → 관리자 반려 → 엔티티 DELETE (TB_APRV_STATS에 이력만 남음)

관리자 등록 → APRV_YN='Y' (즉시 승인, 기존과 동일)
```

### cascade 규칙
- **단어 반려(삭제) 시**: 해당 단어를 포함하는 미승인 용어(APRV_YN='N')도 함께 DELETE
  - TB_TERMS_WORDS: 용어 DELETE 시 FK CASCADE(tb_terms_words_fk_1)로 자동 삭제 → 앱에서 별도 처리 불필요
  - 각 용어에 대해 TB_APRV_STATS에 반려 이력 INSERT
  - 알림 다이얼로그로 cascade 삭제 대상 표시
  - **순서 중요**: 미승인 용어 먼저 DELETE → 그 후 단어 DELETE (tb_terms_words_fk_2에 ON DELETE CASCADE 없음, 순서 어기면 FK 위반)
- 이미 승인된 용어(APRV_YN='Y')는 영향 없음
- 도메인 반려: cascade 없음 (단독 삭제)

### TB_TERMS_WORDS FK 제약 현황
| FK | 참조 | 동작 |
|---|---|---|
| tb_terms_words_fk_1 | TB_TERMS(terms_id) | ON DELETE CASCADE (용어 삭제 시 매핑 자동 삭제) |
| tb_terms_words_fk_2 | TB_WORD(word_id, word_nm) | ON UPDATE CASCADE (단어명 변경 시 자동 반영, DELETE CASCADE 없음) |

### 적용 대상
- TB_WORD, TB_TERMS, TB_DOMAIN (엔티티 삭제)
- TB_APRV_STATS (반려 이력 기록, APRV_STAT=3)

## 2. 영향성 분석

### 2.1 DB 스키마

**TB_APRV_STATS에 REQ_ITEM_NM 컬럼 추가**
```sql
ALTER TABLE TB_APRV_STATS ADD COLUMN REQ_ITEM_NM VARCHAR(200);
```
- 현재: 항목명은 엔티티 테이블 JOIN으로 조회 (`WORD_NM as reqItemNm` 등)
- 문제: 반려로 엔티티 삭제 시 JOIN 불가 → 이름 유실
- 해결: 모든 이력 INSERT 시 항목명도 함께 저장 → JOIN 없이 이력 단독 조회 가능
- APRV_YN, 유니크 인덱스 등 나머지 스키마는 현행 유지

### 2.2 변경이 필요한 영역

#### approve.xml — 반려 처리 SQL 추가/변경
| SQL ID | 현재 | 변경 |
|--------|------|------|
| updateWordAprvStat | APRV_YN CASE WHEN 업데이트 | 승인(2): APRV_YN='Y' 업데이트 / 반려(3): DELETE |
| updateTermsAprvStat | 동일 | 동일 패턴 |
| updateDomainAprvStat | 동일 | 동일 패턴 |
| (신규) deleteWordByReject | - | 단어 물리 삭제 SQL |
| (신규) deleteTermsByReject | - | 용어 물리 삭제 SQL |
| (신규) deleteDomainByReject | - | 도메인 물리 삭제 SQL |
| (신규) cascadeDeleteTermsByWordId | - | 단어 반려 시 연관 미승인 용어 일괄 삭제 (TB_TERMS_WORDS는 FK CASCADE 자동 정리) |
| selectUnapprovedTermsByWordId | 미승인 용어 조회 | 그대로 사용 (cascade 대상 조회용) |

#### DataStandardController.java — 반려 로직 변경
| 위치 | 현재 | 변경 |
|------|------|------|
| putStdAprvStat (반려 분기) | updateXxxAprvStat 호출 | DELETE SQL 호출 + 이력 INSERT |
| putStdAprvStat (WORD 반려) | 단순 업데이트 | cascade 로직 추가: 연관 미승인 용어 조회 → 삭제 → 이력 |
| reRequestApproval | 반려 항목 재요청 | **삭제** (물리삭제로 재요청 불가) |

#### MMApproval.vue — 반려 후 cascade 알림
| 변경 | 내용 |
|------|------|
| 반려 API 응답 처리 | cascadeTerms 배열이 있으면 알림 표시 |
| 알림 텍스트 | "단어 반려로 인해 다음 용어 N건이 함께 삭제되었습니다: [목록]" |

#### DSMyRequest.vue — 반려 항목 표시
| 현재 | 변경 |
|------|------|
| 엔티티 JOIN으로 항목명 표시 | TB_APRV_STATS 단독 조회 (LEFT JOIN, 엔티티 없으면 이력만 표시) |

### 2.3 변경 불필요한 영역

| 영역 | 이유 |

## 3. 개발 계획

### Phase 0: 중복 등록 메시지 개선
**파일 1개 — DataStandardController.java**

현재 유니크 제약 위반 시 "이미 등록된 단어명입니다." 일괄 표시.
승인 상태에 따라 메시지를 분기한다.

| 상황 | 메시지 |
|------|--------|
| 동일명 승인 건 존재 (APRV_YN='Y') | "이미 승인된 단어명입니다." |
| 동일명 승인대기 건 존재 (APRV_YN='N') | "승인 대기 중인 단어명입니다." |

**구현**: INSERT 전 SELECT로 동일명 조회 → 존재 시 APRV_YN 확인 후 메시지 분기 → INSERT 시도 자체를 하지 않음.
단어/용어/도메인 등록(create) + 수정(update) API 모두 적용.

기존 `translateDuplicateError`는 fallback으로 유지 (예상 못한 DB 에러 대비).

### Phase 1: DB + approve.xml — 스키마 변경 + 반려 삭제 SQL 추가
**DDL 1건 + SQL 신규 4~5개 + 기존 SQL 수정 2개**

#### 1-1. DDL
```sql
ALTER TABLE TB_APRV_STATS ADD COLUMN REQ_ITEM_NM VARCHAR(200);

-- 기존 이력에도 항목명 채우기 (가능한 범위에서)
UPDATE TB_APRV_STATS a SET REQ_ITEM_NM = w.WORD_NM
  FROM TB_WORD w WHERE a.REQ_ITEM_ID = w.WORD_ID AND a.REQ_TP = 'WORD' AND a.REQ_ITEM_NM IS NULL;
UPDATE TB_APRV_STATS a SET REQ_ITEM_NM = t.TERMS_NM
  FROM TB_TERMS t WHERE a.REQ_ITEM_ID = t.TERMS_ID AND a.REQ_TP IN ('TERMS','CODE') AND a.REQ_ITEM_NM IS NULL;
UPDATE TB_APRV_STATS a SET REQ_ITEM_NM = d.DOMAIN_NM
  FROM TB_DOMAIN d WHERE a.REQ_ITEM_ID = d.DOMAIN_ID AND a.REQ_TP = 'DOMAIN' AND a.REQ_ITEM_NM IS NULL;
```

#### 1-2. insertStdAprvStat 수정
```sql
-- REQ_ITEM_NM 컬럼 추가
INSERT INTO TB_APRV_STATS (REQ_ID, REQ_TP, REQ_ITEM_ID, REQ_ITEM_NM, APRV_STAT, ...)
VALUES (#{id}, #{reqTp}, #{reqItemId}, #{reqItemNm}, #{aprvStat}, ...)
```

#### 1-3. selectStdAprvStatList / 요청현황 쿼리 수정
- 항목명 조회를 엔티티 JOIN → `COALESCE(엔티티명, a.REQ_ITEM_NM)` 으로 변경
- 엔티티 존재 시 최신 이름, 삭제 시 이력의 이름 사용

#### 1-4. 반려 삭제 SQL 신규

```sql
-- 단어 물리 삭제
<delete id="deleteWordByReject">
  DELETE FROM TB_WORD WHERE WORD_ID = #{reqItemId}
</delete>

-- 용어 물리 삭제
<delete id="deleteTermsByReject">
  DELETE FROM TB_TERMS WHERE TERMS_ID = #{reqItemId}
</delete>

-- 도메인 물리 삭제
<delete id="deleteDomainByReject">
  DELETE FROM TB_DOMAIN WHERE DOMAIN_ID = #{reqItemId}
</delete>

-- 단어 반려 cascade: 미승인 용어 물리 삭제
-- (TB_TERMS_WORDS는 FK CASCADE로 자동 정리됨)
<delete id="cascadeDeleteTermsByWordReject">
  DELETE FROM TB_TERMS
  WHERE APRV_YN = 'N'
  AND TERMS_ID IN (
    SELECT tw.TERMS_ID FROM TB_TERMS_WORDS tw
    WHERE tw.WORD_ID = #{wordId}
  )
</delete>
```

기존 `updateWordAprvStat`, `updateTermsAprvStat`, `updateDomainAprvStat`은 **승인 시에만** 사용되도록 변경:
```sql
-- 반려 분기 제거, 승인 전용으로 단순화
<update id="updateWordAprvStat">
  UPDATE TB_WORD SET APRV_YN = 'Y',
    APRV_USER_ID = #{aprvUserId},
    APRV_STAT_UPDT_DT = #{aprvStatUpdtDt}
  WHERE WORD_ID = #{reqItemId}
</update>
```

### Phase 2: DataStandardController.java — 반려 로직 변경
**파일 1개**

**putStdAprvStat 메서드 변경:**
```
현재:
  승인(2) → updateXxxAprvStat (APRV_YN='Y')
  반려(3) → updateXxxAprvStat (APRV_YN='N') ← 사실상 무의미

변경:
  승인(2) → updateXxxAprvStat (APRV_YN='Y') + 변경이력
  반려(3) →

      5. TB_APRV_STATS INSERT (단어 반려 이력)
      6. Response에 cascade 목록 포함
    TERMS/CODE인 경우:
      1. deleteTermsByReject
      2. TB_APRV_STATS INSERT
    DOMAIN인 경우:
      1. deleteDomainByReject
      2. TB_APRV_STATS INSERT
```

### Phase 4: DSMyRequest.vue — 반려 항목 표시 대응
**파일 1개 + approve.xml 쿼리 확인**

반려된 항목은 엔티티가 삭제되므로, 요청 현황에서 반려 이력을 보여주려면:
- 현재 쿼리가 TB_APRV_STATS만으로 조회하는지 확인
- 엔티티 JOIN 시 LEFT JOIN으로 변경 (없으면 이력의 항목명만 표시)
- TB_APRV_STATS에 항목명(REQ_ITEM_NM) 컬럼이 없으면 추가 고려

> **확인 필요**: TB_APRV_STATS에 항목 이름이 저장되는지, 아니면 ID만 있고 엔티티에서 JOIN하는지.
> ID만 있으면 반려 시 이름을 같이 저장하거나, LEFT JOIN으로 처리해야 함.
