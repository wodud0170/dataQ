## #87-1. 용어 등록 모달의 동의어 입력 정책 정립 🔵

### 사용자 원문 (2026-05-10)
> "지금 용어사전 → 등록 때 동의어를 입력하면 분석이 되는데, 동의어도 이미 있으면 그냥 이미 있는 용어로 넘겨야 하는 건가?"

### 발견 컨텍스트
- 시연 대본 § 3-2 (용어 등록 v2 자동 분석) 검토 중
- 현재 등록 모달에서 한글 용어명 입력 시 1초 디바운스 후 `analyzeTermsBatch` 자동 호출
- 분석 결과로 단어 분리 + 영문약어 합성됨
- 그러나 사용자가 입력한 한글 용어명이 **이미 등록된 용어** 또는 **이미 등록된 단어의 동의어 (synonym)** 와 일치할 때 동작이 모호

### 화면 / 위치
- `데이터 표준 사전 > 용어 > [등록]` 모달
- 컴포넌트: `q-center/vue/front/src/components/DSTerm.vue`
- 분석 API: `/api/std/analyzeTermsBatch`

### 현재 동작
- 입력값에 대해 `analyzeTermsBatch` 가 토큰 분리 + 매칭만 수행
- 입력 그 자체가 등록된 용어/동의어인지 별도 lookup 없음
- 사용자가 [등록] 누른 시점에 `selectTermsByNm` 으로 unique 검사만 함 → "이미 등록된 용어명" swal

### 정책 후보
| 안 | 동작 | 장단점 |
|---|---|---|
| (a) **이미 등록된 용어/동의어 안내 + 사용자 선택** | 입력 1초 후 lookup → 일치 시 "이미 등록된 용어 / 동의어 — '%s' 용어를 사용하시겠습니까?" 알림 | 안전. 사용자 의도 확인. 권장 |
| (b) 자동 redirect | 일치 시 자동으로 그 용어 화면으로 이동 / 모달 닫힘 | UX 점프 — 의도와 다를 수 있음 |
| (c) 동의어로 그대로 입력 허용 | 사용자 입력값을 동의어 컬럼에 추가 + 별도 처리 | 동의어/용어 경계 모호 |

### 권장: (a)
- 분석 진입 시점에 입력값에 대해 `selectTermsByNm` + `selectTermsBySynonym` (신규 매퍼) 동시 호출
- 일치 시 분석 결과 위에 회색 배너로 "이미 등록된 용어/동의어입니다 — 이 용어로 가시려면 [이동]" 노출
- 분석은 그대로 진행 (사용자가 무시하고 신규 등록할 가능성도 허용)

### 영향도
- 신규 매퍼 1개 (`selectTermsBySynonym` — `ALLOPH_SYNM_LST` 배열 contains 검색)
- DSTerm.vue 분석 결과 영역 위에 안내 배너 추가
- 백엔드 endpoint 신규 또는 `analyzeTermsBatch` 응답에 `existingMatch` 필드 추가

### 추정
- 백엔드 + 프론트 — 반나절

## #87-2. 도메인 등록 데이터 타입 통합 🔵

### 사용자 원문 (2026-05-10)
> "도메인이 갖고있는 데이터타입은 varchar2 string 등을 varchar로 통합하는 뭐 그런 처리를 해야 할 것 같음. 도메인을 등록할 때 드롭다운 해보면 varchar2 등 쓸데없이 다른 것들이 생김."

### 발견 컨텍스트
- 시연 중 도메인 등록 화면에서 데이터 타입 드롭다운 확인
- VARCHAR / VARCHAR2 / STRING 등 사실상 동일한 타입이 분리되어 노출
- 외부 DBMS (Oracle 의 VARCHAR2, MySQL 의 STRING/TEXT) raw 타입이 도메인 사전 안으로 그대로 침투

### 화면 / 위치
- `데이터 표준 사전 > 도메인 > [등록]` 모달의 데이터 타입 드롭다운
- 컴포넌트: `DSDomain.vue`
- 백엔드: `selectDataTypeList` 류 매퍼 (TB_DOMAIN.DATA_TYPE distinct)

### 현재 동작
- 도메인 사전의 DATA_TYPE 컬럼 distinct 값을 그대로 드롭다운에 노출
- 외부 DBMS 의 raw 타입 (VARCHAR2 / NUMBER / NVARCHAR2 등) 이 누적되면서 옵션 폭증

### 제안
1. **DataQ 표준 데이터 타입 17종 정의** — 컬럼 화면 v-combobox 와 동일한 표준
   `VARCHAR / CHAR / TEXT / CLOB / BLOB / NUMBER / NUMERIC / DECIMAL / INTEGER / BIGINT / SMALLINT / FLOAT / DOUBLE / DATE / TIMESTAMP / TIME / BOOLEAN`
2. **수집 단계 매핑 테이블** — DBMS dialect 별 raw 타입 → DataQ 표준 타입
   - Oracle: VARCHAR2 → VARCHAR / NUMBER → NUMERIC / DATE → TIMESTAMP / NVARCHAR2 → VARCHAR ...
   - MySQL: STRING / TINYTEXT → TEXT / DATETIME → TIMESTAMP ...
   - PostgreSQL: bigint → BIGINT / numeric → NUMERIC ...
3. **마이그레이션** — 기존 도메인 row 의 비표준 DATA_TYPE 값을 표준으로 일괄 변환

### 영향도
- 컬럼 그리드와 도메인 등록 모달의 드롭다운 옵션 통일
- 수집 시 dialect 별 매핑 적용 (DataModelService 또는 신규 TypeMapper)
- 기존 데이터 일회성 마이그레이션 (UPDATE TB_DOMAIN SET DATA_TYPE = 매핑값)

### 추정
- 매핑 테이블 + UI 정리 + 마이그레이션 — 1~2일

## #87-3. 컬럼 편집의 PK/FK 입력 시 인덱스·제약조건 자동 생성 🔵

### 사용자 원문 (2026-05-10)
> "컬럼에서 FK를 다른 테이블로 참조해서 등록할 수 있고, FK 명도 등록해서 지정하면 제약조건에 그게 추가되는 식.
> PK도 마찬가지, PK 이름을 지정해서 저장하면 인덱스와 제약조건에 추가되는 식으로
> 나중에 모델링을 정말 이걸로도 할 수 있게 하고 싶어."

### 발견 컨텍스트
- 시연 대본 § 4 (논리 모델 — 직접 입력) 작성 중
- 현재 컬럼 그리드의 PK / FK 체크박스만 토글 가능 → 인덱스/제약조건 테이블에는 row 자동 생성 없음
- DataQ 단독으로 ERwin 없이도 모델링까지 완결하고 싶다는 비전

### 화면 / 위치
- `데이터 모델 > 컬럼` 그리드
- 백엔드: `saveAttrs` UPDATE/ADD 분기
- 매퍼: `tb_data_model_index`, `tb_data_model_constraint` cascade insert

### 현재 동작
- ATTR 행의 PK_YN, FK_YN, FK_PARENT_OBJ_NM, FK_PARENT_ATTR_NM 만 저장
- 인덱스/제약조건 테이블에는 row 자동 추가 없음 → DDL 다운로드 시 PK/FK 가 제약조건으로 표현 안 됨

### 제안 — UI
1. 컬럼 그리드에 **PK명 / FK명 / 참조 테이블 / 참조 컬럼** 입력 셀 추가 (PK_YN/FK_YN 체크 시 활성화)
2. 또는 PK/FK 체크 시 별도 미니 모달로 이름·참조 입력 받기
3. 입력 안 하면 자동 생성 규칙 — `PK_<TABLE>` / `FK_<TABLE>_<PARENT>` 같은 패턴

### 제안 — 백엔드 cascade
- ADD/UPDATE 시 PK_YN='Y' 변경 감지 → tb_data_model_index INSERT (UNIQUE/PK 인덱스) + tb_data_model_constraint INSERT (CONSTRAINT_TYPE='P')
- FK_YN='Y' 변경 감지 → tb_data_model_constraint INSERT (CONSTRAINT_TYPE='R' + REF_OWNER/REF_TABLE_NM/REF_COLUMN_NM)
- PK_YN/FK_YN 해제 시 cascade DELETE 또는 비활성화 정책

### 영향도
- 컬럼 그리드에 셀 4개 (PK명, FK명, 참조 테이블, 참조 컬럼) 추가
- saveAttrs 백엔드에 cascade INSERT/UPDATE 로직 — 5단계
- 매퍼 신규 — `upsertIndexFromPk`, `upsertConstraintFromPk`, `upsertConstraintFromFk`
- DDL 생성기에 PK/FK 제약조건 출력 (이미 일부 있을 수 있음 — 확인)

### 추정
- UI + 백엔드 cascade + 매퍼 — **3~5일**

### 효과
- DataQ 가 ERwin 없이도 모델링 완결성 확보
- 신규 환경 구축 시 DataQ → CREATE TABLE + 제약조건 + 인덱스 SQL 한 파일로 끝

## #87-4. 표준화 dryRun 응답에 표준 플래그(termsStndYn / domainStndYn) 미리 평가 🔵

### 사용자 원문 (2026-05-10)
> "변환 성공했는데 왜 이러냐"
> "지금 표준 쪽에 왜 X 로 나오냐 표준 변환 전부 성공한 건데"

### 발견 컨텍스트
- 시연 대본 § 4-3 (모델 ① 한글명 기준 표준화) 실제 테스트 중
- [한글명 기준 표준화] 클릭 → 그리드에 영문명/타입/길이 즉시 채워짐 (dryRun)
- 그러나 표준 컬럼은 X(❌) 그대로 → "변환 성공인데 왜 표준 X?" 사용자 혼란
- [저장] 누른 후 백엔드 동적 검증으로 Y 갱신은 잘 됨 (이번 세션 fix 완료)

### 현재 동작 (이번 세션 fix 후 기준)
- dryRun 응답 `items[]` 에는 `newAttrNm / newAttrNmKr / newDataType / newDataLen / newDataDecimalLen` 만 포함
- 프론트는 이 값들로 row.attrNm 등만 갱신, **termsStndYn / domainStndYn / wordLst 는 _orig 옛값 그대로**
- 그래서 그리드의 표준 컬럼이 X 로 보임 (저장 전)
- [저장] 시점에 백엔드 UPDATE 분기가 동적 표준 검증 (validateAttrStandards + applyStandardFlags) → Y 로 갱신

### 제안
1. **백엔드** `lookupForKr` / `lookupForEng` 안에서 검증을 추가로 돌려 결과를 items 에 포함:
   ```java
   StdDataModelAttrVo recheck = new StdDataModelAttrVo();
   recheck.setAttrNm(newAttrNm); recheck.setDataType(newDataType);
   try {
       validateAttrStandards(recheck);
       applyStandardFlags(recheck);
       item.put("newTermsStndYn", "Y");
       item.put("newDomainStndYn", "Y");
       item.put("newWordLst", recheck.getWordLst());
       item.put("newWordStndLst", recheck.getWordStndLst());
   } catch (Exception e) {
       item.put("newTermsStndYn", "N");
       item.put("newDomainStndYn", "N");
   }
   ```
2. **프론트** items 적용 시 `row.termsStndYn / domainStndYn / wordLst` 도 같이 `$set`

### 효과
- 표준화 직후 그리드의 표준 컬럼이 즉시 ✅ 로 갱신 → 사용자가 결과 확인 후 [저장] 결정
- "왜 표준 X 냐?" 혼란 제거

### 영향도
- 백엔드 lookupForKr / lookupForEng — validateAttrStandards 호출 추가
- 프론트 resolveSelected / resolveByEng — items 적용 시 표준 플래그도 set
- 회귀 영향 없음 (값 추가일 뿐, 기존 흐름 변경 X)

### 추정
- 백엔드 + 프론트 — **반나절**

## #87-5. DB 수집 시 스키마 + 객체 종류 단위 선택 수집 🔵

### 사용자 원문 (2026-05-10)
> "DB에서 수집해올 때 스키마별로 테이블·컬럼, 인덱스, 제약조건 각 별로 선택 수집 가능하게.
> 이 기능이 나중에 필요할 것 같아서."

### 발견 컨텍스트
- 시연 대본 § 5-2 (모델 ② 수집 모델) 작성 중
- 현재는 스키마 다중 선택 후 **테이블/컬럼/인덱스/제약조건 일괄 수집**
- 대용량 운영 DB (스키마 수십 개, 테이블 수만 개) 에서 일부 객체만 가져오고 싶은 케이스 대응 부족

### 화면 / 위치
- `데이터 모델 > 데이터 모델 관리 > [신규 모델 + 수집]` 모달
- 백엔드: q-executor `DataModelService.collect()`

### 현재 동작
- 스키마 체크박스 다중 선택 → 선택된 스키마 전체에서 테이블·컬럼·인덱스·제약조건을 모두 수집
- "어느 스키마에서는 테이블만, 다른 스키마에서는 인덱스도" 같은 선택 불가

### 제안 — UI
- 수집 모달에 **스키마 × 객체 종류 매트릭스** 체크박스
  ```
            테이블/컬럼   인덱스   제약조건
  USER1     [✓]          [✓]     [✓]
  HR        [✓]          [ ]     [ ]
  SALES     [ ]          [✓]     [✓]
  ```
- 또는 스키마 선택 후 단계 2: "이 스키마에서 어떤 객체를 가져올지" 체크박스

### 제안 — 백엔드
- `DataModelService.collect()` 에 객체 종류별 ON/OFF 플래그 추가
- 수집 이력 (TB_DATA_MODEL_CLCT) 에 어떤 객체가 수집됐는지 메타 보관

### 영향도
- 수집 모달 UI (스키마 × 객체 매트릭스)
- 수집 서비스 분기 — `if (collectIndex) { collect index... }`
- 수집 이력 메타 — 수집 범위 기록 (`COLLECT_SCOPE_JSON` 같은 신규 컬럼)

### 추정
- UI + 수집 로직 분기 + 이력 메타 — **2~3일**

### 효과
- 대용량 DB 에서 부분 수집 가능 → 모델 가벼움 유지
- 인덱스/제약조건은 운영 부담이 큰 객체이니, 필요한 스키마만 선택해 비용 줄임

## #87-6. 진단 결과에서 데이터 모델 직접 수정 / 자동 반영 🔵

### 사용자 원문 (2026-05-10)
> "진단 결과에서 데이터 모델을 직접 수정 가능할 수 있는 케이스가 있음 (표준화 칩, 코멘트 다름, 타입 다름 등등).
> 지금은 일일이 수정하거나 물리 DB 연결 같은 경우 물리 DB 를 재수집하면 그만이겠지만,
> 논리 모델 같은 경우도 그냥 사실 표준화 변환을 다 하는 식으로 작업을 하는 게 맞겠지.
> 그러나 ERwin 임포트 같은 경우는 모델을 먼저 수정하고 DDL 로 내보낼 수 있어야 함.
> 이에 표준 진단에서 직접 모델을 자동 변경할 수 있는 방법 또한 넣어 놔야 함."

### 발견 컨텍스트

- 현재 진단 결과는 "이슈 보고" 만 함 — 사용자가 직접 컬럼 화면으로 가서 수정해야 함

- 그러나 **진단 결과 → 모델 자동 반영** 이 없어 ERwin 임포트 케이스 같은 경우 개선 사이클이 길어짐

### 모델 출처별 시나리오 분기

| 모델 출처 | 이슈 발견 시 권장 흐름 | DataQ 가 자동화해야 할 부분 |
|---|---|---|
| **물리 DB 연결 (수집)** | DB 자체를 ALTER + 재수집 | 재수집 트리거. 모델 자동 수정은 부적절 (실 DB 진실) |
| **논리 모델 (직접 입력)** | 한글명 또는 영문명 기준 표준화 dryRun → 일괄 저장 | 컬럼 화면의 표준화 버튼 (이미 구현) |
| **ERwin / XMI 임포트** | 모델을 표준에 맞게 자동 수정 → DDL 다운로드 → ERwin 으로 다시 import | **진단 결과 화면에서 직접 모델 자동 반영 기능 필요** |

### 제안 — 진단 결과 화면의 [모델 자동 반영] 액션
- 진단 결과 테이블 상세 / 컬럼 상세 행에 [모델 반영] 버튼 추가
- 클릭 시 — 해당 이슈 유형별로 표준 권장값을 모델에 적용
  - **TERM_NOT_EXIST** (용어 미존재) — [용어 빠른 등록] 모달 (현재 있음) → 등록 후 모델 표준 플래그 갱신
  - **TERM_KR_NM_MISMATCH** (한글명 불일치) — 한글명을 표준값으로 일괄 변경
  - **DATA_TYPE_MISMATCH** (타입 불일치) — 타입을 표준값으로 일괄 변경
  - **DATA_LEN_MISMATCH** (길이 불일치) — 길이를 표준값으로 일괄 변경
- 다중 선택 + 일괄 [선택 항목 모두 표준값 반영] 액션
- 반영 후 자동 [재진단] 또는 진단 결과 화면 캐시 갱신
- 반영 결과 confirm — 변경 전/후 비교 + 사용자 확인 후 commit

### 모델 출처 인식 — 권장 흐름 분기
- 모델의 데이터소스 (TB_DATA_MODEL.DM_DS_ID) 가 NULL — 논리 모델 / ERwin 임포트 → [모델 반영] 활성
- 데이터소스 있음 + 수집 이력 있음 — 물리 DB 연결 → [모델 반영] 비활성 + "DB 변경 후 재수집" 안내

### 영향도
- 진단 결과 화면 (DSDataDiagResult.vue) — 행별 [모델 반영] 액션 + 일괄 액션
- 백엔드 신규 endpoint — `/api/diag/applyToModel` (이슈 유형별 분기 처리)
- 매퍼 신규 — 한글명 / 타입 / 길이 일괄 update (기존 saveAttrs 활용 가능)
- 모델 출처 판단 로직 — DM_DS_ID 기반

### 추정
- UI + 백엔드 + 매퍼 — **3~5일**

### 효과
- ERwin 임포트 케이스에서 표준화 사이클 단축 — 진단 → 자동 반영 → DDL 다운로드 → 다시 ERwin 으로 import (왕복 1번)
- 논리 모델도 진단 결과를 보고 즉시 보정 가능
- 물리 DB 케이스는 잘못 자동 반영되지 않게 안전 분기

## #87-11. 승인 프로세스 — 용어 반려 시 포함 단어 처리 정책 🔵

### 사용자 원문 (2026-05-11)
> "승인 프로세스 -> 용어에 포함된 단어를 반려할때 어떻게 하는지"

### 발견 컨텍스트
- 용어는 단어들의 조합으로 등록됨 — 일부는 기존 표준 단어, 일부는 용어 등록 시 같이 신규 등록된 단어
- 용어 승인/반려 시 **포함된 단어 (특히 신규 단어) 의 처리 정책이 명확하지 않음**
- 기존 cascade 반려 정책 (단어 반려 시 연관 미승인 용어 경고) 은 정착되어 있으나 **역방향 (용어 반려 → 신규 단어) 미정의**

### 화면 / 위치
- `관리 > 승인` 화면 (`MMApproval.vue` 추정)
- 백엔드: `TB_APRV_STATS` UPDATE 분기 + `TB_TERMS` / `TB_WORD` 의 APRV_YN cascade

### 현재 동작 (추정)
- 용어 반려 시 — `TB_TERMS.APRV_YN='N'` 또는 row 삭제
- 그 용어에 포함된 신규 단어 (역시 미승인 상태) 는 **그대로 잔류** — 다른 용어가 같은 단어를 사용 중인지 검사 없음
- 또는 같이 cascade 반려 — 정책 어느쪽인지 코드 직접 확인 필요

### 정책 후보
| 안 | 동작 | 장단점 |
|---|---|---|
| (a) **단어는 그대로 보존** | 용어 반려 시 단어는 미승인 상태 유지 → 다른 용어가 살릴 수 있음 | 안전. 단 잔재 데이터 |
| (b) **같이 cascade 반려** | 단어도 함께 반려/삭제 (단, 다른 용어가 사용 중이면 보존) | 깔끔. 종속성 검사 필요 |
| (c) **반려 사유에 따라 분기** | 사용자가 "단어도 같이 반려" 체크박스 선택 | 유연. UI 복잡 |

### 제안
- 정책 확정 + 승인 화면 UX 보강 — 반려 시점에 "이 용어에 포함된 신규 단어 N개 / 다른 용어가 사용 중 M개" 미리 보여주기

### 영향도
- 승인 매퍼 — 반려 시 단어 종속성 검사 + cascade 처리 SQL
- 승인 화면 — 반려 확인 모달에 영향 단어 카운트 노출
- 셀레니움 — 반려 cascade 시나리오 신규

### 추정
- 정책 결정 후 — **1일** (검사 + cascade + UI)

### 후속 — 본 항목은 #87-12 (알림/액션 정비) 와 연동
- 반려 결과 알림에 cascade 영향 (단어 N개 함께 처리) 같이 표시 권장

- 데이터소스 연결 정보 (TB_DATA_SOURCE) 가 이미 있으니, **DataQ 가 직접 ALTER 실행**해서 사이클 단축

### 화면 / 위치
- 표준 진단 결과 화면 (`DSDataDiagResult.vue`)
- 관리자만 보이는 [DB 직접 반영] / [모델에 반영] / [DDL 다운로드] 3종 액션

### 제안 — 액션 매트릭스

| 이슈 유형 | 액션 |
|---|---|
| 용어 미존재 (TERM_NOT_EXIST) | [용어 등록] (현행 유지) |
| 한글명 불일치 / 타입 불일치 / 길이 불일치 | [모델에 반영] / [DB 직접 반영] / [DDL 다운로드] 3선택 |
| TMP_COL_숫자 (#87-17) | [모델 컬럼 화면으로 이동] |

### 백엔드 — DB 직접 반영
- 신규 endpoint `POST /api/diag/applyToDb` (관리자 권한 체크)
- 입력: `{ diagId, dsId, items: [{ owner, objNm, attrNm, action, params }] }`
- 흐름:
  1. 관리자 권한 검증 (없으면 403 반환)
  2. dsId 로 DataSourceUtils.getDBHandler() 호출 → DB connection
  3. 각 item 별 ALTER 문 생성 (RENAME COLUMN / MODIFY DATA_TYPE / ...)
  4. DBMS dialect 별 분기 (Oracle / PG / MySQL)
  5. 트랜잭션 단위 (가능한 DBMS) 또는 건별 try/catch
  6. 권한 에러 (ORA-01031 / Permission denied / ...) → `{success:false, item, reason:'권한 없음'}` 반환
  7. 결과 요약 반환 (성공 N건 / 실패 M건 / 권한 없음 K건)

### 동일 패턴 — 모델 직접 반영 (#87-15 와 연계)

### 제안 — 스키마 변경

#### A. APRV_STATUS 컬럼 추가 (각 모델 테이블에)
- `TB_DATA_MODEL`             → `APRV_STATUS` ('PENDING' / 'APPROVED' / 'REJECTED')
- `TB_DATA_MODEL_OBJ`         → `APRV_STATUS`
- `TB_DATA_MODEL_ATTR`        → `APRV_STATUS`
- `TB_DATA_MODEL_INDEX`       → `APRV_STATUS`
- `TB_DATA_MODEL_CONSTRAINT`  → `APRV_STATUS`

- 기존 row 는 마이그레이션 시 'APPROVED' 로 일괄

#### B. 가시성 정책 (가장 중요)
- **APPROVED row** — 모든 사용자 조회 가능
- **PENDING row (사용자 본인)** — 본인 + 관리자만 조회. 옅은 회색 / 노란 배경 등 시각 표시

- **REJECTED row** — 본인 + 관리자만 조회, 빨간 표시
- 매퍼의 모든 SELECT 에 `WHERE APRV_STATUS = 'APPROVED' OR REQUESTER_USER_ID = #{currentUserId}` 추가

#### C. 진단 / 외부 시스템 노출
- 표준 진단 / 구조 변경 진단 / 모든 외부 노출은 **APPROVED 만**
- 매퍼 `WHERE APRV_STATUS = 'APPROVED'` 추가

#### D. 사용자 흐름
1. 사용자가 컬럼 추가/수정 → row 가 PENDING 으로 저장
2. 사용자에게 "관리자 승인 대기 중" 안내 + [내 변경 요청 현황] 으로 이동 안내
3. 사용자 본인 화면에선 그 row 가 노란 배경으로 표시
4. 관리자 승인 화면에 변경 요청 누적 → [승인] / [반려]
5. 승인 시 → APRV_STATUS='APPROVED' (다른 사용자도 보임)
6. 반려 시 → APRV_STATUS='REJECTED' + 사용자에게 알림 (#87-12 알림 통합 연계)

#### E. 관리자 화면 (기존 승인 화면 확장)
- 탭 추가: "데이터 모델" — 테이블/컬럼/인덱스/제약조건 통합 변경 요청 리스트
- 컬럼 변경 케이스: 변경 전/후 비교 표시
- 일괄 승인 / 일괄 반려 (다중 선택)

## #87-20. 데이터 모델 변경 이력 + 이력에서 DDL 재실행 (관리자 only) 🔵 **(우선순위 1순위)**

### 사용자 원문 (2026-05-14)
> "그리고 데이터 모델 변경 이력도 관리해야함, 변경 이력을 조회하기 +
> 해당 이력에서 DDL로 그 변경을 DB에 반영할 수 있는 기능
> (DDL 복사/출력 및 실제 DB에 반영까지, 관리자 ONLY)
> DDL로 뭐 직접 DB에 붙어서 하는건 전부 관리자 전용 기능임"

### 발견 컨텍스트
- 사용자가 데이터 모델을 변경했을 때 (#87-19 승인 후) 그 변경의 자취가 남지 않으면 추적 불가
- 변경 이력에서 그 시점의 DDL 을 다시 뽑아 DB 에 반영하는 시나리오 (예: 운영 DB 가 모델보다 뒤처져 있을 때 일괄 동기화) 가 필요
- 관리자 only — DB 변경은 위험

### 화면 / 위치
- `데이터 모델 > 변경 이력` (신규 화면)
- 모델 상세에서 [변경 이력] 탭 (선택)
- 이력 row 클릭 → 상세 + [DDL 복사] / [DDL 다운로드] / [DB 반영] (관리자 only)

### 제안 — 스키마

#### A. TB_DATA_MODEL_CHANGE_HISTORY (신규)
```sql
DM_ID                VARCHAR(40)
CHANGE_SEQ           BIGINT (PK)
CHANGE_DT            VARCHAR(14)
CHANGE_USER_ID       VARCHAR(50)
CHANGE_TYPE          VARCHAR(20)  -- ADD_OBJ / DEL_OBJ / RENAME_OBJ / ADD_ATTR / DEL_ATTR / MODIFY_ATTR / ADD_INDEX / ... 
OBJ_OWNER            VARCHAR(100)
OBJ_NM               VARCHAR(200)
ATTR_NM              VARCHAR(200)  -- 컬럼 단위 변경일 때
BEFORE_JSON          TEXT          -- 변경 전 row 스냅샷 (JSON)
AFTER_JSON           TEXT          -- 변경 후 row 스냅샷 (JSON)
DDL_SNIPPET          TEXT          -- 그 변경의 DDL 표현 (재실행용)
APRV_STATUS          VARCHAR(20)   -- PENDING / APPROVED / REJECTED (#87-19 와 연동)
APRV_USER_ID         VARCHAR(50)
APRV_DT              VARCHAR(14)
DDL_EXEC_DT          VARCHAR(14)   -- 실제 DB 반영 시각 (NULL = 미반영)
DDL_EXEC_USER_ID     VARCHAR(50)
DDL_EXEC_RESULT      VARCHAR(20)   -- SUCCESS / FAILED / SKIPPED
```

#### B. 이력 생성 트리거
- `saveAttrs` / `updateObj` / `deleteObj` / `addObj` / 모든 변경 endpoint 가 변경 시 한 row 자동 INSERT
- BEFORE_JSON / AFTER_JSON 은 변경 시점 ATTR/OBJ row 를 JSON 직렬화
- DDL_SNIPPET 은 변경 타입별 ALTER 문 생성 (RENAME COLUMN ... / ADD COLUMN ... / MODIFY ...)

#### C. 이력 조회 화면
- 필터: 모델 / 사용자 / 변경 타입 / 기간 / 승인 상태 / DDL 반영 여부
- row 한 줄: `[시각] [사용자] [변경 타입] OWNER.OBJ.ATTR [상태]`
- 행 클릭 → 우측 상세 패널:
  - 변경 전/후 diff
  - 생성된 DDL_SNIPPET
  - [DDL 복사] / [DDL 다운로드] / [DB 반영] (관리자 only) / [DB 반영 취소] (관리자 only)

#### D. DB 반영
- #87-18 의 applyToDb 와 동일 매커니즘 — DDL_SNIPPET 을 dsId 로 실행
- 권한 에러 → 안내 반환
- 성공 시 DDL_EXEC_DT / DDL_EXEC_RESULT 업데이트
- 동일 이력을 두 번 반영 못 하도록 idempotency 가드 (또는 명시적 [재실행])

#### E. 관리자 전용 일괄 작업
- 다중 이력 선택 → [선택 항목 DB 반영] (트랜잭션 단위)
- 모델 시점 비교 — "오늘 시점 모델" vs "DB 현재 상태" 차이만큼 DDL 일괄 추출 (구조 변경 진단과 연계)

### 영향도
- 신규 테이블 1개 (TB_DATA_MODEL_CHANGE_HISTORY)
- DDL 마이그레이션 (DDL_full_schema.sql 갱신)
- 모든 변경 endpoint 에 이력 INSERT 후크 — saveAttrs, updateObj, addObj, deleteObj 등 10+
- 신규 화면 1개 + 라우팅 1개
- 신규 endpoint — list / detail / executeDdl / cancelExec
- 권한 분기 (관리자 only)

### 추정
- DDL + 매퍼 + 이력 후크 — **5일**
- 화면 + DDL 실행 — **3일**

### 의존 관계
- **연관 강함**: #87-18 (DB 직접 반영) — 동일 실행 매커니즘 공유 가능 → 두 항목 같은 사이클에 진행 권장
- **연관**: #87-19 (승인 워크플로우) — APRV_STATUS 동기화
- **연관**: #87-12 (알림 통합) — 반영 성공/실패 알림

## 거버넌스 묶음 (87-18 / 87-19 / 87-20) — 자연스러운 설계 의견

### 핵심 통찰
세 항목은 **사용자/관리자 권한 분리** 와 **DB ↔ 모델 양방향 동기화** 라는 두 축의 다른 단면. 따로 구현하면 충돌·중복 다발. 같이 묶어 한 사이클로 가는 게 정합성 ↑.

### 권장 진행 순서
1. **(0단계) 권한 모델 정리** — admin / user 권한 체크 헬퍼 통일. 현재 분산되어 있음.
2. **(1단계) #87-19 승인 워크플로우** — DDL + 매퍼 가시성. 모든 변경의 기반.
3. **(2단계) #87-20 변경 이력** — #87-19 의 APRV_STATUS 와 동시 INSERT 후크. 한 트랜잭션 안에서.
4. **(3단계) #87-18 DB 직접 반영** — #87-20 의 DDL_SNIPPET 재사용. 신규 코드 최소화.

### 사용자/관리자 권한 분기 가이드 (자연스러운 설계)

| 작업 | 사용자 | 관리자 |
|---|---|---|
| 진단 결과 조회 | ✓ | ✓ |
| 진단 실행 | ✗ | ✓ |
| 모델 조회 (APPROVED) | ✓ | ✓ |
| 모델 조회 (본인 PENDING) | ✓ (본인만) | ✓ (전체) |
| 모델 변경 요청 | ✓ (PENDING 으로 저장) | ✓ (즉시 APPROVED 옵션) |
| 모델 변경 승인/반려 | ✗ | ✓ |
| 변경 이력 조회 (APPROVED) | ✓ | ✓ |
| 변경 이력 조회 (PENDING/REJECTED) | ✓ (본인만) | ✓ (전체) |
| DDL 다운로드 / 복사 | ✓ | ✓ |
| **DB 직접 반영** | ✗ | ✓ |
| **변경 이력에서 재실행** | ✗ | ✓ |

### 시각 표시 통일안
- **노란색 (FFF8E1)** — 본인 PENDING (사용자 본인이 신청한 미승인)
- **빨간색 (FFEBEE)** — REJECTED (반려)
- **회색 옅음 (F5F5F5)** — 미저장 dirty (편집 중)
- **흰색 / 기본** — APPROVED (정상)

→ #87-19 dirty 표시 vs PENDING 표시를 명확히 구분 (사용자 혼란 방지)

### 단계별 마이그레이션 안전성
- **#87-19 도입 시 기존 row 모두 APPROVED** 로 채워 호환성 유지
- 매퍼 가시성 필터는 default ON 하되, 일부 매퍼 (관리 화면) 는 명시적 OFF
- 권한 헬퍼는 기존 `WebSessionService.isAdmin()` (이미 존재) 재사용

### 알림 통합 (#87-12)
- 변경 요청 시 → 관리자에게 알림
- 승인/반려 시 → 요청자에게 알림 + 결과 화면 라우팅
- DB 반영 성공/실패 → 실행자에게 알림

### 위험 요소
- **#87-19 의 매퍼 가시성 필터** — 누락하면 미승인 row 가 다른 사용자에게 노출. 매퍼 50+ 일괄 검토 + 회귀 테스트 필수
- **#87-18 의 DB 권한 에러** — DBMS 별 에러 코드 다름 (Oracle ORA-01031 / PG insufficient_privilege / MySQL 1142 등). 메시지 변환기 필요
- **#87-20 의 이력 INSERT 후크** — saveAttrs 같은 batch endpoint 에서 N건 변경 시 N건 이력 INSERT. 대량 변경 시 성능 모니터링 필요

### 약식 견적
- 권장 순서대로 3개 묶음 — **약 3~4주 (1인 풀타임 기준)**
- 분할: #87-19 (2주) + #87-20 (1주) + #87-18 (1주)
