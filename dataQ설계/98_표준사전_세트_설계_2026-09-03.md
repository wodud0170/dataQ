## 1. 왜 지금 나왔나

국가기록원(RAMS) SMETA 등록자료를 NavidM Meta 에 적재하려다 막혔다.

| 자료 | 건수 |
|---|---|
| 단어 | 3,679 |
| 도메인 | 642 |
| 용어 | 14,963 |
| 테이블 / 컬럼 | 122 / 3,127 |

이걸 기존 사전(행안부 공통표준 시드)이 들어 있는 DB 에 올리면 섞인다. 그리고 섞이는 방식이 나쁘다.

**일괄등록은 중복을 실패가 아니라 skip 으로 처리한다.**

```java
// ExcelUploadService.java:87 — 단어
if (session.selectOne("word.selectWordByEngAbrvNm", dataRow.get(3)) != null) {
    result.addSkip();
    continue;
}
```

용어(:177)·도메인(:358)도 같다. 그래서 RAMS 의 `BTWN = 간(사이)` 을 올릴 때 기존 사전에 뜻이 다른 `BTWN` 이 이미 있으면 **조용히 건너뛰고 "성공"으로 보고된다.** 사용자는 다 올라간 줄 안다. 이후 진단은 남의 사전 기준으로 돌아간다.

즉 이건 "언젠가 필요한 확장" 이 아니라 **지금 이 자료로 바로 재현되는 결함**이다.

## 2. 현재 구조의 제약 (사실)

### 2.1 유니크가 전부 전역

```
tb_word          word_nm / word_eng_abrv_nm     (각각 2개씩 중복 정의)
tb_terms         terms_nm / terms_eng_abrv_nm   (terms_nm 2개 중복 정의)
tb_domain        domain_nm                      (2개 중복 정의)
tb_domain_grp    domain_grp_nm
tb_domain_clsf   domain_clsf_nm
tb_code_data     (code_nm, code_val)
```

전역 유니크 인덱스 **12개**. 두 기관의 사전이 물리적으로 공존할 수 없다.

> 부수 발견 — 같은 컬럼에 유니크 인덱스가 두 벌씩 걸려 있다.
> `tb_word_ux_2` 와 `uix_word_eng_abrv_nm`, `tb_terms_ux_1` 과 `uix_terms_nm`,
> `tb_domain_ux_1` 과 `uix_domain_nm`. 세트 도입과 무관하게 정리 대상.

### 2.2 스코프 키가 될 만한 컬럼이 이미 있으나 용도가 다르다

`tb_word` · `tb_terms` · `tb_domain` 에 `req_sys_cd`(요청시스템) 가 있다. 하지만 이건 **"어느 시스템이 이 표준을 요청했는가"** 라는 이력 메타데이터지 소속이 아니다. NULL 도 허용된다. 스코프 키로 재활용하면 의미가 겹쳐서 나중에 더 꼬인다. **새 키를 둔다.**

### 2.3 사전을 읽는 곳

매퍼 참조 128회 / 12개 파일.

| 테이블 | 참조 | 테이블 | 참조 |
|---|---:|---|---:|
| tb_domain | 39 | tb_terms_words | 11 |
| tb_terms | 35 | tb_code_data | 7 |
| tb_word | 24 | tb_domain_clsf | 7 |
| tb_domain_grp | 5 | | |

파일: `word.xml` `terms.xml` `domain.xml` `approve.xml` `diag.xml` `qualDiag.xml` `qualColRule.xml` `qualDomainRule.xml` `qualRule.xml` `search.xml` `termResolve.xml` `impact.xml`

### 2.4 무거운 로직은 사전을 통째로 메모리에 올린다 — 이게 유리하다

```java
// DiagService.java:99 — 표준 진단
List<StdTermsVo> allTerms = sqlSessionTemplate.selectList("terms.selectAllTermsForDiag");

// TermRecommendService.java:21,28,38,47 — 자동 표준화
terms.selectAllTermsByNm / word.selectAllWords
word.selectWordUsageCounts / domain.selectAllDomains
```

진단과 자동표준화는 행마다 조회하지 않고 **한 번에 다 읽어 Map 으로 쓴다.** 그래서 제품에서 가장 무겁고 손대기 싫은 두 로직의 스코프 적용점이 `selectAll*` **5개 쿼리로 모여 있다.** 파라미터 하나 추가하면 끝난다.

`DiagService` 는 이미 `dataModelId` 를 들고 있어서 모델 → 사전 해석이 자연스럽다.

### 2.5 모델에 남는 진단 결과는 사전 종속이다

`tb_data_model_attr` 에 `terms_stnd_yn` · `domain_stnd_yn` · `word_lst` · `word_stnd_lst` 가 있다. 이건 참조가 아니라 **직전 진단의 산출물**이고, 컬럼 화면의 표시·필터에 쓰인다 (datamodel.xml:458, 579).

준수율은 여기서 나오지 않는다. `TB_DIAG_JOB` + `TB_DIAG_RESULT` 에서 잡 단위로 계산된다 (datamodel.xml:110).

→ 그래서 **아무것도 지우거나 갈라 놓을 필요가 없다.** `tb_diag_job` 에 `dict_id` 를 기록만 해두고, 준수율은 지금처럼 최신 하나를 보여준다. `attr` 플래그도 "마지막 진단 결과" 그대로 둔다. (설계 §6.3)

### 2.6 자동 표준화에는 대상 모델 개념이 아예 없다

`DSTermRecommend.vue` 는 `props: ['isMobile']` 이 전부다. 어느 DB 를 표준화하는 중인지, 어느 사전에 등록하는지 모른 채 전역 사전에 바로 쓴다.

```
api/std/registerWord          (DSTermRecommend.vue:968)
api/std/registerTermsBatch    (DSTermRecommend.vue:1223, 1255)
```

`DSTermResolveHistory` · `DSDataModel` 도 `dmId` 참조가 0건이다.

→ 사전을 나누려면 **자동 표준화에 "대상 모델 / 등록할 사전" 선택 단계를 새로 만들어야 한다.** 기존 컬럼에 조건 하나 붙이는 수준이 아니라 화면 흐름 신설이다. 이번 설계에서 가장 큰 단일 작업.

## 3. 목표 / 비목표

**목표**
- 한 인스턴스에서 복수 표준사전 공존
- 작업마다 **[대상 모델] + [쓸 사전]** 을 골라서 수행 — 모델에 사전을 고정 배속하지 않는다
- 같은 모델을 다른 사전으로 재볼 수 있고, 어느 사전으로 쟀는지가 결과에 남는다
- 표준화 관례 차이(형식단어 필수 여부 등)를 사전 속성으로 수용
- 기존 데이터는 무손실로 기본 사전에 담긴다

**비목표 (이번 범위 아님)**
- 사전 간 병합 · 비교 · 상속
- 사전별 권한 분리 (누가 어느 사전을 고칠 수 있는가)
- 사전 버전 관리 / 스냅샷

## 4. 개념

```
표준사전 (tb_std_dict)
  └─ 단어 · 용어 · 도메인 · 도메인그룹 · 도메인분류 · 코드
       + 사전 속성 (형식단어 필수 여부, 영문약어 표기 규칙 …)

데이터 모델 = DB (tb_data_model)
  └─ dict_id → 등록 시 선택, 수정에서 변경 가능 (고정 배속 아님)

모든 작업 = [대상 모델] + [사용할 사전] 을 정하고 시작한다
  진단 실행 · 자동 표준화 · 일괄등록 · 사전 화면
```

### 4.1 사전은 모델 등록 시 고른다. 다만 못 박지는 않는다

**모델을 등록할 때 쓸 사전을 선택한다.** 수집(물리)으로 만들든 논리모델부터 시작하든 같다 — 등록 경로가 하나뿐이라(§4.3) 화면 한 곳, API 한 곳만 손대면 된다.

고정 배속은 아니다. 같은 DB 를 다른 사전으로 재보는 일이 있다 — 기관 표준으로 한 번, 행안부 공통표준으로 한 번. 그래서

- `tb_data_model.dict_id` 는 등록 시 정해지고, **모델 수정 화면에서 바꿀 수 있다.**
- 진단 실행처럼 사람이 개입하는 작업은 **그 자리에서 다른 사전을 지정할 수 있다.** 안 주면 모델에 저장된 값을 쓴다.

사전을 바꿔도 **지난 진단 결과는 지우지 않는다.** 그때 그 사전으로 잰 이력이라 그대로 의미가 있고, 준수율은 어차피 진단 잡 단위로 사전이 구분된다. 다만 재진단 전까지는 "이 표시는 이전 사전 기준" 임을 화면에 알린다 (§6.3c).

### 4.2 사전 없는 모델은 스케줄을 못 쓴다

사전 미지정 모델도 만들 수는 있다. 대신 **예약 실행 계열 기능이 막힌다.** 예약 실행에는 사전을 고를 사람이 없기 때문이다.

| 기능 | 사전 미지정 모델 |
|---|---|
| 수동 진단 실행 | 가능 (실행 시 사전을 고르게 함) |
| 스케줄 등록 · 예약 진단 | **불가** — 등록 단계에서 막고 사유 안내 |
| 자동 표준화 | 가능 (등록할 사전을 고르게 함) |

### 4.3 등록 경로는 하나다 (확인함)

물리·논리 모두 `MODEL_TYPE` 만 다를 뿐 같은 곳을 지난다.

```
DSDatamodelCollection.vue (등록/수정 모달 — add_* / update_* 한 화면)
  → POST api/dm/createDataModel        DataModelController.java:184
  → datamodel.insertDataModel          datamodel.xml:621
  → datamodel.updateDataModel          datamodel.xml:647   (사전 변경)
```

→ 사전 선택 추가는 **화면 1곳 + VO 1개 + INSERT/UPDATE 각 1개.**

### 4.4 원칙

**사전은 소유자가 아니라 이름공간이다.** 사전을 지운다고 모델이 지워지지 않는다. 대신 어떤 사전으로 쟀는지가 결과에 반드시 남아야 한다 (§6.3).

## 6. 코드 변경

### 6.1 조회 계층 — 세 갈래로 나뉜다

**(a) 사전 전체 로드 5곳** — 파라미터만 추가. 가장 쉽고 가장 중요하다.

```
terms.selectAllTermsForDiag   ← DiagService:99
terms.selectAllTermsByNm      ← TermRecommendService:21
word.selectAllWords           ← TermRecommendService:28
word.selectWordUsageCounts    ← TermRecommendService:38
domain.selectAllDomains       ← TermRecommendService:47
```

**(b) 이름으로 단건 조회** — 사전 없이는 답이 안 나오는 것들. 전부 `dict_id` 를 받아야 한다.

```
word.selectWordByEngAbrvNm      terms.selectTermsByEngNm
word.selectWordByForbiddenNm    domain.selectDomainInfoByNm
```

이 넷이 일괄등록 검증의 핵심이고, 지금 전역 조회라 **다른 사전의 단어를 보고 통과/차단시킨다.**

**(c) 화면 목록 조회** — 검색 조건에 `dict_id` 추가. `NDQualityRetrieveCond` 에 필드 하나.

### 6.2 작업 컨텍스트 — 모든 작업은 [모델] + [사전] 으로 시작한다

| 작업 | 모델 | 사전 |
|---|---|---|
| **모델 등록 · 수정** | — | **선택** ← 신규 (§4.1) |
| 표준 진단 실행 | 사용자가 선택 (기존과 동일) | **선택 (기본: 모델의 `dict_id`)** ← 신규 |
| 스케줄 진단 | 스케줄에 저장 | 스케줄의 `dict_id`, 없으면 모델값. **모델에 사전 없으면 스케줄 등록 자체를 막는다** |
| 자동 표준화 | **선택** ← 신규 (지금은 개념 자체가 없음) | **선택 (기본: 모델의 `dict_id`)** ← 신규 |
| 일괄등록 (엑셀) | 해당 없음 | **선택 필수** ← 신규 |
| 표준사전 화면 | 해당 없음 | **선택 (세션 유지)** ← 신규 |
| 승인 워크플로 | — | 대상 레코드의 `dict_id` 따라감 |

자동 표준화가 가장 크게 바뀐다. §2.6 대로 지금은 모델 개념이 아예 없어서, **"어느 DB 를 표준화하는가 / 어느 사전에 등록하는가"** 선택 단계를 새로 만들어야 한다.

### 6.3 진단 결과는 "어느 사전으로 쟀는지" 와 한 몸이다

모델을 여러 사전으로 잴 수 있게 되므로 (§4.1), 결과만 남기면 의미가 없어진다.

**(a) 진단 이력** — `tb_diag_job.dict_id` 를 남긴다. 컬럼 하나이고, 나중에 "이 수치가 왜 튀었나" 를 답할 수 있는 유일한 기록이다.

**추이 그래프는 건드리지 않는다.** 준수율은 지금처럼 **최신 진단 결과 하나**를 보여주고 추이도 한 선으로 그린다. 사전명은 진단 이력 목록과 상세에만 표시한다.

초안에서는 사전이 다른 진단끼리 추이를 갈라 그리려 했으나 **철회한다.** 두 가지 이유다.

첫째, 사전을 바꾸는 일 자체가 드물다. 거의 발동하지 않을 코드다.

둘째, 더 중요한데 — **사전을 바꿔 준수율이 뛰면 그건 왜곡이 아니라 신호다.** 62% → 88% 는 "자를 바꿔서 숫자가 좋아 보이는 것" 이 아니라 **이전 사전이 그 모델을 제대로 덮지 못하고 있었다**는 뜻이다. 그 사실은 감추거나 갈라 놓을 게 아니라 한 선에 그대로 드러나야 한다. 사전을 잘못 물린 게 이상 상태였던 것이고, 그래프는 그걸 보여주는 게 맞다.

**(b) 모델에 남는 플래그** — `tb_data_model_attr` 의
`terms_stnd_yn` · `domain_stnd_yn` · `word_lst` · `word_stnd_lst` 는
**"마지막 진단의 결과"** 라는 뜻으로 확정한다. 화면에서 이 값을 보여줄 때는 항상 마지막 진단이 어느 사전이었는지를 같이 보여준다.

**(c) 모델 수정에서 사전을 바꿀 때 — 아무것도 지우지 않는다**

초안에서는 플래그를 초기화하려 했으나 철회한다. 지난 진단은 무의미해지는 게 아니라 **"그때 그 사전으로 잰 결과"** 라는 이력이다. 지울 이유가 없다. 사전 변경 자체도 드문 일이다.

구조상으로도 지울 필요가 없다.

| 무엇 | 어디서 나오나 | 사전 구분 |
|---|---|---|
| 준수율 · 추이 | `TB_DIAG_JOB` + `TB_DIAG_RESULT` (datamodel.xml:110, diag.xml:109) | `tb_diag_job.dict_id` 로 **자동 구분됨** |
| 컬럼 화면의 표준 여부 표시 · 필터 | `tb_data_model_attr.TERMS_STND_YN` (datamodel.xml:458, 579) | 마지막 진단 결과 |

준수율은 진단 잡 단위로 계산되므로 `dict_id` 만 붙이면 이력이 알아서 사전별로 갈린다. `attr` 플래그를 지워도 준수율은 그대로고, **컬럼 화면의 표시 정보만 사라진다.** 손해만 있다.

**대신 할 일** — 사전이 바뀌었는데 재진단을 아직 안 했으면 화면에 그 사실을 알린다.

- 모델·컬럼 화면 상단: `표준 여부는 2026-09-01 「행안부 공통표준」 기준입니다. 현재 사전은 「RAMS 표준」 — 재진단 필요`
- 강제하지 않는다. 배지와 [재진단] 버튼까지.

판단 근거는 `tb_diag_job` 의 마지막 잡 `dict_id` 와 현재 `tb_data_model.dict_id` 비교.

### 6.4 승인 — 컬럼 추가 없이 해결된다

승인 대기 목록은 `tb_aprv_stats` 를 안 읽는다. `TB_TERMS` · `TB_WORD` · `TB_DOMAIN` **원본에서 UNION ALL 로 직접 뽑는다** (approve.xml:6). `tb_aprv_stats` 는 "이미 신청된 건 제외" 하는 `NOT EXISTS` 에만 쓰인다.

원본 테이블에는 어차피 `dict_id` 가 붙으므로 — SELECT 절에 `dict_id` 한 줄, WHERE 에 필터 하나. **`tb_aprv_stats` 에는 컬럼을 추가하지 않는다.**

승인 이력 조회 3곳(approve.xml:156, 159, 299)도 `req_item_id` 로 원본을 찾을 수 있어 별도 스코프 키가 필요 없다.

## 7. 규칙을 어디에 둘 것인가

처음엔 전역 시스템설정(`tb_sys_config`)으로 빼려 했다. 설계를 진행해 보니 **틀렸다.**

형식단어를 마지막에 두는 관례는 *사전마다 다르다.* 행안부 공통표준은 그렇게 쓰고, RAMS SMETA 자료는 안 그렇다. 그러니 이건 시스템 속성이 아니라 **사전 속성**이다. → `tb_std_dict.term_last_word_clsf_yn`

같은 성격으로 앞으로 사전 속성에 들어갈 만한 것들:
- 영문약어 표기 규칙 (대문자만 / 숫자 허용 여부) — 지금 `^[A-Z0-9]+$` 하드코딩
- 단어 설명 필수 여부
- 형식단어의 도메인분류명 필수 여부 — 지금 무조건 필수

**기본값은 전부 "완화"** 로 둔다. 기존 사전(DEFAULT)만 현재 동작을 유지하도록 `Y` 로 시드한다.

### 11.3 RAMS 적재 — 별도 인스턴스를 안 가는 이유

검토 중에 "RAMS 전용 스택을 한 벌 더 띄우자" 는 안이 나왔으나 **철회한다.**

별도 인스턴스는 *세트가 없을 때* 사전이 섞이는 걸 막는 우회책이다. 세트를 만들 거라면 그 작업이 통째로 버려진다 — compose 오버라이드, 빈 DB 초기화(스냅샷 이미지라 정품 이미지 + initdb 로 새로 구성해야 함), 그리고 나중에 본 인스턴스로 이관까지.

세트가 있으면 그냥 이렇게 끝난다.

```
사전 추가 「RAMS 표준」 → 그 사전 선택 → 단어·도메인·용어 업로드 → 모델에 RAMS 사전 지정
```

**기존 사전은 건드리지 않는다.** §8 대로 지금 데이터는 전부 `DEFAULT` 사전에 담기고, RAMS 는 그 옆에 새 사전으로 선다. 둘이 한 인스턴스에 공존하므로 화면에서 비교도 된다.

> 별도 인스턴스가 정당해지는 경우는 하나뿐 — **세트 1~4단계 완성보다 RAMS 적재 마감이 먼저일 때.**
> 그 상황이 오면 그때 다시 판단한다.
