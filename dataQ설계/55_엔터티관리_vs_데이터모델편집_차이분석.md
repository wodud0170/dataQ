# SMETA "엔터티 등록/관리" vs DataQ "데이터모델 편집" — 심층 차이 분석

**작성일:** 2026-04-21
**연계 문서:** `54_DataQ_vs_SMETA_데이터모델관리_비교.md`
**목적:** 표면상 비슷해 보이는 두 기능의 **본질적 차이**를 개념·데이터 구조·사용자·워크플로우 전 관점에서 해부. 향후 엔터티 도입 여부·범위를 판단하기 위한 근거 문서.

---

## 0. 한 줄 요약

**엔터티 관리는 "물리 DB가 없어도 성립하는 업무 개념 설계"이고, DataQ 데이터모델 편집은 "물리 DB 객체 또는 그에 준하는 단위를 다루는 것"이다.** 같은 그리드에 행을 추가해도 **행이 가리키는 대상의 추상화 레벨이 다르다**.

---

## 1. 개념적 추상화 레이어의 차이

### 1-1. 세 개의 레이어 (Data Architecture 표준)

데이터 모델링은 전통적으로 3계층으로 나뉜다.

```
┌─────────────────────────────────────────┐
│ 개념 모델 (Conceptual)                    │  업무 개념 수준
│ — 주제영역, 주요 업무 객체               │
├─────────────────────────────────────────┤
│ 논리 모델 (Logical)                      │  업무 규칙 + 정규화
│ — 엔터티, 속성, 관계, 식별자              │
├─────────────────────────────────────────┤
│ 물리 모델 (Physical)                     │  DBMS 종속
│ — 테이블, 컬럼, 타입, 인덱스, 제약조건    │
└─────────────────────────────────────────┘
```

### 1-2. SMETA "엔터티"의 위치

SMETA의 엔터티는 **논리 모델 레이어**의 단위다. 물리 DB가 없어도(예: 신규 시스템 설계 초기) 존재 가능.

- 예: "고객" 엔터티 — 업무 개념
- 속성: "고객번호"(식별자), "고객명", "고객등급", "가입일시"
- 관계: "고객" 1:N "주문"
- **이 시점에 물리 테이블명·타입·DBMS는 결정되지 않음**

엔터티는 이후 변환 과정을 거쳐 물리 테이블로 "구현(implement)"된다:
- 엔터티 "고객" → 테이블 `TB_CUSTOMER`
- 속성 "고객등급" → 컬럼 `CUST_LVL_CD VARCHAR(4)` (도메인 매핑)

### 1-3. DataQ "데이터모델 편집"의 위치

DataQ의 `TB_DATA_MODEL_OBJ` / `TB_DATA_MODEL_ATTR`은 **물리 모델 레이어**에 가깝다. 논리/물리 분리가 구조적으로 안 되어 있고, **행 하나가 곧 DB 객체 하나**를 가리킨다.

실제 VO/테이블 컬럼을 보면 물리 지향성이 분명하다:

```
TB_DATA_MODEL_OBJ
  ├─ OBJ_NM           (물리 테이블명 — PK의 일부)
  ├─ OBJ_NM_KR        (한글명 — 보조)
  ├─ OBJ_OWNER        (스키마/소유자 — 물리 개념)
  ├─ OBJ_DESC
  └─ OBJ_ATTR_CNT

TB_DATA_MODEL_ATTR
  ├─ ATTR_NM          (물리 컬럼명 — PK의 일부)
  ├─ ATTR_NM_KR
  ├─ DATA_TYPE        (VARCHAR, NUMBER ... DBMS 타입)
  ├─ DATA_LEN
  ├─ NULLABLE_YN
  ├─ PK_YN / FK_YN    (DB 제약조건 플래그)
  └─ DEFAULT_VAL
```

- PK가 `(DM_ID, OBJ_NM)` — **물리명이 식별자**
- `DATA_TYPE`이 `VARCHAR`/`NUMBER` 등 DBMS 타입 — **도메인 개념 아님**
- `OWNER`가 스키마명 — **DBMS 배포 기반**

53번 구현으로 `TMP_TBL_N`·`TMP_COL_N` 자동 생성이 붙어 **물리명 없이도 행을 만들 수 있게** 됐지만, **구조(스키마)는 여전히 물리 모델 그대로**다. "논리"라는 건 `modelType='LOGICAL'` 플래그 하나에 불과하다.

### 1-4. 핵심 차이

| 관점 | SMETA 엔터티 | DataQ 데이터모델 편집 |
|------|------|------|
| 추상화 레이어 | 논리 모델 | 물리 모델 (물리명 생략 허용만 추가됨) |
| 행의 정체 | "업무 객체(Customer)" | "물리 테이블 또는 그 후보(TMP_TBL_1)" |
| 속성의 정체 | "업무 속성(고객등급)" | "컬럼(CUST_LVL_CD VARCHAR(4))" |
| DBMS 종속성 | 없음 | 있음 (타입·길이·소유자) |
| 물리 구현 전 존재 가능 여부 | 가능 (설계 단계) | 가능하지만 "임시 물리" 형태 |

## 2. 계층 구조 — 주제영역의 유무

### 2-1. SMETA 3계층

```
주제영역(Subject Area)  "고객관리"
 └─ 엔터티(Entity)      "고객", "고객연락처", "고객등급이력"
     └─ 속성(Attribute)  "고객번호"(식별자), "고객명", ...
```

주제영역은 **업무 묶음**이다. 동일 엔터티가 여러 주제영역에 속하기도 하고(공유 엔터티), 주제영역 단위로 담당자/결재자가 다르기도 하다.

### 2-2. DataQ 2계층

```
데이터 모델(DM_ID)  "운영DB_2026_04"
 └─ 테이블(OBJ)    "TB_CUSTOMER", "TB_CUSTOMER_CONTACT", ...
     └─ 컬럼(ATTR)  "CUST_ID PK", "CUST_NM VARCHAR(50)", ...
```

"데이터 모델"은 사실상 **수집 대상 DBMS 한 덩어리** 또는 **하나의 논리 작업 단위**다. 업무 분류가 아니다.

| 항목 | SMETA | DataQ |
|------|------|------|
| 최상위 | 주제영역(업무 분류) | 데이터 모델(수집 단위) |
| 중간 | 엔터티 | 테이블(OBJ) |
| 하위 | 속성 | 컬럼(ATTR) |
| 계층 수 | 3 | 2 |
| 최상위의 본질 | 업무 영역 | 기술적 수집/작업 단위 |

## 3. 식별자·명명 전략의 차이

### 3-1. SMETA — 논리명 우선

- **엔터티명은 업무 용어** (예: "고객")
- **속성명도 업무 용어** (예: "고객등급")
- 물리명(TB_CUSTOMER, CUST_LVL_CD)은 표준사전 기반으로 **자동 생성**
- 식별자는 엔터티 ID + 속성 시퀀스 (내부 UUID/seq) — 업무명이 바뀌어도 추적 가능

### 3-2. DataQ — 물리명 우선

- PK가 `(DM_ID, OBJ_NM)` / `(DM_ID, OBJ_NM, ATTR_NM)` — **물리명이 곧 식별자**
- 한글명(`OBJ_NM_KR`, `ATTR_NM_KR`)은 보조 정보
- 53번으로 `TMP_TBL_N` 자동 생성을 도입했지만, 이 이름도 한번 생성되면 식별자로 고정됨
- **물리명을 바꾸면 사실상 다른 행이 됨** (소프트 삭제 + 신규 INSERT)

### 3-3. 결과적 차이

| 시나리오 | SMETA | DataQ |
|----------|------|------|
| 엔터티/테이블 이름 변경 | 엔터티 ID 유지, 표시명만 변경 | 새 OBJ_NM으로 insert + 기존 soft delete |
| 속성 한글명 변경 | 속성 ID 유지 | ATTR_NM_KR 업데이트 (ATTR_NM은 그대로) |
| 물리명만 바꾸고 싶음 | 변환 규칙 수정으로 재생성 | 행을 다시 만들어야 함 |
| 같은 업무 속성을 2개 테이블에 반영 | 속성을 공유 참조 가능 | 각 테이블에 별도 row |

## 4. 관계(Relationship)의 의미

### 4-1. SMETA — 업무 관계

- "고객"이 "주문"을 **한다** — 이 동사가 관계의 이름
- 관계 유형: 1:1, 1:N, N:M, 식별관계/비식별관계
- 관계는 **제약조건이 아니라 업무 규칙의 명세**
- 이후 물리 변환 시 FK 제약으로 구현되거나, 중간 테이블(N:M 해소)로 전개됨

### 4-2. DataQ — FK 제약 플래그

- `FK_YN = 'Y'` 플래그만 있음
- 53번 엑셀 업로드로 참조 테이블/컬럼 이름은 받지만 **`TB_DATA_MODEL_CONSTRAINT` INSERT 미완**
- 관계에 업무 의미(이름, 동사)가 없음
- 관계의 유형(식별/비식별, 1:1 / 1:N / N:M) 구분 없음

### 4-3. 의미의 차이

SMETA에서 "고객-주문" 관계를 삭제하면 "고객이 주문을 할 수 없다"는 업무 변경이 명시된다. DataQ에서 FK_YN='N'으로 바꾸면 "DB 레벨 참조 제약이 없어진다"는 기술적 의미만 있다.

## 5. 소유자·생명주기

### 5-1. 소유자

| 레이어 | SMETA 엔터티 | DataQ 데이터모델 편집 |
|------|------|------|
| 설계 주도 | 업무 분석가, 데이터 아키텍트 | DBA, 개발자 |
| 주 사용자 | 업무 담당자 (결재 승인) | 개발자 (수집 결과 확인) |
| 결재 참여 | 엔터티 단위 결재 필요 | 표준사전만 결재. 모델은 대부분 자유 수정 |

### 5-2. 생명주기

**SMETA 엔터티**
```
요청(신규 등록) → 결재(팀장/관리자) → 승인 → 논리모델 반영
  → 변환 규칙 적용 → 물리모델 생성 → DBMS 배포 신청 → 결재 → 배포
```

**DataQ 데이터모델**
```
(A) 수집 경로: DBMS 접속 → 자동 수집 → 표준화 진단 → 컬럼 수정(자유) → 저장
(B) 수동 경로: [테이블 추가] → [컬럼 추가/붙여넣기/업로드] → [선택 컬럼 물리 변환] → 저장
```

- DataQ에는 **"설계 승인"** 단계가 구조적으로 없음
- 반대로 SMETA에는 **"자동 수집 + 표준화 자동추천"** 파이프라인이 약함

## 6. 변환 방향 — 탑다운 vs 바텀업

### 6-1. SMETA (탑다운)

```
업무 요구사항
  → 개념 모델 (주제영역)
    → 논리 모델 (엔터티·속성·관계)  ← 사용자가 설계
      → 물리 모델 (테이블·컬럼·타입)  ← 자동 변환
        → DBMS 배포
```

- "먼저 설계하고 구현한다"
- 표준사전·도메인이 변환 규칙의 입력
- ERwin 연계는 논리·물리 양쪽 다 지원

### 6-2. DataQ (바텀업 + 부분 탑다운)

```
(기본: 바텀업)
DBMS 현황 → 수집 → 물리 데이터 모델 → 표준화 진단 → 비표준 컬럼 탐지 → 자동 추천 → 수정

(53번 이후: 부분 탑다운)
빈 모델 생성 → [테이블 추가] → [컬럼 추가] → [선택 물리 변환] → 이미 물리 모델
```

- "있는 것을 분석하고 개선한다"가 기본
- 53번으로 탑다운 경로가 추가됐지만 **중간 레이어(엔터티)가 없어** SMETA의 설계 흐름과는 다름

## 7. 데이터 모델의 "존재 목적" 차이

| 관점 | SMETA | DataQ |
|------|------|------|
| 왜 등록하는가 | 업무 모델을 조직 표준으로 확정하고 DBMS 배포로 연결 | 품질 진단·표준 준수율 측정·현행 DBMS 관리 |
| 최종 산출물 | DDL 스크립트 + 유지관리되는 논리모델 | 품질 리포트 + 표준 준수율 통계 |
| 모델이 사라지면 | 조직의 설계 자산이 소실 | 진단 통계가 없어짐 (재수집 가능) |
| DBMS 없이 가치 | 충분 (신규 시스템 설계 단계) | 매우 제한적 |

## 8. "엔터티"를 도입한다면 — 구체적 변화

### 8-1. 데이터 모델 변화

**신규 테이블**
```sql
CREATE TABLE TB_SUBJECT_AREA (
  SA_ID         VARCHAR(36) PRIMARY KEY,
  SA_NM         VARCHAR(100) NOT NULL,
  SA_PARENT_ID  VARCHAR(36),   -- 계층
  SA_DESC       VARCHAR(500),
  ...
);

CREATE TABLE TB_ENTITY (
  ENT_ID        VARCHAR(36) PRIMARY KEY,   -- 내부 식별자
  SA_ID         VARCHAR(36),               -- 주제영역
  ENT_NM_KR     VARCHAR(200) NOT NULL,     -- 논리명 = 업무명
  ENT_TYPE      VARCHAR(20),                -- 키/메인/행위/이력 등
  ENT_DESC      VARCHAR(1000),
  APRV_YN       CHAR(1),
  ...
);

CREATE TABLE TB_ENTITY_ATTR (
  ENT_ID        VARCHAR(36),
  ATTR_SEQ      INT,
  ATTR_NM_KR    VARCHAR(200),
  TERMS_ID      VARCHAR(36),   -- 용어사전 연결
  DOMAIN_ID     VARCHAR(36),   -- 도메인 연결 (→ 물리타입 자동결정)
  PK_YN         CHAR(1),
  REQUIRED_YN   CHAR(1),
  PRIMARY KEY (ENT_ID, ATTR_SEQ)
);

CREATE TABLE TB_ENTITY_REL (
  REL_ID        VARCHAR(36) PRIMARY KEY,
  FROM_ENT_ID   VARCHAR(36),
  TO_ENT_ID     VARCHAR(36),
  REL_NM        VARCHAR(100),   -- 업무 관계명 (예: "주문한다")
  CARDINALITY   VARCHAR(10),    -- 1:1, 1:N, N:M
  IDENTIFYING_YN CHAR(1)         -- 식별/비식별
);

-- 엔터티 → 물리 테이블 매핑 (n:1 또는 n:n 가능)
CREATE TABLE TB_ENTITY_TO_OBJ (
  ENT_ID        VARCHAR(36),
  DM_ID         VARCHAR(36),
  OBJ_NM        VARCHAR(100),
  MAPPING_TYPE  VARCHAR(20),    -- ONE_TO_ONE / SPLIT / MERGE
  PRIMARY KEY (ENT_ID, DM_ID, OBJ_NM)
);
```

### 8-2. UI 변화

- 메뉴 "데이터 모델" → "논리 모델(엔터티)"과 "물리 모델(수집/테이블)" 분리
- 엔터티 화면: 주제영역 트리 + 엔터티 리스트 + 속성 그리드
- 관계 화면: 엔터티 간 관계 리스트
- 기존 컬럼 편집 화면은 "물리 모델" 탭으로 유지

### 8-3. 변환 흐름 변화

```
(신규)
엔터티 등록 → 속성 등록(용어사전 연결) → [물리 모델 생성] 클릭
  → 표준사전 기반 OBJ_NM 생성
  → 도메인 기반 DATA_TYPE/LEN 결정
  → TB_DATA_MODEL_OBJ / ATTR INSERT

(기존 53번 경로는 유지)
빈 모델 → 테이블 추가 → 컬럼 그리드 편집 → [선택 컬럼 물리 변환]
```

### 8-4. 결재 변화

- 엔터티 단위 결재 (`TB_ENTITY.APRV_YN`) 신설
- 기존 표준사전 결재 프레임워크(`TB_APRV_STATS`) 재사용
- 승인 후에만 "물리 모델 생성" 가능

## 9. 도입 여부 판단 — 결정 요소

### 9-1. 도입 논리

- **공공 조달 RFP 대응**: 주제영역·엔터티·속성 계층이 RFP에 거의 항상 명시됨
- **설계 자산화**: 조직이 논리 모델을 유지하는 가치 인식 시
- **기존 기능과 공존 가능**: 수집·자동추천은 유지, 엔터티는 별도 진입점

### 9-2. 도입 부담

- 테이블 5종 신설 + 컨트롤러 2~3종 신설
- 기존 "데이터 모델" 메뉴와 네비게이션 재편
- 결재 프레임워크 확장
- 용어사전·도메인과의 참조 무결성 관리

### 9-3. 중도 선택지 — "엔터티 경량 도입"

풀 스펙 대신 다음만 도입해도 SMETA 기능 체크리스트 상당수를 충족한다:

- 주제영역(`TB_SUBJECT_AREA`) — 단순 분류
- 테이블(OBJ)에 `SA_ID` + `ENT_TYPE` 컬럼 추가 (엔터티 전용 테이블 신설 회피)
- `OBJ_NM_KR`을 엔터티명으로 재활용 (기존 데이터 활용)
- 관계는 53번 후속 FK 완성으로 대체

**장점:** 기존 구조 유지하며 "엔터티 계층이 있다"는 요건 충족
**단점:** 엔터티-테이블 분리(1:N 매핑)가 불가능. 진짜 논리 모델링은 아님

## 10. 결론

1. **SMETA 엔터티 관리**와 **DataQ 데이터모델 편집**은 UI·데이터 구조가 비슷해 보여도 **추상화 레이어가 다른 기능**이다.
2. SMETA는 **논리 → 물리**, DataQ는 **물리/수집 → 표준화**가 기본 흐름이다.
3. 53번 구현으로 DataQ의 물리 모델 편집 편의성이 엔터티 관리 수준에 근접했지만, **"업무 개념으로서의 엔터티"는 여전히 없다**.
4. 도입 시 **5종 테이블 신설 + UI 재편 + 결재 확장**이 최소 범위. 경량 도입 시 2종 테이블로 축소 가능하나 진짜 논리 모델링 가치는 제한적.
5. **결정 기준은 공공 조달 RFP 대응 필요성.** 내부 품질 관리 용도로만 쓸 거면 불필요.
