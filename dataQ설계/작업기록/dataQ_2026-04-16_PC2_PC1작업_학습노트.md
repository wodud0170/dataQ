## 2. `FROM DUAL` 제거 (어제 PC2에서 추적한 이슈의 확정 수정)

### 배경
PC2에서 대시보드 건수 0 이슈 추적 중 `FROM DUAL`이 PostgreSQL에 없어 터지는 걸 확인했었음. PC1 사용자가 C안(SQL에서 제거)을 채택해서 전량 정리.

### 수정 범위 (2개 파일)
- [search.xml](../../q-common/src/main/resources/mapper/stnd/search.xml) — `selectDataboardInfo`의 외부 `from DUAL` 및 `aprvStatRequestedCnt` 서브쿼리 `from DUAL` 제거
- [terms.xml](../../q-common/src/main/resources/mapper/stnd/terms.xml) — 5곳의 `(select ... from dual)` → 단순 concat 표현식으로 교체 (VARCHAR/CHAR 길이 문자열 생성부)

### 내가 배운 것
- **패턴 1**: `from DUAL`을 직접 삭제 (select에 FROM 없이 괜찮음)
- **패턴 2**: `(select A.X||'...' from dual)` 같은 Oracle 스타일 더미 서브쿼리는 서브쿼리 자체를 걷어내고 표현식만 남기면 됨
- 작업일지에 따르면 **14건 전부 제거** 완료. terms.xml 외에 다른 매퍼에도 있었던 것으로 추정 → 앞으로 새 쿼리 작성 시 `FROM DUAL` 절대 금지.

### PC2 세션 작업 반영
이미 push했던 [dataQ_2026-04-14_작업일지.md](dataQ_2026-04-14_작업일지.md)의 "남은 작업 → 대시보드 FROM DUAL 해결" 항목은 **해결 완료**로 간주. 당시 A/B/C안 중 C안(SQL 제거) 채택.

## 4. 승인 프로세스 재설계 (핵심)

어제 PC2에서 발견했던 "일괄등록 무조건 APRV_YN=Y 하드코딩" 보안 구멍이 **정식 재설계**로 이어졌음. 설계서 [38_승인프로세스_재설계.md](../38_승인프로세스_재설계.md)와 구현(`e5d8037`)이 같은 날 push됨.

### 4.1 재설계 핵심 원칙

| 구분 | 권한 | 등록 시 상태 |
|---|---|---|
| 관리자 (`ADM_YN=true`) | 즉시 승인 `APRV_YN='Y'` | 모든 등록 경로 동일 |
| 일반 사용자 (`ADM_YN=false`) | 승인대기 `APRV_YN='N'` + `TB_APRV_STATS` 생성 | 관리자 승인 후 반영 |

**모든 표준 데이터(단어/용어/도메인/도메인그룹/도메인분류/코드/코드데이터)에 동일 적용.** 예외 없음.

### 4.2 승인 상태 단순화 (4단계 → 2단계 + 최종)
```
전: 0(요청) → 1(검토중) → 2(승인) | 3(반려)
후: 0(승인대기) → 2(승인) | 3(반려)
```
- `APRV_STAT = 1`(검토중) 완전 제거
- 상태 라벨 "요청" → "승인대기"

### 4.3 APRV_YN 설정 통일 (Critical 수정)

| 경로 | 수정 전 | 수정 후 |
|---|---|---|
| 단건 등록 | 관리자=Y, 일반=N (정상) | 동일 |
| 엑셀 일괄등록 | **무조건 Y** | `isAdminUser()` 체크 → Y/N 분기 |
| `registerTermsBatch`(자동추천) | **APRV_YN=NULL 버그** | 관리자 체크 + 설정 |
| 도메인그룹/분류 일괄등록 | **무조건 Y** | `isAdminUser()` 체크 |

### 4.4 `isAdminUser()` 구현 위치
- [sysinfo.xml](../../q-common/src/main/resources/mapper/stnd/sysinfo.xml)에 `selectIsAdmin` 쿼리 신규
- `ExcelUploadService`에서 `String aprvYn = isAdminUser(session, userId) ? "Y" : "N";` 한 줄로 결정
- 이후 word/term/domain/group/clsf 전부 이 변수 공유

### 4.5 내 작업에 미치는 영향
- 어제 내가 작성한 [DSDomainGroup.vue](../../q-center/vue/front/src/components/DSDomainGroup.vue) / [DSDomainClassification.vue](../../q-center/vue/front/src/components/DSDomainClassification.vue)의 일괄등록 경로도 `ExcelUploadService.uploadDomainGroups/uploadDomainClsfs` 내부에서 이제 관리자 분기가 걸릴 것 (PC1에서 서비스 코드까지 수정됐는지는 diff로 확인했는데, 작업일지 상 "일괄등록 APRV_YN 관리자 분기" 범위에 포함됨)
- **앞으로 새로운 일괄등록/자동 등록 경로 추가 시 반드시 `isAdminUser()` 분기를 포함해야 함** — 기본값은 Y가 아니라 "사용자 권한에 따라"

## 5. 변경 이력 `CHANGE_SOURCE` 컬럼 신설

### 이유
`TB_CHANGE_HISTORY.SUMMARY`에 자유 텍스트만 있어서 "관리자 직접등록"과 "승인 경유 등록"이 구분 불가 → 통계/필터 불가.

### 구현
- DDL: `ALTER TABLE TB_CHANGE_HISTORY ADD COLUMN CHANGE_SOURCE VARCHAR(20);`
- 값 종류:
  - `ADMIN_DIRECT` — 관리자 직접등록
  - `USER_REQUEST` — 일반 사용자 등록 (승인대기)
  - `ADMIN_APPROVE` — 관리자 승인
  - `ADMIN_REJECT` — 관리자 반려
  - `BULK_UPLOAD` — 일괄등록
  - `AUTO_RECOMMEND` — 자동 표준화 추천
- [changehistory.xml](../../q-common/src/main/resources/mapper/stnd/changehistory.xml) INSERT/SELECT 반영
- [DSChangeHistory.vue](../../q-center/vue/front/src/components/DSChangeHistory.vue)에 "등록 경로" 필터 + 그리드 컬럼 추가

### 내가 지킬 점
- **앞으로 변경 이력 insert 호출 시 `changeSource` 값을 반드시 지정해야 함.** 안 넣으면 NULL → 필터에서 누락.
