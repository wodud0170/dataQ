## 4. 대시보드 `표준현황` 0건 출력 문제 (원인 규명, 미해결)

### 증상
일괄등록 후 `TB_TERMS/TB_WORD/TB_DOMAIN`은 데이터가 있고 `APRV_YN='Y'` 상태지만, 대시보드 카드엔 0건 표시.

### 추적 과정 (반복적 헛다리)
1. **가설 A (틀림)**: 승인여부 필터 때문. → 업로드 코드는 `setAprvYn("Y")` 하드코딩, 승인화면(N 필터)에 안 보이는 건 맞지만 대시보드(Y 필터)엔 **보여야 정상**. 오히려 "일반 사용자 일괄등록도 무조건 자동승인" 보안 구멍만 드러남.
2. **가설 B (틀림)**: PostgreSQL이 camelCase alias를 소문자로 접어서 MyBatis HashMap 매핑 실패. → snake_case로 고쳤다가 `mapUnderscoreToCamelCase`가 HashMap엔 적용 안 된다는 걸 깨닫고, 같은 파일 내 `AS "wordNm"` 쓰는 다른 쿼리 보고 따옴표 camelCase로 재수정. **사용자가 "다른 PC에선 같은 Postgres로 작동했다"고 지적** → 원복.
3. **가설 C (확정)**: `FROM DUAL` — Oracle 전용 더미 테이블. PostgreSQL엔 기본 없음. 다른 PC의 DB엔 `orafce` extension 또는 수동 DUAL view가 있었을 것.

### 진짜 원인
> **Docker 이미지 구성 시 "사용자 데이터만 포함한 dump"를 기반으로 제작 → `pg_dump --data-only`는 extension/view/함수를 안 가져옴 → `orafce` 또는 수동 `public.dual` view가 유실 → `selectDataboardInfo`의 `... from DUAL`이 relation 없음 에러 → 프론트 catch에서 조용히 0 렌더**

### 해결 방안 (미적용, 선택 대기)
A. Docker DB에 DUAL view 생성 (즉시 수정, SQL 무변경):
```sql
CREATE VIEW public.dual AS SELECT 'X'::text AS dummy;
GRANT SELECT ON public.dual TO PUBLIC;
```
B. `orafce` extension 설치 (Oracle 호환 함수 전반 제공)
C. SQL에서 `FROM DUAL` 전량 제거 (사용자가 거절 — 건드리지 말라 지시)

사용자는 **A안 선호 + 기존 DB의 Oracle 잔재 전체 분석** 예정.

### 교훈
- "다른 PC에서 됐다"는 증언은 **환경 차이**를 먼저 의심할 것. 코드부터 고치지 말 것.
- Docker로 DB 옮길 때 `pg_dump --data-only`는 함정: schema/extension/view/함수 전부 빠짐.
