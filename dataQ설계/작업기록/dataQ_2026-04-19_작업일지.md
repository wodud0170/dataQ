## 1. 용어등록 모달 "등록됨" 칩 버그 분석 (분석만, 수정 X)

### 요구
데이터 표준 사전 > 용어 등록 모달에서, 입력 용어를 형태소 분석기로 쪼갠 결과 중 **사전에 없는 단어**임에도 "등록됨" 칩이 붙어 표시되는 버그. 사용자는 "분석해서 문서로만 뽑고, 고치지는 말 것"을 요청.

### 문서
- [42_용어등록_미등록단어_등록됨칩_버그분석.md](../42_용어등록_미등록단어_등록됨칩_버그분석.md)

### 핵심 원인
`DataStandardController.getTermsTokenListByNm` — 사전에 없는 토큰에 대해 placeholder `StdWordVo`를 생성해 리스트에 추가하는 한 줄이 원인:

```java
// [DataStandardController.java:573-629]
if (wordVoLst.size() > 0) { ... } else {
    StdWordVo wordVo = new StdWordVo();
    wordVo.setWordNm(token);
    wordVo.setPartOfSpeech("NN");
    wordVoLst.add(wordVo);     // ← 이 한 줄이 문제
}
```

프론트(`DSTerm.vue`)는 `wordLst.length > 0`으로 "등록됨" 칩을 표시하므로, placeholder가 있는 토큰까지 등록된 것처럼 보이게 됨.

### 파급 영향 (4가지)
1. DB `TB_TERMS_WORDS.WORD_ID` null 삽입 위험
2. 형식단어 검증 우회
3. 영문 약어 → `undefined_...` 오염
4. 인라인 폼 데드 코드

### 권장 수정 방향
Option A — 백엔드에서 placeholder VO 추가 라인 제거, 빈 리스트로 반환하여 프론트가 자연히 "미등록"으로 판정하도록.

## 3. Oracle 테스트 DB 한글 코멘트 깨짐 → 컨테이너 교체

### 최초 증상
`doctorkirk/oracle-19c` 컨테이너의 SALES_APP 스키마를 DataQ에서 수집하면 한글 코멘트가 전부 `¿¿`로 깨져 들어옴. DBeaver 등 타 클라이언트에서도 동일하게 깨져 보임.

### 진단 과정
1. 먼저 DataQ 수집 쿼리(`OracleGetAttrs`, `OracleGetObjs`)와 JDBC 드라이버(orai18n.jar) 확인 → 클라이언트 측은 정상 구성
2. `NLS_LANG=AMERICAN_AMERICA.AL32UTF8` 환경변수로 재접속 후 `COMMENT ON` 재실행 → **여전히 깨짐**
3. `DUMP()` 함수로 실제 저장 바이트 확인:
   ```
   Typ=1 Len=2 CharacterSet=WE8MSWIN1252: bf,bf  (=¿¿)
   ```
4. `NLS_DATABASE_PARAMETERS.NLS_CHARACTERSET` 조회 결과: **WE8MSWIN1252** (Western European, 한글 저장 **불가능**)

### 근본 원인
`doctorkirk/oracle-19c` 이미지는 DB 자체의 character set이 `WE8MSWIN1252`로 **baked-in** 되어 있어 환경변수/클라이언트로 교정 불가. DB가 한글을 애초에 저장할 수 없음.

### 해결: 컨테이너 교체 (Option A)
- **이미지 변경**: `doctorkirk/oracle-19c` → `gvenzl/oracle-xe:21-slim-faststart`
  - DB character set 기본값 AL32UTF8
  - SID(`XE`) + PDB(`XEPDB1`) 구조 (Service Name 접속)
- **기존 스키마 구조 덤프**: 제거 전 14 테이블/81 컬럼 구조, 20 제약조건, 17 인덱스, 최소 데이터(각 스키마 2행)를 `ALL_TAB_COLUMNS`/`ALL_CONSTRAINTS`/`ALL_INDEXES`에서 전부 캡처
- **init SQL 작성**: [init_oracle_testdb.sql](../테스트/init_oracle_testdb.sql)
  - 3 스키마(SALES_APP/HRM_APP/INV_APP) + TESTUSER 생성
  - 14 테이블 + PK/FK/UK + 인덱스
  - 한글 코멘트 14 테이블 / 81 컬럼 모두 포함
  - 한글 테스트 데이터(고객/부서/창고) 삽입
- **접속 정보 문서 갱신**: [오라클_테스트환경_접속정보.md](../테스트/오라클_테스트환경_접속정보.md)
  - SID(`ORCLCDB`) → Service Name(`XEPDB1`)
  - 컨테이너명 `oracle-19c` → `oracle-xe`
  - DataQ 데이터소스 재등록 안내 포함

### 검증
- `NLS_CHARACTERSET = AL32UTF8` ✓
- `DUMP(COMMENTS)`: `고객` → `Typ=1 Len=6: 234,179,160,234,176,157` (UTF-8 6바이트 ✓)
- TESTUSER로 `ALL_TAB_COMMENTS` 14개 / `ALL_COL_COMMENTS` 81개 정상 조회 ✓

### drivers.xml — Oracle(Service Name) 드라이버 추가 (root lib)
- q-center/lib, q-executor/lib에는 기존에 있었으나 **루트 `lib/drivers.xml`에 누락**된 것을 발견하여 추가
- 동일하게 Tibero(Service Name)도 함께 추가해 일관성 유지

```xml
<driver>
  <driverType>Oracle</driverType>
  <driverName>Oracle(Service Name)</driverName>
  <className>oracle.jdbc.driver.OracleDriver</className>
  <urlType>jdbc:oracle:thin:@//%s:%d/%s</urlType>
  <driverFile>lib/jdbc/ojdbc8-21.1.0.0.jar;lib/jdbc/orai18n-21.1.0.0.jar</driverFile>
</driver>
```

## 4. 데이터소스 수정 시 연결테스트 NPE — 앱 버그 이슈 리포트

### 증상
기존 Oracle 데이터소스(SID=ORCLCDB)를 Service Name=XEPDB1로 **수정** 후 연결테스트:
- 프론트: "알 수 없는 오류가 발생했습니다" 모달
- 서버: `java.lang.NullPointerException`
  ```
  at DBConnectionManager$DBConnectionPool.getConnection(DBConnectionManager.java:228)
  at DBConnectionManager.getConnection(DBConnectionManager.java:94)
  at DBConnection.getConnection(DBConnection.java:158)
  at DBConnection.connect(DBConnection.java:118)
  at SysInfoController.testDataSource(SysInfoController.java:201)
  ```

### 회피책 (확인됨)
- **신규 데이터소스로 등록**: 정상 동작
- q-center 재시작: 기존 등록건도 정상 동작

### 원인 (확정)
`com.ndata.datasource.dbms.connection.DBConnectionManager`가 **static Map으로 dsn별 풀을 캐시**. 데이터소스 수정은 `TB_DATA_SOURCE` row만 update할 뿐 **캐시된 풀을 invalidate하지 않음**. SID 시절의 옛 풀이 재사용되며 NPE.

### 문서 (이슈 리포트)
- [45_데이터소스수정_풀캐시_NPE_이슈.md](../45_데이터소스수정_풀캐시_NPE_이슈.md)

### 권장 수정 방향 (3가지)
| 옵션 | 변경 범위 | 비고 |
|-----|----------|------|
| A | `SysInfoController.testDataSource` | 연결테스트 진입 시 옛 풀 close — 최소 변경, 권장 |
| B | `SysInfoController.updateDataSource` | 저장 직후 옛 풀 close — 테스트 없이 수정만 해도 수집/진단이 신규 연결정보로 |
| C | common-0.0.1-SNAPSHOT.jar 내부 | `DBConnectionManager.invalidate(dsn)` 공식 추가 — 근본 수정 |

**단기**: A + B 병행 (jar 수정 불필요).
**장기**: C로 이관.

> 이 세션에서는 **수정 없이 이슈 리포트만 작성**.
