## 1. 패키지 구성

| 이미지 | 내용 | 갱신 트리거 |
|---|---|---|
| `dataq-db:snapshot` | timescaledb 2.10.0-pg13 + 현재 PGDATA 박힘 | DDL/seed 데이터 변경 |
| `dataq-center:latest` | temurin-8-jre + q-center JAR + lib/jdbc + Vue 정적 산출물 | q-center 코드/Vue 변경 |

## 2. 패치 시나리오 3종

### 시나리오 A — 코드만 변경 (가장 흔함)

q-center 또는 q-executor 의 Java/Vue 만 바뀌고 DB 스키마 무변경.

**사용자 액션:**
1. 코드 수정 완료
2. `mvn package -DskipTests -T 1C`  (루트, Vue webpack 포함, ~60s)
3. **세션에 "코드 패치 배포해" 라고 요청**

**자동 실행 (이 세션):**
1. JAR 갱신 확인 (`q-center/target/*.jar`, `q-executor/target/q-executor.jar`)
2. `docker compose build q-center q-executor` (dataq-db 는 건드리지 않음)
3. `docker save -o ~/Desktop/dataq-stack.tar dataq-db:snapshot dataq-center:latest dataq-executor:latest`
4. 결과 보고 (이미지 사이즈, tar 사이즈)

→ **배포 PC 측 절차는 4번 참조.**

---

### 시나리오 B — DB만 변경 (DDL/seed 갱신)

dataq-db 의 PGDATA 가 바뀌었고 JAR 은 그대로.

**사용자 액션:**
1. dev `dataq-db` 컨테이너에 DDL/데이터 적용 완료
2. **세션에 "DB 패치 배포해" 라고 요청**

**자동 실행 (이 세션):**
1. 사용자에게 `docker stop dataq-db` 요청 (라이브 복사는 데이터 일관성 깨짐)
2. stop 확인 후 PGDATA 추출:
   ```bash
   docker run --rm --volumes-from dataq-db \
     -v "$(pwd -W)/docker/dataq-db/pgdata":/dst \
     alpine sh -c "rm -rf /dst/* /dst/.* 2>/dev/null; cp -a /var/lib/postgresql/data/. /dst/"
   ```
   - **주의**: 기존 pgdata/ 안 내용을 먼저 비워야 함 (잔존 데이터 섞임 방지)
3. `docker compose build dataq-db`
4. `docker save -o ~/Desktop/dataq-stack.tar dataq-db:snapshot dataq-center:latest dataq-executor:latest`
5. 사용자에게 `docker start dataq-db` 안내 (dev 환경 복구)

---

### 시나리오 C — 둘 다 변경 (DDL + 코드 동시)

A + B 합본. 순서:

1. 사용자: JAR 빌드 + DDL 적용 완료 + `docker stop dataq-db`
2. 자동: PGDATA 추출 → `docker compose build` (3개) → `docker save`
3. 사용자: `docker start dataq-db`

## 3. 빌드 머신(이 PC) 측 검증 체크리스트

- [ ] `docker images | grep dataq` — 3개 이미지 `CREATED` 가 방금인지
- [ ] `ls -lh ~/Desktop/dataq-stack.tar` — 파일 사이즈 정상(~675MB±)
- [ ] (선택) `docker compose up -d` 로 로컬 검증 후 `down -v` — 단, dev `dataq-db` 와 컨테이너명/포트 충돌 주의

## 4. 배포 PC 측 절차

**옮길 파일 2개:**
- `dataq-stack.tar` (USB/네트워크 복사)
- `docker-compose.deploy.yml` (변경되면 같이, 안 바뀌면 생략 가능)

**명령 (배포 PC PowerShell):**

```powershell
# 1) 기존 컨테이너 정지 (영속 volume 은 유지)
docker compose -f docker-compose.deploy.yml down

# 2) 새 이미지 import (동일 tag 는 자동 덮어씀)
docker load -i dataq-stack.tar

# 3) 기동
docker compose -f docker-compose.deploy.yml up -d

# 4) 상태/로그 확인
docker compose -f docker-compose.deploy.yml ps
docker compose -f docker-compose.deploy.yml logs -f q-center
# → http://localhost:28090
```

### ⚠ DB 데이터 갱신을 반영하려면 (시나리오 B/C)

배포 PC 의 named volume `dataq-db-data` 가 우선시되므로, 이미지의 새 PGDATA 가 반영되려면 **volume 삭제 필요**:

```powershell
docker compose -f docker-compose.deploy.yml down -v   # ← -v 핵심
docker load -i dataq-stack.tar
docker compose -f docker-compose.deploy.yml up -d
```

> **운영 데이터 유실 주의**: 배포 PC 에서 사용자가 만든 데이터가 있다면 `-v` 는 그것까지 삭제. 운영 데이터 보존이 필요한 시나리오면 `pg_dump` 백업 → 신 이미지 기동 → 복원 패턴으로 가야 함.

## 5. 흔한 함정

| # | 함정 | 대응 |
|---|---|---|
| 1 | 라이브 dataq-db 에서 PGDATA raw cp → 데이터 깨짐 | 반드시 `docker stop` 후 추출. `postmaster.pid` 없는지 확인 |
| 2 | 배포 PC volume 우선 → 새 DB 이미지 반영 안 됨 | `down -v` 로 volume 삭제 (시나리오 B/C) |
| 3 | dev `dataq-db` 와 compose `dataq-db` 컨테이너명 충돌 | 빌드 머신에서 compose 검증 시 dev 정지 또는 compose 안 띄움 |
| 4 | 배포 PC 에서 실수로 `docker compose build` | deploy 파일엔 `build:` 없으므로 무시됨, 무해 |
| 5 | 이미지 tag 가 `latest`/`snapshot` 고정 → 롤백 어려움 | 중요 패치는 `docker tag dataq-center:latest dataq-center:2026-05-22` 등 백업 tag 추가 |
| 6 | jasypt 키 변경 시 q-executor 부팅 실패 | 평문 password 환경변수 override (현재 방식) 그대로 유지하면 무관 |
| 7 | TZ 미설정 시 로그 9시간 차이 | compose 에 `TZ: Asia/Seoul` 명시됨 (그대로 유지) |
