**조사 방법과 한계** — 웹 페이지만 읽고 첨부 파일(hwpx·pdf)은 내려받지 않았다. 핵심 규격인 법령정보센터의 「별표 4 메타데이터 표준 관리항목」은 첨부 파일이라 열지 않았고, 검색 엔진이 색인한 본문 발췌로 항목명을 확인했다. 발췌는 표 구조가 깨져 있어 항목의 소속(정보시스템/DB)과 표시(IRM 연계·자동수집)의 위치가 틀릴 수 있다. 표에서 "확인됨 [S2]" 는 발췌 원문을 본 것, "확인됨 [S2 요약]" 은 검색 도구의 요약으로만 본 것이다.

## 1. 요약

**알게 된 것**

1. 제출 의무의 근거는 「공공기관의 데이터베이스 표준화 지침」(행정안전부고시 제2025-19호, 2025.2.24 시행)이다. 공공기관의 장은 소관 DB 의 "메타데이터 표준 관리항목"(별표 4)을 **기관 메타데이터 관리시스템**에 등록하고, **중앙 메타데이터 관리시스템**과 연계해 최신으로 유지해야 한다(제14~16조). 중앙 시스템은 공공데이터활용지원센터가 운영하고(제16조⑥) NIA 공공지능데이터인프라팀이 맡는다 [S13]. 상위 법률은 「인공지능 및 데이터 기반 행정 활성화에 관한 법률」(구 데이터기반행정법, 2026.8.28 시행) 제16조다. [S1][S8]
2. 별표 4 는 정보시스템·데이터베이스·테이블·컬럼 단위로 나뉘고, 항목마다 필수(*) 표시, 정보자원관리시스템(IRM) 연계 표시, "자동수집 연계 시 보유 DB 로부터 자동 수집되는 정보" 표시가 있다. 검색 발췌로 항목 36개를 확인했고 2개는 이름만 보였다. 2023년 개정에서 43개 → 38개로 정비됐고 2025년 개정에서 다시 정비됐다(2025년 판 항목 수는 미확인). [S2][S4][S5]
3. 정보시스템은 **IRM(정보자원관리시스템, 2024.3 범정부 EA 에서 바뀜)에 먼저 등록**해야 하고, 정보시스템명·유형은 IRM 과 같게 써야 한다(2025년 개정 제16조③1호). [S1][S2][S16]
4. 전송 파일 양식·인코딩·코드표·전송 규격(에이전트·SFTP)·검증 규칙은 **공개 자료에서 찾지 못했다.** 운영 기관(NIA 공공지능데이터인프라팀)이 기관에 주는 자료로 보인다. 공개된 것 중 양식에 가장 가까운 것은 SMETA 교육자료 p.91 의 기관메타 업로드 엑셀 화면이며 앞쪽 열만 보인다.
5. 우리 쪽은 수집한 테이블·컬럼 구조(소유자·이름·타입·길이·NULL·PK·FK·제약조건)가 있으나 기관·정보시스템·DB 단위 항목과 공개 여부·개인정보·암호화·발생주기·테이블유형·개방데이터목록이 없다. 또 수집할 때 데이터타입을 공통 이름으로 바꿔 저장해(Oracle VARCHAR2→VARCHAR 등, 102번 §4.10) 별표 4 의 "DBMS 종속 데이터타입 그대로" 와 맞지 않는다.

**아직 모르는 것** — 별표 4 원문 전체(2025년 판), 업로드 양식의 전체 열과 코드표, CSV 허용 여부·인코딩·파일명 규칙, 중앙메타 연계(에이전트·SFTP) 규격과 처리 결과 회신 방식, 등록 기한(지침은 "변경이 생기면 현행화" 만 정한다).

**구현 착수 여부** — 항목 저장 구조·입력 화면·내부 검증·예약 실행 연결(약 18인일)은 지금 확인된 항목 정의로 시작할 수 있다. 파일 생성·전송·연계 모니터링·실제 연계 시험(약 9인일)은 규격 원문 없이 할 수 없고, 104번 WP5 완료 기준 "범정부 전송 파일이 규격 검증을 통과한다" 도 지금은 만족시킬 수 없다. 104번 §3.3 은 WP5-78 을 조사·설계까지만 정했으므로 구현 착수 시점은 결정이 필요하다(§7.4).

### 2.3 주변 변화 — 확인 필요

- 행정안전부가 2024.10 "국가공유데이터 플랫폼" 구축에 착수했고(2025.6 구축 목표) [S18], NIA 는 2023.11 "기관공유데이터 관리시스템" 구축 사업을 시작해 지금 기관에 보급하고 있다(기관 메타데이터 정보 조회 기능 포함) [S19][S13]. 이것과 기관메타 보급본의 관계, 연계 대상이 바뀌는지는 공개 자료로 확인되지 않았다.
- SMETA 교육자료(p.86)는 기관명·기관코드 등을 "EA 포털" 기준으로 쓰라고 하지만, 범정부 EA 는 2024.3 정보자원관리시스템(IRM)으로 바뀌었다 [S16]. 2025년 지침도 IRM 명칭을 쓴다.

## 3. 항목 정의 — 별표 4 와 우리 테이블 대조

열 설명
- **필수**: 별표 4 발췌의 `*` 표시와 SMETA p.91 업로드 양식의 `(*)` 를 함께 봤다. 둘이 다르면 `*?`, 빈칸은 미확인.
- **구분**: IRM = IRM 연계로 수집되는 항목 표시, 자동 = "자동수집 연계 시 보유 DB 로부터 자동 수집" 표시, 입력 = 기관 입력. `?` 는 발췌에서 표시 위치가 불분명한 것.
- **우리 쪽**: 지금 있는 테이블·컬럼. **제안**: 없으면 "신규" 와 제안 이름(§6.2).
- 화면 라벨은 별표 4 항목명을 그대로 쓴다.

| 기관코드 | | 입력 | 없음 | 신규 `TB_GOV_META_CONF.INST_CD` | 추정 — SMETA p.86·88 (정보시스템코드 앞 7자리) |

## 6. 우리 쪽 설계 초안

### 6.1 원칙

- **테이블·컬럼 항목은 `TB_DATA_MODEL_OBJ`·`TB_DATA_MODEL_ATTR` 에 컬럼으로 더한다.** ① 재수집 UPSERT 가 기존 행에서 갱신하는 컬럼이 정해져 있어(테이블은 코멘트·컬럼 수·사용 여부·삭제일시만, 102번 DM-B02) 새 컬럼은 재수집 뒤에도 남는다. 컬럼 쪽 UPSERT 의 갱신 목록에 새 컬럼을 넣지 않도록 확인한다. ② 테이블 물리명·소유자를 바꿀 때 하위 행을 따라 바꾸는 처리(DM-017)를 늘리지 않아도 된다.
- **기관·정보시스템·DB 항목은 별도 테이블로 둔다.** `TB_SYS_INFO` 는 WP2 시스템 계층이 쓰고, `ndata.TB_DATA_SOURCE` 는 이전 플랫폼 스키마라 건드리지 않는다.
- **코드값은 매핑 테이블로 분리한다.** 우리 값(예: DBMS_TP "Oracle")과 범정부 코드(예: "ORA")를 따로 둬서 코드표를 받으면 데이터만 넣는다.
- **생성 대상 행은 표준 진단과 같은 기준**(사용 중 + 승인된 행, 102번 DG-B04)으로 고른다.
- 104번 §5 규칙을 따른다 — DDL 을 바꾸면 `DDL_full_schema.sql`·`01_schema.sql`·`DDL_변경이력.md` 갱신, 새 필드는 VO → resultMap → SELECT → 화면.

- `q-executor/src/main/resources/META-INF/dm-collect.xml` 의 `{DBMS}GetAttrs` 4종(Oracle·PostgreSQL·MariaDB·Cubrid)에 원본 타입 열을 더해 `DBMS_DATA_TYPE` 에 넣는다. 공통명 `DATA_TYPE` 은 그대로 둔다(표준 진단·DDL 생성이 쓴다). WP4 에서 만드는 Tibero·SQL Server 쿼리에도 같은 열을 넣는다.

### 6.4 생성·내보내기

실행은 q-executor 가 한다(수집·진단과 같다). q-center 는 요청과 조회만 한다.

1. **대상 고르기** — 전송대상 정보시스템(`TB_GOV_META_SYS.SEND_YN='Y'`) → 그 시스템의 DB(`TB_SYS_INFO.SYS_DS_LST`) → 그 DB 를 데이터소스로 쓰는 모델(`TB_DATA_MODEL.DM_DS_ID`, `USE_YN='Y'`) → `GOV_SEND_YN='Y'` 테이블과 그 컬럼(`USE_YN='Y'`, 승인 상태 없음 또는 APPROVED).
   - 한 DB 를 여러 모델이 쓰면(스키마 범위가 다른 모델) 같은 테이블이 두 번 나올 수 있다 → (DS_ID, 소유자, 테이블명)으로 중복을 없애거나 DB 마다 대표 모델을 정한다(결정 필요).
   - 모델의 시스템(`DM_SYS_CD`)과 시스템의 데이터소스 목록(`SYS_DS_LST`)이 어긋날 수 있다 → 검증에서 경고.
   - 데이터소스가 없는 논리 모델은 DB 정보가 없어 빠진다(SMETA 도 오프라인 DBMS 를 뺀다).
2. **검증** — 필수 항목 누락, 코드 매핑 없음, IRM 시스템명·코드 비어 있음, 한글 컬럼명 규칙(한글, 특수문자·공백 불가), 부분공개·비공개인데 사유·근거 없음, 개인정보여부 Y 인데 암호화여부 N, FK 참조 테이블이 전송대상이 아님. 마지막 둘은 규격을 받기 전까지 경고로 두고 나머지는 오류로 한다. 오류는 `TB_GOV_META_SEND_ERR` 에 남기고 오류가 있으면 파일을 만들지 않는다.
3. **레코드 만들기** — 규격과 상관없는 내부 레코드(정보시스템·DB·테이블·컬럼 값 + 코드 매핑 결과)를 먼저 만든다. 테이블 수는 전송대상 테이블로 센다. PK정보·FK정보·Not Null 여부·제약조건 초안은 여기서 조합한다.
4. **파일 쓰기** — 규격을 받은 뒤 writer 를 붙인다. ① 기관메타 업로드 엑셀(Apache POI — q-common·q-center·q-executor 에 이미 있음) ② CSV(인코딩·구분자는 규격대로) ③ 규격이 요구하면 시스템·DB 단위로 나눔. 파일은 `META_FILE_DIR` 에 쓰고 보관 개수를 넘는 옛 파일은 지운다.
5. **전송** — 연계 방식에 따라. 기관메타: 사용자가 생성·전송 화면에서 내려받아 기관메타에 올린다(시스템 작업 없음). 중앙메타: 정해진 경로에 둔다(가져가는 쪽 규격 확인 필요). SFTP: 접속해서 올린다 — SFTP 라이브러리가 지금 없다(q-center·q-executor `pom.xml`, `lib/` 확인) → 추가 필요.
6. **이력** — `TB_GOV_META_SEND` 에 상태·건수·파일·전송 결과를 남긴다.

### 6.5 예약 실행 연결 (`TB_DIAG_SCHEDULE` / `DIAG_TYPE`)

**지금 구조**
- `DIAG_TYPE` 은 'STANDARD | STRUCT | BOTH' 이고(컬럼 주석) 서버가 이 셋만 받는다(`DiagScheduleController.java:305-307`).
- 등록 검증은 유형과 상관없이 모델에 표준사전이 있어야 한다(`DiagScheduleController.java:313-317`).
- 실행은 `ScheduledDiagLauncher.launch` 가 유형별로 진단을 띄우고 실행 이력에 `DIAG_JOB_ID`·`STRUCT_DIAG_ID` 를 적는다(`ScheduledDiagLauncher.java:63-80`).
- 완료 감지는 이 두 ID 의 상태만 본다. 둘 다 없으면 건너뛰고(`DiagSchedulerRunner.java:196-206`), 60분이 지나면 ERROR 로 마감된다(`DiagSchedulerRunner.java:257-268`). 새 유형이 두 ID 를 쓰지 않으면 실행이 끝나도 RUNNING 으로 남다가 60분 뒤 ERROR 가 된다.
- 중복 기동 방지는 같은 모델 + 같은 유형으로 판단한다(`DiagSchedulerRunner.java:139-146`).
- `TB_DIAG_SCHEDULE.DATA_MODEL_ID` 는 NOT NULL 이다.

### 7.2 대상 기관에 물을 것

1. 지금 쓰는 연계 방식 — 보급받은 기관메타를 쓰는지, 다른 메타 솔루션인지, 에이전트가 설치돼 있는지, SFTP 연계 서버가 있는지.
2. 기관코드, IRM 정보시스템 목록(이름·코드·유형), 시스템별 운영부서·담당자.
3. 정부 BRM 을 쓰는지 기관 자체 BRM 을 쓰는지.
4. 전송 대상 시스템·DB 범위와 테이블 제외 기준(미사용·개발·권한·로그).
5. 기존 기관메타에 등록된 값(공개 여부·사유·근거, 발생주기, 개방데이터목록 등)을 엑셀로 받아 옮길 수 있는지.
6. 개인정보·암호화 컬럼 현황 자료(개인정보 영향평가 결과 등)가 있는지.
7. 실태점검 일정과 현행화 마감.
8. 메타 서버에서 연계 서버(또는 중앙)까지의 망 경로와 반출 승인 절차.

### 7.3 NIA(운영 기관)에 물을 것

1. 2025년 개정 별표 4 의 항목 목록·변경 내역과 업로드 양식·코드표.
2. 기관이 쓰는 상용 메타 솔루션이 중앙 메타와 연계할 때의 절차(에이전트 설치, SFTP 계정, 인증, 시험 환경).
3. CSV 허용 여부·인코딩·파일명 규칙, 변경분 전송 가능 여부, 삭제 표현.
4. 처리 결과(성공·오류)를 돌려주는 방법.
5. 기관메타 보급본과 기관공유데이터 관리시스템의 관계, 연계 대상이 바뀌는지.
