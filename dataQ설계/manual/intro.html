NAVIDMeta

표준은 문서에 있고,
데이터는 DB 에 있다.

두 개가 얼마나 어긋나 있는지 아무도 정확히 모릅니다. 대개는 엑셀로 대조하다 포기합니다. Navid Meta 는 그 격차를 숫자로 재고, 줄이고, 통제된 절차로 좁힙니다.

문제

격차는 재지 않으면 존재하지 않는 것처럼 다뤄집니다

표준화 지침은 있습니다. 단어 사전도 있습니다. 그런데 어제 개발자가 만든 테이블이 그 사전을 따랐는지는 아무도 모릅니다. 확인하려면 컬럼 하나하나를 사전과 대조해야 하는데, 컬럼이 수천 개면 그건 하지 않는 일이 됩니다.

어긋남을 네 가지로 분류합니다

"표준을 안 지켰다" 는 조치로 이어지지 않습니다. 어떻게 안 지켰는지가 정해져야 무엇을 고칠지가 정해집니다. Navid Meta 는 컬럼 단위로 다음 넷 중 하나를 판정합니다.

용어 미존재
컬럼 영문명에 해당하는 표준 용어가 사전에 없습니다. → 용어를 등록하거나, 한글명으로 자동 생성합니다.
한글명 불일치
용어는 있는데 컬럼 코멘트가 표준 한글명과 다릅니다. → COMMENT 스크립트를 받아 반영합니다.
타입 불일치
도메인이 정한 데이터 타입과 다릅니다. VARCHAR·VARCHAR2·CHAR 처럼 같은 계열은 어긋남으로 보지 않습니다. → ALTER 스크립트를 받습니다.
길이 불일치
도메인이 정한 길이와 다릅니다. → ALTER 스크립트를 받습니다.
운영 무부하

진단은 운영 DB 를 건드리지 않습니다

표준 진단은 수집해 둔 스냅샷과 승인된 용어 사전만 비교합니다. 대상 DB 에 접속하지 않으므로 업무 시간에 돌려도 부하가 없습니다.

단일 지표

준수율 하나로 추적합니다

(전체 컬럼 − 이슈 컬럼) ÷ 전체 컬럼. 이슈 건수가 아니라 이슈가 있는 컬럼 수로 셉니다. 한 컬럼에 문제가 셋이어도 하나로 셉니다.

해소

한글명 하나로 표준 영문명까지 만듭니다

표준화가 막히는 실제 지점은 "이 컬럼을 영어로 뭐라고 쓸 것인가" 입니다. Navid Meta 는 한글 컬럼명 목록을 받아 형태소로 쪼개고, 표준 단어 사전·동의어·사용빈도로 단어를 확정한 뒤, 영문약어를 조합하고 도메인까지 추천합니다.

사람이 검토한다

자동은 제안까지, 확정은 사람이

결과를 기등록·자동완성·부분매칭·미매칭 넷으로 나눠 보여주고, 행마다 단어 분해를 직접 고칠 수 있습니다. 검토한 것만 일괄 등록됩니다.

이름이 바뀌면 참조도

물리명을 바꾸면 딸린 것들이 따라갑니다

컬럼 물리명이 바뀌면 그 이름을 참조하던 인덱스·제약조건·FK 부모 참조가 함께 갱신되고, 변경 이력과 한글→영문 변환 이력이 자동으로 남습니다.

통제

고친 것이 실제 DB 에 닿기까지가 제품 안에 있습니다

대부분의 표준화 도구는 "이렇게 바꾸세요" 에서 끝납니다. 그 다음은 메일과 엑셀로 넘어가고, 무엇이 실제로 반영됐는지는 다시 알 수 없게 됩니다. Navid Meta 는 신청 → 승인 → DDL 실행 → 결과 기록까지를 한 화면 흐름 안에 둡니다.

되돌릴 수 있다

반려하면 변경 전으로 돌아갑니다

일반 사용자의 변경은 초안으로 저장돼 다른 사람에게 보이지 않습니다. 반려하면 변경 전 값으로 원복되고, 그 컬럼을 FK 로 참조하던 신청까지 연쇄 반려됩니다.

기록이 남는다

실행 결과까지 이력에 남습니다

승인된 변경의 DDL 을 관리자가 실제 DB 에 실행하면 성공·권한없음·실패가 이력에 기록됩니다. 무엇이 반영됐고 무엇이 안 됐는지가 남습니다.

차별점

다른 표준화 도구와 갈리는 네 지점

01

한글 단일 입력 표준화

형태소 분석 + 동의어 매핑 + 사용빈도 가중으로 한글명에서 표준 단어를 확정하고 영문약어와 도메인까지 도출합니다. 영문명을 사람이 짓지 않습니다.

02

진단 결과가 곧 조치 스크립트

이슈 유형에 따라 행마다 다른 버튼이 붙고, 누르면 대상 DBMS 문법에 맞는 ALTER·COMMENT 스크립트가 나옵니다. 진단과 조치 사이에 번역 단계가 없습니다.

03

승인에서 DB 반영까지 폐루프

설계 변경이 실제 운영 DB 에 닿고, 그 결과가 다시 제품에 기록됩니다. 재수집·재진단으로 준수율이 실제로 올랐는지 확인됩니다.

04

다중 스키마를 1급으로 다룸

소유자(스키마)가 테이블·컬럼의 식별 키에 포함됩니다. 같은 테이블명이 여러 스키마에 있어도 서로 덮어쓰지 않고, 진단 집계와 제외 설정도 스키마 단위로 격리됩니다.

사용자

두 개의 역할로 운영합니다

권한 모델이 단순합니다. 표준을 정하고 통제하는 쪽과, 현업에서 등록·변경을 신청하는 쪽입니다.

적용 범위

지원하는 것과 지원하지 않는 것

도입 판단에 필요한 사실입니다. 연결만 되는 것과 실제로 수집되는 것은 다릅니다.

DBMS테이블 · 컬럼인덱스 · 제약조건

PostgreSQL 지원지원
Cubrid 지원미지원
MariaDB 지원미지원
Tibero · SQLServer · Altibase · Goldilocks 수집 불가수집 불가

미리 알아두실 것

  • Tibero · SQLServer · Altibase · Goldilocks 는 데이터 소스 등록과 연결 테스트는 통과하지만 모델 수집이 되지 않습니다. 이 경우 ERwin XML / XMI 2.1 설계 파일 임포트로 우회합니다.
  • 데이터 품질 진단(값 프로파일링·업무 규칙 검증)은 제품 라인업 분리 결정으로 현재 메뉴에 없습니다. 표준 진단과 구조 변경 진단이 제공 범위입니다.
  • 재수집은 병합 방식이라 운영 DB 에서 삭제된 대상을 자동으로 지우지 않습니다. 구조 변경 진단으로 확인한 뒤 정리합니다.
그 밖에

표준화 실무에 필요한 것들

공공기관 지침 관리 항목 준수

데이터베이스 표준화 지침 별표 1 의 표준단어 관리 항목 9개 (표준단어명·영문명·영문약어명·설명·형식단어여부·도메인분류명·이음동의어·금칙어·제정일자)를 모두 보유합니다.

구조 변경 감지

수집 시점 스냅샷과 현재 DB 를 컬럼·인덱스·제약조건 3축으로 대조해 추가·변경·삭제를 건별로 남깁니다. 우리 모르게 바뀐 것을 찾습니다.

영향도 분석

단어를 바꾸기 전에 그 단어를 쓰는 용어와 실제 컬럼을, 도메인을 바꾸기 전에 그 도메인을 쓰는 용어를 미리 보여줍니다.

ERD · 설계 파일 연동

수집된 모델로 ERD 를 자동 생성해 PNG·PDF 로 내보내고, ERwin XML 과 XMI 2.1 을 양방향으로 주고받습니다.

대량 입력 3경로

소량은 그리드 인라인 편집, 중량은 엑셀 붙여넣기, 대량은 xlsx 업로드로 미리보기 검증 후 적재합니다. 저장은 단일 트랜잭션입니다.

진단 자동화

표준·구조 진단을 일·주·월 또는 Cron 으로 예약합니다. 중복 실행을 막고 실패 원인을 유형별 접두어로 분류해 기록합니다.
