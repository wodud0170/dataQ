NAVIDMeta

표준은 문서에 있고,
데이터는 DB 에 있다.

두 개가 얼마나 다른지는 대개 아무도 모릅니다. 확인하려면 컬럼을 하나씩 사전과 맞춰봐야 하는데, 수천 개면 하지 않게 됩니다.

Navid Meta 는 그 차이를 측정합니다. 그리고 줄이는 데까지 갑니다.

문제

재지 않는 격차는 없는 것으로 취급됩니다

표준화 지침도 있고 단어 사전도 있습니다. 문제는 어제 만들어진 테이블이 그 사전을 따랐는지 확인할 방법입니다.

확인 작업은 대개 이렇게 흘러갑니다. 누군가 DB 에서 컬럼 목록을 뽑습니다. 엑셀에 붙여넣고 사전과 대조합니다. 몇백 줄쯤에서 속도가 떨어지고, 다음 달에는 다시 하지 않습니다. 그 사이 컬럼은 계속 늘어납니다.

계측

어긋남을 네 가지로 나눕니다

"표준을 안 지켰다" 만으로는 무엇을 고칠지 정해지지 않습니다. Navid Meta 는 컬럼마다 다음 넷 중 하나로 판정하고, 유형마다 다른 조치를 붙입니다.

용어 미존재
컬럼 영문명에 맞는 표준 용어가 사전에 없습니다. 용어를 등록하거나 한글명에서 자동 생성합니다.
한글명 불일치
용어는 찾았는데 컬럼 코멘트가 표준 한글명과 다릅니다. COMMENT 스크립트를 받습니다.
타입 불일치
도메인이 정한 데이터 타입과 다릅니다. VARCHAR·VARCHAR2·CHAR 처럼 같은 계열은 어긋남으로 보지 않습니다. ALTER 스크립트를 받습니다.
길이 불일치
도메인이 정한 길이와 다릅니다. ALTER 스크립트를 받습니다.
운영 무부하

진단은 운영 DB 를 건드리지 않습니다

수집해 둔 스냅샷과 승인된 용어 사전만 비교합니다. 대상 DB 에 접속하지 않으므로 업무 시간에 돌려도 됩니다.

단일 지표

준수율 하나로 추적합니다

(전체 컬럼 − 이슈 컬럼) ÷ 전체 컬럼. 이슈 건수가 아니라 이슈가 있는 컬럼 수로 셉니다. 한 컬럼에 문제가 셋이어도 하나입니다.

해소

한글명 하나로 영문 표준명까지 만듭니다

표준화가 실제로 막히는 지점은 "이 컬럼을 영어로 뭐라고 쓸 것인가" 입니다. 사람마다 다르게 쓰고, 그래서 표준이 무너집니다.

Navid Meta 는 한글 컬럼명 목록을 받아 형태소로 나눕니다. 표준 단어 사전과 대조하고, 동의어를 따라가고, 사용 빈도로 후보를 정렬해 단어를 확정합니다. 거기서 영문약어를 조합하고 도메인까지 추천합니다.

확정은 사람이

자동은 제안까지입니다

리뷰 단계에서 행마다 단어 분해를 직접 고칠 수 있습니다. 검토를 거친 것만 등록됩니다.

참조가 따라온다

물리명이 바뀌면 딸린 것들도

컬럼 물리명이 바뀌면 그 이름을 참조하던 인덱스·제약조건·FK 부모 참조가 함께 갱신됩니다. 변경 이력과 변환 이력도 남습니다.

통제

고친 것이 실제 DB 에 닿기까지

표준화 도구는 보통 "이렇게 바꾸세요" 에서 끝납니다. 그 다음은 메일과 엑셀로 넘어가고, 무엇이 반영됐는지는 다시 알 수 없게 됩니다.

Navid Meta 는 신청부터 DDL 실행까지를 한 흐름 안에 둡니다. 일반 사용자의 변경은 초안으로 저장되어 다른 사람에게 보이지 않습니다. 관리자가 승인하면 반영되고, 반려하면 변경 전 값으로 돌아갑니다.

데이터 소스 등록 | v +-> 모델 수집 --> 표준 진단 --> 이슈별 조치 스크립트 | | | v | 변경 신청 | | | v | 관리자 승인 | | | v +--------------------------- DDL 을 실제 DB 에 반영
되돌릴 수 있다

반려하면 원래대로

변경 전 값으로 원복되고, 그 컬럼을 FK 부모로 참조하던 신청까지 연쇄 반려됩니다. 참조 관계를 따라 끝까지 전파됩니다.

기록이 남는다

실행 결과까지 이력에

DDL 실행 결과가 성공·권한없음·실패로 기록됩니다. 무엇이 반영됐고 무엇이 남았는지 나중에 확인됩니다.

구성

세 덩어리로 나뉩니다

화면과 API 를 담당하는 서버, 무거운 작업을 처리하는 워커, 그리고 메타 정보를 담는 DB 입니다.

사용자 브라우저 | v q-center (화면 · API · 승인) | \ | \ 작업 요청 v v 메타 DB q-executor (수집 · 진단 · 스케줄) ^ | \ +----------+ \ JDBC 조회 v 대상 운영 DB

q-center

화면과 API. 표준 사전 CRUD, 승인 워크플로, 진단 결과 조회를 담당합니다. 무거운 작업은 직접 하지 않고 워커에 넘깁니다.

q-executor

워커. 대상 DB 접속이 필요한 수집·구조 진단, 시간이 걸리는 표준 진단, 예약 실행을 맡습니다. 화면이 멈추지 않도록 분리돼 있습니다.

메타 DB (PostgreSQL)

표준 사전, 수집된 모델 스냅샷, 진단 결과, 변경 이력이 들어갑니다. 대상 운영 DB 와는 별개입니다.

대상 운영 DB

수집과 구조 진단 때만 JDBC 로 조회합니다. 표준 진단은 접속하지 않습니다. 쓰기는 관리자가 DDL 반영을 눌렀을 때만 일어납니다.

차별점

다른 표준화 도구와 갈리는 네 지점

01

한글 단일 입력 표준화

형태소 분석에 동의어 매핑과 사용빈도 가중을 더해 한글명에서 표준 단어를 확정합니다. 영문명을 사람이 짓지 않습니다.

02

진단 결과가 곧 조치 스크립트

이슈 유형에 따라 행마다 다른 버튼이 붙고, 누르면 대상 DBMS 문법에 맞는 ALTER · COMMENT 스크립트가 나옵니다. 사이에 번역 단계가 없습니다.

03

승인에서 DB 반영까지 닫힘

설계 변경이 실제 운영 DB 에 닿고 그 결과가 다시 제품에 남습니다. 재수집·재진단으로 준수율이 올랐는지 확인됩니다.

04

다중 스키마를 1급으로

소유자가 테이블·컬럼의 식별 키에 들어갑니다. 같은 이름이 여러 스키마에 있어도 서로 덮어쓰지 않고, 진단 집계와 제외 설정도 스키마 단위로 나뉩니다.

도입

첫 준수율이 나오기까지

표준 사전이 이미 있다면 3단계에서 시작합니다. 없다면 1단계부터 쌓습니다.

  1. 표준 사전 구축

    도메인 분류 → 단어 → 도메인 → 용어 순으로 쌓습니다. 엑셀 일괄 업로드를 지원하므로 기존 사전이 있으면 그대로 올립니다.

  2. 데이터 소스 등록

    대상 DB 접속 정보를 넣고 연결을 확인합니다. 수집 가능한 DBMS 는 아래 표에서 확인하세요.

  3. 모델 수집

    스키마를 지정해 테이블·컬럼·인덱스·제약조건을 읽어옵니다. 설계 파일(ERwin XML / XMI)로 대신할 수도 있습니다.

  4. 첫 진단

    준수율과 이슈 분포가 나옵니다. 여기서부터 어디를 먼저 손댈지 정해집니다.

  5. 조치와 재진단

    이슈 유형별로 조치하고 다시 진단합니다. 이후에는 스케줄로 자동 실행해 추이를 봅니다.

미리 알아두실 것

  • Tibero · SQLServer · Altibase · Goldilocks 는 데이터 소스 등록과 연결 테스트가 통과합니다. 그런데 모델 수집은 실패합니다. 이 경우 ERwin XML / XMI 2.1 설계 파일 임포트로 우회합니다.
  • 데이터 품질 진단(값 프로파일링 · 업무 규칙 검증)은 제품 라인업 분리로 현재 메뉴에 없습니다. 표준 진단과 구조 변경 진단이 제공 범위입니다.
  • 재수집은 병합 방식이라 운영 DB 에서 삭제된 대상을 자동으로 지우지 않습니다. 구조 변경 진단으로 확인한 뒤 정리합니다.

구조 변경 감지

수집 시점 스냅샷과 현재 DB 를 컬럼 · 인덱스 · 제약조건 3축으로 대조합니다. 추가 · 변경 · 삭제를 건별로 남깁니다.

영향도 분석

단어를 바꾸기 전에 그 단어를 쓰는 용어와 실제 컬럼을 보여줍니다. 도메인도 마찬가지입니다.

ERD · 설계 파일

수집된 모델로 ERD 를 그려 PNG · PDF 로 내보냅니다. ERwin XML 과 XMI 2.1 은 가져오기와 내보내기 양쪽을 지원합니다.

대량 입력 3경로

소량은 그리드 인라인 편집, 중량은 엑셀 붙여넣기, 대량은 xlsx 업로드로 미리보기 검증 후 적재합니다. 저장은 단일 트랜잭션입니다.

진단 자동화

표준 · 구조 진단을 일 · 주 · 월 또는 Cron 으로 예약합니다. 중복 실행을 막고 실패 원인을 유형별로 기록합니다.
