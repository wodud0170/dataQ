**작성일**: 2026-04-13
**대상**: 구조 변경 진단 세션 기준, 인덱스/제약조건 수집 확장을 위한 사전 분석

---

## 1. 현재 수집 구조 (AS-IS)

### 1.1 수집 흐름 (DataModelService.java)

```
collectDataModel() 실행
  │
  ├─ 1. TB_DATA_MODEL_CLCT 시작 (clctId 생성)
  ├─ 2. OBJ 수집 → TB_DATA_MODEL_OBJ (테이블 메타)
  ├─ 3. ATTR 수집 → TB_DATA_MODEL_ATTR (컬럼 메타)
  ├─ 4. STATS 저장 → TB_DATA_MODEL_STATS (OBJ_CNT, ATTR_CNT)
  └─ 5. TB_DATA_MODEL_CLCT 완료 처리
```

- 스키마별 루프: `schemas` 리스트를 순회하며 각 스키마에 대해 OBJ/ATTR 쿼리 실행
- Named Query 방식: `dm-collect.xml`에서 DBMS타입 + "GetObjs"/"GetAttrs" 조합으로 쿼리 가져옴
- WebSocket 알림: 각 단계마다 진행 상황 실시간 전송

### 1.2 현재 수집 항목

| 대상 | 저장 테이블 | 수집 항목 |
|------|------------|----------|
| 테이블 | TB_DATA_MODEL_OBJ | owner, 테이블명, 한글명, 컬럼수, 생성일, 수정일 |
| 컬럼 | TB_DATA_MODEL_ATTR | owner, 테이블명, 컬럼명, 한글명, 타입, 길이, 소수자리, nullable, PK(Y/N), FK(Y/N), 기본값, 순서 |

### 1.3 PK/FK 수집 방식 (현재의 한계)

**Oracle (OracleGetAttrs)**:
- PK: `USER_CONSTRAINTS` + `USER_CONS_COLUMNS` JOIN → 컬럼별 Y/N 판정
- FK: 동일 방식 → 컬럼별 Y/N 판정
- **문제**: `USER_CONSTRAINTS` 사용 (현재 접속 사용자 소유만) → 다른 스키마 조회 시 PK/FK 누락 가능
- **누락 정보**: 제약조건명, 복합키 순서, FK 참조 테이블/컬럼

**MariaDB (MariaDBGetAttrs)**:
- PK: `information_schema.COLUMNS.column_key = 'PRI'` → Y/N
- FK: `information_schema.key_column_usage.referenced_table_name IS NOT NULL` → Y/N
- **주의**: FK 서브쿼리가 스칼라 서브쿼리 → 다중 FK 컬럼 시 에러 가능
- **누락 정보**: 동일 (제약조건명, 참조 상세 없음)

**Cubrid (CubridGetAttrs)**:
- PK: `DB_INDEX.IS_PRIMARY_KEY = 'YES'` → Y/N
- FK: `DB_INDEX.IS_FOREIGN_KEY = 'YES'` → Y/N
- **누락 정보**: 동일

**PostgreSQL**: Named Query 자체가 없음 (미지원)

## 3. dm-collect.xml 현황

### 3.1 현재 Named Query 목록 (8개)

| DBMS | OBJ (테이블) | ATTR (컬럼) | INDEX | CONSTRAINT |
|------|-------------|------------|-------|------------|
| Cubrid | CubridGetObjs ✅ | CubridGetAttrs ✅ | ❌ | ❌ |
| Oracle | OracleGetObjs ✅ | OracleGetAttrs ✅ | ❌ | ❌ |
| MariaDB | MariaDBGetObjs ✅ | MariaDBGetAttrs ✅ | ❌ | ❌ |
| PostgreSQL | ❌ | ❌ | ❌ | ❌ |

### 3.2 Oracle 쿼리 이슈

- `OracleGetAttrs` (L66-141): **176줄** — PK/FK 판정 서브쿼리가 `USER_CONSTRAINTS` 사용
  - `USER_*` 뷰: 현재 접속 사용자 소유 객체만 조회
  - `ALL_*` 뷰: 접속 사용자가 접근 가능한 모든 객체 조회
  - 메인 쿼리는 `ALL_TAB_COLUMNS`, `ALL_TAB_COMMENTS` 등 `ALL_*` 사용하는데
  - PK/FK 서브쿼리만 `USER_CONSTRAINTS` 사용 → **스키마 불일치 위험**
  - 다른 사용자의 스키마를 수집할 때 PK/FK가 전부 null로 나올 수 있음

### 3.3 MariaDB 쿼리 이슈

- `MariaDBGetAttrs` (L173-208): FK 서브쿼리가 스칼라 서브쿼리
  ```sql
  (select column_name from information_schema.key_column_usage 
   where ... and referenced_table_name is not null) as FK_COLUMN
  ```
  - 한 테이블에 FK가 2개 이상이면 서브쿼리가 다중 행 반환 → **에러 가능**

### 3.4 PostgreSQL 부재

- PostgreSQL Named Query가 전혀 없음
- 현재 시스템 내부 DB가 PostgreSQL인데, **외부 PostgreSQL DB 수집 시 쿼리 없어서 실패**
- 29_설계문서에 PostgreSQL 인덱스/제약조건 쿼리는 작성해 놓음 → OBJ/ATTR 쿼리도 함께 추가 필요

## 4. 구조 변경 진단 (StructDiagService) 현황

### 4.1 현재 diff 로직

```
run() 메서드:
  1. 수집 스냅샷 ATTR 로드 → prevMap (key: owner|tableNm|columnNm)
  2. 실제 DBMS 접속 → currMap
  3. diff:
     - currMap에만 있으면 → ADDED
     - prevMap에만 있으면 → DELETED
     - 둘 다 있는데 dataType/dataLen/nullableYn 다르면 → MODIFIED
  4. 결과 → TB_STRUCT_DIAG_DETAIL (DIAG_ID, SEQ, OWNER, TABLE_NM, COLUMN_NM, CHANGE_TYPE, prev/curr 타입/길이/nullable)
```

### 4.2 인덱스/제약조건 확장 시 변경 필요 사항

**TB_STRUCT_DIAG_DETAIL 확장 방안** (2가지):

| 방안 | 설명 | 장점 | 단점 |
|------|------|------|------|
| A: 기존 테이블 확장 | DETAIL에 CHANGE_CATEGORY (COLUMN/INDEX/CONSTRAINT) 컬럼 추가 + INDEX_NM, CONSTRAINT_NM 등 추가 | 쿼리 단순, 기존 코드 변경 최소 | COLUMN_NM이 인덱스/제약조건과 의미가 달라짐 |
| B: 별도 테이블 | TB_STRUCT_DIAG_INDEX_DETAIL, TB_STRUCT_DIAG_CONSTRAINT_DETAIL 신규 생성 | 깔끔한 분리 | 테이블 3개 JOIN, 프론트 로직 복잡 |

**StructDiagService.run() 확장**:
- ATTR diff 후 INDEX diff, CONSTRAINT diff 추가
- 각각 `toIndexMap()`, `toConstraintMap()` 헬퍼 필요
- 인덱스 키: `owner|tableNm|indexNm|columnNm|columnPos`
- 제약조건 키: `owner|tableNm|constraintNm|columnNm|columnPos`

**compareSchema() 확장**:
- 테이블별 비교 결과에 `indexes`, `constraints` 필드 추가

### 4.3 TB_STRUCT_DIAG_HISTORY 통계 확장

현재 통계 컬럼:
```
TOTAL_TABLES, TOTAL_COLUMNS
ADDED_TABLES, ADDED_COLUMNS, MODIFIED_COLUMNS
DELETED_TABLES, DELETED_COLUMNS
```

추가 필요:
```
ADDED_INDEXES, MODIFIED_INDEXES, DELETED_INDEXES
ADDED_CONSTRAINTS, MODIFIED_CONSTRAINTS, DELETED_CONSTRAINTS
```

## 8. 결론

**현재 상태**: 테이블/컬럼 수집 및 구조 변경 감지는 완성. 인덱스/제약조건은 설계 문서(29번)만 있고 코드/DDL 전무.

**핵심 갭**:
1. **수집 인프라 부재**: TB_DATA_MODEL_INDEX/CONSTRAINT 테이블, Named Query, 수집 로직 모두 없음
2. **기존 PK/FK 수집 품질 이슈**: Oracle `USER_CONSTRAINTS` 문제, MariaDB 스칼라 서브쿼리 문제
3. **PostgreSQL 지원 공백**: OBJ/ATTR 수집조차 Named Query 없음
4. **구조 진단 확장 필요**: diff 로직, DETAIL 테이블, 프론트 모두 확장 대상

**우선 권장**: Phase 1(수집 기반)부터 순서대로 진행. Oracle `USER_CONSTRAINTS` → `ALL_CONSTRAINTS` 수정도 함께 처리하면 기존 PK/FK 수집 품질도 개선됨.
