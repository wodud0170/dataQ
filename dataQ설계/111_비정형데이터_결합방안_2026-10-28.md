## 0. 요약

지금 제품의 메타 모델은 **DB 테이블·컬럼만** 다룬다. 비정형을 결합하는 방법은 세 갈래로 제안한다.

1. **비정형 자산 카탈로그** — 파일 서버·객체 스토리지·DB 안의 파일을 수집해 테이블처럼 목록·이력·권한·결재로 관리한다.
2. **비정형을 표준화의 재료로** — 문서에서 표준 단어·용어 후보를 뽑고, 테이블정의서 문서에서 모델 초안을 만들고, JSON·XML·CSV 의 키를 컬럼처럼 표준 진단한다. 지금 있는 표준 사전·용어 분석·결재 흐름에 그대로 이어진다.
3. **정형–비정형 연결** — 파일 경로·BLOB 를 담은 컬럼과 실제 파일, 테이블을 설명하는 문서를 서로 연결해 영향도·검색·개인정보 목록에 넣는다.

재개발은 한 번에 갈아엎지 않고 **플랫폼 갱신 → 자산 메타 모델 → 내용 처리 → 연결·검색 → (선택) LLM** 순서로 단계를 나눈다(§6). 플랫폼 갱신은 비정형과 별개로도 필요하다 — Spring Boot 2.7 은 2023-11, Vue 2 는 2023-12, PostgreSQL 13 은 2025-11 에 커뮤니티 지원이 끝났다.

## 2. 결합할 비정형 유형

| 유형 | 예 | 메타로 잡을 것 | 내용에서 뽑을 것 |
|---|---|---|---|
| 문서 | HWP·HWPX, PDF, DOCX·XLSX·PPTX | 경로·형식·크기·해시·작성/수정일·작성자·페이지 수 | 본문 텍스트, 표, 핵심 명사구, 개인정보 패턴 |
| 반정형 | JSON, XML, CSV, 로그 | 파일 단위 기술 메타 | 추론 스키마(경로·타입·출현율), 키 이름 |
| 이미지·스캔본 | TIFF·JPG·스캔 PDF | 해상도·EXIF·쪽 수 | OCR 텍스트(선택) |
| 시청각 | 영상·음성 | 코덱·길이·해상도·비트레이트 | 음성 → 텍스트는 선택(별도 모델 필요) |
| DB 안 비정형 | BLOB·CLOB·BYTEA, 파일 경로·URL 을 담은 컬럼 | 그 컬럼이 파일 참조라는 사실, 대상 저장소 | 표본 값의 형식(경로 패턴·MIME) |

저장소: 파일 서버(로컬·SMB·NFS), S3 호환 객체 스토리지, 문서관리시스템·전자결재(연계 API — 기관마다 다름).

예: 기록물 관리 시스템처럼 철·건 메타는 DB 에, 전자 파일·시청각 파일은 저장소에 있는 시스템. 지금은 DB 쪽만 이 제품의 관리 대상이다.

## 3. 결합 방식

### 3.1 비정형 자산 카탈로그

- **수집기** — 저장소 유형별(파일 시스템·SMB·S3). 수정 시각·해시로 증분 수집, 대용량은 표본 수집과 수집 시간대 제한. 원본은 복제하지 않고 **참조(경로·해시)만** 저장한다.
- **메타 계층**
  - 기술 메타: 경로, 크기, 형식(MIME), 해시, 생성·수정 시각, 소유자
  - 내장 메타: PDF·Office 문서 속성, EXIF, HWP 문서 정보
  - 내용 메타: 언어, 쪽 수, 키워드, 개인정보 포함 여부
  - 관리 메타: 업무 분류, 담당자, 보존기간, 공개 구분 — 지금의 사용자 정의 속성(UDP)을 자산 전체로 넓혀 재사용
- **구조** — 저장소 → 컬렉션(폴더·버킷 접두어 + 포함/제외 패턴) → 항목(파일) → 구성 요소(쪽·표·JSON 경로). 데이터 모델 → 테이블 → 컬럼과 같은 3단 구조라 화면·권한·결재를 같은 방식으로 붙일 수 있다.
- **변경 감지** — 구조 변경 진단의 비정형판: 파일 추가·삭제·변경, 반정형 스키마 변경(키 추가·타입 변경)을 수집 이력에 남긴다.

### 3.2 비정형을 표준화의 재료로

지금 있는 표준화 기능과 직접 이어지는 부분이다.

| 기능 | 흐름 | 재사용하는 것 |
|---|---|---|
| 문서 → 표준 후보 | 업무 문서·매뉴얼·요구사항 정의서에서 명사구 추출 → 사전에 없는 단어·용어를 출현 수·근거 문장과 함께 후보로 → 담당자가 골라 등록 신청 | KOMORAN 형태소 분석, 용어 자동 분석, 단어·용어 등록 검사, 결재 |
| 반정형 키 표준 진단 | JSON 키·XML 요소·CSV 헤더를 컬럼처럼 보고 표준 진단. 영문 키(camelCase·snake_case)는 단어로 쪼개 영문약어 역매핑 | 표준 진단, 영문명 역매핑(`resolveAttrsByEng`), 표준 후보 |
| 정의서 문서 → 모델 초안 | 테이블정의서·엔터티정의서(XLSX·HWP·PDF)의 표를 읽어 지금 엑셀 업로드 형식으로 바꾼 뒤 업로드·검사·결재 | 엑셀 업로드, DDL 값 검사, 모델 결재 |
| 메타데이터 항목 표준 | 비정형 자산의 관리 항목 자체를 표준으로 관리(예: 기록관리 메타데이터 표준, Dublin Core, 기관 자체 항목) — 항목명은 용어로, 값 범위는 도메인·코드로 | 용어·도메인·코드 사전 구조 |

### 3.3 정형–비정형 연결

- **파일 참조 컬럼** — 수집할 때 BLOB·CLOB 컬럼과, 값 표본이 경로·URL 형식인 문자열 컬럼을 "파일 참조 컬럼" 으로 표시하고 저장소 자산과 연결한다. 영향도(컬럼 → 파일 저장소)에 들어간다.
- **문서 ↔ 테이블** — 문서 본문에 나오는 테이블명·컬럼명·한글명을 모델과 맞춰 "관련 문서" 로 연결한다. 테이블 화면에서 근거 문서를 바로 본다.
- **개인정보** — 컬럼의 개인정보 표시와 같은 분류를 파일에도 붙여 "개인정보 포함 파일" 목록을 만든다.
- **DQ 제품과 경계** — 이 제품은 연결 관계와 파일 존재 여부까지 메타로 기록한다. 손상 파일·누락 비율 같은 값 품질 측정은 DQ 제품이 한다.

## 4. 검색·AI

| 구분 | 방안 | 비고 |
|---|---|---|
| 전문 검색 | 기본: 메타 저장소 PostgreSQL 에 한국어 n-gram 인덱스. 파일 수백만 건 이상이면 OpenSearch(nori 분석기)를 선택 구성으로 | 공공 구축은 구성 요소 수가 곧 운영 부담이라 기본은 DB 하나 |
| 의미 검색 | 추출 텍스트·표준 용어 설명을 임베딩해 pgvector 로 검색. "고객 식별 번호" ↔ "고객번호" 같은 표준 용어 추천을 형태소 분석과 함께 쓴다 | 임베딩 모델은 기관 내부 설치형 |
| LLM (선택 모듈) | 테이블·컬럼 설명 초안, 문서 요약, 메타 질의응답(근거 문서 인용) | 외부 API 없이 OpenAI 호환 API 를 내는 기관 내부 모델 서버에 붙인다. 결과는 바로 반영하지 않고 **제안 → 담당자 확인 → 결재** |

LLM 이 없어도 §3 기능은 규칙·형태소 분석으로 동작하게 한다. 폐쇄망·GS인증 환경에서 LLM 은 별도 선택 구성이다.

참고: 지티원은 2026-02 MetaCatalog v3 로 비정형 문서(PDF·Word·PPT) 메타 자동 추출·ML 태깅·LLM 설명 작성을 냈다(`dataQ설계/100_메타마이너_비교_및_제품화_제안_2026-10-02.md` §2). 우리 제품에는 지금 이 영역 기능이 없다.

## 5. 재개발 구조 (권장안)

```
[웹·API]  q-center 후속 — Spring Boot 3, Java 17 이상, Spring Security 6, MyBatis(기존 SQL 자산 유지)
   │
[작업 실행기]  q-executor 후속 — DB 수집·진단 + 비정형 수집기, 작업 큐
   │
[내용 처리기]  신규 — 문서 파싱(Apache Tika, HWP 는 hwplib·hwpxlib), OCR(선택), 형태소 분석(KOMORAN), 임베딩 호출
   │
[저장]  PostgreSQL 16 이상(메타 + pgvector) / 파생물(추출 텍스트·썸네일)은 파일·객체 저장소 / 원본은 참조만
   │
[모델 서버]  선택 — 기관 내부 임베딩·LLM (OpenAI 호환 API)

[화면]  Vue 3.5 + Vuetify 4 (10-28 기준 npm 최신 안정판 — Vue 3.5.44, Vuetify 4.3.1)
```

- **언어는 Java 로 통일한다.** Tika·hwplib·hwpxlib·KOMORAN 이 모두 Java 라 지금 팀·배포 방식 그대로 간다. 임베딩·LLM·OCR 모델은 별도 모델 서버로 떼어 우리 코드에 Python 을 들이지 않는다.
- **메타 모델 일반화** — 자산 공통 테이블을 두고 관계형(테이블)·파일·반정형을 유형별 확장 테이블로 둔다. 지금의 `TB_DATA_MODEL_OBJ`·`ATTR` 은 그대로 두고 자산 ID 만 붙여 기존 매퍼·화면 영향을 줄인다.
- **화면** — Vue 2 + Vuetify 2 → Vue 3.5 + Vuetify 4 는 사실상 다시 쓰기다(화면 75개, Vuetify 는 2 → 3 에서 컴포넌트 사용법이 크게 바뀌었다). 탭을 옮기면 화면 상태가 사라지는 지금 구조 문제(110번 1.10-B11)도 이때 탭·라우터 설계를 바꿔 함께 푼다.
- **작업 큐** — 대용량 파일 수집·내용 추출은 오래 걸리고 재시도가 필요하다. 지금 STOMP 단순 브로커 대신 작업 테이블 기반 큐(재시도·중단 재개)를 두고, 진행 메시지만 WebSocket 으로 보낸다.

새 테이블 초안 (구현 때 CLAUDE.md DDL 정책 — 덤프 2종·변경이력·sync 스크립트):

| 테이블 | 용도 | 지금 것과 대응 |
|---|---|---|
| `TB_ASSET` | 자산 공통(유형·이름·시스템·담당·상태) | 테이블·파일·반정형 모두 |
| `TB_UNST_STORE` | 저장소(유형 FS·SMB·S3·DB, 접속 정보 — 데이터 소스와 같은 보안 처리) | `ndata.TB_DATA_SOURCE` |
| `TB_UNST_COLL` | 컬렉션·수집 범위(경로 접두어, 포함/제외, 주기) | `TB_DATA_MODEL` |
| `TB_UNST_ITEM` | 파일 항목(경로·크기·MIME·해시·시각·소유자) | `TB_DATA_MODEL_OBJ` |
| `TB_UNST_ITEM_META` | 내장·내용 메타 키·값(표준 항목 ID 연결) | `TB_UDP_VAL` |
| `TB_UNST_FIELD` | 반정형 추론 스키마(경로·타입·출현율) | `TB_DATA_MODEL_ATTR` |
| `TB_UNST_CLCT` | 수집 이력·변경 건수 | `TB_DATA_MODEL_CLCT` |
| `TB_UNST_CHUNK` | 추출 텍스트 조각·임베딩 | 없음 |
| `TB_ASSET_LINK` | 정형–비정형 연결(컬럼↔저장소, 문서↔테이블, 근거·신뢰도) | 영향도 |
| `TB_STD_CANDIDATE` | 문서·반정형에서 나온 표준 후보(출현 수·근거) | 표준 등록·결재 |

## 6. 단계

공수는 지금 코드 규모로 잡은 **추정치**이고 버퍼는 넣지 않았다. 단계마다 상세 설계 뒤 다시 잡는다.
