| 항목 | 67번 | 70번 (변경) |

| 기존 테스트 룰 (16건) | — | **폐기** (신 시스템으로 새로 작성) |

## 1. 핵심 정책

### 1.1 검증 단위 = 컬럼당 단일 규칙
- OR 검증 배제 (다중 정규식 = 외부 DB 풀스캔 N배 부하)
- 컬럼은 **딱 1개 규칙** 적용 (도메인 룰 1개 OR 커스텀 룰 1개)

### 1.2 default = 도메인의 SORT_ORD = 1
- 컬럼이 도메인 보유 시 자동으로 그 도메인의 첫번째 룰(SORT_ORD=1)이 적용
- 별도 매핑 INSERT 불필요 — TB_QUAL_COL_RULE 에 행 없으면 default 적용
- 사용자가 명시적으로 다른 SORT_ORD 또는 커스텀 매핑 시 그것 우선

### 1.3 사용자 셀프-서비스
- 컬럼 화면에서 본인이 적용 규칙 변경 가능 (관리자 호출 X)
- 다른 도메인 룰 선택, 또는 "커스텀…" 으로 신규 룰 등록
- 변경 후 **그 컬럼만 재진단** (외부 DB 부하 1 SQL)

### 1.4 결과 영역
- 기존 결과 테이블에서 해당 컬럼만 갱신
- 다른 컬럼/테이블의 결과는 그대로 보존
- 시계열 누적 (HISTORY) 으로 개선 추이 가시화

## 2. DDL 변경

### 2.1 신규: TB_DOMAIN_RULE (도메인 1:N 룰)
```sql
CREATE TABLE TB_DOMAIN_RULE (
    DOMAIN_RULE_ID  VARCHAR(40)  NOT NULL,
    DOMAIN_ID       VARCHAR(40)  NOT NULL,
    RULE_NM         VARCHAR(200) NOT NULL,
    RULE_TYPE       VARCHAR(20)  NOT NULL,         -- REGEX/RANGE/LENGTH/ENUM
    RULE_PARAMS     TEXT,
    SORT_ORD        INTEGER      NOT NULL DEFAULT 1,  -- 1=default
    USE_YN          CHAR(1)      NOT NULL DEFAULT 'Y',
    DESCR           TEXT,
    CRET_DT         TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    CRET_USER_ID    VARCHAR(40),
    UPDT_DT         TIMESTAMP,
    UPDT_USER_ID    VARCHAR(40),
    CONSTRAINT PK_TB_DOMAIN_RULE PRIMARY KEY (DOMAIN_RULE_ID)
);
CREATE INDEX IX_DOMAIN_RULE_DOM ON TB_DOMAIN_RULE (DOMAIN_ID, SORT_ORD);
```

### 2.2 신규: TB_QUAL_COL_RULE (컬럼 → 적용 규칙)
```sql
CREATE TABLE TB_QUAL_COL_RULE (
    DM_ID           VARCHAR(40)  NOT NULL,
    OBJ_NM          VARCHAR(100) NOT NULL,
    ATTR_NM         VARCHAR(100) NOT NULL,
    DOMAIN_RULE_ID  VARCHAR(40),         -- 도메인 룰 사용 시
    CUSTOM_RULE_ID  VARCHAR(40),         -- 사용자 커스텀 룰 (TB_QUAL_RULE.RULE_ID)
    EXCLUDE_YN      CHAR(1)      DEFAULT 'N',  -- Y=진단 제외 명시
    UPDT_DT         TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    UPDT_USER_ID    VARCHAR(40),
    CONSTRAINT PK_TB_QUAL_COL_RULE PRIMARY KEY (DM_ID, OBJ_NM, ATTR_NM)
);
-- 둘 중 하나만 채움. 둘 다 NULL + EXCLUDE_YN='N' = default(도메인 SORT_ORD=1) 적용
```

### 2.3 신규: TB_QUAL_PROFILE_HISTORY (시계열 누적)
```sql
CREATE TABLE TB_QUAL_PROFILE_HISTORY (
    DIAG_ID       VARCHAR(40)  NOT NULL,
    DM_ID         VARCHAR(40)  NOT NULL,
    OBJ_NM        VARCHAR(100) NOT NULL,
    ATTR_NM       VARCHAR(100) NOT NULL,
    TOTAL_CNT     BIGINT,
    NULL_CNT      BIGINT,
    DISTINCT_CNT  BIGINT,
    EMPTY_CNT     BIGINT,
    MIN_VAL       VARCHAR(200),
    MAX_VAL       VARCHAR(200),
    AVG_VAL       NUMERIC(20,4),
    STD_VAL       NUMERIC(20,4),
    MIN_LEN       INTEGER,
    MAX_LEN       INTEGER,
    DIAG_DT       TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT PK_TB_QUAL_PROFILE_HISTORY PRIMARY KEY (DIAG_ID, DM_ID, OBJ_NM, ATTR_NM)
);
CREATE INDEX IX_QUAL_PROFILE_HIST_TIMELINE
    ON TB_QUAL_PROFILE_HISTORY (DM_ID, OBJ_NM, ATTR_NM, DIAG_DT DESC);
```

### 2.4 폐기: TB_QUAL_RULE.DOMAIN_ID
- 컬럼 자체는 schema 호환을 위해 유지하되 미사용 (NULL)
- 도메인 룰은 TB_DOMAIN_RULE 로 분리

## 3. 진단 흐름 (BusinessRuleService 재설계)

```
[입력 단위] DM_ID (모델) + OBJ_NM(옵션) + ATTR_NM(옵션)

1. 컬럼 목록 조회
   - ATTR_NM 지정 → 그 컬럼 1개
   - OBJ_NM 만 지정 → 그 테이블의 컬럼들
   - 둘 다 NULL → 모델의 모든 컬럼

2. 각 컬럼 → 적용 규칙 결정 (단일):
   a. TB_QUAL_COL_RULE 조회
      - EXCLUDE_YN='Y' → 진단 제외
      - CUSTOM_RULE_ID NOT NULL → TB_QUAL_RULE 조회 → 그 룰 사용
      - DOMAIN_RULE_ID NOT NULL → TB_DOMAIN_RULE 조회 → 그 룰 사용
   b. 매핑 없음 + 컬럼이 도메인 보유 (TB_DATA_MODEL_ATTR.DOMAIN_ID)
      → TB_DOMAIN_RULE WHERE DOMAIN_ID=? AND USE_YN='Y' ORDER BY SORT_ORD LIMIT 1
   c. 도메인도 없음 → 진단 제외 (조용히 skip)

3. 룰 → SQL 빌드 (RuleSqlBuilder 그대로 — RULE_TYPE 별 dispatch)

4. 외부 DB 에 SQL N개 (컬럼당 1) 직렬 실행
   - 위반 카운트 + 전체 카운트
   - 위반률 90% 초과 → 자동 중단 + INFO 마킹 (68번 §5)

5. 결과 적재 (모두 UPSERT — 컬럼당 1행)
   - TB_QUAL_RULE_RESULT INSERT (DIAG_ID 별 신규)
   - TB_QUAL_PROFILE_RESULT UPSERT (직전값 — 해당 컬럼만)
   - TB_QUAL_PROFILE_HISTORY INSERT (시계열 누적 — 해당 컬럼만)
   - 다른 컬럼의 RESULT/HISTORY 는 그대로 보존
```

### 3.1 핵심 차이 — 부하 격리

```
모델 100컬럼, 사용자가 EMAIL 컬럼만 룰 변경

[기존 67번]   /api/qual/rule/run (모델 단위)
              → 100 SQL 외부 DB 실행
              → 100 컬럼 결과 적재

[70번]        /api/qual/rule/runColumn?dmId=...&objNm=...&attrNm=EMAIL
              → 1 SQL 외부 DB 실행
              → EMAIL 컬럼만 적재 (나머지 99 그대로)
```

## 6. 구현 단계 (우선순위)

### Phase 1 (이 세션)
1. **DDL**: TB_DOMAIN_RULE / TB_QUAL_COL_RULE / TB_QUAL_PROFILE_HISTORY 신규
2. **VO/Mapper/Controller**: 도메인 룰 + 컬럼 매핑 CRUD + 단위 진단 API
3. **q-executor BusinessRuleService 재설계**: 컬럼별 effective rule 결정 + 단위별 실행
4. **q-executor ValueProfileService 보강**: 컬럼/테이블 단위 입력 + HISTORY 적재
5. **테스트 SQL 재작성**: 04 폐기 + 새 도메인 룰 + 컬럼 매핑 SQL
6. **셀레니움 시나리오 재작성** (D~F 폐기, A~C 갱신, 신규 D' E' F'):
   - D': 컬럼이 도메인 보유 → 자동 default 진단 (매핑 INSERT 없이)
   - E': 사용자가 컬럼 룰 변경 → 그 컬럼만 재진단 → 결과 갱신 검증
   - F': 통계 메뉴 진입 (placeholder 검증)

### Phase 2 (다음 세션)
1. 통계 메뉴 본격 시각화 (Chart.js/Recharts 등)
2. 도메인 룰 등록 UI (관리자)
3. 컬럼 화면의 적용 규칙 드롭다운 UI 본격 구현
4. 위반 샘플 행 fetch (PK 자동 결정)

## 7. 시드 데이터 — 도메인 룰 마이그레이션

기존 카탈로그 (CAT_EMAIL, CAT_PHONE, CAT_RRN 등 7건) 를 TB_DOMAIN_RULE 로 마이그레이션:

| 도메인 | 룰 SORT_ORD | 패턴 |
|---|---|---|
| 이메일 | 1 | `^[A-Za-z0-9._+-]+@[A-Za-z0-9.-]+\.[A-Za-z]{2,}$` |
| 전화번호 | 1 (default) | `^010-\d{3,4}-\d{4}$` (하이픈 있는 표준) |
| 전화번호 | 2 | `^010\d{8}$` (하이픈 없음 — 사용자 변경 옵션) |
| 전화번호 | 3 | `^0\d{1,2}-\d{3,4}-\d{4}$` (지역 + 하이픈) |
| 주민등록번호 | 1 | `^\d{6}-?[1-4]\d{6}$` |
| 사업자등록번호 | 1 | `^\d{3}-?\d{2}-?\d{5}$` |

→ 도메인 ID 는 표준사전의 기존 도메인을 사용. 미존재 시 신규 도메인 등록 후 룰 매핑.

## 8. 미정/리스크

- **TB_DATA_MODEL_ATTR 의 DOMAIN_ID 컬럼 존재 여부** — 컬럼 메타에 도메인 매핑이 이미 들어있는지. 없으면 표준사전의 word→domain 매핑을 통해 우회 추정 필요.
- **카탈로그 시드를 어느 도메인에 배치** — 현재 표준사전의 도메인명과 카탈로그명의 매칭 로직 확인 필요.
- **컬럼별 effective rule 조회 성능** — 모델당 100~수백 컬럼 시 N+1 query. selectList JOIN 으로 단일 SQL 화 검토.
- **HISTORY 무한 누적** — 90일 후 soft-purge 정책 (별도 cron 필요).
