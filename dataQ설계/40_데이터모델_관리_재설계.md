# 데이터 모델 관리 재설계

**작성일:** 2026-04-17  
**목적:** 현재 "수집 only" 구조에서 "설계 + 수집 + 편집" 통합 구조로 확장  
**배경:** SMETA 경쟁을 위해 논리모델 설계, 수동 편집, GAP 분석 기능이 필요

---

## 1. 현재 구조 (AS-IS)

### 데이터 흐름

```
DBMS (운영 DB)
    ↓ 수집 (collect)
TB_DATA_MODEL_CLCT (수집 이력, 매번 새 스냅샷)
    ↓
TB_DATA_MODEL_OBJ  (테이블 스냅샷)
TB_DATA_MODEL_ATTR (컬럼 스냅샷)
TB_DATA_MODEL_INDEX (인덱스 스냅샷)
TB_DATA_MODEL_CONSTRAINT (제약조건 스냅샷)
```

### 테이블 관계

```
TB_DATA_MODEL (마스터)
  ├── DM_ID (PK)
  ├── DM_DS_ID (FK → TB_DATA_SOURCE) ← 데이터소스 필수
  ├── MODEL_TYPE
  └── ...
  │
  └── TB_DATA_MODEL_CLCT (수집 이력)
       ├── DM_CLCT_ID (PK)
       ├��─ DM_ID (FK)
       ├── CLCT_START_DT / CLCT_END_DT
       └── CLCT_CMPTN_YN
       │
       ├── TB_DATA_MODEL_OBJ (PK: CLCT_ID + DM_ID + OBJ_NM)
       ├── TB_DATA_MODEL_ATTR (PK: CLCT_ID + DM_ID + OBJ_NM + ATTR_NM)
       ├── TB_DATA_MODEL_INDEX (PK: CLCT_ID + SEQ)
       └── TB_DATA_MODEL_CONSTRAINT (PK: CLCT_ID + SEQ)
```

### 현재 특징

- 수집할 때마다 **전체 스냅샷**이 새로 생성됨
- 수집 3번 → 테이블/컬럼 데이터 3벌
- 최신 스냅샷 = `max(CLCT_END_DT)`로 조회
- 구조 진단: 이전 스냅샷 vs 현재 실제 DBMS 비교
- **수동 편집 불가**, **데이터소스 없이 모델 생성 불가**

### 현재 한계

| 한계 | 영향 |
|------|------|
| 모델 원천이 수집(DBMS)뿐 | 논리모델 설계 불가 |
| 스냅샷이 불변 | 수집 후 수동 수정 불가 |
| DM_DS_ID 필수 | 데이터소스 없는 순수 설계 모델 불가 |
| 구조 진단 = 과거 vs 현재 | 설계 vs 현실(GAP 분석) 불가 |

## 2. 목표 구�� (TO-BE)

### 지원해야 하는 시나리오

#### 시나리오 A: 기존 수집 (변경 없음)
```
DBMS 수집 → 스냅샷 생성 → 표준 진단 → 구조 진단 (이전 vs 현재)
```

#### 시나리오 B: 수집 + 수동 편집
```
DBMS 수집 → 스냅샷 생성 → 최신 모델에서 테이블/컬럼 추가·수정·삭제
→ 재수집 시 새 스냅샷으로 갱신
```

#### 시나리오 C: 구조 진단 → 모델 반영
```
구조 진단 실행 → 변경점 목록 → 선택한 변경점을 현재 모델에 반영
```

#### 시나리오 D: 논리모델 설계 (데이터소스 없음)
```
빈 모델 생성 (MODEL_TYPE='LOGICAL', DM_DS_ID=NULL)
→ 웹에서 테이블/컬럼 직접 설계
→ 표준 기반 물리명/타입 자동 변환
→ DDL 생성
```

#### 시나리오 E: 논리모델 + 데이터소스 연결 → GAP 분석
```
논리모델 설계 완료 → 데이터소스 연결 → DDL 배포
→ DBMS 수집 → 구조 진단: 설계 모델 vs 수집 결과 (GAP 분석)
```

## 3. 스키마 변경

### TB_DATA_MODEL 변경

```sql
-- DM_DS_ID를 NOT NULL → NULL 허용으로 변경 (논리모델은 데이터소스 없음)
ALTER TABLE TB_DATA_MODEL ALTER COLUMN DM_DS_ID DROP NOT NULL;
```

|------|------|------|
| DM_DS_ID | NOT NULL → **NULLABLE** | 논리모델은 NULL, 나중에 연결 가능 |
| MODEL_TYPE | 기존 컬럼 활용 | 'PHYSICAL' / 'LOGICAL' |

```sql
-- 'DBMS'   : 기존 DBMS ���집
```

## 4. 논리명과 DB 코멘트 처리 규칙

### 원칙: 논리명(NM_KR)과 DB 코멘트(COMMENT)는 별개 필드

```
OBJ_NM_KR / ATTR_NM_KR   → 논리명 (설계 기준, 사용자가 편집)
OBJ_COMMENT / ATTR_COMMENT → DB 코멘트 (수집 시 자동 저장, 원본 보존)
```

### 모델 원천별 초기값

| 모델 원천 | NM_KR (논리명) 초기값 | COMMENT (코멘트) 초기값 |
|----------|---------------------|----------------------|
| **DBMS 수집** | DB 코멘트 값 복사 (코멘트 = 초기 논리명) | DB 코멘트 원본 저장 |
| **논리모델 설계** | 사용자가 직접 입력 | NULL (DB 없으므로) |
| **ERwin 임포트** | ERwin Name (논리명) | NULL |

**수집으로 시작한 모델의 경우:**
- 최초 수집 시 `ATTR_NM_KR = ATTR_COMMENT = DB 코멘트`
- 이후 사용자가 `ATTR_NM_KR`(논리명)을 수정 가능
- `ATTR_COMMENT`는 수집 원본 그대로 유지
- 재수집 시 `ATTR_COMMENT`만 갱신, 사용자가 수정한 `ATTR_NM_KR`은 보존

### GAP 분석에서의 활용

논리명과 코멘트가 분리되면 **"한글명 불일치"**를 GAP 분석 항목으로 진단 가능:

```
GAP 분석 결과 — 한글명 비교:
┌──────────┬──────────────┬─��────────────┬────────┐
│ 컬럼      │ 논리명(설계)   │ DB코멘트(현실) │ 상태    │
├──────────┼──────────────┼──────────────┼────────┤
│ USR_NM   │ 사용자이름     │ 사용자명      │ ⚠ 불일치 │
│ USR_ID   │ 사용자식별자   │ 사용자식별자   │ ✓ 일치  │
│ REG_DT   │ 등록일자       │ (없음)        │ ⚠ 누락  │
└──────────┴──────────────┴──────────────┴────────┘
→ 불일치 건은 "코멘트 스크립트 일괄 생성"으로 연계 가능 (기존 기능 재활용)
```

## 5. 모델 편집 규칙

### 모든 모델(수집/논리 무관)에서 편집 가능

최신 스냅샷의 테이블/컬럼을 웹에서 직접 추가·수정·삭제 가능.

### 편집 시 표준 검증 필수

논리명을 수정하거나 새 테이블/컬럼을 추가할 때, **실제 반영 전에 표준 준수 여부를 검증**해야 한다:

| 검증 항목 | 설명 | 예시 |
|----------|------|------|
| 논리명 → 표준 용어 분리 가능 | 한글 논리명이 표준 단어 조합으로 분리되는가 | "사용자이름" → "사용자" + "이름" (O) |
| 물리명 → 표준 영문약어 조합 일치 | 물리명이 표준 단어의 영문약어 조합인가 | USR_NM = USR + NM (O) |
| 데이터타입 → 표준 도메인 일치 | 데이터타입/길이가 표준 도메인 정의와 맞���가 | VARCHAR(100) = 가변문자100 도메인 (O) |

**표준 미준수 시:** 저장은 가능하되 경고 표시 + 표준 진단에서 이슈로 잡힘.
(완전 차단 vs 경고 후 저장 허용은 추후 결정)

## 6. 핵심 규칙: "최신 스냅샷 = 현재 모델"

```
수집 1 (2026-04-01, DBMS)    ← 과거 스냅샷 (읽기 전용)
수집 2 (2026-04-10, DBMS)    ← 과거 스냅샷 (읽기 전용)
수집 3 (2026-04-15, DBMS)    ← ★ 최신 = "현재 모델" (편집 가능)
```

- **과거 스냅샷**: 읽기 전용, 이력 조회용
- **최신 스냅샷**: 편집 가능한 "현재 모델"
- **수동 편집**: 최신 스냅샷의 OBJ/ATTR을 직접 INSERT/UPDATE/DELETE
- **재수집**: 새 스냅샷 생성 → 그게 새로운 "현재 모델" (기존 수동 편집분은 이전 스냅샷에 남아있음)

## 7. 모델 유형별 동작

### 물리모델 (MODEL_TYPE = 'PHYSICAL')

기존 수집 기반 모델. 변경 최소.

| 동작 | 설명 |
|------|------|
| 생성 | 데이터소스 선택 → 모델 생성 (기존과 동일) |
| 수집 | DBMS 접속 → 새 스냅샷 생성 (기존과 동일) |
| **수동 편집 (신규)** | 최신 스냅샷에서 테이블/컬럼 추가·수정·삭제 |
| 표준 진단 | 기존과 동일 |
| 구조 진단 | 기존과 동일 (이전 스냅샷 vs 현재 실�� DBMS) |
| **구조 진단 → 모델 반영 (신규)** | 변경점을 선택하여 현재 모델에 반영 |

### 논리모델 (MODEL_TYPE = 'LOGICAL')

신규. 데이터소스 없이 순수 설계.

| 동작 | 설명 |
|------|------|
| 생성 | 모델명 입력 → 빈 모델 생성 (DM_DS_ID = NULL) |
| 초기 스냅샷 | CLCT_TYPE='MANUAL'인 빈 CLCT 레코드 1개 자동 생성 |
| 설계 | 웹에서 테이블/컬럼/인덱스/제약조건 직접 추가 |
| **물리명 자동 변환 (신규)** | 한글 논리명 입력 → 자동표준화 추천 엔진 → 영문 물리명 생성 |
| **물리 타입 자동 결정 (신규)** | 도메인 선택 → DBMS별 물리 데이터타입 자동 매핑 |
| 표준 진단 | 가능 (설계한 모델이 표준에 맞는지 검증) |
| 수집 | **불가** (데이터소스 없음, 수집 버튼 비활성화) |
| 구조 진단 | **불가** (비교할 DBMS 없음) |

### 논리모델 + 데이터소스 연결 후

| 동작 | 설명 |
|------|------|
| 데이터소스 연결 | 모델 설정에서 DM_DS_ID 지정 |
| DDL 생성 | 물리모델 기반 CREATE TABLE DDL 생성 |
| 수집 | **가능** (연결된 DBMS에서 수집) |
| 구조 진단 | **가능** (설계 모델 vs 실제 DBMS = **GAP 분석**) |
| 재수집 시 | 새 CLCT(DBMS) 생성. 설계 모델은 이전 스냅샷으로 보존 |

## 8. 구조 진단 확장: GAP 분석

### 현재 구조 진단

```
비교 대상:  이전 수집 스냅샷  vs  현재 실제 DBMS
결과:       추가된 테이블/컬럼, 삭제된 테이블/컬럼, 변경된 컬럼
의미:       "지난번 수집 이후 뭐가 바뀌었나?"
```

### 확장: GAP 분석 (논리모델 기준)

```
비교 대상:  논리모델 (설계)  vs  현재 실제 DBMS (또는 수집 스냅샷)
결과:       
  - 설계에 있는데 DB에 없음 → "미생성" (배포 필요)
  - DB에 있는데 설계에 없음 → "미등록" (비표준 또는 설계 누락)
  - 둘 다 있는데 타입/길이 다름 → "불일치" (수정 필요)
의미:       "설계한 대로 만들어졌는가?"
```

### 구현 관점

기존 구조 진단 로직을 **재사용** 가능:
- 현재: `이전 CLCT 스냅샷` vs `실제 DBMS`
- GAP: `논리모델 CLCT 스냅샷` vs `실제 DBMS`
- 비교 로직은 동일, 비교 대상만 다름

## 9. 시나리오별 데이터 흐름 상세

### 시나리오 A+: 수집 시 논리명/코멘트 처리

```
1. 최초 수집
   → ATTR_COMMENT = DB 코멘트 원본 ("사용자명")
   → ATTR_NM_KR = DB 코멘트 복사 ("사용자명")  ← 코멘트가 초기 논리명
   
2. 사용자가 논리명 수정
   → ATTR_NM_KR = "사용자이름" (수정)
   → ATTR_COMMENT = "사용자명" (원본 유지)
   
3. 재수집
   → ATTR_COMMENT = DB 코멘트 갱신 (DB에서 새로 가져옴)
   → ATTR_NM_KR = 사용자가 수정한 값 보존 ("사용자이름")
   
4. GAP 분석에서 "사용자이름" vs "사용자명" → 불일치 표시
```

### 시나리오 B: 수집 + 수동 편집

```
1. DBMS 수집 → CLCT #1 생성 (CLCT_TYPE='DBMS')
   OBJ: TB_USER, TB_ORDER
   ATTR: TB_USER.USER_ID, TB_USER.USER_NM, ...
   (ATTR_NM_KR = ATTR_COMMENT = DB 코멘트)

2. 사용자가 TB_PRODUCT 테이블 수동 추가 (표준 검증 통과 필수)
   → CLCT #1 (최신)의 OBJ에 INSERT
   → CLCT #1의 ATTR에 컬럼들 INSERT
   → ATTR_NM_KR = 사용자 입력, ATTR_COMMENT = NULL (DB에서 온 게 아니므로)

3. 재수집 → CLCT #2 생성 (CLCT_TYPE='DBMS')
   → DBMS에서 가져온 전체 스냅샷으로 새로 생성
   → CLCT #2가 새로운 "현재 모델"
   → 수동 추가한 TB_PRODUCT는 CLCT #1에 남아있음 (이력)
   → DBMS에 TB_PRODUCT가 실제로 있었다면 CLCT #2에도 포함됨
```

### 시나리오 C: 구조 진단 → 모델 반영

```
1. 구조 진단 실행
   결과: TB_NEW_TABLE이 DBMS에 추가됨 (모델에는 없음)

2. 사용자가 "모델에 반영" 선택
   → 최신 CLCT의 OBJ에 TB_NEW_TABLE INSERT
   → 해당 컬럼들도 ATTR에 INSERT

3. 구조 진단 재실행 → 해당 건은 더 이상 변경점으로 안 뜸
```

### 시나리오 D: 논리모델 설계

```
1. "새 모델" 생성
   → TB_DATA_MODEL INSERT (DM_DS_ID=NULL, MODEL_TYPE='LOGICAL')
   → TB_DATA_MODEL_CLCT INSERT (CLCT_TYPE='MANUAL', 빈 스냅샷)

2. 테이블 추가: "사용자"
   → OBJ INSERT (OBJ_NM_KR='사용자')
   → 자동표준화 추천: '사용자' → TB_USER
   → OBJ_NM = 'TB_USER' 자동 설정

3. 컬럼 추가: "사용자이름"
   → ATTR INSERT (ATTR_NM_KR='사용자이름')
   → 자동표준화 추천: '사용자이름' → USR_NM
   → 도메인 자동 추천: 가변문자100 → VARCHAR(100)
   → ATTR_NM='USR_NM', DATA_TYPE='VARCHAR', DATA_LEN=100

4. 표준 진단 실행 → 설계한 모델이 표준에 맞는지 검증
```

### 시나리오 E: 논리모델 → 데이터소스 연결 → GAP 분석

```
1. 논리모델 설계 완료 (위 시나리오 D)

2. 데이터소스 연결
   → TB_DATA_MODEL UPDATE SET DM_DS_ID = '...'

3. DDL 생성
   → 논리모델의 OBJ/ATTR 기반 CREATE TABLE DDL 텍스트 생성

4. DBA가 DDL을 DBMS에 실행 (수동 배포)

5. DBMS 수집
   → 새 CLCT 생성 (CLCT_TYPE='DBMS')
   → 실제 DBMS에서 테이블/컬럼 수집

6. 구조 진단 (GAP 분석)
   → 논리모델 CLCT vs 수집 CLCT 비교
   → "설계한 대로 만들어졌는가?" 결과 도출
```

## 10. 수동 편집 시 이력 처리 — 미결 사항

### 옵션 A: 최신 스냅샷 직접 수정 (단순)

```
수동 편집 → 최신 CLCT의 OBJ/ATTR 직접 UPDATE/INSERT/DELETE
이력: 없음 (편집 전 상태를 알 수 없음)
```
- **장점**: 구현 단순
- **단점**: 편집 이력 추적 불가

### 옵션 B: 편집할 때마다 새 CLCT 생성 (이력 보존)

```
수동 편집 → 현재 스냅샷 복사 → 새 CLCT(MANUAL) 생성 → 거기서 수정
이력: 편집 전후를 스냅샷으로 비교 가능
```
- **장점**: 완전한 이력 보존
- **단점**: 매 편집마다 전체 복사 → 데이터 폭증

### 옵션 C: 편집 이력을 별도 테이블로 관리 (중간)

```
수동 편집 → 최신 CLCT 직접 수정 + 변경 이력을 별도 테이블에 기록
TB_DATA_MODEL_EDIT_LOG (CLCT_ID, 변경유형, 대상, 변경전값, 변경후값, 일시, 사용자)
```
- **장점**: 이력 추적 가능, 데이터 폭증 없음
- **단점**: 별도 테이블/로직 필요

## 12. 구현 우선순위 (제안)

### 1단계: 수집 모델 편집 가능하게

| 작업 | 상세 |
|------|------|
| CLCT_TYPE 컬럼 추가 | ALTER TABLE |
| 최신 스냅샷 수동 편집 API | 테이블/컬럼 추가·수정·삭제 API |
| 편집 UI | 기존 테이블/컬럼 조회 화면에 추가·수정·삭제 버튼 |
| 구조 진단 → 모델 반영 | 변경점 선택 → 현재 모델에 적용 |

### 2단계: 논리모델 생성

| 작업 | 상세 |
|------|------|
| DM_DS_ID NULL 허용 | ALTER TABLE |
| 논리모델 생성 화면 | 데이터소스 없이 모델 생성 |
| 테이블/컬럼 직접 설계 UI | 한글 논리명 입력 기반 |

### 3단계: 자동 변환 + GAP 분석

| 작업 | 상세 |
|------|------|
| 논리명 → 물리명 자동 변환 | 자동표준화 추천 엔진 연동 |
| 데이터타입 매핑 테이블 | 논리타입 → DBMS별 물리타입 관리 |
| 데이터소스 연결 기능 | 논리모델에 DBMS 연결 |
| GAP 분석 | 설계 모델 vs 수집/실제 DBMS 비교 |

### 4단계: DDL + 배포

| 작업 | 상세 |
|------|------|
| DDL 자동 생성 | DBMS별 CREATE TABLE/INDEX 생성 |
| DDL 결재 연동 (옵션) | 생성된 DDL 승인 후 다운로드/실행 |
