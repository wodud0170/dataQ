## 1. Docker Desktop 기동 실패 — 원인과 복구

### 증상
`docker` CLI 무응답, `wsl -l -v` 에서 `docker-desktop` Stopped, `\\.\pipe\dockerDesktopLinuxEngine` 없음.

### 원인
2026-05-26 비정상 종료로 남은 **고아 AF_UNIX 소켓 파일 2개**. Docker 가 재기동 때 이 파일을 지우려다 실패하며 백엔드 전체가 crash:

```
backend crashed ... initializing Inference manager:
  listening on unix://<HOME>\AppData\Local\Docker\run\dockerInference:
  remove ...: The file cannot be accessed by the system.
backend crashed ... initializing Secrets Engine:
  listening on unix://<HOME>\AppData\Local\docker-secrets-engine\engine.sock: (동일)
```
(`<HOME>` 은 로그 마스킹이지 경로 버그 아님)

### 복구
파일이 `del` / `Remove-Item -Force` / 부모 디렉터리 재귀삭제 **전부 실패**(깨진 reparse point).
**부모 디렉터리 rename** 만 통했고, **두 경로를 동시에** 비워야 성공한다 — 한 쪽만 고치면 다음 서비스에서 또 crash 하며 새 고아를 만든다.

```powershell
Get-Process 'Docker Desktop','com.docker.backend' | Stop-Process -Force
Rename-Item "$env:LOCALAPPDATA\Docker\run" "$env:LOCALAPPDATA\Docker\run.orphan"
New-Item -ItemType Directory "$env:LOCALAPPDATA\Docker\run"
Rename-Item "$env:LOCALAPPDATA\docker-secrets-engine" "$env:LOCALAPPDATA\docker-secrets-engine.broken"
New-Item -ItemType Directory "$env:LOCALAPPDATA\docker-secrets-engine"
Start-Process "C:\Program Files\Docker\Docker\Docker Desktop.exe"
```

기동 대기는 `Test-Path '\\.\pipe\dockerDesktopLinuxEngine'` 로 판정할 것. `docker info` 는 데몬 미기동 시 오래 hang 한다.

격리물: `Docker\run.orphan-40919`, `docker-secrets-engine.broken-20260822`, `settings-store.json.bak-20260822`.
**Docker 설정 자체는 변경하지 않았다.**

## 3. 실제 코드 결함 4건 (수정 완료)

### ① `terms.selectTermsInfo` 미정의 — 용어 승인 변경이력의 현재값이 항상 빈값

- **위치**: `DataStandardController.java` 용어 승인 분기
- **증상**: 호출하는 statement 가 `terms.xml` 에 없음(`selectTermsInfoByNm` 만 존재). 바깥 `catch (Exception ex) { log.warn(...) }` 가 삼켜서 승인 자체는 통과하지만 이력의 `CURR_VALUE` 가 null 로 남음.
- **실측 피해** (`TB_CHANGE_HISTORY`, `CHANGE_TYPE='INSERT'`):

  | TARGET_TYPE | 전체 | CURR_VALUE 있음 | NULL |
  |---|---|---|---|
  | DOMAIN | 23 | 23 | 0 |
  | WORD | 161 | 159 | 2 |
  | **TERM** | **18** | **2** | **16 (89%)** |

- **수정**:
  - `terms.xml` — 기존 `selectTermsInfoByNm` 본문을 `<sql id="termsInfoSelectBody">` 로 추출하고, 같은 본문을 쓰는 `selectTermsInfoById` 신설 (`where A.TERMS_ID = #{termsId}`).
  - `DataStandardController` — `word.selectWordInfoById` 분기와 동일한 형태로 `selectList` + `get(0)`, `targetNm` 보정까지 맞춤.
- **검증**: 일반사용자 용어 등록 → 관리자 승인 실행 → `TB_CHANGE_HISTORY` 에 `TERM / curr_value=StdTermsVo(...)` 기록 확인. 서버 로그의 `승인 이력 조회 실패` 0건. 기존 `getTermsInfoByNm` 회귀도 정상(200, 1건).

### ② `updateAttr` / `updateObj` / `deleteAttr` 가 0건 갱신에도 200 반환

- **위치**: `DataModelController.java`
- **원인**: MyBatis `update`/`delete` 의 반환값(영향 행 수)을 검사하지 않음. 해당 매퍼의 WHERE 는 `OBJ_OWNER` 를 키에 포함하므로 클라이언트가 `objOwner` 를 빼먹으면 **0건 매칭인데 성공 응답**.
- **재현**: XMI import 는 `OBJ_OWNER='XMI'` 로 적재(`DataModelController.java:814`). `objOwner` 없이 `/api/dm/updateAttr` 호출 → 값은 그대로인데 `resultCode=200`.
- **참고**: 같은 프로젝트의 `DiagTargetController` 는 `success: cnt > 0`, `count: cnt` 를 정직하게 돌려준다. `DataModelController` 만 누락돼 있던 일관성 문제.
- **수정**: 세 메서드 모두 영향 행 수를 받아 0이면 `CODE_500` + 대상 식별자(dmId/owner/obj/attr)를 담은 메시지 반환. `deleteAttr` 은 `session.rollback()` 후 반환.
- **검증**: `objOwner` 누락 호출 → 500 "수정 대상 컬럼을 찾지 못했습니다. (dmId=…, owner=null, obj=TB_CPN, attr=CPN_NO)" / DB 값 불변. `objOwner` 포함 재호출 → 200 + DB 반영. 검증 후 원복.

### ③ 스케줄 ERROR 마감 경로가 `LAST_EXEC_*` 미갱신

- **원인**: 정상 완료 경로 `DiagSchedulerRunner.markFinish()` 는 LOG 마감 + `updateScheduleLastExec` 를 함께 하지만, ERROR 로 마감하는 다른 두 경로는 LOG 만 마감했다.
  - `DiagScheduleController` runNow 의 q-executor 호출 실패 분기
  - `ScheduledDiagLauncher.launch()` 의 예외 분기
- **증상**: 실행에 실패한 스케줄은 목록의 "최종 실행" 이 영구히 빈칸. 실측으로 `LAST_EXEC_STATUS = NULL` 확인.
- **수정**: 두 경로에 `updateScheduleLastExec`(status=ERROR, logId) 추가.
- **검증**: 수집 이력 없는 모델로 스케줄 생성 → `runNow` → `LAST_EXEC_STATUS=ERROR / 2026-08-22 22:48:20 / log=5e1Bq07…` 기록 확인. UI 스케줄 목록에도 `ERROR 08-22 22:48` 배지 노출 확인.

### ④ 단어 영향도 분석이 항상 500 — 삭제된 컬럼 참조 (2026-08-23 추가)

- **위치**: `q-common/src/main/resources/mapper/stnd/impact.xml` `selectImpactColumnsByWordId`
- **증상**: `GET /api/std/impact/word?wordId=` 호출 시 항상 500.
  ```
  org.postgresql.util.PSQLException: ERROR: column a.dm_clct_id does not exist
  ```
- **원인**: 쿼리가 `a.DM_CLCT_ID` 로 "최신 수집 회차" 를 골랐는데, **CLCT 폐기(44/48번) 때 `TB_DATA_MODEL_ATTR` 에서 `DM_CLCT_ID` 컬럼이 제거**됐다. `information_schema` 확인 결과 해당 컬럼 0건. 형제 쿼리(`selectImpactTermsByWordId`, `selectImpactTermsByDomainNm`)는 이 컬럼을 안 써서 `impact/domain` 은 정상 동작 → 단어 영향도만 죽어 있었다.
- **수정**: 현재 규약(`DM_ID` + `USE_YN='Y'`)으로 대체하고 모델도 `m.USE_YN='Y'` 로 제한.
- **검증**: `고객` → 용어 28건 / 컬럼 21건, `코드` → 128 / 4097건, `번호` → 543 / 1252건 정상 반환. `impact/domain` 회귀 정상.
- **발견 경로**: 셀레니움이 커버하지 않는 읽기 전용 엔드포인트 84건을 일괄 실호출(§6)한 결과. **UI 테스트만으로는 잡히지 않던 결함.**

## 7. CLAUDE.md DDL self-check 절차 결함

CLAUDE.md 의 push 전 self-check 명령이 **대문자만** 본다:

```bash
grep -oE 'TB_[A-Z_]+' q-common/src/main/resources/mapper/stnd/*.xml | sort -u
```

실제 매퍼는 소문자로도 테이블을 참조한다 — `tb_biz_area`, `tb_subj_area`, `tb_user`, `tb_domain`,
`tb_terms`, `tb_word`, `tb_qual_running_lock`, `tb_data_source` **8개가 이 체크에서 통째로 빠진다**.
`-i` 를 붙여야 46개가 모두 잡힌다.

```bash
grep -ohiE '\btb_[a-z0-9_]+' q-common/src/main/resources/mapper/stnd/*.xml | tr 'A-Z' 'a-z' | sort -u
```

현재는 결과적으로 문제없지만(46개 전부 DDL 에 존재, `tb_data_source` 만 ndata 스키마라 제외),
저 8개 테이블에 DDL 변경이 생기면 self-check 가 못 잡는다. **CLAUDE.md 갱신 필요.**

## 8. 정적 점검에서 이상 없음이 확인된 항목

| 점검 | 규모 | 결과 |
|---|---|---|
| 매퍼 참조 테이블 ↔ DDL | 46개 | 일치 (`tb_data_source` 는 ndata 스키마라 정상 제외) |

| resultMap `property` ↔ VO 필드 | 325개 | 누락 0 (CLAUDE.md 가 경고한 매핑 누락 패턴 없음) |
| MyBatis statement 호출 ↔ XML 정의 | 324개 | 1건 누락(위 결함 ①) 외 정상 |
| Vue API URL ↔ 컨트롤러 엔드포인트 | 208 ↔ 277 | 미매칭 2건은 `/logout`(Spring Security), `/sockjs`(WebSocketConfiguration) 로 정상 등록 |

| `docker/dataq-db/pgdata` git 추적 | — | 안 됨 (정상) |

`UPDATE ... SET` 컬럼 검사도 시도했으나 파서가 `#{x, jdbcType=...}` 를 컬럼으로 오인해 결과를 신뢰할 수 없어 폐기했다.
INSERT 검사는 괄호 균형 파싱이라 정확하며, 그쪽은 깨끗하다.
